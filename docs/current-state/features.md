# Features

* Create conversations, switch between them (sidebar list, ordered by most-recently-active)
* Each conversation has its own URL (`/conversation/{id}`) — a refresh, a bookmark, or a direct link lands back on the same conversation, server-rendered; `/` is the empty "select or start a conversation" state. See [frontend.md](<https://github.com/cconstantine/smelt/blob/main/docs/frontend.md>).
* Delete a conversation from the sidebar (inline confirm, hard delete, cascades to its messages; also stops its sandboxes and browsing session; its model calls stay in the providers page's spend, SME-122). A link to a conversation that doesn't exist says so, and so does a tab left open on one deleted elsewhere, with nothing of it left on screen or in the sidebar (SME-122).
* Send a message, see it appear immediately, watch the assistant's reply stream in live, one bubble per model call, with each tool call appearing as it happens. Every open tab on a conversation sees the reply stream in live, including replies nobody sent from that tab (a finished command's notice, another tab), and a tab reloaded mid-reply picks up the text so far. A tab holds one connection to the server, so several tabs fit even over plain HTTP/1.1; dev can also run over HTTPS/HTTP/2 through Caddy (see SME-27). The sidebar picks up a new conversation's title without a reload. A 2026-09-24 bug bash found and fixed 13 bugs across these flows — see SME-23.
* Stop the model's turn at any time with the Stop button next to Send. It shows in every tab watching the conversation, whoever started the turn. The pod, its terminals and running commands are left alone, and finished commands don't restart the model until the user writes again. One stop is noted once and saves nothing twice, and the stopped reply leaves every tab at once, even with another turn queued (SME-91), as a failed reply's text does (SME-179). A turn starting as another ends always shows Stop, and a Stop the moment a turn starts ends it (SME-179). See SME-26.
* See and stop sandbox pods: a green dot in the sidebar marks conversations with a live pod, updated live. The Sandboxes page (`/pods`) lists every live pod with its conversation, status, uptime, idle time, memory and CPU use against its limits, terminal count, and its sandbox agent's protocol version, marked "restart required" when smelt can't talk to it (SME-53), or "rebuild the image, then restart" when the pod already runs the image a new pod would get, where the model is told not to retry but to ask the user to rebuild it and then replace the pod (SME-121). Stop is there and in each conversation's sandbox panel. Live usage needs smelt to be allowed to read the cluster's metrics (see [setup/sandbox.md](<https://github.com/cconstantine/smelt/blob/main/docs/setup/sandbox.md#pod-metrics>)).
* The agent can call tools mid-conversation and the conversation loop round-trips `tool_use`/`tool_result` blocks automatically, up to a bounded number of turns per send. Every tool result, MCP or native, is capped at 30,000 characters with a note saying how much was cut; `read_file` and `read_terminal_output` cut lines over 2,000 characters and stop at a whole line with `truncated` and a `next_offset` (SME-76). A `read_file` cut line also says which line it is, how long it is, and the `offset` and `character` to read on with, and `read_file` takes `character` to start a read there — so a 40,000-character line reads to its end instead of stopping at 2,000 (SME-189)
* Extended thinking (`ContentBlock::Thinking`) is on by default — the model's reasoning renders as a collapsed-by-default disclosure ahead of its reply; it's shown open only when a reply is thinking alone, with no text (SME-40). Each model's thinking can be turned off on its provider's page, and an Ollama model that reports it can't think starts with it off. An Anthropic account that refuses replayed thinking because the system prompt or tools changed since it was written (preserved thinking, accounts from 2026-08-31) gets the request again with the unacceptable blocks dropped or removed, so the conversation goes on without that reasoning (SME-93; keeping it is SME-98). Since a local Ollama model's Anthropic-compat shim can occasionally fail to keep its reasoning separate from a tool call's own JSON (a real failure mode, not hypothetical), `run_turn` retries — dropping `thinking`, then a few plain regenerations — before giving up; see [api.md](<https://github.com/cconstantine/smelt/blob/main/docs/api.md>) and [setup.md](<https://github.com/cconstantine/smelt/blob/main/docs/setup.md>).
* The agent can create a disposable Kubernetes-pod sandbox for the conversation — at most one live at a time (`create_pod`/`terminate_pod`/`list_pods`; `create_pod` refuses if one already exists, `terminate_pod` first) — with any number of persistent terminals in it (`create_terminal`/`terminate_terminal`/`list_terminals`), and run real shell commands in them (`run_terminal_command`, `send_signal`, `terminal_command_status`, `read_terminal_output`, `list_commands`) — a real, stateful shell (cwd, exported variables persist across separate commands and across turns), output pulled on demand rather than force-fed into every request, with a completion notification actively pushed to the model the moment a command finishes (or is lost to a pod crash), not just whenever something else next happens to touch the conversation — a delivery failure (e.g. no model provider set up) surfaces as a visible error in the chat UI rather than silently stranding the model waiting forever. A command's end is recognised even when its last output has no newline, commands get stdin from `/dev/null` so one that reads stdin can't hang the terminal, and a busy terminal's refusal names the command holding it, how long it has run and how to get out (SME-76). See SME-9 and SME-13.
* The sandbox pod has a configurable memory limit (`SANDBOX_MEMORY_LIMIT`, default `8Gi`) that `create_pod` can override per pod (`memory_limit`), bounded above by a Kubernetes `LimitRange` in `smelt-park` (`max: 64Gi`). It reserves no memory up front (`requests.memory: 0`) and has no CPU request or limit, so idle pods don't hold node capacity (SME-77) — the API server rejects an over-limit request itself, no app-side validation. If the pod dies for any reason (an OOM kill or otherwise — on this cluster, `memory.oom.group=1` means the whole pod dies together, not just the offending process), smelt notices proactively — not just the next time a tool call happens to touch it — reports it to the model in one message carrying whatever reason Kubernetes gave, and fully terminates the pod (not just its terminals) so a fresh `create_pod` is never blocked behind a stale one. See SME-12.
* The agent can also read, edit, and write files in its sandbox pod (`read_file`, `edit_file`, `write_file`, `list_directory`) — `edit_file` is a targeted `old_string`→`new_string` replacement (not a whole-file rewrite), renders as a real line-level diff in the transcript, and — along with an overwriting `write_file` — refuses if the file has changed since it was last read (a content-hash check), rather than silently clobbering a change a terminal command made in between. See SME-11.
* The agent can also find files by name pattern (`glob`, e.g. `**/*.rs`) and search file contents by regex (`grep`, optionally narrowed to files matching a glob filter first) in its sandbox pod — both paginated (`offset`/`limit`, low defaults), with a separate, higher hard scan ceiling bounding worst-case walk cost independent of the requested page (`scan_capped` in the response distinguishes that from ordinary "more pages exist"). `grep` never silently drops a file it can't search (not valid UTF-8, or oversized) — it's named, with why, in the response's `skipped` list. Implemented in-process (the `ignore`/`regex`/`globset` crates — the same libraries ripgrep itself is built on), not by shelling out to an installed binary. See SME-19.
* Sandbox pods run a custom image (`docker/sandbox/Dockerfile`) whose `ENTRYPOINT` is the sandbox agent itself — no separate inject-then-launch step, the agent is the pod's real PID 1 the instant it starts — with commands running as a regular, pre-created `sandbox` user by default (not root), passwordless `sudo` available for anything that genuinely needs it. Delivered with no container registry at all: `scripts/build-sandbox-image.sh` builds the image and streams it straight into the cluster's node (`docker save` piped into a `ctr images import`, via a short-lived helper pod), verified end-to-end against the real cluster rather than assumed. Each image is named after the agent sources it's built from (`smelt-sandbox:src-<hash>`, `scripts/sandbox-image-ref`): `scripts/check.sh`, the browser tier, check servers and CI run that one, so a branch that changes the agent tests its own image (SME-102, SME-84). A server with no `SANDBOX_IMAGE` (the dev server, a deployment) runs the image named after the sources it was built from too (`build.rs` computes the same name), so it can't drift onto an older agent; a node without that image fails `create_pod` within seconds (`ErrImageNeverPull`) naming the image and `scripts/build-sandbox-image.sh`. `smelt-sandbox:latest` is no longer used by default (SME-121). The user can also define named, reusable volumes — smelt doesn't need to know what one's for — mounted into every sandbox pod at a fixed path (a leading `~` expands to the sandbox user's home directory), configured through a `/sandbox-volumes` UI; PVC-backed, so a volume's content persists across every pod that mounts it, not just one conversation's. See SME-17.
* A live sandbox panel shows the conversation's pod (if it has one) and its terminals, each terminal's command history streaming in as it happens — no reload needed. stdout and stderr show grouped by stream: two pipes can't keep their relative order (SME-187). Since SME-122, all of a command's output arrives before its exit (the shell marks the end on both pipes), output that isn't UTF-8 shows as U+FFFD instead of wedging the terminal, a line longer than 64 KiB arrives in pieces, and a command that ends its shell (`exit`) finishes with the shell's status and the terminal's next command gets a new shell, unless a background job the shell started still holds its output (SME-191). Each terminal's titlebar shows its last command's status in a pill (running, exit N, lost) that stays in view however far the output scrolls (SME-144); a command's start is published before it's sent and a failed send's loss is published, so the pill never sticks at running or misses a loss. Each terminal follows its last line while output streams, and keeps following after a resize, a conversation switch away and back, or a reload (SME-108). See SME-10 and SME-11 (which moved the panel from N-pods-with-tabs to the current one-pod-per-conversation shape).
* A live, always-open per-conversation event stream pushes new messages and sandbox pod/terminal/command status to the browser the instant they happen — including turns a finished command's notice pushed with no `send_message` request in flight — so a browser tab stays current without polling
* A tab left open across a deploy keeps working and says it's out of date (SME-43): it skips event types its bundle doesn't know instead of dropping its stream, and when it reconnects to a server built from other sources (or sees such an event) it shows "smelt was updated. Reload to keep this page current." with a Reload button. It never reloads by itself. A reconnect also drops sandbox terminals and pods that went away while the tab wasn't listening.
* Conversation auto-titled from its first user message
* The transcript reads as what happened (SME-41): each tool call is one line saying what it did ("Ran `python3 primes.py`") with its result a click away and failures open; notices (a command finishing, the sandbox stopping) are muted lines naming the command; while a turn runs, every tab shows "Working…" with the elapsed time — the server's, so a reload or a second tab opened mid-turn shows the turn's real age (SME-160) — and the sidebar marks busy conversations. That line has never been measured at phone width with the todo panel open, where a longer elapsed string can cost it a character in the same span: the next sweep should check it there too (SME-144's lesson). A new conversation offers example asks. The transcript follows its bottom as replies arrive, but a small scroll up stays put (SME-83), and a window resize or zoom keeps the follow rather than turning it off (SME-108), while the pointer is over it a panel or the context bar appearing doesn't move the text under the pointer (SME-75). Dark mode follows the system setting, and on a phone the conversation list folds behind a button. Sandboxes come with python3, git, curl and the Docker client.
* The settings pages (Model providers, MCP servers, Sandboxes, Sandbox volumes, Git, Language servers) are linked from the sidebar; a URL that isn't a page shows "Page not found" with a link home; below 720px wide the sidebar becomes a strip above a full-width chat (SME-40).
* The model's replies render as markdown (SME-30): headings, lists and task lists, emphasis, links, images, tables, quotes, and code blocks with a language label, a copy button and syntax highlighting (syntect with two-face's grammars, light and dark themes). The streaming reply renders the same way as it arrives; a code fence still open shows plain until it closes. User messages, thinking, notices and tool rows stay plain text. The reply is treated as untrusted: no HTML string is built, raw HTML shows as text, links only for http/https/mailto, images only from http/https (fetched without a click, an accepted risk), nesting bounded, highlighted code's included (SME-174). A bare URL, `www.` address or email address the model writes without link syntax becomes a link too, whose words are the text it was found in; code and allowed links are left alone, a link that wouldn't go where its text says (URL syntax in an email address, a bidi control) stays text, and every reply link is bidi-isolated from the text around it (SME-104). Each finished reply has a "Copy reply" button on its last bubble that copies the reply's markdown as the model wrote it, every text part from one user action to the next (thinking, tool calls and notices left out); the label counts the parts and the button outlines every bubble it copies while pointed at or just clicked. It works over plain HTTP too, where `navigator.clipboard` doesn't exist, through a hidden `textarea` and `execCommand('copy')` (`crate::frontend::clipboard`, SME-105). See [frontend.md](<https://github.com/cconstantine/smelt/blob/main/docs/frontend.md#markdown-in-replies>).
* History persists across restarts (Postgres, not in-memory) — message content is stored as JSON `ContentBlock`s, not plain text, so tool calls, results, and thinking blocks round-trip through storage exactly like Anthropic's own protocol shape
* Missing/invalid API key surfaces as a visible error in the chat UI rather than hanging or crashing silently
* Model providers (SME-72), on "Model providers" (`/providers`, sidebar), replace the `ANTHROPIC_*` environment variables. A provider is a kind (Anthropic, Ollama, llama.cpp, other), a base URL whose `/v1/messages` every turn goes to, and a key sent as `x-api-key` or a bearer token; pages only ever show the key's last four characters (stored in plain text for now, SME-48). The kind decides how its models are listed and described: Anthropic's `/v1/models` (context window, thinking), Ollama's `/api/tags`, `/api/show` (tools, thinking, a Modelfile's `num_ctx`) and `/api/ps` (the loaded window), another server's `/v1/models` (llama.cpp's `n_ctx`). Each model's context window and thinking can be overridden; a model nothing sizes is shown as "unknown, assuming 200,000". One model is the default. Each conversation has its own, shown in a picker above the message box and changeable there (live in every tab, from its next turn); one without takes the default when its next turn starts and keeps it. With no provider or no default, the picker says so with a link and Send waits. After a switch, thinking signed for the old model isn't replayed. A reply's content blocks are kept by their `index`, so a server that overlaps them (llama.cpp's `llama-server` stops every block at the end of the reply) keeps its commentary between tool calls and its thinking (SME-112). Cost levers (SME-106): a provider's **Prompt caching** (on by default for Anthropic) marks each turn's request with two `cache_control` breakpoints (the system prompt and the end of the transcript; never compaction's request); each model's **Effort** is sent as `output_config.effort` on an Anthropic provider's turns; every model request says `User-Agent: smelt/<version>`. A **llama.cpp** provider (SME-111) also reads `/props` (each slot's window, slots, build, the chat template's caps), shown under its Models heading; its turns send `chat_template_kwargs` with the model's Effort as `reasoning_effort` (template's default, low, medium, high) and the provider's **Keep earlier reasoning** as `preserve_thinking`, each only when the template's caps say it reads it, and `enable_thinking: false` with thinking off (compaction always); its thinking is `{"type": "enabled", "budget_tokens": N}`, three quarters of the reply budget leaving 4,096 to answer, capped by the model's **Reasoning budget**, while every other kind keeps adaptive thinking, except a model whose Anthropic listing says it can't take it (Haiku 4.5 and older), which gets the same budget, at least 1,024 (SME-122). The new-provider form suggests the kind when an address answers `/props` like llama.cpp. Each model also has **Max reply tokens** (else Anthropic's listed `max_tokens`, else 16,384 on Anthropic or Other).
* The agent can call tools on externally-hosted MCP (Model Context Protocol) servers — e.g. GitHub's hosted server — configured through a `/mcp-servers` UI (an index with a live per-server "Connected — N tools"/"Unreachable"/"Sign-in expired" status badge, a create page, and a single-form edit page with in-place header editing). Every configured server's tools are available in every conversation, namespaced as `mcp__<server>__<tool>`. An unreachable server never holds up a turn: listing tools waits at most 10s per server, and model calls skip a server that failed within the last 5 minutes (the status page still tries every time) — see SME-40. Header *values* (auth tokens etc.) are write-only past the initial save — the browser only ever sees header *names* back. See SME-15.
* An MCP server can authenticate via real OAuth instead of a static header — the user clicks Connect on the server's edit page, approves smelt at the provider, and lands back connected (built on `rmcp`'s own MCP-spec OAuth client: discovery, dynamic client registration, PKCE, refresh). The token is fetched for every request and refreshed as it nears expiry, the client secret included for a pre-registered client, so a connection outlives its tokens (GitHub's last 8 hours, Linear's about 24); a sign-in the provider won't refresh any more shows "Sign-in expired" with a Reconnect button instead of Connected (SME-113). A provider without Dynamic Client Registration support (GitHub) instead takes a pre-registered client ID/secret, entered on the new-server form. An OAuth server can have extra headers too (not `Authorization`), e.g. GitHub's `X-MCP-Toolsets` to turn on its Actions tools, which read CI job logs (SME-76). The callback checks the provider's issuer (RFC 9207, MCP's SEP-2468) on success and error responses alike, which providers that advertise it (GitHub, Linear) require; an error response that fails the check shows a fixed message instead of the provider's text. Both connect live (SME-65). A failed sign-in's error stays on the server and the edit page takes it once, so no text in a link shows as smelt's own error (SME-168). Only a callback carrying the sign-in's own `state` ends it, so a forged one can't cancel a Connect or replace its error, and a token refresh is saved only over the exact grant it refreshed, so one finishing after a Reconnect with the same pre-registered client can't overwrite the new grant (SME-177). See SME-16.
* An always-visible indicator shows how full the model's context window is, built on real `usage` numbers from Anthropic's own API responses (not a local estimate) — clicking it (or Enter on it: it's a button, and the view is a dialog that Escape closes, SME-82) opens a detail view (system prompt, every available tool's full definition, message count, a visual segmented-bar breakdown of the window by token category, and what the conversation's completed model calls have used and cost so far). Once a conversation's estimated next request would eat into a reserved ceiling (context window minus the model's own reply budget and a safety buffer — checked *before* sending, not reactively), smelt auto-compacts: a separate summarization call condenses everything so far — explicitly told every currently-live sandbox pod/terminal id so it isn't lost — and the result is persisted as a new message (nothing earlier is ever rewritten or deleted; only what gets replayed to Anthropic on later turns changes). The compaction event renders as its own distinct, collapsed divider in the transcript, live in every tab, and the model is shown the messages it hadn't answered yet, so it answers the one that triggered the compaction (SME-40). See SME-18.
* The agent can track its own multi-step plan as structured state (`todowrite`/`todoread`) instead of only in plain text — a live todo panel in the chat UI (same shape as the sandbox panel) shows the current list update as the model works. `todowrite` is always a whole-list replace (no per-item ids); the list survives a compaction boundary the same way live sandbox pod/terminal state already does. See SME-20.
* The model can ask the user (SME-34): `ask_user` puts one to four questions on a card below the transcript, each with two to four options (single or multi-select) or a free-text field, and the turn ends waiting for the answer, with no time limit. The answer, written once whichever tab gives it, becomes the call's result and a new turn runs on it; notices that arrive meanwhile are saved and reach the model with the answer; a message the user writes instead dismisses the question, also when a Stop catches it queued behind another turn (SME-170). The waiting survives a reload, other tabs and a restart (a `pending_questions` row), the sidebar marks waiting conversations, and the answered call shows as a compact row.
* The agent can look things up on the open web, with two tools for two different jobs: `webfetch` runs a real headless browser (JS execution included, not just a raw HTML fetch) and returns a page's rendered, readable text — for anything that needs real rendering; `http_request` is a plain HTTP client (like `curl`, no browser) for hitting a JSON API or REST endpoint directly, much cheaper than `webfetch` when real rendering isn't needed. Both check every request they make (including any redirect, and — for `webfetch` — every subresource/JS-initiated fetch too) against a shared SSRF guard before it's allowed through, not just the URL the model asked for. For the browser, that guard also sits in a proxy all of its traffic goes through, so popups, WebSockets and service workers are covered too. See SME-21.
* The agent can search the web, through Exa's hosted MCP server (`mcp__exa__web_search_exa`), which smelt adds as a built-in MCP server at startup. No account or key is needed; adding a key on `/mcp-servers` lifts the free limits. It returns titles, URLs and the passages most relevant to the query, and the model reads a result in full with `webfetch`/`http_request`. See SME-24 and [setup/sandbox.md](<https://github.com/cconstantine/smelt/blob/main/docs/setup/sandbox.md#built-in-mcp-servers>).
* The agent can also hold a persistent, interactive browsing *session* open across several tool calls (`open_browser_session`/`browser_navigate`/`browser_click`/`browser_fill`/`browser_back`/`browser_read`/`close_browser_session`) — unlike `webfetch`'s one-shot fetch, the same real page stays open, so the model can click a link, fill a form, and read the result without re-navigating from scratch. A live panel shows the user the exact same page in real time (a real CDP screencast, not a periodic snapshot) and lets them click/type/scroll on it directly too — the user and the model share one real browser session, with no locking between them. The panel scales the page to fit, so the chat stays usable at laptop widths, and a private or local address is refused before anything loads (SME-40). See SME-22. One failed browsing or `webfetch` call fails only that tool call: the session list's lock is recovered after a panic (`browsing::sessions()`), and the shared browser's runtime, if the OS refuses its threads, returns an error and is built again on the next call (SME-119). That holds where panics unwind (`dx serve`, the tests): the release profile has `panic = "abort"`, so a release build still ends on any panic (SME-139).
* A server running in the conversation's sandbox (a dev server, a web app) can be opened in both browsers, with no tunnel or outside service (SME-42). In `webfetch` and browsing sessions, `http://localhost:<port>/` (also `127.0.0.1`, `[::1]`) is that port in the conversation's own pod; every other private or local address is still refused. The model shares a port with `sandbox_preview_url`, which checks something is listening. The sandbox panel then shows an "Open preview · port N" link, live and after a reload, to that port at an origin of its own (`SMELT_PREVIEW_URL`, e.g. `http://5173-42.preview.localhost:8181` in dev, `https://5173-42-smelt.constantlee.us` in production). Live reload works through it. Both routes use a Kubernetes port-forward into the pod, so servers bound to `127.0.0.1` there work, and nothing reaches another conversation's pod. A preview link whose conversation has no running sandbox shows a page saying so, with how to get it back and a link to the conversation (built from `SMELT_BASE_URL`; SME-46). Previews are as protected as smelt itself (no login yet).
* Docker works in every sandbox, as on a Linux machine (SME-33): `docker build`, `docker run`, `docker compose` and buildx, without `sudo`. dockerd runs in a privileged sidecar container next to the unprivileged sandbox, sharing `/workspace` (where terminals start and bind mounts must come from) and a socket. Images, build cache and named volumes live on the conversation's own claim, so a new pod starts with them, and deleting the conversation deletes them. Containers share Docker's own memory limit (`SANDBOX_DOCKER_MEMORY_LIMIT`, or `create_pod`'s `docker_memory_limit`); an OOM kill restarts only Docker, and the model is told, with its terminals and files untouched. A published port is at `localhost`, and any container port at the container's address (in `172.20.0.0/14`), from terminals, `webfetch`, browsing sessions and previews (`sandbox_preview_url`'s `host`). The cost: anything the model runs can become root on the node (see [setup/sandbox.md](<https://github.com/cconstantine/smelt/blob/main/docs/setup/sandbox.md#docker-in-the-sandbox>)); SME-47 would take that back once the node's kernel allows it. **Containers get the pod's uplink MTU** (SME-157). Docker's own default MTU is 1500; on Flannel's VXLAN (k3s's default) the pod's uplink is 1450, and a container advertising MSS 1460 loses every full-MSS segment its peer sends — `git clone` over HTTPS dies on a recv failure, `docker build` fails in whichever `RUN` step reaches out, and it looks like a problem with the site. `start-dockerd.sh` reads the MTU of the interface carrying the pod's default route from `/proc/net/route` and sysfs and starts dockerd with both `--mtu` (the default bridge) and `--default-network-opt bridge=com.docker.network.driver.mtu=` (user-defined bridges — what compose project networks are); neither flag alone covers both. If no uplink MTU can be read the sidecar refuses to start dockerd, with the reason in its container log. Networks already stored in `/var/lib/docker` keep the MTU they were created with; nothing migrates them (see `docs/setup.md`).
* Conversations work on git repos (SME-32). The model clones with `clone_repo`, and the user with "Work on a repo" in a new conversation; both start the sandbox if there's none (SME-49); a conversation can have several, listed in the sandbox panel with what's checked out. A conversation's `/workspace` is its own claim (`sandbox-workspace-<id>`), so checkouts and uncommitted work outlive the pod and go with the conversation. The Git page (`/git`) generates or imports an SSH key (one at a time) and sets the commit name and email; every pod gets them in `/etc/smelt`, and a change reaches running pods at once. The key is stored unencrypted for now (SME-48). A clone lists the repo's `AGENTS.md` files (top-level and nested), which the model loads with the `load_instructions` tool: a loaded file (first 32 KiB) stays in every turn's system prompt under Project instructions, and the context view shows what's loaded and from where. Only a repo the user trusts loads: the first time the model asks for a file from an unknown remote, the chat shows exactly that file on a Trust / Don't trust card, and Trust loads exactly it; the decision is remembered per remote and listed on `/git`. A repo the user opened themselves counts as trusted. A clone never overwrites an existing directory: git refuses it, and the error explains what to do with a cut-off clone's leftovers.
* A third bug bash (SME-51, 2026-09-28) ran the Feature checklist and a whole-codebase review, and fixed 12 findings:
  * **Other sites can't act as the user.** `src/request_guard.rs` refuses a write that a browser marks as coming from another site, a sandbox preview included. Once `SMELT_ALLOWED_HOSTS` names the hosts smelt is reached by, requests for any other host name are refused, which stops DNS rebinding.
  * **Conversations are isolated.** Terminal and command tools only act on the calling conversation's ids.
  * **The private-address guard refuses every non-public range,** CGNAT (Tailscale) included, and `http_request` connects to the addresses it checked. (SME-155 has since removed the address filter: the model's fetch tools and browser reach any address.)
  * **A stop is saved in the conversation** as a notice, shown as "Stopped." everywhere and seen by the model and by compaction.
  * **Pods are deleted with a 20-second grace,** and the sandbox agent exits on SIGTERM.
  * **One live pod per conversation** is a unique index, and pod starts are serialised per conversation and survive a Stop.
