# Architecture (short version)

How the code is laid out, in the space a section of [index.md](index.md) used
to take. [docs/architecture.md](../architecture.md) is the full picture.

* Dioxus fullstack: server functions in `src/api/` (`chat`, `browsing`, `git`, `language_servers`, `mcp`, `pods`, `providers`, `questions`, `sandbox`, `sandbox_volumes`, `version`) are the API surface, with no hand-written browser fetch client. The exceptions: one plain Axum route (`/oauth/mcp-callback/{id}`, the MCP OAuth callback), the `request_guard` layer on every route, and the preview proxy's own listener (`src/preview.rs`). See [api.md](<https://github.com/cconstantine/smelt/blob/main/docs/api.md>).
* `send_message` (`start_turn`) is an ordinary request: it checks the conversation exists, starts the turn in the background, and returns. Everything a turn does reaches the browser on `subscribe_conversation_events`, the one stream each watching tab holds, as `ConversationEvent`s: `MessagesAppended` per message as it's saved, `ReplyReset`/`ReplyDelta` as each model call's text streams, `TurnState`/`TurnError`, plus sandbox and pod changes. A tab that connects mid-reply fetches the text so far (`get_reply_in_progress`). See SME-27.
* `send_message` is a thin wrapper around `run_turn`, a bounded (`MAX_TURNS`) loop that round-trips `tool_use`/`tool_result` turns with the real Anthropic API and persists each one. A per-conversation async lock serializes every writer — a live request and a finished command's notice can both want to persist a turn at the same time. Before building each request, `run_turn_bounded` checks `should_compact` (the last known real `usage` plus a cheap estimate of what's new since then, against a reserved ceiling) and, if crossed, runs `compact_conversation` first — see SME-18. Each request's `max_tokens` is `reply_budget` (SME-111): the smallest of the model's output cap, the room left and half the window, never below 16,384 (`MIN_REPLY_TOKENS`, the room the compaction trigger keeps). A reply that stops at it is kept and followed by a notice every tab shows, naming the limit, what bound it and what to change. A reply cut off in the middle of a tool call keeps what came before; the call it was cut in is dropped, never run, and named in the notice, and any whole calls before it are saved with a "Not run" result (SME-126). The actual history sent is always rebuilt fresh via `history_for_request` (a live `db::list_messages` fetch, not an in-memory accumulator), so a compaction's effect applies immediately. A compaction summarizes only what the last one didn't already cover (the previous summary plus the messages after its boundary), capped to fit the context window, so repeated compactions don't grow until they fail. A briefly unavailable model provider (429/503/529) is retried twice before the turn fails, with the provider's own message. The turn engine is its own server-only module, `src/turn/` (run, state, history, compaction, notify), apart from `api::chat`'s server functions; each conversation's turn state is one `ConversationRuntime` entry, a stopped turn is a typed outcome (`TurnFailure::Stopped`), and everything outside a turn reaches the model through one function, `turn::notify` (save a notice, deliver it, or wake for finished commands) (SME-52).
* `src/anthropic/` talks to the real Anthropic API separately, reducing its SSE stream down to text deltas, `tool_use` blocks, and real `usage` numbers (`TokenUsage`) before `run_turn` relays them to tabs as `ReplyDelta`s. `stream_anthropic_message` takes an `Endpoint` (base URL and `Auth`, whose `Debug` hides the key); `src/anthropic/models.rs` lists a provider's models per kind. `src/providers.rs` resolves the `TurnModel` a turn runs on (once, after saving its message and any pending notices, kept for the whole turn and its compaction), the picker's state, and the providers pages' logic; the context window comes from the model's override, what its provider reported, `context_window_for` (a `claude-*` model), else 200,000.
* Usage and cost (SME-106): every completed model call (each call of a turn's tool loop, and compaction's) is a row in `model_call_usage`, written with the conversation's last-known usage in one transaction, with its cost fixed when written. Prices come from [models.dev](<http://models.dev>)'s catalog (`src/pricing.rs`: fetched at startup and hourly, last good copy kept in `price_catalog`, `SMELT_PRICE_CATALOG_URL` overrides the address), priced as each provider's **Prices from** entry, which the form suggests from the base URL. The providers page lists each model's last 30 days.
* `src/anthropic/tools/` dispatches tool calls by name from one registry of `Tool { def, run }`s, one module per domain (pods, files, todos, git, web, browser, lsp), each tool's definition beside its dispatch (SME-54).
* `src/events.rs` is the per-conversation broadcast bus (`tokio::sync::broadcast`) that `subscribe_conversation_events` forwards and both the tools and `chat.rs` publish to, plus an app-wide bus (`AppEvent::PodsChanged`/`TurnsChanged`) for the sidebar and the Sandboxes page. A conversation's channel exists only while something subscribes (the last `Subscription` removes it), and subscribing to a conversation that doesn't exist is refused, so a tab left on a deleted one says so instead of re-creating it (SME-91). In tests, listening on a conversation id below 100 000 (the range every test database hands out) panics, so no test hears or counts another's events (SME-135). Both decode an unknown type as `Unknown`. `build.rs` hashes the sources into `SMELT_BUILD_ID`, which a tab compares with `api::version::get_build_id` on every stream (re)connect (SME-43).
* `src/db/` (a module per group of tables since SME-163, each re-exported by `db/mod.rs`, so callers write `db::create_conversation`): CRUD functions taking a `&PgPool` parameter, plus a global `OnceLock<PgPool>` for production wiring, no request-scoped extractor plumbing.
* `.github/workflows/ci.yml` runs the full test suite (server + WASM check + the automated browser tier) on every PR, against the same `docker-compose.yml` stack local dev uses — see SME-14. The browser tier's scenarios each run under their own time limit and fail on their own, and a tab marks itself live (`data-live` on the chat panel) once its event stream and snapshot pull are done (SME-59). A state that lasts only while a test server answers (a loading page, a late image) is held open by the scenario with `HeldPage` until it has been seen, not timed by the server (SME-118). The sandbox's real-cluster lifecycle runs as one test per feature (`src/sandbox/pod_lifecycle_tests/`), in parallel, each with ids clear of every other run and a sandbox manager of its own behind `sandbox::get()` (`use_test_manager`), and torn down pass or fail (SME-94). The first such test in a process sweeps `smelt-park-test` of every pod and claim over an hour old, whatever a killed run or failed teardown left; it is test-only and three guards keep it out of `smelt-park` (SME-134). Its real-cluster tests judge age by the API server's own creation times (`sweep_with` takes the moment to judge at; production passes the clock), so a slow runner can't make a young object look old (SME-143).
* Sessions working at once take turns on the shared test cluster and Postgres through one lock, `flock` on `<git common dir>/smelt-cluster.lock`, which the scripts take themselves (SME-100): `scripts/with-cluster-lock` runs one command under it (naming the holder while it waits, re-entering an enclosing holder rather than deadlocking, and logging waited/held times to `smelt-cluster-lock.log`); `scripts/check.sh` and `scripts/browser-tier` build, lint and compile their tests first and lock only the test run; `scripts/cluster-test` does the same for a direct `cargo test`; `scripts/clean-test-namespace.sh` locks too. `scripts/check-server` takes no cluster lock, only a lock on its `CHECK_PORT` held by the server while it runs, so check servers on different ports run alongside each other and alongside gates.
* The repo is kept so any agent, a local model's 262k-token window included, reads each file in one go (SME-163): every tracked text file stays under 40,000 bytes and 2,000 lines, production functions and components under 200 code lines, and every relative doc link and anchor resolves, checked by `src/repo_lints.rs` in `cargo test --features server` and clippy's `too_many_lines` in `scripts/lint-expects`. A big module is a directory of submodules its `mod.rs` re-exports, a big test module is `tests/<topic>.rs` files, the stylesheet is `assets/css/NN-*.css` linked in order, and the process is `docs/development-process.md` (an index) with `docs/personas/` and `docs/process/`. `AGENTS.md` holds the instructions for every agent, and `CLAUDE.md` imports it.
* `src/sandbox/` (split into modules by SME-56: `spec`, `manager`, `claims`, `agent`, `ports`, `files`, `watch`, `exec`, plus `adopt` (SME-115); `mod.rs` re-exports them, so callers say `sandbox::X`; before `init()` a call returns `SandboxError::NotInitialized` instead of panicking, and a stream kube doesn't hand back is `SandboxError::NoStream`, so the module's production code has no `expect()` (SME-95); `scripts/lint-expects`, run by `scripts/check.sh` and CI, refuses a new `expect()` or `unwrap()` outside tests anywhere in smelt unless it's marked with why it can't fail; `unwrap()` since SME-119): `Sandbox`/`SandboxManager` — create/exec/delete a disposable Kubernetes Pod, in a `smelt-park` namespace (a hermetic `docker-compose.yml`-provided `k3s` cluster for tests, the real `homelab` cluster for production). See SME-7. Built on top of that: pod/terminal/command as three separately-guarded lifecycles, a small `axum` agent binary (`src/bin/sandbox_agent/main.rs`) that's the pod's own `ENTRYPOINT` (real PID 1, custom image built and delivered with no registry by `scripts/build-sandbox-image.sh`) multiplexing every terminal that pod hosts (plus the file-tool operations below) over one WebSocket connection. Both ends share one definition of its protocol, `src/agent_protocol.rs`, versioned major.minor: the agent says hello with its version, smelt tells the model to replace a pod whose agent speaks another major, and a pod has one connection at each end (SME-53). See SME-9 and SME-17. A conversation has at most one live pod at a time (`conversation_pod_id` resolves it implicitly — tool calls no longer name a `pod_id`) — see SME-11, which also added `read_file`/`edit_file`/`write_file`/`list_directory`, and SME-19, which added `glob`/`grep`. The live sandbox panel (pod/terminals/commands, streaming output) is layered on top of this — see SME-10. `create_volume`/`delete_volume` manage generic, PVC-backed pod mounts alongside this, exposed via `src/api/sandbox_volumes.rs`. Every pod also has a Docker native sidecar (SME-33), started with `docker/sandbox/start-dockerd.sh` rather than the dind entrypoint so dockerd and its containers stay inside the sidecar's own cgroup, with `/var/lib/docker` on the conversation's `sandbox-docker-<id>` claim and `/workspace` on its `sandbox-workspace-<id>` claim (SME-32; the sidecar hands `/workspace` to the sandbox user); `watch_pods` reports a sidecar restart to the model. Every real server shares `smelt-park` (the dev server, a check server on a scratch database) and names its objects after its own database's ids, so each database has an instance id (`smelt_instance`) and every pod and claim smelt creates is labelled `smelt/instance=<id>`; a server deletes, sweeps, reuses, mounts, watches and reads only its own, and refuses another's of the same name (`SandboxError::NotOurs`). Objects from before the fix are adopted at startup only by the database that already had conversations when it migrated, and never deleted otherwise; a fresh database's ids start above 2,000,000,000 so its names don't meet the dev server's (SME-115). At info, startup logs the database's instance and the summaries of adoption and the claim sweep, and every pod or claim the sweep, a conversation's teardown, a stopped pod or a deleted volume deletes is logged with its name and uid; `scripts/check-server` runs its server at `RUST_LOG=info` and `NO_COLOR=1` unless told otherwise, and keeps the previous run's log as `.check-server.log.prev` (SME-117). The agent listens on loopback only, and relays connections to container addresses (`127.0.0.1:8089`, limited to `src/docker_net.rs`'s range) for the browser routes and previews.
* `src/preview.rs` serves sandbox previews on a listener of its own (`SMELT_PREVIEW_ADDR`, default `0.0.0.0:8181`; `dx serve`'s dev proxy rewrites `Host`, so it can't be a route on the app): `Host` names the conversation and port, and hyper proxies to the pod over `sandbox::open_pod_target` with `Host: localhost:<port>`. The model's browser reaches the same pods through a per-browser-context proxy (`egress_proxy::start_with_sandbox`, set as the context's own `proxyServer` over CDP), with `fetch_guard::check_load` letting `localhost` through only in such a context. Only the sandbox's own pages, the model's own navigations and plain page loads reach a pod (`fetch_guard::allows_request_from`); browsers send a container's plain-http address no `Sec-Fetch-*`, so there a request needs to be a page load (`Upgrade-Insecure-Requests`) or carry a `Referer` from the sandbox (SME-90). See SME-42.
* `src/git.rs` (wire types ungated; the server-only rest is `src/git/server/`, a module per subject since SME-163; server functions in `src/api/git.rs`): one SSH key and the commit identity, written into every pod's `/etc/smelt` over kube exec (`pod_git_files`, `install_git_files`, through `sandbox::PodShell`, which runs git's commands in a pod's sandbox container); a conversation's repos (`conversation_repos`, cloned over kube exec straight into `/workspace/<dir>`, which git refuses if it exists, remotes normalised by `remote_key`); `load_instructions` (the model's tool) loads an `AGENTS.md` into `loaded_instructions`, or for a remote the user hasn't decided about records an `instruction_requests` row with the exact file the trust card shows, which `decide_trust` loads on Trust. See SME-32.
* `src/lsp/` (server-only): language servers (SME-35). `client.rs` is smelt's own JSON-RPC client over any byte stream (cancellation on timeout, server requests answered by a handler); `session.rs` one initialized server with roots, versioned document sync and diagnostics; `pods.rs` the server pods (`lsp-<pod id>-<name>`, labelled `smelt/lsp-of`, pinned to the sandbox pod's node and owned by it), stdio over `pods/exec`, and `note_server_stop` for `watch_pods`; `ops.rs` the `lsp` tool's operations as text; `manager.rs` joins configs, pods and sessions (one per server pod, reopened at most 3 times in 5 minutes); `catalog.rs` the mason and Helix lookup. Configs are the `language_servers` table, with server functions in `src/api/language_servers.rs`.
* `src/frontend/mod.rs`: the `Route` enum (`Home` at `/`, `ConversationRoute` at `/conversation/{id}`, `McpServersRoute`/`McpServerNewRoute`/`McpServerEditRoute`, `SandboxVolumesRoute`/`SandboxVolumeNewRoute`, `PodsRoute` (the Sandboxes page, `/pods`), `GitRoute`, `LanguageServersRoute`/`LanguageServerNewRoute`/`LanguageServerEditRoute`, `ProvidersRoute`/`ProviderNewRoute`/`ProviderEditRoute`, and `NotFound` for anything else) — `Chat` derives which conversation is selected from the router itself (`use_memo` over `router.current::<Route>()`), not a plain owned signal, so it stays correct across client-side navigation as well as a fresh load.
* `src/mcp.rs`: a thin wrapper over the official `rmcp` SDK — a connection registry keyed by `mcp_servers.id`, lazy-connect with a one-retry safety net, and real `tools/list_changed` notification handling. `src/api/mcp.rs` exposes it as server functions; `anthropic::tools::tool_definitions`/`execute` dispatch to it alongside smelt's native tools. See SME-15. `src/mcp_oauth.rs` layers OAuth auth on top — a Postgres-backed `CredentialStore` for `rmcp`'s own OAuth client plus the start/callback/disconnect lifecycle; an OAuth server's transport is `rmcp`'s `AuthClient`, with one shared `AuthorizationManager` per server (SME-113) — see SME-16.
* `src/telemetry.rs` (SME-137): the subscriber (console `fmt` layer on `RUST_LOG`, plus an OTLP/HTTP export layer with its own filter when `OTEL_EXPORTER_OTLP_ENDPOINT` is set). Exported spans run through `telemetry::in_span`, which ends a span's export when its work ends: hyper-util's pooled connections and rmcp's service loop otherwise hold spans open for good. `mark_error` marks a span failed without a console line; `capture_spans` is the tests' in-memory exporter.
