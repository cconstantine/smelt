# SME-242 — a persona gets only the credentials it lists in its sandbox

**Branch:** `sme-242-persona-credentials` — worktree `../smelt-sme-242`, branched from a freshly fetched `origin/main` at `b56ff56`. `git worktree list` at plan time: `/workspace/smelt` (main) and `/workspace/smelt-sme-242` (this branch). Traced against `b56ff56`, which already carries SME-241 (`20261026120000_agents_rule_chain.sql`, `src/personas/rules.rs`), SME-239 (`20261027120000_agent_volumes.sql`) and SME-235/236/238.

## What

Bash in a sandbox reaches the network, so tool rules can't stop a persona from pushing to GitHub as the user. What a pod holds follows the persona: a persona lists the credentials it gets in its own field `smelt.credentials: [git-ssh, …]`; one that lists none gets none; a child never gets more than its parent. Named secrets the user keeps in smelt (a settings page: name + value) ride the same path and land at `/etc/smelt/secrets/<name>`, mode 600 — which is how a Project Manager seat under smelt runs `scripts/pm-wait-for-board` (SME-247). Design: `docs/design/personas/tool-rules.md#credentials`, `persona-files.md`.

## Decisions

**D1 — A credential is a name.** `git-ssh` is built-in and reserved; every other name is one of the user's stored secrets. A pod's effective set is a set of names, never values; values are read only by the install path.

**D2 — The decision, in one function.** `credentials::for_conversation(pool, conversation_id) -> PodCredentials { git_ssh: bool, secrets: Vec<String> }`:

- **no `agents` row** (a conversation without a parent, the user's own): `git_ssh` = a stored key exists, and `secrets` = **every stored secret name**. This is what makes narrowing able to reach anyone — a conjunction can't hand down what the root doesn't hold — and it keeps the design's sentence for `git-ssh` ("a conversation without a parent is unchanged: it gets the key, as every pod does today"). See Question 1.
- **an `agents` row**: the stored `credentials` column. `NULL` — which after this ticket means only a row made before it — falls open to exactly today's behaviour: `{git_ssh: true, secrets: []}`. Falling closed would strip the key from a live pre-SME-242 agent at its next pod restart, which is a behaviour change nothing asked for. (The reverse of SME-241's chain, which falls *open* on corrupt JSON for the same reason — don't strand a live conversation; here the value is a name set smelt wrote.)

**D3 — Fixed at start, written twice, plus a safety write.** `agents.credentials TEXT[]`, nullable:

1. `db::create_child` writes the **parent's effective set** — read from the parent's `agents` row in the transaction that already locks and reads it (`SELECT state, depth, root_id, rule_chain …` gains `credentials`); for a parent with no row, D2's root rule.
2. When the child's persona is read — in `prepare`, right after `persona::snapshot` succeeds — `db::narrow_agent_credentials(pool, child, &[names])` writes `persona ∩ stored`, `UPDATE … WHERE conversation_id = $1 AND state = 'starting'` (every `agents` write is state-gated, per `database.md`). A persona with **no** `credentials` key narrows to the empty array; a persona-less child writes nothing (it keeps its parent's set).
3. for a start that did **not** complete, `agents::start::end_start` first calls `db::clear_agent_credentials(pool, child)` — `credentials = '{}'`, state-gated — before reconciling the pod, so a start cut off before the persona was read leaves no credential behind (the ticket's "a failed or cut-off start leaves no key behind").

Not narrowed in `complete_start`, unlike `rule_chain`'s entry append: the thing that must end up clean is the **pod**, and the exits that clean it (`StartExit::drop` → `end_start`, and `sweep::startup_sweep`) only have the row to read. Writing the narrowed set as soon as the persona is parsed is what lets every exit clean up correctly. The asymmetry with rules is deliberate and gets a comment at both sites.

**D4 — Clone, then remove.** At pod create during `starting`, the column still holds the parent's set, so the key is there and the SSH clone works. Nothing of the model's runs while `starting` (no turn is admitted; a child stopped mid-start never becomes `active`, since `started_at` stays null).

**D5 — "a pod restart" is the same code path.** Sandbox pods are `restart_policy: Never` (`src/sandbox/spec/pods.rs:223`), so a restart is a new pod through `create_pod_attempt_unspanned`, whose install at `src/sandbox/manager/create.rs:290` is the one new-pod site in production (`install_into_new_pod` has exactly one caller there). Re-adopting a running pod after a smelt restart installs nothing new (the files are already in the pod — today's behaviour for keys, unchanged). So the design's "three install sites" are **two code paths**: pod create, and the live-pod loop after a key/identity/secret change — plus the end-of-start reconcile. `docs/design/personas/tool-rules.md#credentials` gets reworded to say that, with the evidence.

**D6 — Reports, three places** (the ticket: "a persona naming a secret that doesn't exist is reported, not silently ignored"; and an ask the parent's chain denies is the same kind of silence):
- `list_personas` (`src/git/server/personas.rs`'s `persona_entry`): the persona's `credentials` list, plus — for a name that isn't `git-ssh` and isn't stored — a note in SME-241's `unmatched_note` style, made against `db::list_named_secrets` read once per listing (like its `server_names`, read once, and reading nothing on failure rather than accusing every name).
- `start_agent`'s parent notice (`start.rs`'s `one_notice`, which already carries the model and rules notes): names dropped for either reason — "its persona lists `linear-key`, which isn't one of your stored secrets", and "its persona asks for `git-ssh`, which its parent's chain doesn't have, so it gets none".
- the child's environment section (D8).

A name that isn't stored is never a parse error: `personas::parse` can't know the deployment's secrets, exactly as a rule naming an unconfigured server isn't one (SME-241).

**D7 — Never the value, anywhere.** `db::NamedSecret` gets a hand-written `Debug` (the `McpServerConfig` precedent: names and "stored?" only); `api::secrets`' summaries carry no value (the `has_oauth_client_secret` write-only precedent); the environment section names paths only; install errors quote paths and the pod's stderr, never content (`install_git_files` already does). A model that holds a credential can `cat` its own file — that's what granting it means; smelt itself never prints a value into a tool result, a span or a prompt.

**D8 — The environment section** (`PromptEnvironment`, `src/turn/history.rs`), one new field gathered per turn (names only):

- `- Credentials: git SSH key at /etc/smelt/keys/<name>; secret linear-api-key at /etc/smelt/secrets/linear-api-key`
- for an agent whose set excludes `git-ssh`: `- No git credential: your persona's smelt.credentials doesn't list git-ssh (or your parent's chain doesn't have it), so /etc/smelt/keys is empty — git push and git fetch over SSH will fail; don't retry them.`
- for a persona name dropped as un-stored: `- Your persona lists credential \`foo\`, which isn't one of the user's stored secrets, so you don't have it.`

A root conversation with no key stays as today (nothing said): only a *narrowed* conversation gets an explanation, which keeps today's prompt tests' shape and answers the case the model can't infer.

## The state model

**Records.**

| Record | States | Who moves it | Who else sees it |
| -- | -- | -- | -- |
| `named_secrets` row | live → deleted | the user (page); only the page | every pod install (names), `list_personas`, the start notice |
| `agents.credentials` | parent's set → narrowed → (never-started) `'{}'`; NULL for pre-ticket rows | `create_child`; `prepare` at persona read; `end_start` when `!done` | pod create, live-pod install, end-of-start reconcile, the prompt, `start_agent`'s notice |
| files in the pod (`/etc/smelt/keys/*`, `/etc/smelt/ssh_config`, `/etc/smelt/secrets/*`) | as installed at the last write | the install path only | the model's own commands |

`named_secrets.name` is **immutable**: it is the name personas list, so a rename would silently re-point every persona at a different credential and leave the old file in pods. Change a name by adding the new one and deleting the old (the delete prunes every reachable pod). Editing the value in place is supported and installs immediately (as a key does).

**No pod keeps a value across a restart.** `/workspace` survives (its PVC); a new pod's files come from the column at create. A terminated pod leaves nothing in the cluster.

**Writers of what a pod holds** — every one, each read of the row at install time (D2), never a cached copy:

| Writer | When | Reads | Partial failure |
| -- | --- | --- | --- |
| `create_pod_attempt_unspanned` (`create.rs:290`) | every new pod, including a restart, including a `starting` child's | the conversation's set, then the values | fails the pod start: the pod is deleted and the row terminated (`start_error`, unchanged). For a child that is its start's failure: report to the parent, no key left in a pod that no longer exists |
| `install_into_live_pods` | after a secret save/delete and after key create/import/delete and identity save (`keys.rs`'s three sites + two new ones) | per pod, its own conversation's set | per-pod: logged and skipped (today's behaviour). A skipped pod keeps the old files until its next create — see Trade-off 2 |
| `run_start`'s reconcile, **before** `db::complete_start` | every child start that reaches the persona read | the (now narrowed) column | `fail_start` with the reason; the state stays out of `active`, so the child never has a turn with a credential it wasn't granted. The exit backstop tries again |
| `end_start` (`StartExit::drop`, `sweep::startup_sweep`) | every way out of `starting`: done, failed, stopped, task dropped, restart | the column, after the `!done` safety write | logged; the child is already out of `starting` and never gets a turn |
| nothing else | — | — | — |

**Readers of the names**, and what each does with a value another writer just changed: the install path (fresh read per install, under `with_install_lock`); the prompt (per turn, so a secret added mid-conversation shows in the *pod's* files only after an install, and the prompt line is built from the same D2 set — one read, one meaning); `list_personas` (per call, live); the start notice (once, at start); `list_agents` (unchanged — it doesn't show credentials). The prompt and the pod can disagree for one install's worth of time (a secret saved after a pod was created and the install failed): Trade-off 2, named with what ends it.

**Readers of the values, and their binding:** `db::list_ssh_keys` and `db::list_named_secrets`, both only inside the install, each binding a value to a *name*, never to a conversation — the conversation binding is D2's name set, decided before any value is read. Two conversations' installs never read each other's names.

**Work already in flight.** A turn running while the user changes a secret or key: the turn keeps running; its pod's files change under it mid-turn (today's behaviour for a key change — unchanged), and its *system prompt* on the next turn shows the new set. A child whose start is in flight while the user deletes a secret: `create_child`'s copy and the persona intersection both re-read at their own moment, so the child simply doesn't get the deleted name; the pre-complete reconcile writes files that match the final column, never the older one. A live agent's set never changes after its start — a secret added later reaches it only if its name is already in the list (names, not values).

**Callers × state, for "is this conversation's credential set knowable?"**

| State of the conversation | pod create asks | live-pod loop asks | end-of-start asks | prompt says |
| -- | -- | -- | -- | -- |
| no `agents` row (root) | D2 root rule, immediately | same | n/a | its own set |
| `starting`, persona unread | the column (parent's set) — install, don't refuse | same (a `starting` child's pod is a live pod) | after the `'{}'` safety write | its first turn hasn't happened; if the user writes in, today's refusal stands |
| `starting`, persona read | the narrowed column | same | the narrowed column | — |
| `active` | the column | the column | the column (backstop) | its set + what it lacks |
| `finished` / `stopped` / `failed` | the column (`'{}'` for one that never started) | the column — **never re-grants** `git-ssh` to an agent whose persona excluded it | done | last known set |

## Trade-offs to flag

1. **The user's own conversation's pod gets a file per stored secret.** Today it gets the SSH key; after this it gets each secret at `/etc/smelt/secrets/<name>`, because a conjunction can't hand down a credential the root doesn't hold — and every named secret must be reachable by some persona (the PM's Linear key is the reason the feature exists). What it adds over today: bash in that pod can use the secret directly, not only through the MCP tools that already carry it server-side. What limits it: nothing in this ticket — SME-243's egress rules are the guard, and the design says so.
2. **A skipped install leaves an old file in a pod.** If `install_into_live_pods` can't reach one pod (starting, ending, stalled exec) it logs and moves on, as it does for keys today: a deleted secret stays readable in that pod until its next create. Worst case, in today's code, forever: a healthy idle pod is never recreated until SME-78 ends it. Fixing it needs a per-pod "credentials out of date" marker and a retry — a separate ticket; this one keeps the existing behaviour and says so.
3. **A child's set is frozen at start** (like the rule chain): a secret added later reaches a live agent only if its name is already listed. Named-list semantics, not value-refresh.
4. **Every way out of `starting` narrows a never-completed child to nothing,** so a failed start can't be "resumed" with credentials: start a new agent.
5. **The pre-`complete_start` reconcile is a handful of pod execs per agent start** (bounded by `INSTALL_TIMEOUT`, 60 s) and its failure fails the start. That's the price of "no key at the first turn" being true by construction rather than by a race between the wake and the cleanup — today `StartExit::drop` spawns its cleanup *after* `complete_start` has already woken the first turn, which is exactly the window this closes.
6. **A persona asking `git-ssh` under a parent that doesn't have it** doesn't get refused up front (its clone may be https); the clone fails and the start report carries git's message. Refusing at `start_agent` would need to know the remote's scheme — kept out, and the notice line (D6) names the narrowing so the parent sees the cause.
7. **`name` is immutable** (see the state model): renaming is delete + add, which is two clicks instead of one, and is what keeps persona files honest.
8. **`ssh_keys` still holds one key** (`refuse_a_second_key`, `20260927130000_one_ssh_key.sql`), so a persona can't ask for a named key; a read-only deploy key stays a later choice, as the design says.

## Questions for the user

1. **Does the user's own conversation (no persona) get every stored named secret?** *Recommended: yes,* as D2 says — it is the only way a named secret can reach any agent through narrowing, and it changes nothing about `git-ssh`. Alternative: exempt named secrets from narrowing (the persona's list alone decides, the root's pod holds no secret files). Cost of the alternative: `for_conversation` grows a second rule (≈40 lines, two more tests), `tool-rules.md#narrowing` needs amending, and a child of a persona-less child of the root starts holding secrets its parent never had — a hole in the one invariant this whole feature rests on.
2. **Should the value be visible again to the user on the page?** *Recommended: no* — write-only, like MCP header values and `oauth_client_secret`: the list shows the name and dates only. Alternative: a "show" button per row. Cost: one more server function that returns a value (the model can't reach server functions by HTTP from a pod — `request_guard` lets a pod's curl through, per `tool-rules.md#egress` item 2 — so "show" would put every secret one `curl` from any pod, which is why I'd not).
3. **Per-secret opt-out of sandboxes** (a checkbox "don't install this one in any pod")? *Recommended: no* — it breaks narrowing again (an agent could then never get it) and it hides a rule the persona file already states. If wanted: one column, one checkbox, and `for_conversation` drops it at the root (≈25 lines, 2 tests).
