## What

Bash in a sandbox reaches the network, so tool rules can't stop a persona from pushing to GitHub as the user. What a pod holds follows the persona: a persona lists the credentials it gets in its own field `smelt.credentials: [git-ssh, …]`; one that lists none gets none. For the git key a child never gets more than its parent; for the user's named secrets the persona alone decides. Named secrets (a settings page: name + value) land at `/etc/smelt/secrets/<name>`, mode 600 — which is how a Project Manager seat under smelt runs `scripts/pm-wait-for-board` (SME-247). Design: `docs/design/personas/tool-rules.md#credentials`, `persona-files.md`.

## Decisions

**D1 — A credential is a name.** `git-ssh` is built-in and reserved; every other name is one of the user's stored secrets. A pod's effective set is a set of names, never values; values are read only by the install path.

**D2 — Two rules, stated separately.** `credentials::for_conversation(pool, conversation_id) -> PodCredentials { git_ssh: bool, secrets: Vec<String> }` is built from two independent functions — deliberately not one intersection, so the named-secret rule can never inherit narrowing by accident:

- **Rule G — `git-ssh`, the chain rule (the design, unchanged).** Root (no `agents` row): granted iff a stored SSH key exists — "a conversation without a parent is unchanged: it gets the key, as every pod does today". An agent: granted iff `git-ssh` is in its `agents.credentials` column, which `create_child` seeds from the parent's bit and the persona narrows (D3). A `NULL` column — after this ticket, only a pre-ticket row — falls open to today's behaviour: granted. (Same reasoning as SME-241's chain falling open on unreadable JSON: don't strand a live conversation whose state smelt wrote.)
- **Rule S — a named secret, the persona's own rule (the user's answer).** A conversation is granted secret `n` iff **its own persona snapshot lists `n`** and `n` is a stored secret at the moment of the read. A conversation with no `agents` row has no persona, so **the user's own pod holds no secret files**; an agent **without a persona holds none** either; ancestors' holdings are irrelevant at every depth. Nothing about Rule S is stored: the names come from `agents.persona_settings` (the snapshot written once at `complete_start`, so the *names* are fixed at start) resolved against `named_secrets` at each read — install, prompt, and report alike.
- **The trap this revision exists to avoid:** `create_child` must **not** copy the parent's secret names, and nothing must ever put a named secret into `agents.credentials`. Copying them, then intersecting, silently re-introduces narrowing and a deep child starts getting nothing. Guarded in code by a comment at the `INSERT` and in tests by T4's subset assertion.

**D3 — What `agents.credentials TEXT[]` stores: the chain bit only.** Nullable, and its only possible member today is `git-ssh`; it stays a `TEXT[]` so a future chain-granted built-in joins without a migration. Writers, all state-gated (`UPDATE … WHERE state = <expected>`, per `database.md`):

1. `db::create_child` — `ARRAY['git-ssh']` if the parent's row has it (or, for a parent with no row, Rule G's root answer), else `'{}'`. Read from the `agents` row the transaction already locks and reads (`SELECT state, depth, root_id, rule_chain …` gains `credentials`).
2. `prepare`, right after `persona::snapshot` succeeds — `db::narrow_agent_credentials` writes the column ∩ (persona lists `git-ssh`). A persona with **no** `credentials` key narrows it away; a persona-less child writes nothing (Rule G inherits).
3. `end_start` when the start did not complete — `db::clear_agent_credentials` writes `'{}'` before the pod is reconciled, so a start cut off before the persona was read leaves no key behind (the ticket's "a failed or cut-off start leaves no key behind"). A never-started child can get secrets too, under Rule S, only if its own persona names them — which requires the persona to have been read, and if it was, Rule S decides on its own merits.

Not narrowed in `complete_start`, unlike `rule_chain`'s entry append: the thing that must end up clean is the **pod**, and the exits that clean it (`StartExit::drop` → `end_start`, `sweep::startup_sweep`) only have the row to read. The asymmetry with rules is deliberate and gets a comment at both sites.

**D4 — Clone, then remove (for the key only).** At pod create during `starting`, the column holds the parent's `git-ssh` bit, so the key is there and the SSH clone works. Nothing of the model's runs while `starting` (no turn is admitted; a child stopped mid-start never becomes `active`, since `started_at` stays null). **Revision 1 makes this window smaller than round 1's:** under Rule S a child's secrets are never installed before its own persona names them, so install-then-remove applies to the git key alone, and the end-of-start reconcile mostly *adds* the persona's secrets and removes the key when the persona excluded it.

**D5 — "a pod restart" is the same code path.** Sandbox pods are `restart_policy: Never` (`src/sandbox/spec/pods.rs:223`), so a restart is a new pod through `create_pod_attempt_unspanned`, whose install at `src/sandbox/manager/create.rs:290` is the one new-pod site in production (`install_into_new_pod` has exactly one caller there). Re-adopting a running pod after a smelt restart installs nothing new (the files are already in the pod — today's behaviour for keys, unchanged). So the design's "three install sites" are **two code paths**: pod create, and the live-pod loop after a key/identity/secret change — plus the end-of-start reconcile. `docs/design/personas/tool-rules.md#credentials` gets reworded to say that, with the evidence.

**D6 — Reports, three places** (the ticket: "a persona naming a secret that doesn't exist is reported, not silently ignored"; a `git-ssh` ask the chain denies is the same kind of silence):
- `list_personas` (`src/git/server/personas.rs`'s `persona_entry`): the persona's `credentials` list, plus — for a name that isn't `git-ssh` and isn't stored — a note in SME-241's `unmatched_note` style, made against `db::list_named_secrets` read once per listing (like its `server_names`: read once, and read-failure reports nothing rather than accusing every name).
- `start_agent`'s parent notice (`start.rs`'s `one_notice`, which already carries the model and rules notes): "its persona lists `linear-key`, which isn't one of your stored secrets, so it gets none until you add it" (and under Rule S that is now *only* about the store, never about an ancestor), plus "its persona asks for `git-ssh`, which its parent's chain doesn't have, so it gets none".
- the child's environment section (D8).

A name that isn't stored is never a parse error: `personas::parse` can't know the deployment's secrets, exactly as a rule naming an unconfigured server isn't one (SME-241). It becomes granted, without a restart, as soon as the user stores it and anything triggers an install (Trade-off 3).

**D7 — Never the value; one capped display.** `db::NamedSecret` gets a hand-written `Debug` (the `McpServerConfig` precedent: names and "stored?" only); the environment section names paths only; install errors quote paths and the pod's stderr, never content (`install_git_files` already does). A model that holds a credential can `cat` its own file — that's what granting it means; smelt itself never prints a value into a tool result, a span or a prompt.

The one exception the user asked for is the settings page's **safe prefix** (Answer 2), defined precisely:

`shown(value)`, computed **at read** in `api::secrets` from the row — never stored in a column (a stored prefix would be a second copy of secret material for SME-48 to miss) and never in `Debug`. With `n` = the value's **byte** length and `k = min(4, n − 8)` (floored at 0): render the first `k` characters followed by `… (n bytes)`, or just `(n bytes)` when `k = 0`. So never more than four characters, and **at least eight bytes of every value are never displayed** — `n = 6` shows nothing of it, `n = 11` shows 3, `n = 40` shows 4. Exact length is shown (it's what makes two rows tell apart); length alone is a signal, and Trade-off 9 bounds what a pod can take.

**D8 — The environment section** (`PromptEnvironment`, `src/turn/history.rs`), one new field gathered per turn from Rule G + Rule S (names and paths only, never a prefix):

- `- Credentials: git SSH key at /etc/smelt/keys/<name>; secret linear-api-key at /etc/smelt/secrets/linear-api-key`
- for an agent whose set excludes `git-ssh`: `- No git credential: your persona's smelt.credentials doesn't list git-ssh (or your parent's chain doesn't have it), so /etc/smelt/keys is empty — git push and git fetch over SSH will fail; don't retry them.`
- for a persona name that isn't stored: `- Your persona lists credential \`foo\`, which isn't one of the user's stored secrets, so you don't have it.`

A conversation with no secrets by rule (the root, a persona-less agent) gets no line about them: only a *named-but-unbacked* or *narrowed-away* case is explained, which keeps today's prompt tests' shape and answers only what the model can't infer.

## The state model

**Records.**

| Record | States | Who moves it | Who else sees it |
| -- | -- | -- | -- |
| `named_secrets` row | live → deleted | the user (page); only the page | every pod install (names + values), `list_personas`, the start notice, the page's prefix |
| `agents.credentials` — **`git-ssh` only** | parent's bit → narrowed → (never started) `'{}'`; NULL for pre-ticket rows | `create_child`; `prepare` at persona read; `end_start` when `!done` | pod create, live-pod install, end-of-start reconcile, the prompt, `start_agent`'s notice |
| `agents.persona_settings.credentials` — **the secret names** | written once at `complete_start`; never rewritten | `complete_start` (the snapshot) | Rule S at every read: pod installs, the prompt, `list_personas`, the notices |
| files in the pod (`/etc/smelt/keys/*`, `/etc/smelt/ssh_config`, `/etc/smelt/secrets/*`) | as installed at the last write | the install path only | the model's own commands |

**No named-secret value or prefix is stored anywhere but `named_secrets.value`.** That is a load-bearing line for SME-48 and for the review: no derived column, no log field, no cache.

`named_secrets.name` is **immutable**: it is the name personas list, so a rename would silently re-point every persona at a different credential and leave the old file in pods. Change a name by adding the new one and deleting the old (the delete prunes every reachable pod). Editing the value in place is supported and installs immediately (as a key does).

**No pod keeps a value across a restart.** `/workspace` survives (its PVC); a new pod's files come from Rule G + Rule S at create. A terminated pod leaves nothing in the cluster.

**Writers of what a pod holds** — every one, each reading the decision at install time, never a cached copy:

| Writer | When | Reads | Partial failure |
| -- | --- | --- | --- |
| `create_pod_attempt_unspanned` (`create.rs:290`) | every new pod, including a restart, including a `starting` child's | Rule G (the column) + Rule S (snapshot ∩ store), then the values | fails the pod start: the pod is deleted and the row terminated (`start_error`, unchanged). For a child that is its start's failure: report to the parent, no credential left in a pod that no longer exists |
| `install_into_live_pods` | after a secret save/delete and after key create/import/delete and identity save (`keys.rs`'s three sites + two new ones) | per pod, that conversation's Rule G + Rule S | per-pod: logged and skipped (today's behaviour). A skipped pod keeps the old files until its next create — Trade-off 2 |
| `run_start`'s reconcile, **before** `db::complete_start` | every child start that reaches the persona read | the narrowed column + the snapshot just prepared | `fail_start` with the reason; the state stays out of `active`, so the child never has a turn with a credential it wasn't granted. The exit backstop tries again |
| `end_start` (`StartExit::drop`, `sweep::startup_sweep`) | every way out of `starting`: done, failed, stopped, task dropped, restart | the column, after the `!done` safety write, + the snapshot if there is one | logged; the child is already out of `starting` and never gets a turn |
| nothing else | — | — | — |

**Readers of the names**, and what each does with a value another writer just changed: the install path (fresh read per install, under `with_install_lock`); the prompt (per turn, the same two rules, so the line and the pod's files can disagree for one install's worth of time — Trade-off 2); `list_personas` (per call, live); the start notice (once, at start, and again correct-by-construction at each install); `list_agents` (unchanged — it shows no credentials). Under Rule S a reader that re-runs gets the store's current contents, which is why a name that was unbacked at start becomes granted at the next install with no restart.

**Readers of the values, and their binding:** `db::list_ssh_keys` and `db::list_named_secrets`, both only inside the install, each binding a value to a *name*, never to a conversation — the conversation binding is Rule G/Rule S's name set, decided before any value is read. Two conversations' installs never read each other's names. `api::secrets` reads values too, only to compute `shown` (D7): a one-way function into a ≤4-character display, with the ≥8-hidden floor.

**Work already in flight.** A turn running while the user changes a secret or key: the turn keeps running; its pod's files change under it mid-turn (today's behaviour for a key change — unchanged), and its *system prompt* on the next turn shows the new set. A child whose start is in flight while the user deletes a secret: the persona read and each install re-read the store at their own moment, so it simply doesn't get that name, and its notice already said so; the pre-`complete_start` reconcile writes files that match the store as it is then, never an older read. A live agent's Rule G bit never changes after its start; its Rule S names never change after its snapshot, but which of them are backed follows the store (Trade-off 3).

**Callers × state, for "is this conversation's credential set knowable?"**

| State of the conversation | pod create asks | live-pod loop asks | end-of-start asks | prompt says |
| -- | -- | -- | -- | -- |
| no `agents` row (root) | G: a stored key exists; S: none | same | n/a | the key if any; nothing about secrets |
| `starting`, persona unread | G: the column (parent's bit) — install, don't refuse; S: none (no snapshot yet) | same (a `starting` child's pod is a live pod) | after the `'{}'` safety write; S still none | its first turn hasn't happened; if the user writes in, today's refusal stands |
| `starting`, persona read | G: the narrowed column; S: snapshot ∩ store | same | both, just narrowed | — |
| `active` | both | both, store read live | both (backstop) | its set + what it lacks |
| `finished` / `stopped` / `failed` | both (`'{}'` for one that never started) | G **never re-grants** `git-ssh` to an agent whose persona excluded it; S keeps granting what its snapshot names while the store backs them | done | last known set |

## The code

New module `src/credentials.rs` (+ `src/credentials/tests.rs`): `PodCredentials`, `for_conversation` (built from `git_ssh_of` and `secret_names_of`, the two rules), `validate_credential_name` (the `validate_key_name` rule, 1–64 of `A-Za-z0-9-_`, plus "not `git-ssh`"), `pod_files(pool, conversation) -> Vec<PodFile>` (git's files + one per granted secret, mode 600), `install_into_pod`, `install_into_new_pod`, `install_into_live_pods`, `reconcile_pod(pool, child)` (write that conversation's decision into its live pod; a no-op when it has none), and `with_install_lock`. The install machinery **moves** into it from `src/git/server/keys.rs` — `POD_GIT_DIR`, `PodFile`, `pod_git_files`, `install_git_files`, `with_install_lock`, `install_into_pod`, `install_into_new_pod`, `install_into_live_pods`, `INSTALL_TIMEOUT` — because a secret install must hold the same lock as a key install (two installs that interleave could each prune the other's write). `keys.rs` keeps the key's own life: generation, import, fingerprints, name/identity validation, `create_key`/`import_key_named`/`delete_key`/`save_identity` and their install calls (now `crate::credentials::…`). `src/git.rs` re-exports `server::*` (`:138`), so the moved items were reachable as `crate::git::*`; after the move the call sites become `crate::credentials::*` — `create.rs:290`, `keys.rs`'s three own-callers, and the tests (`src/sandbox/tests/git.rs`, `src/git/server/tests.rs`, `src/git/server/db_tests/keys.rs`). No crate loses its last use in a moved file, so no `Cargo.toml` comment changes and no sandbox image is renamed.

`install_git_files` becomes `install_pod_files(shell, files, prune_dirs)` — today it prunes only `/etc/smelt/keys`; the new version prunes `/etc/smelt/keys` and `/etc/smelt/secrets` to the kept names, each written `umask 077` + rename-over (unchanged, "never emptied"). Its two test callers move with it.

`src/personas/mod.rs`: `SmeltSettings` gains `credentials: Option<Vec<String>>` (its comment already says later tickets add it), `Persona.credentials: Option<Vec<String>>`; each name checked by `validate_credential_name` (an empty entry or a bad character is a parse error naming the file; a name that isn't stored is not). `src/db/agents/mod.rs` (18,163 B today): `agent_credentials(pool, id) -> Option<Option<Vec<String>>>` (row → column; inner `None` = NULL = Rule G's fall-open) and `narrow_agent_credentials` / `clear_agent_credentials`, all state-gated and documented as `git-ssh`-only. `src/db/agents/start.rs`: `create_child`'s parent read gains `credentials`, and the child `INSERT` writes the chain bit — with the D2 trap comment right there.

**Can a pod read that prefix?** Yes, and the plan says so rather than hoping: `request_guard` refuses cross-site browser *writes* and lets a request with neither header through (`src/request_guard.rs`, `tool-rules.md#egress` item 2), so a pod that knows smelt's URL can `curl` `GET /api/secrets`. Not gated here: making the shared guard refuse pod-originated reads would stop nothing at the real browser caller and would be the SME-173 mistake (a tightening judged on one caller); that is SME-243's egress work. Recorded as Trade-off 9.

## The settings page

New route `/secrets` in `src/frontend/mod.rs` (`SecretsRoute {}` + component; that file is 6,248 B), a line in `src/frontend/pages/chat/mod.rs`'s per-route match (as `Route::GitRoute {} => None`), and a link in `src/frontend/pages/chat/sidebar/mod.rs` beside "Git" (`:205-206`). Layout: at laptop width the page is the single centred column the other settings pages use, nothing beside it; at phone width the same column full-bleed — settings routes replace the chat area, so no side panel sits next to it and the narrowest width any element gets is the viewport minus the page padding, checked at 320 px. The list row is `name` + `shown` (D7's prefix and length, server-computed, never re-derived in the client) + date + Delete, tested with a 64-character name, a `shown` from an 8-byte value (no characters at all) and the `Delete` label at 320 px. Under the form, one muted line: `git-ssh` is built-in; a persona lists a secret by its name and gets it whoever its ancestors are; the file lands at `/etc/smelt/secrets/<name>`; only a short prefix of a stored value is ever shown. `scripts/ui-check` screenshots at 1280 and 375 px with a 64-char name and three rows.
