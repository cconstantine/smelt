## State model

The deployer keeps no database rows; the state is its pod's files, homelab, and the cluster:

| Record | States | Moves it | Who else sees it |
| -- | -- | -- | -- |
| The run | briefed → image-checked → set-up → committed(local) → planned → **gate** → applied → verified → pushed; terminal: stopped-and-reported at any named condition | the seat, per `DEPLOY.md` | only the seat (its pod's `~/` and `/workspace/homelab`) — gone with the pod; the *report* is the durable record |
| homelab `master` | at SHA X | a successful run's push, `smelt <Y>` | every later deploy (`git pull --ff-only` is step 2's "Up to date") — which is why a refused push must be reported, not dropped: repo ≠ cluster is the drift `DEPLOY.md` warns re-applies an old image |
| Terraform state + cluster | drifts only through a successful `-target=module.smelt` apply | apply; **interrupted apply**: log lacks `Apply complete!` and no `terraform` running ⇒ re-`plan`, report what's pending, never re-apply the old plan file; a state lock ⇒ another Terraform runs somewhere: wait, retry, never break the lock | the next deployer (its plan shows the drift), the database objects above all |
| `deploy_kubeconfig` | stored / not | user on `/secrets`; Rule S reads it live at each install — revoking it bites at the pod's next install, not mid-command | nobody else: no other persona names it |

Partial failures: stop-and-report before apply leaves only uncommitted work in the seat's own clone (discarded); failure between apply-complete and push leaves cluster ahead of repo — reported with the commit sha, never silently; the server restart *during* apply is the designed case (log file + restart notice, `DEPLOY.md` steps 5–6). The seat's own pod never restarts mid-run by design (the `terminate_pod` deny; the apply restarts the *server*, not sandbox pods). No shared state gets two writers: one deploy at a time is homelab's state lock, not a rule this file adds — a second concurrent deployer serializes behind the lock or stops and reports it.
