# SME-377 plan: a `notify_user` tool replaces the automatic "done"; the trust card notifies

**Branch:** `sme-377-notify-user`, worktree `/home/dev/wt/sme-377` (cut from `origin/main` at 67fa829).

The ticket holds the user's decision (2026-11-04) and isn't reopened here. This file settles its "To settle at planning" list and says how to build it. Trade-offs to flag and Questions for the user are in the ticket.

## What, and why

Today `turn/lifecycle.rs` notes `Attention::Finished` for every turn that saves an assistant message and isn't waiting on a question. A model that starts a command, ends its turn, is woken by the command's notice and ends again notifies "smelt: done" at each step. SME-370 exempted only idle-notice turns. The user's decision:

1. No turn end notes anything by itself: the automatic `Finished` goes.
2. A new native tool, `notify_user(message)`, notes a new attention kind, `Notified`, which carries the model's message to the desktop notification.
3. A repo trust card (an AGENTS.md card from `load_instructions`, or the repo card a refused `start_agent` files, SME-279) notes `Question`.
4. `Question` (ask_user), `Failed`, `CutOff` and `Refused` work as they do now. A child waiting on its parent never notifies.

## The "To settle at planning" list

|---|---|
| Child agents; can persona rules deny it? | **Not offered to a child.** A new offer, `Offer::TopLevel`, covers it: offered only to a conversation with no parent. `execute` refuses a child's call (one from an old history, or a call to a tool it wasn't offered) with "notify_user is for a conversation the user started; an agent reports to its parent with finish". A conversation's parent never changes, so its tool list stays stable and the prompt cache holds. ## Every path that notes `Finished` today, and what removing it changes

There is **one writer**: `src/turn/lifecycle.rs`'s `Ok(persisted)` arm (lines 167–199). It notes `Finished` when the turn saved an assistant message, `!saved_idle_notice(persisted)` (SME-370), and `question_waits` says nothing is waiting (on a failed read it warns and notes anyway). The four callers that reach it are `run_turn_bounded`'s turns: the user's send, an answer turn, a delivered notice (`deliver_notice`) and a wake. `turn/tests/attention.rs` pins each of them.

Removing it:

- **The arm goes.** The match becomes `Err(Failed | Noted) => note Failed`, `Err(Stopped) => clear_attention`, `Ok(_) => {}`. `saved_idle_notice` (`turn/notify.rs`) and `question_waits` (`turn/questions.rs`) lose their only callers, so they go too, or the server build warns about dead code. Also removed: `turn/tests/wake.rs`'s `test_saved_idle_notice_reads_text_blocks_not_tool_output`. `IDLE_NOTICE_FRAGMENT` stays, since the notice's own `format!` uses it. Its doc drops "read only by `saved_idle_notice`" and keeps the transcript-copy warning.
- **`Attention::Finished` becomes `Attention::Notified`**, in the same lowest-priority slot. The wire string changes from `"Finished"` to `"Notified"`. A tab on an older bundle can't parse the new value. Its stream reconnects and `check_build_id` offers the reload, as for any deploy that changes an event (SME-43).
- **The tab-title count** (`frontend/notifications.rs`, `needers`) counts any `NeedsUser` heard while the tab is in the background. It stops counting finished turns, which is the fix, and counts `Notified` ones instead.
- **The sidebar**: no change. Its `?` mark is `WAITS_FOR_USER`, which never counted a finished turn and already counts trust cards.
- **The Finished cooldown goes**: `FINISHED_COOLDOWN_MS`, `last_finished`, and `should_notify`'s `ms_since_last_finished` parameter.
- **Tests that pin `Finished`**: `src/turn/tests/attention.rs` (the four caller tests, `test_failed_beats_a_later_finished_in_one_busy_spell`, `test_a_turn_that_overflows_once_publishes_finished_not_failed`, and comments in the question test and the SME-370 section); `src/events/wire_tests.rs` (the spelling and priority test); `src/api/notifications/tests.rs` (lines 73–116 and 191); `src/frontend/notifications/tests.rs` (the cooldown and heading cases); `src/browser_tests/notifications.rs` steps 5–7 (`smelt: done`, and the plain-HTTP title count, which a plain reply drove).
- **SME-370's idle-notice tests** (`test_an_idle_notice_wake_publishes_nothing` and its three siblings) stay as they are and still pass. They now pass because nothing is noted automatically: they guard the regression, and they can't go red on this change.

## Where the trust card is raised, and noting `Question`

Cards are filed (`db::request_instruction` / `db::request_repo_trust_card`) at three sites:

1. **`git::load_instructions`** (`src/git/server/instructions.rs:248`), the model's tool, which `anthropic/tools/git.rs:136` calls. `request_or_load` returns `AwaitingTrust`, then `publish_repos` runs. **This site notes `Question`** for `conversation_id`, in the `AwaitingTrust` branch, after the commit and publish.
2. **`start_agent` refused on an undecided repo** (`db::create_child` → `request_repo_trust_card` on the caller's checkout row). `agents/start.rs:211` already does `if *asked { publish_repos(new.caller) }`. **That branch notes `Question`** for `new.caller`, the conversation whose turn is running the call.
3. **A child's own start** (`agents/start.rs` `load_agents_md` → `request_or_load` on the child). The card makes the start fail, and its exit deletes the card. It **notes nothing**: the note goes at sites 1 and 2, not in `request_or_load`, so this path can't reach it.

Both notes go through one new function, `crate::turn::note_trust_card(conversation_id)` in `turn/questions.rs` beside `ask`'s note, which wraps `note_attention(_, Question)`. A note outside a counted turn (a test calling `load_instructions` directly) finds no entry and does nothing, as `note_attention` always has.

A card in a **child's** conversation (a child that cloned a new repo and called `load_instructions`) notes too. The card waits on the user, not the parent, and the sidebar already marks it.

The card is answered by `decide_trust`, which publishes `QuestionsChanged` through `publish_repos`. Every open notification then revalidates, `get_attention(Question)` finds no question and no card, and the notification closes. "Work on a repo" drops cards the same way.

`src/frontend/pages/chat/trust_card.rs` needs no change.

## The tool

New file **`src/anthropic/tools/notify.rs`**, about 3.5 KB, registered **after** `agents::tools()` in `REGISTRY` so every older tool keeps its place in the request:

```rust
pub(crate) const NOTIFY_USER: &str = "notify_user";
pub(crate) const MAX_NOTIFY_CHARS: usize = 200;
// Tool { def, class: Class::READ_ONLY, run: run!(|c| notify(c.conversation_id, c.input)) }, offer: Offer::TopLevel
```

- **Description** (it starts with `smelt`, like every confusable native; see the SME-309 labels test): "smelt: send the user a desktop notification saying `message`, once you've finished what they asked or need them to look at something (a result, a preview, a problem you can't get past). Call it once, as your last step: your turn ends here, and the notification shows when this conversation goes idle. Don't call it while you wait on your own commands, their notices or your agents (their messages wake you), and don't use it to ask anything: `ask_user` notifies by itself. It's a notification in the user's browser, not a message on any MCP server's chat or tracker."
- **Schema:** `{"message": {"type": "string", "description": "one line, up to 200 characters: what's done, or what needs the user"}}`, required.
- **Run:** `parse_notify_message(input)` (the limits above), then `crate::turn::note_notified(conversation_id, message)`, then `Ok("The user will be notified when this conversation goes idle.")`.
- **Class:** read-only, as `ask_user` is (it changes nothing outside the conversation). This adds a row to `class/tests.rs` and to `docs/design/personas/tool-rules.md`.
- **Offer:** `Offer::TopLevel`. `is_offered(TopLevel, has_parent) = !has_parent`. With a failed parent read (`has_parent: None`) it's left out, like the agent tools. `offered_to` gets the arm `(TopLevel, Some(_)) => Err(...)`. Update the `Offer` doc, whose comment says `Offer::Root` is gone, so the two aren't confused.
- **Ending the turn:** `turn/reply.rs` `run_tools`: `if (name == FINISH || name == NOTIFY_USER) && result.is_ok() { finished = true; }`. Update the `run_tools` and `RanTools` docs to match.

**System prompt** (`src/turn/system_prompt.md`, 11 KB): one bullet in "Working style", after the `ask_user` bullet:

> - When you've finished what the user asked, or need them to look at something, call `notify_user` once, as your last step, with one line saying what's done or what needs them: they may be in another tab, and nothing else tells them. Not while you wait on your own commands or agents (their messages wake you, and you're not done yet), and not to ask a question (`ask_user` notifies by itself). An agent has no `notify_user`: it reports with `finish`.

The base prompt is the same for every conversation, so its last sentence is what keeps a child from looking for a tool it doesn't have. `turn/tests/prompt.rs`'s named-tools test checks the name exists. A new assertion pins the "once, as your last step" and "Not while you wait" phrases.

## State model

New runtime fields, in `ConversationRuntime` (`src/turn/state.rs`):

- `notified: Option<String>`: the message of this busy spell's last successful `notify_user`.
- `published_notice: Option<(u64, String)>`: the generation and message of the last `NeedsUser(Notified)` this conversation published, for `get_attention` to read after the spell ended.

`is_idle` requires both to be `None`, so a note racing a delete can't strand an entry, and a published notice isn't freed while it can still be checked.

| Event \ field | `attention` | `notified` | `published_notice` |
|---|---|---|---|
| `admit`, first turn of a spell (0→1) | `None` | `None` | unchanged (the old event may still be on screen; `turn_running` answers `None` for it while the spell runs) |
| `note_notified(msg)` (tool, inside a counted turn) | `max(_, Notified)` | `Some(msg)`, replaced | unchanged |
| `note_notified` with no entry (a delete racing the note) | — | — | — (nothing to note; the conversation is gone) |
| another `note_attention(k)` (Question, Failed, CutOff, Refused) | `max(_, k)` | unchanged | unchanged |
| Stop (`clear_attention`) | `None` | `None` | unchanged |
| last `TurnInFlight::drop`, owed `Notified` | taken | taken | `Some((generation, msg))`, then publish `NeedsUser(Notified, generation)`, all in the same critical section that takes the attention, as now |
| last drop, owed another kind or nothing | taken | taken (dropped) | unchanged |
| `forget_conversation_lock` (delete) | `None` | `None` | `None` |
| server restart | lost | lost | lost; a check of the old event gets `None` (generation 0 ≠ the event's), as for every kind today |

**Readers:** only `api::notifications::attention_details`, through `published_notice(id, generation)`, which returns the message only when the stored generation equals the event's. It runs three checks in order: `turn_running`, `turn_generation`, then the notice. Between them, a new spell can start (then the notice read still returns the old one, and the old event is correct to show until the user acts), or a new spell can end and publish `Notified` again under the **same** generation (a wake with nothing new takes no generation). The read then returns the newer message for the older event. Both share a `tag`, so the newer one replaces the older within a second either way. Nothing else reads these fields.

**Failure partway:**
- The tool's validation refuses: nothing is noted, the turn goes on, and the model sees the error.
- The note lands but saving the tool results fails: the turn fails, `Failed` outranks, and the message is dropped at the drop.
- Several calls in one reply: each runs, and the last valid one wins.
- `notify_user` alongside `ask_user`: the question is recorded first (as now), the note lands, the turn ends, `Question` outranks, and the card is what the user sees.

**Who sees each change:** only the `NeedsUser` app event, which every tab hears. The leader re-checks with `get_attention`, and every other tab only counts it.

**What each caller does per state** of the conversation when `notify_user` runs:

| Conversation state | `notify_user` |
|---|---|
| top level, in a turn | notes, ends the turn |
| child | refused by `offered_to`; not offered |
| deleted mid-turn | note is a no-op; the turn then fails on its next write, as today |
| stopped mid-call | the note may land, then `clear_attention` empties it; nothing published (test T6) |
