## What and why

`clear_ids_base()` (`src/db/git.rs:154`) is `2_000_000_000 + (unix_nanos % 1_000_000_000)`: wall-clock nanoseconds folded through a one-second modulo. The modulo is what breaks it — two calls share a value whenever their sub-second ticks match, whatever second they're in, and on the gate machines the clock's effective granularity is far coarser than a nanosecond, so two near-simultaneous calls matching is routine, not astronomically rare. The test databases are separate, but these ids name objects in the one shared `smelt-park-test` namespace: pod `sandbox-{sandbox_pods.id}`, claims `sandbox-docker-{conversation_id}` and `sandbox-workspace-{conversation_id}` (`src/sandbox/spec.rs:7,341,346`). Two test databases that drew the same base get the same names, and the second sees a kube 409 or SME-115's `NotOurs { ownership: Foreign }` — the instance labels did their job (loud refusal, no cross-database damage); the allocation did not.

Occurrences on record (run evidence):

1. *Traced from the ticket's own record (PR #148, SME-79 review round 1):* two `sandbox::pod_lifecycle_tests` workers drew base 2,035,671,199 → conversation 2035671200 → `NotOurs { name: "sandbox-docker-2035671200" }`; the other test's pod start timed out. Re-run unchanged: green, 1418 passed.
2. *Live gate run 2026-10-27:* `test_file_tools_edit_safely_against_stale_hashes` failed `create_pod: NotOurs { name: "sandbox-docker-2238104065", ownership: Foreign }`; passes alone. (2e9 family.)
3. *SME-239's tip gate at `7b4e400`:* `sandbox::claims::log_tests::test_a_conversations_teardown_logs_what_it_deletes` failed with kube 409, pod `sandbox-3789272077` already exists (3e9 family — log_tests' own `unused_conversation_id`), and `pod_lifecycle_tests::crashes::test_stopping_a_pod_for_the_user_closes_everything_and_says_so` met a foreign `sandbox-docker-2879550413` plus a pod start outlasting the 240 s teardown wait (`pod_start_wait()` = 2×90 s + 60 s, `pod_lifecycle_tests/mod.rs:79-118` — the wait is the collision's downstream cost, not a third bug). Clean re-run at the identical tip.
4. *SME-239's Developer:* two test databases both counted `agent_volumes` ids from 1 and their `agent-volume-1` claims met — caught only by SME-115's labels — and was bandaged by adding `agent_volumes` to `CLEAR_ID_TABLES`.

Two distinct defects sit under one flake, and the fix must address both:

- **(a) two workers, one base.** Every nanos-fold site. Traced at `76483dd`: `db::clear_ids_base()` (2e9+) — used by *both* production `start_ids_clear_if_fresh` (`main.rs:154`) and the test harness `test_support::start_ids_clear_of_other_runs` (`src/db/mod.rs:104`, reached by `own_sandbox` and ~80 test setups); `unused_conversation_id()` (3e9+) duplicated at `src/sandbox/tests/mod.rs:109` and `src/sandbox/claims.rs:441` (log_tests); `uuid_like()` (`src/sandbox/tests/mod.rs:97` — *also* just nanos) feeding `% 1_000_000_000` fixture ids in `tests/docker.rs:11`, `tests/starting.rs:11,227`, `tests/teardown.rs:11,55`, `tests/guards.rs:125`, and the `unique_session_id` names that become ephemeral pod names — `pod_lifecycle_tests/create.rs:158-171` already deletes `sandbox-test-<label>-`-prefixed pods by hand because "a pile of them left Pending": the same class, hand-patched (traced).
- **(b) two databases, ids from 1.** `CLEAR_ID_TABLES` moves only listed sequences (three at `76483dd`, four on 239's branch); every other table counts from 1 in every test database, so *any* table whose id names a cluster object inherits the class until someone remembers to extend the list. `agent_volumes` is the one met so far; occurrence 4 is this class, not (a), and no allocation fix prevents the next one.

Already-right precedents to follow (traced): `src/lsp/pods/tests/cluster.rs:17 unique()` — a seconds seed **plus a process counter** ("the time (so runs don't meet leftovers from earlier ones) plus a count (so tests started at once in this run never share one)"); `sandbox_image_import`'s loader names — pid + run counter (SME-102). `src/bin/sandbox_instance_cleanup/tests.rs:189 unique()` is bare nanos — same flaw, naming scratch databases and objects.

## Design decision

**One allocation stream, allocated atomically per process; the per-table list kept only for production.**

1. **New module `src/id_alloc.rs`** (~3 KB): two id bands, each with a process-wide cursor.
   - `GLOBAL_IDS` — band `[2_000_000_000, 3_000_000_000)`, the sequences that name pods and claims; `clear_ids_base()` becomes its `next_base()`.
   - `FIXTURE_IDS` — band `[3_000_000_000, 4_000_000_000)`, the ids tests pick by hand (conversation/pod fixture ids, and the session-name suffixes that become ephemeral pod names). The old hand-picked `[1_000_000_000, 2_000_000_000)` band retires; tests that wanted two disjoint ids call the allocator twice.
   - `next_base(band)`: the cursor is seeded once per process from wall-clock nanos mixed with `std::process::id()`, and every call advances by `ID_STRIDE = 100_000`. Guarantees: **in one process** every caller gets a distinct base, ≥ `ID_STRIDE` apart, so one test's first ids can never reach the next caller's (a lifecycle scenario uses a few dozen rows in id-naming tables — a thousandfold margin); **across processes** the seeds mix time and pid, and the cluster lock already forbids two test binaries at once (`scripts/with-cluster-lock` holds it until every inheritor exits; the SME-212 guard refuses unlocked runs), so re-runs collide only if their seeds land within a few strides of each other — the same small residual as today, addressed for leftovers by (4) and the sweep. A process that asks for more ids than the band holds (10,000 calls) panics by name rather than wrapping into spent values.
   - The seed is taken once, so a clock that steps backward (NTP) cannot matter.
2. **`clear_ids_base()` = `id_alloc::next_base(GLOBAL_IDS)`.** The harness and the production fresh-database start keep the one function; two scratch check servers started in the same second now differ by pid, not by clock luck. The used-database check (`any last_value < CLEAR_IDS_BASE` → leave it, `db/git.rs:122`) is unchanged, so a database moved once is never moved again, and `test_a_partly_moved_database_finishes_the_move` (`db/tests/instance.rs:58`) still passes with a base ≥ 2,000,100,000.
3. **The test path stops consulting the list.** `move_id_sequences` (`db/git.rs:162`, `#[cfg(test)]`) moves **every sequence in the test database** — `SELECT setval((schemaname||'.'||sequencename)::regclass, $base) FROM pg_sequences WHERE schemaname = 'public'`. The next table whose ids name a cluster object is clear of other runs without anyone remembering a list, which is what makes occurrence 4's fix structural rather than another row. `CLEAR_ID_TABLES` stays for production `start_ids_clear_if_fresh` (there, only the named tables' ids name cluster objects, and the used-database check must read exactly those) — with 239's `agent_volumes` row kept.
4. **Every hand-picked test id goes through the allocator**: both `unused_conversation_id()` copies, the `uuid_like`/`unique_session_id` family (suffix names too), the LSP `unique()`, and — locally, since the helper binaries are separate crates — `sandbox_instance_cleanup`'s `unique()` gets the same seed+counter scheme with a cross-reference comment. A repo-lint guard (`src/repo_lints/id_alloc.rs`, pattern per `src/repo_lints/cluster_lock.rs`) fails the build on a new `as_nanos()`-fold id site or a new `uuid_like`, so the class can't be re-introduced.
5. **Leftovers of killed runs — the direct answer to the brief's question.** SME-134's sweep (`src/sandbox/pod_lifecycle_tests/sweep.rs`) lists *every* pod and PVC in `smelt-park-test` and chooses on age alone ("Names, ids and instance labels don't count: every object in the namespace is a test's"), so **yes, it already covers the `sandbox-docker-*` names** — and the workspace-, volume- and (once 239 merges) `agent-volume-*` claims too. Its real gaps: `MAX_AGE` is one hour, so a re-run within the hour of a killed run keeps the old objects; and `sweep_once` runs only from `own_sandbox`, so processes that only run `claims::log_tests` or `sandbox/tests/cluster` never trigger it. The manual `scripts/clean-test-namespace.sh` (lock-taking) deletes every pod but only claims named `sandbox-docker-*` — it leaves workspace/volume claims behind. Commit 5 closes the two automatic gaps: `choose()` also takes objects whose creation predates **this process's start** (under the lock, those belong to a finished run; the live tests' objects never do), never anything already Terminating (the existing arm is kept — `test_a_stopping_pod_from_another_run_doesnt_hold_up_the_tier` and 253's Terminating tests depend on it), and the script deletes every claim in the namespace.

### Alternatives considered

- **Fold a per-worker differentiator (thread id, test-name hash) into the base beside the nanos** (the ticket's first option): still a probabilistic argument — any value folded through a modulo can meet inside the window. The cursor makes same-process uniqueness structural, which is the case every occurrence sits in.
- **Fold the test database's name into the base**: unique across concurrent tests, but two calls from one test (`db/tests/instance.rs:113` and `pod_lifecycle_tests::test_own_sandbox_sweeps_once_per_process` call the harness twice and require different bases) collide again, and a re-run of the same test re-draws exactly the names a killed run left behind — it makes today's rare leftover meeting deterministic.
- **Make the cluster-visible name carry the database identity** (the ticket's second option): eliminates the class for every table forever, but renames dev/production pods and claims, breaks SME-115 adoption and the sweep's handling, and touches every name reader (`adopt.rs`, `watch.rs`, LSP pods, the cleanup tool). Production blast radius for a harness flake; not this ticket.
- **A Postgres sequence in a shared anchor database** (true atomic allocation across processes): a test writing into the anchor database breaks the one-database-per-test rule, and production has no anchor to point at; the cluster lock already serializes processes, so what's left to protect is re-run-vs-leftovers, which the sweep rule (5) covers directly instead.
- **Per-module turns (a named semaphore per lifecycle module)**: suppresses the symptom for same-named scenarios, serializes more of the suite, and hides the next allocation bug rather than removing it.

## State model

**The allocator** (one cursor per band, one per process):
- *unseeded → seeded*: first call in the process. Seed = `band.base + (mix(nanos_at_process_start, pid) % (band.width − ID_STRIDE))`. One lock, no partial state.
- *seeded → advancing*: every call `cursor += ID_STRIDE`, returns the new value; the cursor never decreases, never repeats, stays inside the band while there is room. A caller that panics after receiving its base leaves it spent — never re-handed.
- *exhausted*: an advance past the band end panics with a named message ("the id band is exhausted"). 10,000 calls per band per process is far beyond any real run; a loud stop beats wrapping into spent values.
- Nothing survives the process by design: cross-process separation is the seed's job (time mixed with pid), and the cluster lock (`SMELT_CLUSTER_LOCK_HELD`, checked by `src/test_lock.rs`) makes "no two processes allocate at once" a premise rather than a hope.

Writers of the numbers: `main` at server start (one production call), `test_support::start_ids_clear_of_other_runs` (every `own_sandbox` and agents/db test setup), the fixture helper sites being rewired, LSP `unique()`, the cleanup bin's local allocator. Readers: the kube names (`pod_name`, `docker_pvc_name`, `workspace_pvc_name`, `sandbox_volume_pvc_name`, and `agent_volume_pvc_name` once 239 merges), the `CONVERSATION_LABEL` value on claims and pods, `pod_start_lock(conversation_id)` keys (two tests sharing an id also share that lock — same defect, same fix), and the events-bus floor `TEST_SHARED_IDS_END = 100_000` (`events/server.rs:169` — unchanged; every band stays far above it).

**Work already in flight**: a test binary that outlived its cluster lock cannot exist — `with-cluster-lock` holds the lock until the command and every descriptor inheritor has exited, and the SME-212 guard refuses any unlocked `#[sqlx::test]`/real-cluster test. A check server takes no cluster lock but makes exactly one allocator call at start, under its port and scratch-database locks; two check servers can overlap only in dev, where the port lock serializes starts. A run with `SMELT_CLUSTER_LOCK_HELD` forged into its environment sits outside every guarantee the harness already makes (docs/testing.md: never set it).

**Cluster objects in `smelt-park-test`, after this change**: created (labelled with the test database's instance) → deleted by the test's own teardown (pass, fail, or cut-off start — machinery unchanged) → *leftover* (a killed run's: not Terminating, created before the next process started) → deleted at the next run's start by the extended sweep, or by age ≥ 1 h as today → gone. A Terminating object is never taken by either arm. A failed sweep delete leaves the object old-or-foreign, which the next sweep takes; the uid preconditions still prevent deleting an object recreated under an old name (existing, tested).

## The flake's ways to fail, and the assertion that tells each apart

- **a1 — `NotOurs { …, Foreign }` on a docker/workspace claim** (occurrences 1, 2): the second worker's `create_pod` met the first's claim. Told apart by T1/T4: two harness bases from one process are ≥ `ID_STRIDE` apart, so the claim names cannot coincide.
- **a2 — kube 409 `sandbox-<id>` already exists** (occurrence 3a): the object is a raw test fixture (no database sequences involved) — T5: the 3e9 fixture helpers never return the same id twice. That absence of sequences is exactly what separates a2 from a1.
- **a3 — the 240 s teardown wait** (occurrence 3b): no separate assertion; it is a1's downstream cost (`tear_down` prints "pod start outlasted", `pod_lifecycle_tests/mod.rs:118`) and disappears with a1/a2.
- **b — two databases both name `agent-volume-1`** (occurrence 4): T3: after one harness move, *no* sequence in the test database is below `base` — it fails while any table still counts from 1, regardless of the allocator.

## Trade-offs to flag

- Harness bases stop looking like `2e9 + that call's sub-second nanos` and become stride-100,000 streams from a process-random seed (e.g. `2,043,7xx,xxx`). Still ≤ 10 digits, inside browser numbers and label values. Any future test that wants an id asserts the invariant (band, distinctness), never a value.
- `ID_STRIDE = 100_000` rows is the separation between two harness moves; a scenario uses a few dozen id-naming rows — a thousandfold margin, and the exhaustion panic converts a pathological loop into a named failure instead of an overlap.
- The sweep's new arm rests on "the cluster lock means no other run at that moment" — enforced since SME-212. A forged `SMELT_CLUSTER_LOCK_HELD` escapes it, as it escapes everything else already.
- The production fresh-database path stays list-driven: a future table whose ids name cluster objects must still be added to `CLEAR_ID_TABLES` for *production* scratch starts (the test path no longer needs it). This is the residual landmine; the lint guard can see test-side folds but not the Rust↔table link. The list's doc comment names the spec functions whose formats it protects.
- Routing LSP `unique()` and the fixture helpers into the shared band changes the digits in test-cluster object names (bigger, less readable in `kubectl get`); the old `uuid_like` band `[1e9,2e9)` retires. Q2 asks if you want both fixture bands kept.
- 239's `agent_volumes` row becomes belt-and-braces for tests (move-every-sequence already covers it) and stays load-bearing for production.
