## The fix's shape, per family

### Family 1a — the sweep's woken-parent asserts (sweep.rs:63, :103)

The awaited-wake set is missing a member (the start.rs:409 wake); that is the
mechanism. Two shapes:

- **(a) Test side (recommended).** Replace the two snapshots with waits on the
  fact they need — the woken parent's *reply lands* — via the module's own
  `eventually` (the `ff97ab5` shape, which passed CI at `ab7b48e`'s next run
  per SME-336). Small, no product surface. Honest bound: `eventually`'s 10 s
  window covers one mock round trip behind an already-awaited wake, unlike the
  `ended.rs` window's three schedulings; if the reproduction shows it missing
  that, the same rule as family 1b applies (bound from the load curve, not a
  number that survives).
- **(b) Product side.** Have `fail_start` return its wake handle and
  `startup_sweep` include it in its returned `Vec`, so tests await every wake
  the sweep provokes and the snapshots stay snapshots. But main.rs:195-200
  shows production *drops* these handles by design ("The wakes run on their
  own"), so this widens a test-only API for a test-only need, and the
  double-wake itself (two wakes for one event) would remain.

This is a real fork — different review surface, different blast radius — and
goes to the user as Question 1. The plan's default is (a) plus the double-wake
clean-up noted in Trade-offs.

### Family 1b — `ended::test_no_notice…`'s 10 s window (ended.rs:105 → mod.rs:137)

No unbounded wait exists on the path (queue.rs:125-147 returns on every
branch; the 10.78 s sighting *completed* past the deadline). The defect is one
budget covering three schedulings: the window opens only after the other two
children's turns are awaited, and must still hold the third child's start
release + first turn + check. The fix is **not** a bigger number:

1. Wait first on the start's exit — the hook already exists
   (`test_hooks::starts_ended`, used at sweep.rs:123) — so the release/done
   step is observed, not budgeted.
2. Then watch the completion fact: `last_turns_checked(commands) > before`
   (the drop-counted hook, test_hooks.rs:67-74), with one wait for the first
   turn's end and the check behind it.
3. Any surviving bound is set from the measured load curve (the reproduction's
   per-step timings), recorded on SME-341, and the `tdd.md` rule applies: make
   it fail every time first — add the delay that crosses the measured boundary
   on the unfixed code, see the red, keep the delay.

A bare bump of 10 s to a number that survives is this ticket's forbidden
laundering and will not be proposed.

### Family 2 — the mount-follow shot (sandbox.rs:372-384, sticky.rs:176-181)

Test-side-only cannot work: the gap never closes on its own (no further
content event exists — that is why the snapshot-phase body is complete), so no
amount of waiting makes the product follow. The fix is **product-side** — make
the follow level-triggered where it is today edge-triggered. Smallest honest
shape: while stuck, after the effect's `scroll_to_bottom`, confirm the body
is at its bottom once layout has a chance to settle and re-scroll if the
position stands still short of it (a recheck on the next frame(s) /
`ResizeObserver` while `is_stuck`), swallowing nothing and re-reading
`get_scroll_size` at each attempt. Constraints the fix must not break, each
already covered by scenario 28 legs: a reader who scrolled up stays put
(leg F4), a window grow must not re-stick a reader the clamp landed onto the
bottom (leg G — `scrolled()`'s client-height guard sticky.rs:88-90 is load-
bearing: only user intent re-sticks), and the never-painted-at-top guarantee
(leg A/B's `assert_never_painted_at_top`). If the re-scroll must know the box
resized, gate it on `is_stuck` — the SME-108 rule protects readers who asked
to be left alone, and a stuck reader *asked* to follow.

Also a test-instrumentation fix (restoring truth, not narrowing): re-install
the sampler after `page.reload()` before the F2/F3 settles
(`terminal_scroll.rs:28-33` is already idempotent per page — it needs calling
once post-reload) so `scroll events:` means what its readers assume. One more
scenario leg is *not* added: leg F2 already exists and is red; it is the
record.

## Trade-offs to flag

- Family 1a's (a) keeps the double-wake in the product (two wakes for one
  restart-failed child). Harmless in production (a wake with nothing pending
  is a recorded no-op, notify.rs:84-89), but it is the reason snapshot-style
  asserts stay unsafe and the reason a future store-after-delta assert can
  race again. Question 1's (b) variant is the root-removal; the PM's split of
  a follow-up is fine either way.
- Family 1b keeps a 10 s-class window for the model turn itself if the load
  curve says one mock turn fits well inside it at the recorded load; the plan
  binds the number to the curve, not to today's 10.
- Family 2's level-trigger touches a hot path for every chat user (the
  transcript shares `StickyBottom`); scenario 28's seven legs are the defense
  and the reason the change stays gated on `is_stuck`.
- The three throwaway PRs spend real CI on a branch whose value is the record;
  that is the point, and the PM holds the trigger.
