# SME-163: Make the repo friendlier to LLMs

**Branch:** `sme-163-llm-friendly`, worktree `~/smelt-worktrees/smelt-sme-163`, cut from `origin/main` at `6e9f3b4`.

The ticket's `## Plan` holds a summary of this file; Trade-offs to flag and Questions for the user are in the ticket.

## What and why

smelt is worked on by Claude (1M-token window) and by local models through smelt itself and other harnesses (the user's llama-server runs `flash-next` with a 262,144-token window). A file an agent must read whole costs context in every session that touches it, and some of the repo's files no longer fit one read of the common harnesses. The ticket asks for:

1. a file-size ceiling that suits both kinds of model, backed by measurements;
2. files with easy break points split under it, big functions refactored, big test files split;
3. `docs/development-process.md` split, with a file per persona;
4. an `AGENTS.md` for non-Claude agents;
5. (this plan adds) a check that keeps the ceiling from being crossed again.

### What one read returns, in the tools that read these files

Each figure was checked in the tool's source or tool description:

* **smelt's own `read_file`:** 2,000 lines per call, and every tool result is capped at 30,000 characters (`src/anthropic/tools/files.rs` `MAX_READ_FILE_LIMIT`, `src/anthropic/tools/mod.rs` `MAX_TOOL_RESULT_CHARS`). This is what a local model working through smelt gets.
* **opencode:** 2,000 lines and 50 KiB per read (`packages/core/src/tool/read-filesystem.ts`: `MAX_READ_LINES = 2_000`, `MAX_READ_BYTES = 50 * 1024`).
* **Claude Code's Read:** 2,000 lines by default. It refuses a whole file over about 25,000 tokens and asks for an offset and limit instead.

## The ceiling

**Recommended: 40,000 bytes and 2,000 lines per tracked text file** (question 1).

* **About 11.4k tokens at the ceiling:** 4.4% of a 262,144-token window, and 1.1% of 1M. A change that reads ten files at the ceiling uses about 115k tokens, under half a local model's window, which leaves room for the system prompt, tools and the conversation. At 50k the same ten files take 55% of the window.
* **Reads:** one read in Claude Code and opencode, two in smelt's `read_file`. A 30k ceiling would make it one read everywhere, but it adds 10 more files to split (42 in all), several of them coherent modules just over 30k (`turn/run.rs`, `sandbox/spec.rs`, `events.rs`). A 50k ceiling leaves `lsp/manager.rs`, `mcp_oauth.rs` and `anthropic/tools/mod.rs` (each half tests) over two reads in every tool.
* **2,000 lines** is every tool's default read length. The 12 files over it are all over 40,000 bytes too, so today the byte limit is what binds. The line limit catches a dense file in future: CSS averages 22 bytes a line.
* **New files** aim at 30,000 bytes or less, so a file has room to grow before it needs splitting. That's a guideline in the docs, not checked.
* **Not counted:** `Cargo.lock`, `terraform/**/.terraform.lock.hcl` (generated), binary files (`docs/images/`, fonts), and `assets/highlight.css`, which a test generates (it's 10k today).

**Functions:** production functions over 200 code lines are split (question 2), using clippy's `too_many_lines` with `too-many-lines-threshold = 200`. That lint counts code lines only, not blanks or comments, so its count runs a little under the table above. Test functions are left to judgment, since clippy doesn't lint test code here. The four browser scenarios over 200 lines are still split, along the steps they already narrate.

## Tests: topic files, not one test per file

Recommended (question 3): split each big test file into **topic files under a `tests/` module directory beside the code**, each under the ceiling, with shared helpers in `tests/mod.rs`. Don't put one test per file.

How Rust and `#[sqlx::test]` handle it (checked in `sqlx-macros-core-0.8.6/src/test_attr.rs:174` and `sqlx-postgres-0.8.6/src/testing/mod.rs`, `sqlx-core-0.8.6/src/testing/mod.rs:48`):

* **The database name.** `#[sqlx::test]` names its database `_sqlx_test_<sha512 of module_path!()::fn_name>`. Before creating it, it drops any old database of that name. The name changes when a test moves to another module, but it stays unique inside the crate. So neither topic files nor one file per test can make two tests share a database.
* **What the cluster-lock rule cares about** (`docs/development-process.md`, "Rules every persona follows"): two runs of the *same* test path at once collide (`dropdb … being accessed by other users`). Moving tests changes no lock behaviour: every run still goes through `scripts/with-cluster-lock` or `scripts/cluster-test`.
* **The leftover.** A renamed test's old database is left behind only if its last run failed (sqlx drops it when a test passes). That's harmless: it's never reused.
* **Integration tests.** One test per file as Cargo integration tests (`tests/*.rs`) would be ruled out anyway. Each file is its own crate and binary, linked against everything with the `server` features, and it can't see the `pub(crate)` items the tests use (smelt is a binary crate with no `lib.rs`). So "one per file" could only mean child modules of the crate.
* **The count.** As child modules, one test per file would turn 1,312 tests into about 1,300 files. Each would repeat its `use` lines, and every helper would have to become `pub(super)`. An agent would need several reads to see a test together with its neighbours and helpers, where today one file holds the whole topic.
* **Navigation.** grep finds a test by name either way. A topic file of 10 to 30 KB gives an agent the test, its siblings and its helpers in one read.

The test paths that docs and scripts mention change with the split. No script or CI step selects tests by path (`scripts/check.sh`, `scripts/browser-tier` and `ci.yml` run whole suites). The docs that name test paths are updated in the same commit, and these are the ones to update:

* `docs/testing.md`: `sandbox::tests::…`, `turn::tests`, `sandbox::agent_connection_tests`, `browsing::browser_tests::run_session_scenarios`, `webfetch::browser_tests::…`, `mcp::tests::test_live_exa_search_…`
* `docs/development-process.md`: `sandbox::tests::test_sandbox_futures_stay_small`, `events::wire_tests::…`
* `scripts/cluster-test`'s usage example.

The rule "Tests live inline with the code they cover: `#[cfg(test)]` blocks in the same `.rs` file" changes. The new rule: tests stay in the module they cover. They go in a `#[cfg(test)] mod tests;` whose file sits beside the code (`foo/tests.rs`, or `foo/tests/<topic>.rs`) once the file would cross the ceiling.

## `AGENTS.md`

## Keeping the ceiling: the check

Recommended (question 5): a **Rust test** plus **clippy's `too_many_lines`**, each with a list of today's offenders that can only shrink.

* **`src/repo_lints.rs`,** a new `#[cfg(all(test, feature = "server"))]` module, with one line added to `src/main.rs`. About 150 lines with its tests:
  * `oversized(files, ceiling, exceptions) -> Vec<Finding>` is a pure function, tested first against fixtures. A file over the ceiling is reported. A listed exception is allowed up to its recorded size and no further. An exception that is now under the ceiling is reported as stale, so the list shrinks when a split lands.
  * `test_no_file_crosses_the_size_ceiling` walks the tracked roots under `CARGO_MANIFEST_DIR`, the same way `highlight.rs`'s test reads `assets/highlight.css`. It skips `target/`, `.git/`, `.browser-check-cache/` and the exclusions above, and fails with each offender, its size and "split it: see docs/process/rules-commits.md". `EXCEPTIONS` starts with the 32 files and their current sizes.
  * `test_docs_links_resolve` checks every relative Markdown link and `#anchor` in tracked `.md` files, using GitHub's slug rules (lowercase, punctuation dropped except `-` and `_`, spaces to `-`, `-1` suffixes for repeats). It protects the doc splits, and it fails today on any link that is already broken (the Developer fixes those first).
* **This needs no new script or CI step.** `cargo test --features server` already runs in `scripts/check.sh` and CI.
* **Functions:** a new `clippy.toml` with `too-many-lines-threshold = 200`, and `-D clippy::too_many_lines` added to `scripts/lint-expects`'s `lints` array (1 line). It covers both the server and the web build. Each production function over the threshold gets `#[expect(clippy::too_many_lines, reason = "SME-163 phase N splits it")]`: about 7 functions, 5 of them components. The phase that splits a function removes its mark. Whether the lint sees inside a `#[component]`'s body is checked first, as a spike. If it doesn't, components are checked by hand in phase 4 and the docs say so.
* Per the rule "A PR that adds a lint or a gate check runs it on the branch merged with the latest `main`", both are run on the merged tree before In Review.

## Phases

Recommended (question 6): **this ticket as phase 1, and three child tickets.** The reason is the overlap rule. While a ticket is in Todo or In Progress, every Planner whose plan touches the same files stops. A single PR touching about 30 source files would hold back planning for SME-73, SME-78, SME-79, SME-96 and SME-162 (all in Up Next and touching `turn`, `sandbox`, `providers` and `scripts`) for its whole run. Small phases keep each file set held briefly. Each phase's move commits are made by a script, kept in the ticket, so a phase can regenerate its moves when `main` moves ("Start a refactor of a file once the open PRs changing it have merged"). That script also proves the move: each item appears verbatim, once, in its new place. So move commits are gated by building every target, with the full `scripts/check.sh` run on the tip ("A commit that only moves code").

## State model

The change adds no product state. What it does have:

| Record | States | Moves by | If it fails partway |
| -- | -- | -- | -- |
| `EXCEPTIONS` list in `src/repo_lints.rs` | an entry per file over the ceiling, with its size cap | a phase removing a split file's entry. The test fails on a stale entry, so the list can only shrink. A file growing past its cap fails the test. | A phase that splits a file but leaves its entry fails the gate on "stale". The fix is to remove the entry. |
| `#[expect(clippy::too_many_lines)]` marks | on each production fn over 200 code lines | a phase splitting the function (the mark is then unfulfilled, and `-D warnings` fails until it's removed) | same as above |
| sqlx test databases | named from each test's path | a moved test gets a new name. The old one is dropped at a passing run's end, or left behind by a failed one. | A leftover old-name database is never reused. Harmless. |
| The sandbox image tag (phase 3) | `smelt-sandbox:src-<hash of agent sources>` | phase 3 moves `src/bin/sandbox_agent.rs`, so the hash changes once | The gate builds the new tag itself. The dev server keeps its own tag until the user's checkout moves (no `--latest`). |
| Other branches' edits to moved files | | `main` moving under a phase | The phase's move script runs again on the new `main` (it doesn't rebase moves). A branch that edited a moved file before the merge resolves by applying its hunk to the new file: the PR says which file each old range went to. |

Readers of the moved docs: every persona brief and memory that names a section keeps working through the stubs. The Project Manager's next briefs should name the new files.

## How it's checked

* **Phase 1:**
  * `test_docs_links_resolve` passes, and it's seen failing first on a link broken on purpose.
  * The size test fails first on a fixture tree.
  * `scripts/check.sh` runs on the tip.
  * Docs-only commits are gated by building every target, with a file-list script, per the rule.
  * By hand: open `CLAUDE.md` in a fresh Claude Code session in the worktree, and confirm `/memory` shows `AGENTS.md`'s content imported.
* **Code phases:**
  * Each move commit carries a script that proves the move (every item verbatim, once, in its new place), and is gated by building every target.
  * `scripts/check.sh` and `scripts/browser-tier` run on each phase's tip.
  * The test count is unchanged from before the phase (`cargo test -- --list | wc -l`), apart from the renames.
  * For phase 4, the CSS byte-equality test, and screenshots of the chat page at 1400 and 390 wide before and after, which should be identical.
