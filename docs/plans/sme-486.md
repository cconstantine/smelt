# SME-486 plan: the Claude subscription's usage windows, recorded and shown

**Branch:** `cconstan/sme-486-smelt-records-the-claude-subscriptions`, cut from `origin/main` f2aa516, in the Planner's conversation clone `/workspace/smelt` (a conversation seat works in branches of its one clone, rules.md, "Working from a conversation sandbox"). Removed before the PR merges, as development-process.md says; the ticket keeps the record.

## What and why

On 2026-11-11 the user saw 45% of the five-hour limit used in under an hour, and the Claude Code PM couldn't see it. Every API call the `claude` CLI makes streams a `rate_limit_event` with the subscription's windows. smelt reads that event today only to explain a capped turn (`src/claude_cli/errors.rs`, `RateLimit`), then drops it. This plan has smelt:

1. **Parse** each event's `rate_limit_info.unifiedWindows` into numbers: per window, its utilization, status and reset time.
2. **Keep** the latest reading per provider and window in the database, so it survives a restart or deploy.
3. **Serve** it read-only: `GET /api/providers/{id}/usage`, plus a conversation-scoped read for the chat indicator.
4. **Show** it on a Claude Code provider's page, on the providers list, and as a small indicator in a Claude Code conversation's context bar.
5. Give `scripts/pm/smelt-api` a read-only **`usage`** subcommand that prints the numbers and a hold/ok verdict.
6. Put the **threshold rule** in the PM persona: above it, the PM starts no new Driver, asks running Drivers to hold after their current seat, records this on the tickets and notifies the user.

Only numbers leave the parser. The session id, uuids, tokens and any other string in the event are never stored, served or logged (see "Never a session id or token").

## Evidence for the event's shape

The fixtures are real captures, sanitized by `src/claude_cli/capture/sanitize.rs`, which pins every `resetsAt` to `1767225600` and zeroes ids. Six of the twelve fixtures (`capped`, `kill`, `loop`, `pending`, `resume`, `thinking_off`) carry the event. `loop.jsonl` has one (the CLI sends it once per run, not per API call). Its shape, from `capped.jsonl`:

```json
{"type":"rate_limit_event","session_id":"…","uuid":"…",
 "rate_limit_info":{"status":"allowed","rateLimitType":"five_hour","resetsAt":1767225600,
   "isUsingOverage":false,"overageStatus":"rejected","overageDisabledReason":"out_of_credits",
   "unifiedWindows":{"five_hour":{"utilization":0.09,"status":"allowed","resetsAt":1767225600},
                     "seven_day":{"utilization":0.32,"status":"allowed","resetsAt":1767225600}}}}
```

- `utilization` is a fraction (0.09 = 9%), the same number claude.ai shows as a percent.
- `resetsAt` is Unix seconds.
- `status` is `allowed`, `allowed_warning` or `rejected`. `errors.rs` already handles `rejected`, and the CLI emits `allowed_warning` near a cap.
- `bad_token`, `bad_model`, `missing` and `overflow` carry no event, because those runs fail before any API call. Such a run records nothing and the last reading stands.
- The captured windows are only `five_hour` and `seven_day`. A window with any other name (Anthropic has had per-model weekly windows) is kept and shown with its numbers but no pace, since its length isn't known. Its name must pass the name check below.

**Fixture limit:** every fixture has the same `resetsAt`, so the pace and reset-passed tests use synthesized events (marked so in the test). The parse test reads the real fixtures.

## How it works

### Parsing (`usage::Reading::from_event`)

The parser reads only `rate_limit_info.unifiedWindows`. Each entry becomes a `Window { name, utilization, status, resets_at }`, with every field checked:

- **`name`**: must match `^[a-z0-9_]{1,32}$`, or the entry is dropped. A token never matches, because tokens have upper case or `-`.
- **`utilization`**: must be a finite JSON number from 0 to 10, or the entry is dropped. Above 1.0 is possible with overage.
- **`status`**: one of `allowed`, `allowed_warning` or `rejected`, else stored as `unknown`.
- **`resetsAt`**: an integer between 2020 and 2100, else `None`.

A reading is a `Vec<Window>` plus `seen_at`, the server's clock when the line was read. An event without `unifiedWindows`, or with no valid window, gives no reading, so the last one stands. `errors.rs`'s `RateLimit` is unchanged: the capped-turn error message keeps its own path.

### The pending slot, then the record

`usage::seen(conversation_id, event)` parses and puts the reading into a process-wide `Mutex<HashMap<i64, Reading>>`, keyed by conversation. A newer reading replaces an older one. This is the `session::note_delivered` pattern already in this module. `note` is synchronous and `Run` knows no provider, so the slot holds the reading until the caller, which knows `turn_model.provider_id` and has the pool, calls `usage::record`.

`record` takes the conversation's entry (removing it) and upserts one row per window:

```sql
INSERT … ON CONFLICT (provider_id, window_name) DO UPDATE SET …
WHERE provider_usage_windows.seen_at <= EXCLUDED.seen_at
```

A failed upsert is a `tracing::warn!` naming only the provider id and the sqlx error, then dropped: a reading never fails a turn.

### Table `provider_usage_windows`

| Column | Type |
|---|---|
| `provider_id` | `BIGINT NOT NULL REFERENCES inference_providers(id) ON DELETE CASCADE` |
| `window_name` | `TEXT NOT NULL` |
| `utilization` | `DOUBLE PRECISION NOT NULL` |
| `status` | `TEXT NOT NULL` |
| `resets_at` | `TIMESTAMPTZ NULL` |
| `seen_at` | `TIMESTAMPTZ NOT NULL` |

The primary key is `(provider_id, window_name)`. There is no text column that could hold a session id.

### The read side: wire types and pace

`ProviderUsage { provider_id, windows: Vec<UsageWindow> }`. Each `UsageWindow` has:

- `name`, `utilization`, `status`, `resets_at` and `seen_at`, as stored.
- `reset_passed: bool`, true when `resets_at` is before now. The utilization is then from an ended window and the UI says "reset since".
- `elapsed_fraction: Option<f64>`, the share of the window already used up. `five_hour` is 5 h long and `seven_day` 7 d; any other name gives `None`. It is computed as `1 − (resets_at − now) / length`, clamped to 0..1.
- `projected: Option<f64>`, the utilization at this rate by reset: `utilization / elapsed_fraction`. It is `None` when `elapsed_fraction < 1/7` (the first day of a week, or the first ~43 min of five hours), when the reset has passed, or when there is no `resets_at`.

`get_provider_usage(id)` errors "That provider no longer exists." as `get_provider` does. A provider with no reading returns empty `windows`. Rows are kept and served whatever the provider's kind (a provider switched away from Claude Code keeps its old rows); the UI shows the section only for the Claude Code kind.

`get_conversation_usage_windows(id)` returns `Option<ProviderUsage>`: `None` unless the conversation's provider (`conversations.provider_id`) is of kind Claude Code. It uses the same resolution as `providers::conversation_model`.

Both routes are `#[get]` server functions, the repo's way for `/api/...` (AGENTS.md and docs/architecture.md list only three non-server-fn exceptions). They read only and change nothing.

### `smelt-api usage PROVIDER_ID [--json]`

The subcommand is a GET through the route table (route `usage`); nothing else is sent. It prints one line per window, from a fixed list of fields:

```
five_hour  45%  allowed          resets 2026-11-13T14:20Z  seen 2026-11-13T12:02Z
seven_day  32%  allowed          resets 2026-11-17T09:00Z  seen 2026-11-13T12:02Z  pace 112%
verdict    hold: seven_day on pace for 112% by reset
```

With `--json` it prints the same whitelisted fields as JSON, never the raw body. `verdict` is one of:

- `ok`;
- `hold: <reasons>`;
- `unknown: no reading` (no windows, or every window `reset_passed`). The PM treats unknown as ok and notes it.

The thresholds are constants in `smelt_api.py`, the defaults from Q2:

- `HOLD_FIVE_HOUR = 0.70`
- `HOLD_SEVEN_DAY = 0.90`
- `HOLD_PACE = 1.0`
- any window `allowed_warning` or `rejected` holds too.

A window whose reset has passed never holds. The exit status is 0 whatever the verdict, 1 on a non-2xx answer, 2 on usage or a network error, the same as the other subcommands. The PM reads the verdict line.

### The PM rule

This goes in `docs/personas/project-manager.md`, *Usage hold (SME-486)*, and is pointed to from the persona file.

- **When to check.** Before starting any Driver, and on each pass while Drivers run, the PM runs `smelt-api usage <id>` for the Claude Code provider its Drivers use (`smelt-api providers` lists it).
- **On `hold`:**
  - it starts no new Driver;
  - it sends each running Driver one message: "Usage hold (SME-486): finish your current seat, start no next one, report, and wait for my resume";
  - it comments `Usage hold: <verdict line>` on each affected ticket and on the project's board ticket (if it keeps one), with the time;
  - it calls `notify_user` once.
- **Resume.** On a later pass whose verdict is `ok` (typically after `resets_at`), it messages each held Driver "Usage hold lifted", comments `Usage hold lifted`, and resumes starting Drivers.
- **On `unknown`:** it proceeds, and says so in its pass note.
- **Not a gate on the user.** The user can lift a hold by saying so.

The persona file gains a paragraph pointing at that section, with no frontmatter change.

## State model

**Record: a provider's window row `(provider_id, window_name)`.** Its states are none, then fresh (`resets_at` in the future), then stale (`resets_at` passed, kept as is).

| Event | none | fresh | stale |
|---|---|---|---|
| A turn's CLI call reads an event, then `record` | → fresh | replaced if `seen_at` ≥ the row's | replaced (the new window) |
| An older reading arrives late (two conversations racing on one provider) | → fresh | kept (the WHERE refuses it) | kept, unless its `seen_at` is newer |
| The time passes `resets_at` | — | → stale (computed on read, no write) | — |
| The provider is deleted | — | row cascades | row cascades |
| The provider's kind changes from Claude Code | — | kept; the UI hides it, the API still serves it | same |
| A server restart or deploy | — | kept (database) | kept |
| A turn whose run fails before any API call (bad token or model) | no change | no change | no change |

**Writers** (every path that writes a row), all through `usage::record`:

1. `turn::call::call_claude_cli` after `run::call` returns Ok, once per model call of a turn.
2. The same after Err: a capped turn's event (status `rejected`) is recorded, and that is the reading that matters most.
3. `turn::call::stream_for_kind`'s Claude Code branch (`once::once`, the compaction summary), Ok or Err.

Each takes only its own conversation's pending entry. The capture tool (`claude_cli/capture`) parses no events through `note`, so it writes nothing (the Developer checks with grep).

**Pending-slot transitions** (one entry per conversation, memory only):

| Event | No entry | Entry held |
|---|---|---|
| `seen` | → held | replaced (newer) |
| `record` | nothing written | taken and written |
| A Stop drops the call future mid-stream | — | stays; the next `record` for that conversation writes it, still with its true `seen_at`, so it can't overwrite a newer row |
| A restart | — | lost: at most one call's reading. The next call brings a fresh one. |
| A conversation deleted with an entry held | — | stays until restart. Bounded at one small entry per conversation that ever ran on Claude Code since the restart. `record` is the only reader, and nothing reads the slot otherwise. |

**Readers, and what each does with a value that just changed:**

| Reader | What it does |
|---|---|
| `get_provider_usage` | Reads rows at the request; `reset_passed` and `projected` use the request's now. |
| `get_conversation_usage_windows` | The same, plus it resolves the conversation's provider at the request. A model switch takes effect on the next fetch. |
| Chat indicator | Fetches on select, after each new `ContextUsageUpdate` and when the conversation's turn ends. `ContextUsageUpdate` is published by `CallRecorder::finish` after `call_claude_cli` returned Ok, so after `record`, and the fetch sees the new row. A failed call (a capped turn) publishes no `ContextUsageUpdate`, so the turn-end fetch is what shows a `rejected` reading. That fetch hangs off whatever `ConversationState` field says the turn is running, read in the component and not written, so `state.rs` stays untouched. B1's check 4 covers the `ContextUsageUpdate` fetch and T5 the capped turn's row. The turn-end fetch has no browser test, because the tier has no Claude Code turn, so it is part of the hand check. A fetch that lands after the user switched conversations is dropped (selected-id check plus request counter, as `open_context_detail` does). A reading recorded by another conversation on the same provider shows here on this conversation's next update or reselect, not live. That is an accepted staleness of at most one turn, flagged below. |
| Provider page and list | Fetched on page load; no live refresh. |
| `smelt-api usage` | Reads at each run; the PM runs it each pass. |

**Work in flight:** a turn in flight keeps writing readings for the provider it resolved at its start (`TurnModel` is a snapshot). Its rows say which provider they are for, so a mid-turn model switch can't mislabel them.

**What fails partway:** `record` takes the entry, then the upsert fails. The reading is lost and logged (provider id and error only), and the next call brings a new one. That is accepted: one missed reading, never a wrong one.

## Never a session id or token

How it's enforced:

1. The parser reads only the four fields above from `unifiedWindows` and checks each (name regex, number range, status allowlist). It never keeps the event or `rate_limit_info`.
2. The table has no column for anything else.
3. The wire types have no field for anything else.
4. No `tracing` call in `usage.rs` or the call sites takes the event or any of its strings. The one warn names the provider id and the sqlx error.
5. The client prints whitelisted fields only, never the raw body: its `--json` rebuilds the windows from those fields.

How it's tested (red first). Each test plants a marker in every string the event can carry: `session_id`, `uuid`, `overageDisabledReason`, a window named `SK_ANT_MARKER_…`, a window named `sk-ant-…`, and a status `sk-ant-…`.

- **T2**, the parser: the marker is absent from the serialized `Reading`.
- **T6**, the API through the real caller (the fake CLI streams it in a turn): the marker is absent from `get_provider_usage`'s JSON, from every DB row (`SELECT row_to_json`), and from captured logs during the turn, using the log capture `src/telemetry/tests.rs` uses.
- **P3**, the client: a `fake_smelt.py` answer carrying an extra `"session_id": "MARKER"` field and a marker window name never prints the marker, in text or `--json`.
