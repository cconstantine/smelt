**Where newlines die and where they don't — the probe and the spec:**

1. A single-line control cannot hold newlines at all. Spec (WHATWG HTML Living Standard, input element, text-field section — fetched 2026-10-31): the value "must have a value that contains no U+000A LINE FEED (LF) or U+000D CARRIAGE RETURN (CR) characters. The value sanitization algorithm is as follows: **Strip newlines from the value.**" Probe: setting `input[type=password].value = "apiVersion: v1\nclusters:\n  - name: x\r\n..."` read back `"apiVersion: v1clusters:  - name: xcurrent-context: y"` — gone, silently.
2. **Paste is worse than the spec: Chromium's edit path replaces each newline with a *space*.** Probe: `document.execCommand('insertText', false, "line1\nline2\n\nline4")` into a focused single-line input read back `"line1 line2  line-four"` — one space per newline (paste takes this edit path; the setter strips, and both lose). This fits the ticket's forensic artifact exactly: the stored `deploy_kubeconfig` had space-run histogram {1×22, 3×3, 5×5} and zero newlines — runs of 1, 3, 5 are exactly one space per newline joined to 0-, 2-, 4-space indents of 2-space-indented clientcmd YAML.
3. A `<textarea>` keeps them. Probe: the same `insertText` read back `"line1\nline2\n\nline4"`; the value setter likewise keeps `\n`, normalizing `\r\n` to `\n` (so a Windows-terminated paste is stored LF — newline-preserving normalization done by the browser before smelt ever sees it).

**The code trace, form → row → pod file (all at `e3869e4`):**

- The page's two value fields are single-line password inputs — the corruption site, and the only one in smelt's own code: the Add form's `#secret-value` ([`src/frontend/pages/secrets.rs:107-114`](https://github.com/cconstantine/smelt/blob/e3869e4709931e348473a2949a0f85807ec91e05/src/frontend/pages/secrets.rs), `input { r#type: "password" }`) and the Change control's `.secret-change-input` (`:191-199`, same).
- Nothing between the field and the row rewrites the value: `save_secret_of` validates then binds `&value` as-is (`src/api/secrets.rs:136-163`); `validate_secret_value` (`:57-65`) knows only "non-empty, ≤ 65,536 bytes" — no character rule; `create_named_secret` / `set_named_secret_value` bind the text as a parameter (`src/db/secrets.rs:78-98`); the column is `TEXT NOT NULL CHECK (value <> '')` (`migrations/20261028120000_named_secrets.sql:11-17`) — newline-agnostic by construction. The Dioxus server-fn call rides JSON, where `\n` escapes and un-escapes losslessly. **The save path is innocent: what reaches the browser control is what is stored.**
- Install never was the culprit (the ticket already proved it live, and the code says so): `pod_files` passes `secret.value` straight into `PodFile.content` (`src/credentials.rs:240-241`) and `install_pod_files` streams raw bytes through stdin into `cat > "$1.new"` + atomic rename — no heredoc, no quoting to lose bytes in (`:272-297`); SME-326's first run confirmed install byte-fidelity, and git private keys have shipped the same fact since SME-242: multi-line PEM, the same TEXT columns, the same installer, and the checklist's `creds-key` row's push works (`docs/feature-checklist/integrations.md:32`).
- **So the story is paste-side plus prevention**, exactly the brief's alternative: the single-line password input flattened the paste inside the browser, matching the stored artifact byte-for-byte; the server, the column and the install are innocent at head.
- **The display hides it** (the SME-277-family answer): `shown` is the first ≤ 4 bytes plus the exact byte count (`src/api/secrets.rs:79-92`), and paste-flattening preserves the byte count (a newline becomes a space, not nothing), so the broken kubeconfig renders *indistinguishably* from a good one. The page renders `shown` verbatim and holds no structural fact about the value (`pages/secrets.rs:184-188`, `:248-255`). The user had no way to see the corruption on `/secrets`.

## What

Make a named secret pasted as real YAML stay real YAML: **save → store → display → install, multi-line-safe end to end**, and make the display honest enough that a flattened secret can never sit invisible again. Three parts:

1. **The save-side fix:** both value fields become a `<textarea>` — the in-house pattern for pasting multi-line credentials already shipped next door (the git key box, `src/frontend/pages/git.rs:303-311`: `textarea { rows: 8, ... }` for an OpenSSH PEM). With a textarea the browser keeps newlines (probed), and every smelt layer behind the field already keeps them (traced), so no other write-path code changes. **No validation is added** — the deliberate call, argued in Scope.
2. **Honest display:** each row gains a **line count**, computed at read exactly like `shown` and never stored — `apiV… (1981 bytes)` becomes `apiV… (1981 bytes) · 47 lines` for a real YAML file and `… (1981 bytes) · 1 line` for the flattened one. Byte count alone cannot do this (it survives flattening intact — Evidence 2); line count is the smallest fact that separates the two states. This is the ticket's "visibly line-counted at save" ask, met at display.
3. **Automated pins at every layer an automated test can reach:** the page already has a browser-tier scenario (`scenario_secrets_page`, `src/browser_tests/settings.rs:426-535`, with a 375px fit pass at the end), and extending it with a real **paste** is the one test that goes red on the unfixed code. The db-, api- and credentials-layer tests pin byte-exact newlines so no future change can mangle them quietly — those pass before the fix and are stated as pins, not as red fixtures (the honesty rule in plan.md, "Which part each test needs").

## Scope — and what is *not* done (no gold-plating)

In: the two textarea controls (Add form and Change) + their CSS; `SecretSummary.lines` + the row's rendering and title; the tests listed below; one feature-checklist row.

Not done, on purpose:

- **No server-side newline validation or normalization.** "Validate rather than silently mangle" was the ticket's question; the trace answers it: nothing on the server mangles, and with a textarea nothing in smelt can. A textarea makes the browser *keep* `\n` and normalize `\r\n`→`\n` before smelt sees anything (probed), so values are stored byte-exact from the browser onward, and a direct-API write with `\r` inside is stored and installed as the bytes the user sent — byte-fidelity is the promise, not a guess. No CR-refusal, no trim, no trailing-newline management: kubeconfig consumers take it either way, and smelt adding bytes the user didn't paste is its own bug class.
- **No integrity recheck or repair of stored values.** No migration can tell a deliberately one-line token from a flattened YAML file; the existing flattened `deploy_kubeconfig` stays until the user re-pastes it (Hands-on step 4, which is also the ticket's acceptance).
- **No reveal control.** D7 stays: `shown`'s arithmetic is unchanged, the value still never leaves the database, and the page stays write-only. `lines` is a structural count in the same read-time-computed family, never a partial value.
- **Not the git keys, `git-ssh`, or `SecretName`s**: keys are already a textarea (the fix's precedent); names are file names, CHECKed.
- **Not the ticket's "job pages always verify by USE" item** (SME-242's pre-flight note): `deploy_kubeconfig` already has its use-check at its only consumer — the deployer's standing `kubectl auth whoami` gate in `DEPLOY.md` setup (SME-326). Generalizing verify-by-USE across credential-holding job pages is a process call for the Project Manager — a candidate follow-up ticket, not this diff.

## How — shape

The Add form's value control:

```rust
textarea {
    id: "secret-value",
    class: "secret-value-input",
    required: true,
    rows: 8,
    spellcheck: "false",
    placeholder: "Paste the whole credential — multi-line stays multi-line.",
    value: "{value}",
    oninput: move |e| { value.set(e.value()); action_error.set(None); },
}
```

The Change control is the same shape (`rows: 4`, class `secret-change-input`, placeholder "new value"). Dioxus `oninput` reads `element.value`, and for a textarea that value keeps newlines (probed); the signal → JSON → `save_secret` path is untouched code. The page's copy (the intro paragraph, "Values are never shown again after you add one") stays true; `lines` is not a showing of the value.

`line_count` is `str::lines().count()`: `"a"` → 1, `"a\n"` → 1 (a trailing newline is not a phantom 48th line on a 47-line kubeconfig), `"a\n\nb"` → 3, `"\n"` → 1. Singular/plural: `1 line`, `N lines` — pinned by the page test.

**State model:** no new state, no new transitions. The page remains the *only* writer of `named_secrets` (SME-242 D7); every reader is unchanged — install (`pod_files` → `install_pod_files`, byte-faithful at head and proven live), Rule S and `list_personas` (names only), display (reads `value` to compute `shown` + `lines`, writes nothing back). Multi-line values ride the existing writer transition (add/change → live-pod install) with the existing partial-failure semantics — per-file atomic write, install lock — and the newline-ness of a value interacts with none of them. No pod-restart question changes: secret files are installed per save and re-installed on pod start exactly as SME-242 shipped.

## How it will be checked by hand

On a scratch database (`CHECK_SCRATCH_DB=1 scripts/check-server start`, branch ref — SME-115's fix is an ancestor here):

1. `/secrets` → paste a 6-line YAML block into the Value box → **Add**: the box showed it multi-line the whole time; the row reads `… (N bytes) · 6 lines` for the exact N; the box clears; the page body holds none of the value.
2. **Change** it to a 10-line block → the row says `10 lines`. Then paste the same block from a Windows-terminated source (CRLF): still `10 lines` — LF-normalized in the browser, one byte per line break fewer than pasted, which is the documented browser rule, not smelt's.
3. Under a persona that lists the secret (SME-242's `creds-secret` pattern): `wc -l /etc/smelt/secrets/<name>` and `sha256sum` it — equal to the pasted (LF-normalized) bytes. Verify-by-use without kubectl.
4. **The acceptance bar (user + first deployer seat; post-merge):** re-paste the real `deploy_kubeconfig` YAML on `/secrets` — the row must say `~47 lines`, not `1 line` — then run a deployer seat; its `DEPLOY.md` setup step `kubectl auth whoami` against the installed file succeeds **with no local reconstruction** (contrast SME-326's first run, which needed one). Until step 4 happens, the stored flat value stays flat and the next deployer run still fails — record that on the ticket at merge so nobody reads "merged" as "the credential is fixed".

## Trade-offs to flag

- **The value is visible in the box while typing and pasting.** The `type=password` dots go with the input. D7's promise — never shown *again*, no reveal, value never leaves the database — is untouched: the box starts empty and is never re-filled from the store. The Q1 question exists because that loss, however cosmetic, is a change to the page's stated privacy.
- **CRLF pastes become LF.** Before smelt sees the bytes (browser rule, probed): kubectl- and terraform-safe, and the only way to store a CR byte is a direct API call, which then installs as sent. Chosen over smelt-side rejection because rejecting what the browser already rewrote protects nothing.
- **The line count is one more derived disclosure.** Bounded like `shown`'s exact byte length already is (SME-242 Trade-off 9): a count of line breaks reveals structure class ("token" vs "YAML file"), never value bytes, and never more than prefix + length already do.
- **The stored flattened `deploy_kubeconfig` is not repaired by this ticket** — only made fixable visibly. Until the user re-pastes it, deployer runs still die on it; the row's `1 line` now says so at a glance.
