## Storage map: what the claims actually hold (traced evidence, per the PM's note)

From `build_pod_spec` (`src/sandbox/spec.rs:562–699`) and `start-dockerd.sh` at this head:

- **`sandbox-workspace-<id>` claim → mounted at `/workspace` in both containers**
  (`workspace_volume`, spec.rs:732). Holds repos, source, Rust `target/` directories. This
  is the confirmed 18–31 GB bulk the clean-up passes saw. Removing the claim frees it.
- **`sandbox-docker-<id>` claim → mounted at `/var/lib/docker` in the Docker sidecar only**
  (`docker_data_volume`, spec.rs:747; `mount(DOCKER_DATA_VOLUME, "/var/lib/docker")`,
  spec.rs:583). `start-dockerd.sh` execs dockerd with **no `--data-root` override** (last
  line), so dockerd's default data-root is that claim: top-level dind images, build cache,
  **compose named volumes** (a compose project run inside a seat stores its named volumes —
  `docker-data`, `k3s-data`, `postgres-data`, … — under `/var/lib/docker/volumes` of this
  same daemon), nested containers' writable layers and any local-path data all land on the
  claim. Removing the claim frees all of it. Nested containers' bind mounts of `/workspace`
  land on the workspace claim.
- **Ephemeral, freed when the pod ends, never on the claim:** the sandbox container's
  writable layer (its `/home/sandbox`, apt installs, `/tmp`, anything written outside
  `/workspace` and the global volumes — there is no claim for `/home`), the sidecar's own
  root, and the `docker-sock` emptyDir (spec.rs:572). None of this is freed by claim
  removal; none needs to be — a *stopped* conversation has already lost it.
- Global `sandbox_volumes` claims (`sandbox-volume-<id>`) and 239's `agent-volume-<id>`
  claims are separate objects; this ticket never removes them.

The observed inconsistency (four Developer seats finding compose named volumes on the claim
vs the Reviewer seat's recreated pod with an empty daemon) is **not** explainable by how the
pod died or when the conversation was created: the pod spec is identical either way
(`restart_policy: Never`, no controller; a crash fully terminates the pod, SME-12), and
every conversation pod since SME-32/33 mounts both claims. An empty `/var/lib/docker` on
recreate means the docker claim itself was absent or replaced between the two pods — a
host-side/local-path deletion (the disk panic that day had the user doing host-side `du`
over the storage dirs; a `kubectl delete pvc` does exactly this), or an older
`docker compose down -v` run against that same daemon cleared the named volumes while
leaving images. Nothing in this design changes either way: removal deletes both claims by
name with the SME-115 guard, and whatever is on them is gone. This also bounds what the
confirmation copy may promise: claim removal frees the node's local-path storage, not the
pod-layer space (already free for stopped conversations) — see Trade-offs.

## State model

There is **no database row for a claim** and this plan adds none. Claims are cluster objects
labelled `smelt/conversation=<id>` + `smelt/instance=<uuid>` (spec.rs:352/358,
`build_conversation_pvc_spec`); the DB says nothing different about a conversation whose
claims are gone — its `conversations` row is untouched, `sandbox_pods` rows only ever track
pods, and the one DB write removal makes is marking that conversation's `ready`
`conversation_repos` rows `failed` (the checkouts are gone; new
`db::fail_repos_after_storage_removal`, `src/db/repos.rs`; `cloning` rows are left, they're
already failed by the normal crash paths). State is **derived at read time** from two facts:
the claim objects (per name) and the live-pod row.

Per-claim states (both claims share them; they can differ transiently if a delete fails
halfway):

| State | What it means | What moves it |
|---|---|---|
| none | no PVC of that name | first `create_pod` after removal: `ensure_conversation_pvcs` creates it (`claims.rs:311`) |
| held | claim exists, conversation has a live pod (or an LSP pod) mounting it | pod created / `create_pod`; leaving held: pod Stop, crash-cleanup, removal |
| free | claim exists, no pod of the conversation | a Stop; a removal that's been requested while still Terminating |
| removing | claim exists with `metadata.deletion_timestamp` set (pvc-protection holds it until no pod mounts it) | accepted delete; ends when the last mounting pod is gone |

Writers of the two claims (every path):

| Writer | Effect |
|---|---|
| `create_pod_attempt` (`manager/create.rs:264`) via `ensure_conversation_pvcs` | create-if-missing; **new guard: a Terminating claim is waited out, then re-created fresh, never adopted** (see The reuse guard) |
| `teardown_conversation_with` (`manager/teardown.rs:60`) → `delete_conversation_pvcs` | conversation delete: pods first, then both claims, best-effort, ownership-guarded |
| `sweep_orphaned_conversation_claims` (`main.rs`, startup) | claims whose conversation isn't in this DB (own instance label only) |
| **new** `sandbox::remove_conversation_storage` (`manager/storage.rs`) | this ticket: stop pods (incl. LSP), wait, delete both named claims |
| pre-SME-115 adoption paths (`ensure_conversation_claim`'s Unlabelled arm; `adopt.rs`) | only for unlabelled claims, only for `owns_unlabelled` databases; removal never adopts |

Readers: the new `/api/storage` list and the panel (both instance-labelled list only),
`wait_for_conversation_pods_gone` (pods, not claims), the sweep listing, and — new —
`ensure_conversation_pvcs` reading the claim's `deletion_timestamp` before reusing.
Language-server pods mount the workspace claim (`src/lsp/pods.rs:97–106`
`"claimName": workspace_pvc_name(...)`), so LSP pods are *holders* of held state:
removal must take them out first.

Per-caller table (states × what each caller does):

| Caller | none | free | held | removing |
|---|---|---|---|---|
| `create_pod` | creates both | reuses both | refused (`PodAlreadyExists`) | **new:** waits ≤ 20 s for each Terminating claim to go, then creates; else `Timeout` "sandbox storage is still being removed; try again" |
| `remove_conversation_storage` | no-op, reports "nothing stored" | delete both | stop pod + LSP pods, wait pods gone, delete both | leave (already deleting), report `removing` |
| conversation delete (`teardown`) | — | delete | deletes pods+LSP then claims (unchanged) | skips already-deleting (`claims.rs:372`) |
| startup sweep | — | deletes only if conversation gone from DB | same | skips deleting (`claims.rs:30`) |
| `lsp::pods::start_with` | can't happen (pod live ⇒ claim exists) | n/a (no live sandbox pod) | mounts (unchanged) | can't happen: removal deletes LSP pods before the claims, and LSP start refuses without a live sandbox pod |
| panel / `/pods` storage list | "no stored volumes" | row + Remove | row (Remove notes it stops the pod first) | row marked "removing…" |
| the model's tools | — | — | `create_pod`/`terminate_pod` unchanged; no new tool | next `create_pod` gets the wait |

Races (each: what breaks it, what converges):

- **remove vs `create_pod` in flight** (no shared lock; `pod_start_lock` guards starts only):
  removal closes the pod row via `force_terminate_pod` mid-start; the start's existing
  B1/B5 checks (`create.rs:286,293`: record no longer live / conversation gone) delete the
  pod it just made and fail with `stopped_while_starting` (existing, SME-122). The claim
  delete then finds the pods gone (removal waited) or the claim Terminating behind the
  start's pod, which that pod's deletion frees. Nothing shares a dying claim with a live
  pod. No new test (timing-heavy); the lifecycle tests below pin the surrounding pieces.
- **remove vs conversation delete**: both end in the same guarded deletes; uid preconditions
  (`delete_claim_if_unchanged`, `claims.rs:103`) and already-deleting skips make repeats
  no-ops. A conversation deleted between the existence check and the claim list: removal
  deletes claims for a dead conversation — exactly what its teardown would do; safe.
- **remove vs remove** (two tabs / double click): second sees the claims gone or Terminating
  and reports it; no claim is deleted twice against a fresh same-name claim because each
  delete is held to the uid read at list time.
- **fresh `create_pod` immediately after a removal** (the done-when case): covered by the
  reuse guard + the bounded wait — see The reuse guard; lifecycle test 4 pins it.
- **create while the claim is Terminating but its holder pod is an LSP pod removal deleted**:
  LSP pods are waited out by the same extended wait.

Failure partway (each step's failure and the state it leaves):

| Failure | State left | Recovery |
|---|---|---|
| pod terminate fails (kube error) | nothing removed | error surfaces; claims still listed |
| pods not gone in 30 s (`STORAGE_REMOVAL_POD_WAIT`, > `POD_DELETE_GRACE_SECS` 20 s) | pod row already closed (terminate first), claims intact | error "…still stopping, try again"; a retry deletes the claims (pods already terminated in the DB sense, wait re-checks) |
| claim A deleted, claim B's delete fails | A gone, B free or Terminating | result counts it (`claims_failed`), UI refetch shows B and the user hits Remove again; the sweep will *not* catch it (conversation alive) — that's why the count is returned, not just logged |
| repos marking fails (DB) | claims already gone | logged, not returned; panel repo rows stale until the next repos refresh — a display lag with nothing on disk depending on it |
| model notice / event publish fails | all cluster work done | turn::notify is best-effort by design; PodsChanged listeners refetch on their next event |

## The deletion path: `sandbox::remove_conversation_storage` (new `src/sandbox/manager/storage.rs`)

```
pub async fn remove_conversation_storage(pool, conversation_id) -> Result<StorageRemoval, SandboxError>
pub struct StorageRemoval { pub pod_stopped: bool, pub lsp_pods_stopped: u8,
                           pub claims_deleted: u8, pub claims_failed: u8 }
```

Steps, each with the SME-115 guard and an SME-117-style info log line:

1. `db::conversation_exists` — gone: return a zero `StorageRemoval` Ok (its teardown owns
   the claims now; a panel mid-delete shouldn't error).
2. Read `db::smelt_instance`; failure aborts with a logged warning (teardown's posture).
3. Live pod row (`db::list_sandbox_pods`): `close_pod_terminals` (watch.rs:260, the same
   un-noticed mechanics `stop_pod_for_user` uses) then `force_terminate_pod`
   (terminate.rs:50) — this publishes `SandboxPodUpdate{terminated}` and `PodsChanged`
   itself. Deliberately **not** `stop_pod_for_user`: its "user stopped pod" notice would
   double with the removal notice.
4. Delete the conversation's language-server pods: the same label-selector best-effort
   delete teardown uses (`delete_listed`, teardown.rs:93, with
   `LSP_OF_LABEL=<id>,INSTANCE_LABEL=<id>`); their stdio connections drop and restart
   lazily, as they already do when teardown deletes them.
5. Wait for the conversation's pods to be gone — extend `wait_for_conversation_pods_gone`
   (claims.rs:276) with an `extra_labels` parameter (create passes `[]`, removal passes
   `[LSP_OF_LABEL]`; the existing ours + `!instance` selector pair applies to each label).
   Timeout 30 s → `Timeout` error as in the table above.
6. Delete the two claims **by name** (`docker_pvc_name`, `workspace_pvc_name`) — never by
   label selector, so 239's `agent-volume-*` and the global `sandbox-volume-*` claims can
   never be caught even if labels change later. New helper `remove_conversation_claim` in
   `claims.rs` beside `delete_conversation_pvcs` (same match arms: ours+uid →
   `delete_claim_if_unchanged`; Unlabelled → leave + warn + count as failed; Foreign →
   leave + info; already-deleting → count as already-gone). Returns the counts.
7. Best-effort confirm both names read `None` within a few seconds (bounded `get_opt`
   poll) — this is what makes the panel's post-remove refetch land on "none" instead of
   "removing…" and what makes the very next `create_pod` usually skip the guard's wait;
   the guard covers whoever still lands in the window.
8. `db::fail_repos_after_storage_removal(pool, conversation_id)`:
   `UPDATE conversation_repos SET status='failed', error=$2 WHERE conversation_id=$1 AND
   status='ready'` with a "the sandbox storage was deleted; clone again" error (panel shows
   Clone failed, `clone_repo`'s retry path works). RETURNING count, logged.
9. If a pod was stopped: `turn::notify` with `Notice::Save` (the model learns next turn,
   like a user Stop): "The user removed this conversation's sandbox storage: /workspace and
   the Docker images, build cache and volumes are gone. Repos there need cloning again; the
   next sandbox starts with fresh empty volumes." If no pod: no notice (nothing running
   experienced it).
10. `events::publish_app(AppEvent::PodsChanged)` in every non-empty case — reuse it rather
    than add an `AppEvent` variant: an unknown variant would trip `STALE_BUNDLE` in every
    older tab's stream loop (`frontend/pages/pods.rs:28`). Update `PodsChanged`'s doc
    comment (events/mod.rs:225) to say it also covers stored-volume changes.

## The reuse guard in `claims.rs`

`ensure_conversation_claim` (claims.rs:328) currently returns Ok for any existing
`Ownership::Ours` claim, **including one with `deletion_timestamp` set** — which before
this ticket was unobservable (only teardown/sweep delete claims, and then no
create follows for that conversation). After this ticket, a `create_pod` racing a removal
would mount a doomed claim: the pod starts, the finalizer releases the moment its holder
pods are gone, the PV (local-path, retain=Delete) goes, and the live pod's `/workspace`
falls out from under it. Fix (the one claims.rs mid-function edit): in the `Some(existing)`
path, if `existing.metadata.deletion_timestamp.is_some()`, poll `get_opt` every 500 ms up
to `TERMINATING_CLAIM_WAIT = 20 s` for it to vanish, then create the fresh spec (loop back);
if it lingers, `SandboxError::Timeout(Some("this conversation's sandbox storage is still
being removed; try again"))`. (The create path already waited for the conversation's pods
before this, so normally only finalizer/detach latency remains — seconds.)

## API (extend `src/api/pods.rs`, no new module; 239 never touches this file)

- `#[get("/api/storage")] get_stored_storage() -> Vec<StoredStorage>`:
  one PVC list with selector `smelt/conversation,smelt/instance=<this>` (exactly the
  sweep's selector — instance-scoped, so a check server's list can never show or act on
  production's claims and vice versa), grouped per conversation-label value, names filtered
  to the two `sandbox-` prefixes (belt after the label guard), titles from
  `db::list_conversations`, conversations without a DB row dropped.
  `StoredStorage { conversation_id, conversation_title, volumes: Vec<StoredVolume> }`,
  `StoredVolume { kind: workspace|docker, size: Option<String>, deleting: bool }`, `size`
  = `status.capacity["storage"]` falling back to `spec.resources.requests.storage`
  (local-path: equal to the request, "20Gi"). A pure `storage_rows(claims, &titles)`
  helper carries the grouping/kind/size logic so it's unit-testable without a cluster.
- `#[post("/api/storage/{conversation_id}/remove")] remove_stored_storage(conversation_id)
  -> StorageRemoval` — calls the manager fn, maps `SandboxError` via
  `e.to_string()` like `stop_pod`.

## Size-display decision

Show, per claim: **presence + requested/bound size from the PVC object** (`status.capacity`
else `spec.resources.requests.storage` — cheap: the one instance-labelled list per page
refresh and per panel load; this is what's cheap enough to poll at the page's existing
30 s/PodsChanged cadence). Deliberately **not** measured usage this ticket:

- PVC capacity under local-path is the *request* (20Gi), not usage — it must be labelled as
  the claim size, never "used".
- `du` inside the pod reports real usage but needs a running pod — and the conversations
  that hold the disk are the *stopped* ones (the occurrence data: users stop seats
  deliberately). Measuring a stopped claim means starting a short-lived helper pod that
  mounts it (precedent: the image-import helper pod) — real new machinery: naming,
  timeout, cleanup, RBAC-free but UI-visible latency.
- No cluster API reports per-PVC usage: metrics-server is CPU/memory, kubelet stats only
  cover running pods' ephemeral storage.

The ticket's own wording ("or at least that one exists") and its Done-when (which names no
size) support shipping presence+capacity now; measured bytes go in a follow-up ticket
(the helper-pod `du` described above, paired naturally with SME-229's node-level warning).

## How to check by hand (after merge, user/dev steps)

On the deployed smelt: open a finished seat conversation → panel shows "Sandbox storage:
/workspace 20Gi · Docker images 20Gi" → Remove volumes (confirm) → the line goes, `/pods`
Stored volumes drops the row, node `du` of the local-path storage falls by the
conversation's GBs. Ask the model for a sandbox there: it starts, `ls /workspace` empty,
`docker images` empty; the first gate rebuilds the compose images (this is the docker
claim's cost — expect minutes). With a live pod: Remove first stops it (transcript shows
the notice) then deletes. A language-server next to the pod (edit a Rust file first) is
gone after a Remove and comes back on the next edit.

## Trade-offs to flag

- Removing frees only what sits on the claims. The sandbox container's own writable layer
  (apt installs, `~`, `/tmp`) was already gone when the pod stopped, and the node's
  containerd image store (the 87% panic's other half) is SME-229/cluster-doctor's story;
  the confirmation copy says what is lost, not "this frees N GB".
- Deleting the Docker claim costs the next gate's image rebuild (compose dev image, k3s
  image pulls, nested sandbox-image build) — minutes, not free. One control for both
  claims keeps the UI honest about what's lost; separate controls would let a user keep
  images while clearing `target/`, at the cost of a second button + copy on two surfaces.
- A pre-SME-115 **unlabelled** claim of the same name is left (never ours to delete) and
  counted as failed in the result — but if this database `owns_unlabelled`, the next
  `create_pod` adopts it (existing SME-115 behaviour), so the "fresh empty volumes" promise
  is really "fresh unless an unlabelled pre-fix claim was here"; in practice the deployed
  databases adopted theirs at the fix. Logged and returned, not silent.
- Removal doesn't take `pod_start_lock`; a start racing it converges through the existing
  SME-122 checks and reports "the sandbox was stopped while it was starting".
- LSP pods get stopped as collateral (they mount the claim); their lazy restart already
  exists for teardown.
