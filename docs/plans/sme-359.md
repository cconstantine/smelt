# SME-359 plan: a script in the sandbox can call the conversation's MCP tools

**Branch:** `sme-359-mcp-from-scripts`, worktree `/home/dev/wt/sme-359` (from `origin/main` at `6d2831d`).

The Questions for the user and the Trade-offs to flag are in the ticket, not here. The design below assumes the recommended answer to each question; each section says where an answer would change it.

## What and why

The user (2026-11-03): let a script the model writes call the conversation's MCP tools, so a batch of calls, or a call whose result only feeds the next one, costs no model turns. The model reads the script's output once.

What ships:

- A local endpoint in every sandbox pod: HTTP over a **Unix socket**, `$SMELT_MCP_SOCKET` (`/run/smelt/mcp.sock`). It has two routes, list the tools and call one.
- `smelt-mcp`, a small curl wrapper in the image: `smelt-mcp tools`, and `smelt-mcp call linear/list_issues '{"query":"…"}'`. Results come back as JSON on stdout.
- The sandbox agent forwards each request **up the WebSocket smelt already holds to that pod**. smelt runs the call in-process, through the same rule chain and `mcp::call_tool_classed` a model call uses, and sends the result back down the same socket.

## The six items to settle

### 1. Transport: the agent's WebSocket, reversed (chosen)

| Option | Verdict |
| -- | -- |
| **A. Request/response over the existing agent WebSocket. The agent serves a Unix socket in the pod.** | **Chosen.** |
| B. An HTTP endpoint smelt serves, which the pod dials | Rejected. The pod would need a network path to smelt, which [tool-rules.md#egress](../design/personas/tool-rules.md#egress) ("Never smelt", SME-243) says a ruled pod must not have. Every pod can reach smelt's public URL today only because of a gap. It would also need a bearer token in the pod (item 3). |
| C. A local MCP proxy in the pod speaking MCP to scripts | Rejected. Scripts would need an MCP client library, where curl or `json` is enough. It also still needs option A's channel to reach smelt. |
| D. A CLI only, with no socket | Rejected. Python and other scripts would have to spawn a process per call. The CLI ships anyway, as a thin wrapper over A. |

Option A needs no new network path. smelt dials the agent through a Kubernetes port-forward (`sandbox::agent::connect`), so the pod never reaches smelt. A Unix socket can't be reached by a port-forward, a preview or `webfetch`'s `localhost` route at all. So unlike a new TCP port it needs no entry in `ports::check_reachable_port`, which today refuses 8088 and 8089 because those routes could otherwise drive them. Docker containers in the pod don't see it (item 6, Trade-offs).

A comparable design, checked in source: Cloudflare's Code Mode (`cloudflare/agents`, `packages/codemode/README.md`). Its sandboxed code calls tools through bindings that "route them back via Workers RPC" to host-side connectors. Credentials stay host-side (the Stripe example reads `env.STRIPE_KEY` in the host's `request()`). External `fetch()` is blocked (`globalOutbound: null`). Legacy `createCodeTool` *excludes* tools marked `needsApproval` from code, which is the precedent for Question 1's ceiling.

**Wire protocol, minor bump to 1.1** (`src/agent_protocol.rs`). An addition the other end can ignore: smelt's `AgentMessage::Unknown` already swallows unknown events, and only a 1.1 agent ever sends one.

```rust
// agent → smelt
AgentMessage::McpRequest { call_id: u64, command_id: Option<String>, request: McpRequest }
#[serde(tag = "kind", rename_all = "snake_case")]
enum McpRequest { List, Call { tool: String, arguments: String /* raw JSON text */ } }
// smelt → agent
ClientMessage::McpResponse { call_id: u64, status: u16, body: String /* JSON text */ }
```

- **The agent doesn't parse the arguments or the results.** smelt picks the HTTP status and builds the body, and the agent writes both out as they come. That keeps the agent (and `serde_json` in the shared file) out of the semantics.
- **`call_id`s are the agent's own**, a counter per agent process, never reused. A late `McpResponse` for an id that's no longer waiting is dropped.
- `src/fixtures/agent_protocol_v1.jsonl` gains one line per new message. The fixture test pins the existing lines byte for byte.

**The socket's HTTP API** (axum over `tokio::net::UnixListener`; axum 0.8.9 has `impl Listener for UnixListener`, `src/serve/listener.rs:46`):

| Request | Answer |
| -- | -- |
| `GET /v1/tools` | `200 {"tools":[{"name":"linear/list_issues","server":"linear","tool":"list_issues","class":"read-only","description":…,"input_schema":{…}}]}`: only what this conversation's scripts may call (item 4) |
| `POST /v1/call` `{"tool":"<server>/<tool>","arguments":{…}}` | `200 {"content":[…MCP content blocks as sent…],"structured_content":…|null,"text":"<the text blocks joined>"}` |
| the tool's own `is_error` | `422`, same shape, plus `"is_error":true` |
| a bad request (not JSON, no `tool`, arguments not an object, an unknown server or tool) | `400 {"error":…}` / `404 {"error":…}` |
| refused by a rule or the ceiling | `403 {"error":"<the rule's text>"}` |
| over a limit (item 6) | `429 {"error":…}` with `Retry-After` |
| smelt not connected, or disconnected mid-call | `503 {"error":…,"outcome":"unknown"}`. A call in flight may already have reached the server. |
| smelt's call failed (connect, transport, timeout) | `502 {"error":…}` |

- **The tool name accepts both `<server>/<tool>`** (the tool-rule grammar's name, by the configured server name and the listed tool name) **and the model's `mcp__<server>__<tool>`**, resolved through `mcp::resolve_tool`. A model will often paste the name it sees.
- **Result data isn't cut to `MAX_TOOL_RESULT_CHARS`**: that cap is for the model's context, and not reading every result is the point. It is bounded at **8 MiB** of serialized body instead, a 502 beyond that. tungstenite's and axum's default WebSocket message caps are 64 MiB. A request body is bounded at 1 MiB.
- `structured_content` is MCP's `structuredContent` (rmcp 3.1.2 `CallToolResult::structured_content`), which is exactly what a script wants when the server sends it.

**`smelt-mcp`** (`docker/sandbox/smelt-mcp`, a POSIX `sh` script of about 30 lines over `curl --unix-socket "$SMELT_MCP_SOCKET" --fail-with-body`; curl is already in the image):

- `smelt-mcp tools [server]`.
- `smelt-mcp call <tool> [<json>|-]`: arguments from the argument or from stdin.
- Exit 0 for a 2xx; 1 for a tool error (422); 2 for a refusal or limit (403/429); 3 for anything else. The body always goes to stdout.

### 2. Credentials never enter the pod

- **Nothing new is written into the pod.** The channel carries tool names, arguments and results only. Headers, OAuth grants and client secrets stay in smelt's process (`REGISTRY`, `OAUTH_CLIENTS`, `PgCredentialStore`), exactly as for the model's calls. `credentials::for_conversation` is untouched, and so is the pod spec's environment, except `SMELT_MCP_SOCKET`, set by the agent on each terminal's `bash` (`shell.rs::spawn_shell`), a path.
- **Error text is the one way a credential could leak.** An error string from smelt's call path could quote the server's URL (a static-header server whose key sits in its query, e.g. `…?exaApiKey=`), or a header value. Every error source that reaches the new sink (the pod), and what each can quote:

| Source | Can quote |
| -- | -- |
| `ensure_connected`'s connect error (`ConnectError.message`, reqwest/rmcp) | the server URL with its query |
| a transport `ServiceError` in `call_tool_unspanned` (`format!("…failed: {e}")`) | the URL; the server's reply body |
| `CALL_TIMEOUT`'s message | server and tool names only |
| the class-override read error | Postgres's text |
| the rule refusal (`allows_at`) | the rule text, the tool name |
| the tool's own `is_error` content | the tool's output: the result itself, not a credential |

- **The fix, `mcp::redact_secrets(config, text)`**, applied in `call_tool_unspanned`'s error mapping. It replaces the server URL's query string, every `extra_headers` value and any OAuth access or refresh token text in the stored grant with `<redacted>`, so **both** paths gain it: the model's calls too, since anything the model sees it can write into the pod. Tests put a marker into each source (item: Test plan T9).
- **Pre-existing, unchanged:** the namespace's service-account token is mounted in every pod (SME-63). Named secrets and `git-ssh` follow SME-242's rules.

### 3. Per-pod authentication

**No token. The channel is the identity.** A request arrives on the WebSocket smelt itself dialed to one pod, `pod_name(pod_id)`, through `refuse_foreign`'s ownership check (SME-180). Its conversation is the `TerminalConnection.conversation_id` resolved at connect from `sandbox_pods`.

- **The message carries no conversation or pod id**, so a pod can't name another.
- **Pod B's processes can't reach pod A's socket**: different pods, different filesystems.
- **Pod B's agent can't reach pod A's WebSocket**: smelt dials out, and the agent listens on loopback only.
- `TerminalConnection` gains `pod_id` (today it's only in the connect closure), so the handler can also check the pod is still the conversation's live pod (item: state model, check 1).

**Inside the pod**, the socket is `0600`, owned by `sandbox` (the agent's user), in `/run/smelt` (`0700`, made in the Dockerfile). So any process running as `sandbox` can call, and `sudo` too. That is every process the model runs, untrusted code it fetched included: an npm `postinstall` from a cloned repo can call the same tools. Items 4 and 6 and Question 1 bound what that code can do, and the Trade-offs name it.

### 4. The same rule chain a model call goes through, plus one ceiling

A script call goes through one new function, `anthropic::tools::execute_mcp_for_script(pool, conversation_id, tool, arguments)`, in `src/anthropic/tools/mod.rs`'s `server` module, so it shares `call_rule_chain` with `execute`:

1. **Resolve** `<server>/<tool>` (or `mcp__…`) to a configured server. A deleted server is a 404. There's no per-server "enabled" flag in this codebase: a configured server is an offered one, so "per-server enablement" is the chain's `<server>/*` patterns.
2. **Read the chain strictly**: `call_rule_chain`, which fails closed (SME-354 B10). An unreadable chain refuses with the same text as a model call.
3. **`mcp::call_tool_raw`** (C1's split of `call_tool_classed`) checks the class on the connection the call goes out on, with the user's override and the SME-295 fingerprint narrowing. Its `check_class` is `chain.allows_at(ToolRef::Mcp{…}, class)` **and** `script_ceiling().allows(class)`. A refusal names which one: the rule's own text, or "scripts may call up to <ceiling> tools; <tool> is <class>; ask the model to call it".
4. **The script ceiling** (Question 1) is a deployment setting, `SANDBOX_MCP_SCRIPT_CLASS` = `read-only` | `no-destructive` | `all`, default `no-destructive`. It is parsed by the same parser as a persona's `class`. It only narrows: it's one more conjunct after the chain.
5. **`GET /v1/tools`** lists what `tool_definitions_for` offers this conversation (same chain, same `judged_class`), filtered by the ceiling, with the real server and tool names and input schemas. The listing is best-effort like the offer. The call is the check.

**Spans:** the existing `mcp call` span (server, tool, never input or output, SME-137), under a new `script mcp call` span carrying `conversation_id`, `pod_id`, `command_id`, `smelt.tool.class` and the outcome, never the arguments or result.

### 5. What the transcript shows (Question 2)

**No per-call entries in the chat transcript.** A loop of 200 calls would flood it and cost the model a read of each, which is what the feature exists to avoid. Instead:

- **A record per call:** a new table `sandbox_mcp_calls`, which the summaries below read. Columns: `id`, `conversation_id` (FK cascade), `pod_id` (FK → `sandbox_pods` cascade), `command_id` (nullable, FK → `terminal_commands(command_id)` ON DELETE SET NULL), `server`, `tool`, `class` (nullable: refused before the class was known), `outcome` (`running`/`ok`/`tool_error`/`refused`/`limited`/`failed`, `CHECK`ed), `started_at`, `finished_at`. Plus an index `(command_id)` and an index `(conversation_id, started_at)`. **No arguments or results**: the SME-137 rule, and an argument can carry a secret the script read.
- **The sandbox panel's command entry** shows one line under the command: "MCP: 14 calls · linear/list_issues ×12, linear/save_comment ×2 · 1 refused". It comes with the snapshot (`SandboxCommandSummary.mcp_calls: Option<McpCallSummary>`) and updates live through a new `ConversationEvent::SandboxMcpCalls { command_id, summary }`, published after each call finishes, at most every 500 ms per command (trailing edge), so a fast loop doesn't flood the event stream.
- **The model** gets the same line in `terminal_command_status` and at the head of `read_terminal_output`. The completion notice ("Terminal command X finished: exit code N.") is built in `src/turn/notify.rs`, which SME-357 (In Progress) changes, so it doesn't get the line here. That's a follow-up ticket filed at the close-out, once SME-357 merges.
- **Calls with no command** (a process the agent can't trace to a terminal, item 6) are counted per pod and shown on the panel's pod line: "MCP calls outside any command: N".

**Attribution:** the agent reads the caller's pid from `SO_PEERCRED`, through a custom `axum::extract::connect_info::Connected<IncomingStream<UnixListener>>` that calls `stream.io().peer_cred()` (tokio's `UnixStream::peer_cred`, `UCred::pid`). It walks `/proc/<pid>/stat`'s ppid up to a terminal's `bash_pid`, and takes that terminal's `current` command id. The walk stops at pid 1 (the agent itself, the reaper of orphans), or after 64 steps. Found nothing means `command_id: None`.

### 6. Rate and cost limits (Question 3)

A script call costs no model tokens. Its cost is the provider's quota, and for a writing tool, the writes. The limits are enforced on smelt's side, in memory (`src/sandbox/script_mcp/limits.rs`), per conversation:

| Limit | Default | Env | Over it |
| -- | -- | -- | -- |
| rate | 60 calls/min, a burst of 20 (token bucket) | `SANDBOX_MCP_CALLS_PER_MINUTE` (0 = no script calls) | 429, `Retry-After` from the bucket |
| in flight | 4 at once | `SANDBOX_MCP_MAX_IN_FLIGHT` | 429 at once (no queueing, which would hold agent memory and hide the stall) |
| per command | 1,000 calls (counted in `sandbox_mcp_calls`); calls with no command share a per-pod budget of the same size | `SANDBOX_MCP_CALLS_PER_COMMAND` | 429 "this command has made 1,000 MCP calls, its limit (`SANDBOX_MCP_CALLS_PER_COMMAND`)" (no `Retry-After`); a new command starts a new budget, which the model decides on, visibly |

- Each call keeps `CALL_TIMEOUT` (120 s) and the connect's own budgets.
- The agent also bounds its own waiting calls at 16 (a 429 from the agent beyond that) and gives up on a call after **180 s** with a 503 "outcome unknown". That's past `CALL_TIMEOUT` plus `CONNECT_TIMEOUT` plus a margin, so smelt's own timeout normally answers first.
- **Unnoticed is the other half:** the summary line (item 5) makes the count visible to the user and to the model, on the command and while it runs.
- `0` turns script calls off for the deployment, the kill switch. The environment section then omits the `smelt-mcp` line.

## How: the model's view

The system prompt's environment section (`src/turn/history.rs`, under the MCP servers list, only when servers are configured and `SANDBOX_MCP_CALLS_PER_MINUTE` > 0) gains one line:

"- Scripts in your sandbox can call these MCP tools without a model turn: `smelt-mcp tools` lists them, `smelt-mcp call <server>/<tool> '<json args>'` calls one, JSON on stdout (or HTTP on the Unix socket `$SMELT_MCP_SOCKET`, `POST /v1/call`). Your tool rules apply, scripts are capped at <ceiling> tools, and at <N> calls a minute."

The line is static per deployment, so the cached prompt stays stable.

## State model

**Records:**

- **The waiting call in the agent** (`AppState.mcp_waiting: HashMap<call_id, oneshot::Sender<(u16, String)>>`).
- **The smelt-side call task.**
- **The `sandbox_mcp_calls` row.**
- **The rate bucket and in-flight count**, in memory per conversation.
- **The socket file.** `/run/smelt` is in the container's filesystem, so it's gone with the pod. The agent removes a stale socket file before binding (an agent restart in the same container), and a bind failure is logged and leaves the agent serving the WebSocket: script calls fail, terminals don't.

**Pod restart:** nothing survives. In-flight calls die with the connection. Rows stay, marked `running`, and the panel reads a `running` row older than 180 s as **"outcome unknown"**: derived at read, no sweep.

**The agent's waiting call, state × event:**

| State ↓ / event → | request arrives on the socket | `McpResponse` with its id | WebSocket replaced (a newer smelt connection takes over) | WebSocket closes | 180 s pass | script disconnects |
| -- | -- | -- | -- | -- | -- | -- |
| none | no connection → 503 at once; ≥16 waiting → 429; else send `McpRequest`, → waiting | dropped (late or unknown id) | — | — | — | — |
| waiting | (another id) | → answered: write status and body | fail it 503 "outcome unknown", since the reply would come on the old socket | 503 "outcome unknown" | 503 "outcome unknown"; a later response is dropped | the waiter is removed; a later response is dropped. smelt can't be told to stop a call in flight, so the call finishes and is recorded. |
| answered | — | a repeat is dropped | — | — | — | — |

A send that fails after the waiter is registered (the socket's writer is gone) removes the waiter and answers 503 "outcome unknown" (it may have been queued).

**The smelt side, per `McpRequest`.** The reader loop (`handle_agent_message`) never waits on a call: it spawns a task.

1. **Check 1, the pod and the conversation.** The pod is the conversation's live pod (`sandbox_pods` status), and the conversation isn't `deleting_at`. Otherwise 503 "this sandbox is being stopped".
2. **Check 2, the agent's state.** A conversation that's an agent must be `active`. `finished`/`stopped`/`failed` → 403 "this agent has finished". `starting` can't run commands.
3. **The limits**, taken.
4. **Insert the row** (`running`).
5. **Execute** (item 4).
6. **Finish the row**, release the limits, publish the summary event (debounced), send the `McpResponse` on **the connection it came on** (`conn.send`). A send to a closed connection is dropped silently; the agent already answered 503.

**What can change between a check and the act, and who changes it:**

- **Check 1 → act:** the user stops the pod, the idle stop fires, or the conversation is deleted. The call already sent finishes (≤ `CALL_TIMEOUT`), the same as a model call in flight. The row's update then finds no row (deleted with its conversation) or a pod row now stopped. The update is by `id`: one that matches nothing is ignored, logged at debug.
- **Check 2 → act:** `stop_agent` or `finish` lands. The call goes on (≤ 120 s). The next call is refused. That window is the call's own duration. Written in Trade-offs.
- **The chain:** written twice and never again (create, complete), so nothing changes it mid-call.
- **The class override:** read at the call (SME-240), the same as a model call.
- **A server edit or delete mid-call:** `evict` semantics, unchanged: "settings changed while connecting" once, or the call on the old connection finishes.

**Every writer of `sandbox_mcp_calls`:** the insert (step 4), the finish (step 6), and the cascades (conversation delete; pod row delete; command delete → `command_id` NULL). A refusal before the row (an unknown server, a malformed request) writes no row and isn't counted. A refusal by a limit writes a `limited` row without taking a slot. A refusal by a rule writes a `refused` row. Readers: the panel snapshot, the event's summary, the two model tools, and the per-command budget's count. The count runs at step 3 before the insert, so two concurrent calls can both pass at 999: the in-flight cap (4) bounds the overshoot to 3. Written in Trade-offs.

**What each caller does in each state of the pod's connection:**

| Connection state | script call | model's own tool call |
| -- | -- | -- |
| connected | goes | goes |
| not connected yet (smelt just restarted) | 503 at once, "smelt isn't connected to this sandbox right now; it reconnects when the model next uses the sandbox". With Question 4's yes: smelt reconnects every live pod at startup, so the window is the restart itself. | reconnects (`reconnect_if_needed`) |
| connect in progress | 503 at once (the agent has no socket to send on) | waits for the connect |
| smelt older than the agent (a rollback): the 1.0 smelt ignores `mcp_request` as `Unknown` | the agent's 180 s bound answers 503 "outcome unknown" (nothing was sent) | as today |
| agent outdated (1.0 image) | there's no socket: `smelt-mcp` says `$SMELT_MCP_SOCKET` is unset (the 1.0 agent sets nothing), so the model is told to restart the pod | `AgentOutdated` as today |

**Rows for work already in flight:**

- **`SANDBOX_MCP_*` read at startup:** a change takes a restart, and calls in flight keep what they started with.
- **The ceiling:** read per call from the parsed setting.

## Test plan

Each test is seen red first; "expected:" lines are predictions. Server tests are `#[sqlx::test]` and run through `scripts/cluster-test`. The smelt-side tests drive a fake agent connection (`agent_connection_tests`' `test_dialers`, an in-memory `AgentIo`) sending `McpRequest` text, with `MockMcpServer` registered in `REGISTRY` (as `mcp::tests::classes` does) and `gated_http` for in-flight tests.

**smelt side (`src/sandbox/script_mcp/tests.rs`):**

- **T1, an allowed call.** It returns 200 with the content blocks, `structured_content` and `text`. A 40,000-character result comes back whole: not capped at 30,000 (expected red: no handler, so no reply; then a 30,000-character cut if it went through `execute`).
- **T2, the chain denies by name** (`deny: [mock/echo]`) **a read-only tool.** → 403 naming the rule, and the mock server never received `tools/call`. Needs the chain part; passes with only the ceiling in? No: echo is read-only, so the ceiling allows it. Bites.
