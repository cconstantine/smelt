# SME-286: a tool call written as text gets a correction, not a silent end

**Branch:** `sme-286-unparsed-tool-call` (worktree `~/smelt-worktrees/smelt-sme-286`, from `origin/main` `b151495`)

## What and why

When a reply's text holds a tool call the provider didn't parse, smelt saves it as ordinary text. If the reply made no real call, the turn ends with no error. If it made one, the real call runs and the written one is dropped without a word. The model then believes the call ran. This change:

1. Detects tool-call markup in a reply's text blocks, outside code, for each form the chat templates produce (below), and reads the tool's name where it can.
2. Saves a **correction notice** (a user-role message, like the cut-off notice) that says the call didn't run, whether its name is offered, and which offered tools have similar names. The turn carries on.
3. Bounds it: after 3 corrections in a row, the 4th such reply ends the turn with a visible error.
4. Also nudges once after a reply with **no text and no tool call** (thinking only, or empty), the case in conversation 2294639357.
5. Shows both notices in the transcript as notice lines.

### What the providers do with an unparsed call (checked in source)

- **llama.cpp** (`common/chat-auto-parser-generator.cpp`, `common/chat.cpp`; identical at the deployed `31288c9c6` and at master, checked by diff). With tools offered and `tool_choice` auto, it builds a lazy grammar triggered by the format's start marker (`data.grammar_triggers = {{WORD, trigger_marker}}`, `grammar_lazy`). Each call's name is `p.literal(name)` over the offered tools only. So once the marker is out, the model can't write an unknown name. A final parse that fails throws ("The model produced output that does not match the expected … format", `common_chat_peg_parse`), and the request fails. It doesn't come back as text. llama.cpp is therefore unlikely to produce this bug, which is consistent with the evidence coming from `strata`. Older llama.cpp builds (before the PEG parser) fell back to returning the whole output as content. A server built on them, or on a looser parser, does produce it.
- **Ollama** (`model/parsers/qwen3coder.go`, `parseToolCall`) passes an unknown name through as a real tool call; it looks the tool up only to type the parameters. smelt then answers with its existing tool error (`unknown tool: …`, or the MCP server's own refusal). Output that Ollama's XML unmarshal rejects stays text.
- **Anthropic.** Claude's calls are structured `tool_use` blocks, and an unknown name still arrives as a `tool_use`, which gets the existing error. Claude very rarely writes call markup as text: its own `<function_calls>`/`<invoke name=…>` form, sometimes namespaced. Anthropic documents an empty `end_turn` reply ("exactly 2–3 tokens with no content … particularly after tool results") and recommends, as a last resort, "add a continuation prompt in a NEW user message" rather than retrying ([handling stop reasons](https://platform.claude.com/docs/en/api/handling-stop-reasons#empty-responses-with-end_turn)). The same page says "Don't add text blocks after a `tool_result`", which applies to the mixed case (see Trade-offs).
- **Other** (strata, LiteLLM, vLLM, …) can do anything. Hence detection lives in smelt.

## Detection: `src/text_calls.rs` (new, shared by both builds)

`text_calls::find(text: &str) -> Vec<TextCall>`, where `TextCall { name: Option<String> }`, is server-only (`#[cfg(feature = "server")]`, like `crate::mcp`, which `similar` uses; its tests run under `--features server`, as every turn test does). It scans a **text block** only, never thinking: models reason about calls in their thinking. No regex crate; it's hand-scanned.

**Masked first, never matched:** fenced code blocks (a line starting with ```` ``` ```` or `~~~`, up to its closing fence or the end of the text; an unclosed fence runs to the end, as in CommonMark), inline code spans (backtick runs), lines indented 4 or more spaces (indented code), and blockquote lines (`>`).

**Two kinds of marker:**

- **Special-token markers**, which never occur in prose. These count anywhere in an unmasked line, mid-line included: `[TOOL_CALLS]`, `<|tool_calls_section_begin|>`, `<|tool_call_begin|>`, `<｜tool▁calls▁begin｜>`, `<｜tool▁call▁begin｜>`, `<|tool_call>call:`, `<|tool_call_start|>`, and `<|channel|>commentary to=functions.` / ` to=functions.` followed by `<|channel|>`. The name is read where the form has one, and is `None` otherwise.
- **Tag markers**, which can appear in prose. These count only at a line's start (at most 3 spaces of indent), and only with the structure that names a tool. Every tag may carry a namespace prefix ending in `:` or `｜` (`minimax:`, `seed:`, `<｜DSML｜`, Claude's own):
  - `<tool_call>`, then optional whitespace, then `<function=NAME>` (Qwen3-Coder, Qwen3.5, Seed-OSS, Nemotron 3)
  - `<tool_call>`, then optional whitespace, then a JSON object with a string `"name"` (Hermes 2/3, Qwen 2.5/3)
  - `<tool_call>NAME`, then a newline or `<arg_key>` or `</tool_call>` (GLM-4.5/4.6/4.7). NAME must be one token of name characters
  - `<function=NAME>`, then `<parameter=` or `{` (bare Qwen3-Coder; Llama 3.1 / Functionary 3.1)
  - `<function_calls>` or `<minimax:tool_call>`, then optional whitespace, then `<invoke name="NAME">`; or `<invoke name="NAME">` at line start, then `<parameter name=` or `</invoke>` (Claude, MiniMax-M2, DeepSeek V3.2 DSML)

Name characters are `[A-Za-z0-9_.:-]`. Any other character ends the name, and a name of 0 or more than 128 characters is `None`.

**Samples (real artifacts, rules-code.md):** each form's fixture is copied from llama.cpp's `tests/test-chat.cpp` **at `31288c9c6`** (the deployed build), with its line cited in a comment: Qwen3-Coder/Qwen3.5 (`:2173`), Hermes JSON (`:5551`), GLM (`:4406`), MiniMax-M2 (`:5684`), Seed-OSS (`:3469`), Mistral `[TOOL_CALLS]NAME[ARGS]` (`:2629`), DeepSeek V3.1 (`:3936`), Kimi K2 (`:5210`), Gemma 4 (`:3031`), LFM2 (`:2032`), gpt-oss (`:6742`), Llama 3.1 `<function=…>{…}</function>` (`:6173`), DeepSeek V3.2 DSML (the format comment at `:4012`). The evidence's own two texts come verbatim from 2294639360 #98 (prose, then the markup) and #96's second text block. Fixtures live in `src/text_calls/fixtures/*.txt`, read with `include_str!`, each well under the size ceiling.

**Not detected (stated as limits):** a bare JSON object with no wrapper (Llama 3.x custom tools, `{"name": …, "parameters": …}`), since a model printing JSON would match it; Functionary v3.2's `>>>NAME`; and any form not in this list.

### Similar offered tools: `text_calls::similar(name, offered: &[&str]) -> Vec<String>`

The name splits into an MCP server (`mcp__<server>__`, via `crate::mcp::parse_tool_name`) and words: the rest, split on `_ - .`, lowercased, with a trailing `s` dropped from words over 3 letters. A candidate's score is 2 × shared words, plus 1 if it's on the same server. A candidate needs at least one shared word. Results are sorted by score, then by name, and capped at 5. When the name's server isn't one that offers any tool, the notice says so: "no MCP server `github` is offered". On the evidence's tools, `mcp__linear.app__add_issue_comment` lists `mcp__linear.app__save_comment` and `…list_comments` ahead of any tool on another server.

### Notices (shared, both builds)

- `text_call_notice(calls, offered) -> String` (server). It starts with `TEXT_CALL_NOTICE_START` = "Your last reply wrote a tool call as text instead of making it, so it didn't run." Then one sentence per call: "`N` isn't an offered tool; similar offered tools: `a`, `b`." / "`N` isn't an offered tool, and no offered tool has a similar name." / "`N` is offered, but a call written in a reply's text isn't made." / "One call's tool name couldn't be read." It ends "Make the call as a tool call, not as text in your reply." The exact wording is the Developer's, but it must name every call and its suggestions.
- `parse_text_call_notice(text) -> Option<Vec<String>>` (both builds): the names, for the transcript. It round-trips with the builder (tested, like `parse_cut_off_notice`).
- `EMPTY_REPLY_NOTICE` (both builds): "Your last reply had no text and no tool call. Carry on: make the tool call you need, or answer."
- **Why not `src/api/chat.rs`,** where `cut_off_notice` lives: SME-246 (In Progress) changes `src/api/chat.rs`. A module of its own keeps this plan off that file (see Overlap).

## Turn loop: `src/turn/run.rs`, `src/turn/reply.rs`

After `save_stop_notice`, `run_turn_steps` decides on the reply with a new `reply::after_reply(...)` in `reply.rs`. That function saves any notice, publishes it with `record_saved`, adds it to `pending_new_content`, and returns what to do next. A turn-local `TextCallStreak { corrections: usize, nudged: bool }` lives in `run_turn_steps`. It's in memory, per turn, and never persisted. The offered names come from `request.tools`, which the turn already holds for the call it just made.

| The reply (after `save_reply`) | What happens | Streak afterwards |
| -- | -- | -- |
| cut off (`is_cut_off`) or refused | unchanged: its notice, and the turn ends `Ok` | — |
| has `tool_use` blocks and `stop_reason == "tool_use"`, with no markup | unchanged: tools run, the loop goes on | `corrections = 0`, `nudged = false` |
| has `tool_use` blocks and `stop_reason == "tool_use"`, **with markup** (mixed) | tools run and their results are saved as now; **then** the correction notice is saved as a user message of its own, after the results. The loop goes on (or ends, if `run_tools` says `ends`: the notice is still saved, so the model reads it with the answer) | `corrections = 0` (a real call ran), `nudged = false` |
| no `tool_use` blocks, with markup (whatever the `stop_reason`, `tool_use` included) | the correction notice is saved; the loop goes on (`continue`) | `corrections += 1` |
| the same, when `corrections` was already 3 | the correction notice is saved (the model reads it next turn); the turn ends `Err`: "The model wrote a tool call as text instead of making it 4 times in a row (the last: `N`), so the turn stopped." | — |
| no `tool_use`, no non-blank text, `stop_reason` not cut off or refused (thinking only, or empty) | if `!nudged`: `EMPTY_REPLY_NOTICE` is saved, the loop goes on, `nudged = true`; else the turn ends `Ok` (the model meant to stop) | `corrections = 0` |
| no `tool_use`, text with no markup | unchanged: ends `Ok` | — |

**A `stop_reason` of `tool_use` with no `tool_use` block** used to save an empty tool-results message, which the next request then sent as an empty user message. It now takes the "no `tool_use`" rows. `run_tools` is reached only with at least one call.

### State model

- **Records:** the reply, the notice (a user-role `messages` row, `content` = one text block), and the streak, which lives in memory for one `run_turn_steps` call. There's no new table, column or migration.
- **Writers:** only the turn loop, holding the turn lock. Nothing else writes a correction.
- **Readers of the notice:** the model, through `history_for_request` (a plain user text; consecutive user messages are allowed, and notices already sit after tool results); compaction (summarized like any user text); the transcript, through `system_notice`; and `record_stop`, which checks only for `STOP_NOTICE`, so it's unaffected.
- **A Stop**, landing anywhere, drops the body as now. The reply was already saved. The notice is either saved or not: it's one `create_message` inside the body, which can't be half done. With no notice, the next turn's history ends at the markup reply. That is today's state, and the user chose to stop.
- **A restart mid-turn:** the same as a Stop, as far as these rows go.
- **A failed notice save** (database error): the turn fails `Err`, as every other `create_message` in the loop does.
- **A child agent:** an exhausted streak is a turn failure, so `agents::after_last_turn` tells its parent with the error text (the existing `Err` path). A mixed reply with a successful `finish` still saves its notice after the results. It's harmless, and the transcript shows it.
- **The error after the bound** is kept for a tab that reconnects and published as `TurnError` exactly as other turn failures are (`run_turn_bounded`, `start_turn`). Nothing new.
- **Work in flight:** a model or provider switch mid-turn already applies from the next turn (SME-72). The streak doesn't care which model wrote the reply.
