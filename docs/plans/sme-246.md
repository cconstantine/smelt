## What

Turn the flat conversation list into a tree: a child conversation renders indented under its parent, collapsible, with its persona (`<dir>:<name>`) and its status derived from the design's table (`docs/design/personas/agents.md#statuses`: stored `agents.state` first, then a turn in flight (`turn::turn_running`), then a question/card waiting for the user, then `ask_parent`, then `finished`, else `idle`). One server function returns the flat node list with persona and status; the client builds the tree and keeps it live over the existing `AppEvent` bus. A waiting child is visible from its collapsed parent (a bubble-up mark with a count) and from its parent's conversation header (a banner with links). The waiting signal itself (which SME-71's notifications will reuse) learns to count a trust card: today `db::list_waiting_conversations` reads only `pending_questions` with `asked_of = 'user'`.

Decisions the design left to this Planner:

- **No new `AppEvent`.** The tree is the conversation list, so an `agents.state` change is a `ConversationsChanged` (already published by create/delete/start/fail and by every saved notice). The tree resource refetches on the three signals the sidebar already bumps: `conversations_changed`, `turns_changed`, `questions_changed`.
- **The tree carries the busy and waiting marks.** Today the sidebar refetches three lists (`get_conversations`, `get_busy_conversations`, `get_waiting_conversations`) on three signals. The tree node carries `status` (derived at query time, so it already includes running and waiting) and `waiting_for_user`, so those two resources go away and any bump costs one tree query instead of up to three list queries. `live_pods` (`PodsChanged`) stays as it is.
- **Collapse state is per-tab in a signal** (a `HashSet<i64>` of collapsed ids, default expanded), not stored server-side and not in localStorage: a reload re-expands, and a waiting descendant's bubble-up mark shows on the parent row whether it is collapsed or not.

## How

### Data

`agents` gains `persona_dir TEXT`: the checkout directory of the repo the persona was loaded from, written at `complete_start` next to `persona_name`/`persona_path`/`persona_commit` (the start flow has the parent's repo row: `NewChildRepo.dir` in `src/db/agents/start.rs`; `agents/start.rs` already formats `{dir}:{name}` for its tool reply). The sidebar shows `{persona_dir}:{persona_name}`; when either is null (no persona, or a child started before this migration) it shows what it has — `persona_name` alone — never a bare `:`. Alternative rejected: joining the child's `conversation_repos` row at read time — a child can clone more repos later, and nothing then identifies which held its persona.

`db::conversation_tree(pool)` returns one row per conversation (every conversation, not just agents — the sidebar shows both):

```
SELECT c.id, c.title, c.created_at, c.updated_at, c.parent_id,
       COALESCE(a.state, 'active') AS state,   -- a user conversation behaves like an active agent
       a.persona_name, a.persona_dir,
       (EXISTS (SELECT 1 FROM pending_questions q
                WHERE q.conversation_id = c.id AND q.answer IS NULL AND q.asked_of = $1)) AS waiting_user,
       (EXISTS (SELECT 1 FROM pending_questions q
                WHERE q.conversation_id = c.id AND q.answer IS NULL AND q.asked_of = $2)) AS waiting_parent,
       (EXISTS (SELECT 1 FROM instruction_requests r WHERE r.conversation_id = c.id)) AS has_card
FROM conversations c LEFT JOIN agents a ON a.conversation_id = c.id
```

`api::chat::get_conversation_tree()` turns rows into `AgentTreeNode { id, title, created_at, updated_at, parent_id, persona: Option<String>, status: String, waiting_for_user }`: `status = agents::status(state, running_set.contains(id), waiting_user || has_card, waiting_parent)`, with `running_set = turn::busy_conversations()` fetched once per call; roots keep the list's `updated_at DESC` order, children sort `id ASC` (stable as more agents join; the tool-side `list_child_agents` newest-first order is a different context and stays).

`api::chat::get_waiting_children(id)` → `Vec<(i64, String)>` of **descendants** at any depth under `id` (recursive CTE on `parent_id`) that wait for the user by the same predicate (asked_of='user' row OR card). `ask_parent` rows never match, so a child waiting on its parent never lights the mark (design).

`db::list_waiting_conversations` unions `SELECT conversation_id FROM instruction_requests` — trust cards count, as the design's table says, for the sidebar and for SME-71 later.

### Live

No new event. `publish_repos` (`git/server/clone.rs`, ~166) additionally publishes `AppEvent::QuestionsChanged`; every write of an `instruction_requests` row ends there (verified: `instructions.rs:266`, `trust.rs:53/175`, `clone.rs:260/294/430/494`, `child_ref.rs:200`, `end_start` at `agents/start.rs:317` after `delete_instruction_requests_of`), so cards appear/vanish in the waiting set live without touching `instructions.rs` or `trust.rs`. A repo-list-only change now also bumps `QuestionsChanged` — one extra sidebar refetch, harmless.

### Sidebar (client)

`sidebar/tree.rs` holds the pure part: `build_tree(&[AgentTreeNode], &collapsed) -> Vec<TreeRow { node, depth, waiting_under: usize }>`. Roots in list order; children by `id ASC` under their parent; a collapsed parent's descendants are dropped from the output but counted into `waiting_under` (count of waiting descendants, any depth); a node whose `parent_id` isn't in the list (a refetch racing a cascade delete) renders as a root; a `depth` cap of 3 for indentation (rows deeper share the cap). Unit tests: nesting, order, collapse hides/marks, bubble-up through a collapsed middle level, missing parent, cap.

`sidebar/mod.rs` renders each row: caret button (only for nodes with children, `aria-expanded`, a tab stop) + the existing title span/link + `.conversation-agent-meta` (`<dir>:<name> · <status>`, only for nodes with a persona or an `agents` row — a user conversation shows no meta line) + the existing busy/waiting/pod/age/delete, unchanged, fed from `node.status`/`node.waiting_for_user` instead of the two dropped resources + a `.agents-waiting` count badge on the parent row when `waiting_under > 0` (shown whether collapsed or not). The local optimistic edits (`new_conversation` insert, delete retain) keep working on the node vec. `.sidebar-toggle` on a phone gets the waiting count when any visible row waits.

### Header banner

`chat/agents_waiting.rs`: `AgentsWaitingBanner { selected, conversations_changed, questions_changed }` — `use_resource` on `get_waiting_children(selected)`, keyed with the id so a switch refetches; renders `div.agents-waiting-banner` — "1 of your agents is waiting for you" / "2 agents under you are waiting" — each a link that navigates to that child. Nothing renders when the list is empty (no row, no gap: the element is conditional).

## State model

Stored, per conversation row: `agents.state` (the only stored status), `conversations.paused_at` (mirror), `pending_questions.answer/asked_of`, `instruction_requests` rows. Per-tab, lost on reload: the collapsed set. Nothing in the sandbox.

**Status is never stored** — `get_conversation_tree` derives it at query time from `agents.state` + `turn::busy_conversations()` + the two EXISTS + the card EXISTS, in the design's table order (the same `agents::status` the `list_agents` tool uses). So a status can't disagree with its source, and any bump refreshes every status in the list.

**Every writer of `agents.state`, and how each reaches the sidebar** (the eight `UPDATE agents SET state` sites; grep at `1da5c10`):

| Writer | Site | Reaches the tree today | Change |
| -- | -- | -- | -- |
| start done (`starting→active`) | `db/agents/start.rs:162`, caller `agents/start.rs` | `ConversationsChanged` at `agents/start.rs:128` | none |
| start failed (`→failed`) | `db/agents/start.rs:246`, caller `fail_start` | `ConversationsChanged` at `agents/start.rs:279` (+ notice) | none |
| `finish` (`active→finished`) | `db/agents/mod.rs:156`, caller `agents/queue.rs::finish` | nothing app-wide (the parent's wake saves a notice → `ConversationsChanged` via `turn/notify.rs:34`, but a paused parent isn't woken by a saved notice? it is queued, and queue saves it — the notice publish fires; still not guaranteed: a queued-but-not-saved path) | **add** `ConversationsChanged` in `queue.rs` after the `Queued` outcome commits |
| `stop_agent` (subtree `→stopped`) | `db/agents/mod.rs:257/276` (`stop_subtree`), caller `queue.rs::stop_agent` | `TurnsChanged` only if a turn was running to stop (`turn/state.rs:369/447`) | **add** `ConversationsChanged` after the `Stopped` outcome |
| message reopen (`finished→active`) | `db/agents/mod.rs:293` / `db/agents/messages.rs:100` (delivery tx) | the delivery's own path bumps when it saves a message; a delivery to a paused/stopped child is refused before the reopen | **verify** the delivery commit publishes a `ConversationsChanged` or the wake's turn start publishes `TurnsChanged`; if neither for a paused recipient, publish in the caller after commit |
| user's send/answer reopens (`finished/stopped→active`) | start_turn's admission | the open conversation's send already bumps `conversations_changed` (`send_action` takes it) | none |
| delete's marking | `db/agents/delete.rs:52` | `ConversationsChanged` at `api/chat.rs:73` | none |

Partial failures: every publish above is after `tx.commit()`, so a failed transaction publishes nothing and the tree keeps the old (still true) status; the next bump re-derives. A publish lost to a dropped task (e.g. `end_start`'s spawned cleanup) leaves the mark stale until the next bump — `QuestionsChanged` fires on the card delete there anyway (`publish_repos` → new publish), and the tree re-derives wholesale on any bump, so no state drift is possible beyond staleness-until-next-event.

**Readers:** `get_conversation_tree` (sidebar) and `get_waiting_children` (banner) each read at their own call moment — a tree row and a banner link can therefore disagree for the moment between two refetches (one bump re-derives both within a round-trip); both always read current rows, never a cached decision. `get_busy_conversations`/`get_waiting_conversations` keep their current meaning for the conversation-stream side (the sidebar stops using them; `get_waiting_conversations` is otherwise unconsumed — verified: only `sidebar.rs:45`).

**Pause:** the design's table has no "paused" state; a paused child (`state = 'active'`, `paused_at` set) reads `idle`. See Questions.

**Collapse** is UI-only: lost on reload, never shared across tabs; the waiting count on a collapsed parent comes from the same query as everything else, so it needs no extra state.

## Questions for the user

1. **A paused child reads `idle`.** The design's table has no paused row; the user's Stop pauses a child (`paused_at`) and the child stays `active`, so the sidebar shows it idle — indistinguishable from between-turns. Show "paused" in the meta line (about a column read: `conversations.paused_at` is already in the row, ~10 lines, no new event), or keep the table exactly as written? Keeping it is cheaper; the row is visible in the transcript.
2. **"Stop this group" button** (optional in the ticket, `stop_subtree` exists at `db/agents/mod.rs:231`): adding it means one more sidebar button + one server function + a browser case (~150 lines, no new event). It belongs to SME-245's budget story too. Recommend: leave out now.

## Trade-offs to flag

- `list_waiting_conversations` gains cards: a conversation with a pending trust decision now shows the sidebar "?" like an `ask_user` card. That's the design's intent (and SME-71's signal), but it changes today's visible behaviour — a conversation mid-trust-card has always looked ordinary in the sidebar.
- `publish_repos` publishing `QuestionsChanged` fires on repo-only changes too (a clone): one extra sidebar tree refetch there. No correctness cost; the tree re-derives everything per fetch anyway.
- The tree replaces three sidebar list fetches with one, refetched on any of the three signals: a turn start/end now refetches the (slightly larger) tree instead of just the busy-ids list. One query per bump either way, more rows per query.
- Old agents have `persona_dir` NULL and show persona name only.
- A tree refetch mid-cascade-delete can momentarily render an orphaned child as a root (parent row already gone); the next bump (the delete publishes `ConversationsChanged`) removes it. The tree function also guards this rather than dropping the row.
