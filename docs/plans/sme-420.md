## What

On a llama.cpp provider, a reply that stops `max_tokens` having written far less
than its budget is a *window stop*: the server's slot filled (SME-73's tell).
SME-386 round 2's M1 says a reply cut off past the usual trigger, where compacting
would free room, must not end the turn — it compacts and carries on, because a
child agent that stops there ends with no report. But on the window-stop path the
`carries_on` decision reads a `CompactionProgress` record the learner has just
wiped, so the stop that *should* trigger the room compaction instead ends the turn.

The order in `run_turn_steps`, on one reply:

1. `run.rs:451–453` — `overflow::window_stop(kind, stop_reason, output, budget)` is
   true for LlamaCpp-kind `max_tokens` with `0 < written + 64 < budget`
   (`overflow.rs:190–196`), and `overflow::learn_window_stop` runs.
2. The learner moves `turn_model.context_window` down to the measured slot:
   the turn-only path at `overflow.rs:436`
   (`turn_model.context_window = turn_model.context_window.min(window)` — taken when
   the server reports no window, SME-439), or via `learn_as` (`overflow.rs:423`,
   which sets it at `overflow.rs:520–522`) when the stop is plausible against the
   report or repeats in a later turn.
3. `run.rs:468` — `p.measured(&turn.usage, turn_model.context_window)` now passes
   the **changed** window. `CompactionProgress::sync` (`compaction_progress.rs:168–178`)
   sees a different window and replaces the whole record with
   `Self { window: Some(new), ..default() }` — `after`, `awaiting`, `tight`,
   `room_retried` all gone. `measured` then returns at its `!awaiting` guard
   (`compaction_progress.rs:323`) without setting `after`.
4. `run.rs:474–480` — `cut_off` (`is_cut_off`, `run.rs:474`) and the RoomLeft
   budget are true, but `p.cut_for_room(sized, turn_model.context_window)`
   (`run.rs:479`) computes `frees_room` from `sized.zip(self.after)`
   (`compaction_progress.rs:353`) — `after` is `None` after the wipe, so
   `frees_room` is false; and `room_only()` (`compaction_progress.rs:451–453`,
   `tight && no guess`) is false too. It returns false.
5. `carries_on` false → the stop notice saves (`run.rs:481`), `why_if_stuck` says
   nothing (the wipe cleared `stuck` too, `run.rs:487–489`), and the turn ends at
   `after_reply` (`run.rs:494–507`). The child's cut-off `finish` call was dropped
   mid-stream (a cut-off call is dropped and not run — `room_limited.rs:147–166`),
   so `finish` never ran: no `agent_messages` report row, no parent wake.

`compaction_progress/tests.rs:228` —
`assert!(!tight().cut_for_room(Some(90_000), 500_000), "a window learned since")` —
pins the wipe on purpose: measurements learned against one window say nothing about
another. That is right *between* steps. It is wrong inside the step that changed the
window itself, because `measured` (:468) and `cut_for_room` (:479) run against the
record the learner wiped seconds earlier — the step sized its request, its budget and
`sized` (`run.rs:391`) against the *old* window, so the old window is the only correct
frame for its own decision.

## Chosen fix

Decide `measured` and `cut_for_room` from the window the step was sent at (the
ticket's first suggested fix). In `run_turn_steps`, just before the window-stop
block (`run.rs:444–453`):

```rust
// SME-420: this step's sizes were built against the window it was sent
// at. A window-stop learner below may move `context_window` mid-step (a
// llama.cpp slot stop measures the server's real room); `measured` and
// `cut_for_room` below would read that as a window change and wipe the
// very record this step's cut-off decision needs — the turn would end
// instead of compacting for the room, and a child would end with no
// report (SME-420). Decide this step from `window_at_send`; the new
// window still moves the meter below (SME-439's intent) and every
// later size, and the record re-syncs to it at the next step's `step`.
let window_at_send = turn_model.context_window;
```

and pass it at the two decision sites: `p.measured(&turn.usage, window_at_send)`
(:468) and `p.cut_for_room(sized, window_at_send)` (:479). Nothing else changes.

Why this and not "treat a learned-window stop as a room cut for that turn" (the
ticket's second option): that needs a new `CompactionProgress` entry point (a new
file-region in `compaction_progress.rs`, SME-482's live file) and a way to bypass
`frees_room` — which would also re-compact right after a compaction that just got
cut, the churn `sized == None` exists to prevent. And it is unnecessary: with the
pre-learning window the record already says `tight`, `after = 13,600`,
`sized ≈ 24,000`, `frees_room` true — exactly the M1 decision SME-386 designed,
one step before. `cut_off` stays true, so the reply is still kept as cut, the notice
still saves, and the "once only" `room_retried` still applies.

Scope notes:

- The meter (`recorder.finish`, `run.rs:457`) keeps the **new** window — SME-439's
  deliberate intent ("a save moves the meter", `run.rs:448–450`; `window_learning.rs`
  T8 pins it). So does the next step's `p.step(...)` (`run.rs:354`) — that is where
  the record re-syncs, wiping the old-window measurements exactly as designed.
- The *refusal* learner's mid-step change (`overflow::recover` → `learn`,
  `run.rs:410–432`) stays as today: there the new window is the server's named
  number and the record's old-window numbers are genuinely stale, and a recovery
  that compacted already forces `sized = None` (`run.rs:428–430`). The escape
  simulation (`tests/escape.rs:390–397`) models exactly that shape and stays green.
- `compaction_progress/tests.rs:228` is **not** touched, and the wipe itself is not
  touched: production simply stops calling `cut_for_room`/`measured` with a window
  the learner changed under their feet. A window change between steps (a provider
  page edit, a saved learner seen by the next turn) still wipes and still kills
  `cut_for_room` — the growth case the unit test guards.

## State model (what moves, who reads it)

The record is the conversation's `CompactionProgress` (`ConversationRuntime`), the
window fields on `TurnModel` (turn copy) and the model row (saved learner). The
transition this plan changes is exactly one: `sync`'s wipe now fires for this
record only at a step boundary (`p.step`), never mid-step under the step's own
decisions. Per-caller, on the window-stop step:

| Reader | window argument | |
|---|---|---|
| `p.step` (run.rs:354, *next* iteration) | `turn_model.context_window` | unchanged — re-syncs/wipes here |
| `p.measured` (run.rs:468) | → `window_at_send` | **changed** |
| `p.cut_for_room` (run.rs:479) | → `window_at_send` | **changed** |
| `recorder.finish` meter (run.rs:457) | new window | unchanged (SME-439 intent) |
| `save_stop_notice` (run.rs:481) | new window | unchanged (number-free wording) |
| `p.why_if_stuck` (run.rs:487) | new window | unchanged |
| `floor_fired` / build (next iteration's build) | new window | unchanged |

A step that `carries_on`s re-enters the loop in the same turn: its next `step`
syncs to the learned window, wipes `after`/`tight` — and compact-continues anyway,
because the projection of the slot-filling conversation (≈ the learned window) is
over the fresh record's `compaction_ceiling(window)` trigger, so the owed room
compaction happens even though `compact_for_room` goes with the wipe. (Verified
against `budgets.rs:59` / `compaction_progress.rs:163–165` with buffer 4,096:
ceiling(24,584) = 20,488 < projected ≈ 24,644.)

Work in flight: a mid-turn window change reaches everything from the next step on;
the only reader deliberately held back is the step that made the measurement.

parent transcript). A user who does run llama.cpp with slots sees, after the fix:
the stop notice, a compaction divider, and the reply continuing — instead of the
turn just ending.

## Trade-offs to flag

- A step's `measured`/`cut_for_room` can now act on `after`-vs-`sized` numbers
  computed against a window that has just been proved too big. That is the point
  (they are the numbers the request was sized by), but the resulting room
  compaction is chosen for the old window's trigger; the next step re-syncs and
  would refuse to repeat it if the new window made it pointless. Judged acceptable:
  it costs one summary in a state that was already compacting every-other-step.
- A non-tight window stop no longer wipes the record mid-step (it wipes at the next
  `step`, one decision later). Same end state, one decision sooner for
  `measured`'s `after`; no behaviour pinned on the difference.
- `room_limited.rs` passes the 30,000-byte aim (~31k) and stays well under the
  40k ceiling; it is already a topic-split test file, so the move-first rule
  (which targets inline `foo.rs` tests) doesn't apply; a further split would cost
  more review than it saves.
