## Trade-offs to flag

1. **The user's own pod holds no secret files, and the git key only.** That is narrower than the alternative the user declined. The exposure moved: **any persona that names a stored secret gets it, whoever its ancestors are** — so for named secrets the whole guard is "which persona file you ran under" (a persona file can only be started from a repo the user trusts, since untrusted repos' personas are never listed or started — SME-235's gate) plus SME-243's egress. A grandchild of a chain that holds nothing can hold a secret no ancestor ever had: accepted by the user, and T13/T1 pin it. Flip side to know: the user's own conversation cannot run `scripts/pm-wait-for-board` off a file — that needs a persona agent, since the root gets no secrets.
2. **A skipped install leaves an old file in a pod.** If `install_into_live_pods` can't reach one pod (starting, ending, stalled exec) it logs and moves on, as it does for keys today: a deleted secret stays readable in that pod until its next create. Worst case in today's code: forever, since a healthy idle pod is never recreated until SME-78 ends it. Fixing it needs a per-pod "credentials out of date" marker and a retry — a separate ticket; this one keeps today's behaviour and says so.
3. **What is frozen at start, and what is live** (round 1's Trade-off 3, re-checked under Rule S): frozen — the Rule G bit, and the *names* in the agent's persona snapshot. Live — which of those names the store backs, and every value. So a persona naming `linear-api-key` started before the user stored that secret gets it at the next install, with no restart; the start notice says it was unbacked at start, and the prompt says so until it isn't.
4. **Every way out of `starting` clears a never-completed child's chain bit to `'{}'`,** so a failed start can't be resumed with credentials: start a new agent.
5. **The pre-`complete_start` reconcile is a handful of pod execs per agent start** (bounded by `INSTALL_TIMEOUT`, 60 s) and its failure fails the start. That's the price of "no key at the first turn" being true by construction rather than by a race between the wake and the cleanup — today `StartExit::drop` spawns its cleanup *after* `complete_start` has already woken the first turn, which is exactly the window this closes.
6. **A persona asking `git-ssh` under a chain that doesn't have it** isn't refused up front (its clone may be https); the clone fails and the start report carries git's message, while the notice names the narrowing as the cause. Refusing at `start_agent` would mean knowing the remote's scheme — kept out.
7. **`name` is immutable** (see [part 1's state model](sme-242.md#the-state-model)): renaming is delete + add — two clicks instead of one, and what keeps persona files honest.
8. **`ssh_keys` still holds one key** (`refuse_a_second_key`, `20260927130000_one_ssh_key.sql`), so a persona can't ask for a *named* key; a read-only deploy key stays a later choice, as the design says.
9. **A pod can `curl` the secret list and take `shown`** — at most four leading characters with at least eight bytes always hidden, plus the length and the name — because `request_guard` lets a header-less request through (`tool-rules.md#egress` item 2). It is capped by D7's arithmetic and bounded by there being no reveal control at all; the general fix (a pod must not reach smelt) is SME-243's, and tightening the shared guard here would stop nothing at the browser caller while breaking plain curl use (SME-173).
10. **"A child never gets more than its parent" now holds for `git-ssh` and volumes, not for named secrets.** `tool-rules.md#narrowing` and the docs get amended to say exactly that, so the invariant a reviewer checks is the real one.

## Answers recorded

1. **Named secrets are exempt from narrowing** (the user chose the alternative to round 1's recommendation): Rule S above, and `for_conversation` split into two rules so the exemption can't be undone by an inherited intersection. The user accepted the cost: the second rule (≈40 lines, tests T1's rows and T13), the `#narrowing` amendment, and a child holding a secret no ancestor had. `git-ssh` keeps the chain rule unchanged.
2. **Write-only, with a safe prefix on the page** (no reveal control): D7's `shown` — ≤4 characters, ≥8 bytes always hidden, plus the byte length, computed at read, never stored, never in a tool result, the environment section, a log or `Debug`. Reachable by a pod's curl, capped and recorded as Trade-off 9.
3. **No per-secret sandbox opt-out** — no column, no checkbox; the persona file already states who gets what.

## How it will be checked by hand

1. `/secrets`: add `linear-key`, then a 64-char name; try `git-ssh` (refused) and an empty value (refused). Check the row shows only a ≤4-character prefix and a byte length. In the user's own conversation, `ls -l /etc/smelt/keys` shows the key and `/etc/smelt/secrets` is **empty** (the root holds none).
2. A scratch repo at `/tmp/x` (bare origin, trusted) with persona files: `[git-ssh]`, `[]`, `[linear-key, nope]`, and one pair nested two deep where only the grandchild's persona names `linear-key`. In each agent ask for `ls -l /etc/smelt/secrets /etc/smelt/keys` and a `git push`: the `[]` one has no key file, fails the push, and its context detail view's System-prompt pane already said why; the `nope` one's parent carries the "not one of your stored secrets" notice, and `list_personas` shows the same note; the deep grandchild **does** have `/etc/smelt/secrets/linear-key` while its parent does not.
3. Store `nope` on the page, then terminate and re-create that agent's pod (or start a fresh agent on the same persona): the file appears without any change to the persona file.
4. Delete `linear-key` while a granted agent's pod is live: its file goes (check from inside the pod).
5. Restart the server with a child `starting`: the startup sweep fails it and leaves no key in its pod (T7 (c), by hand once).
