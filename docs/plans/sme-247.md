## Ground this plan reads from (checked 2026-10-27, on `origin/main` at `76483dd`)

- The parser (`src/personas/mod.rs`) accepts exactly `name`, `description`, and `smelt:` with `model` and `tools` (`rules::check`); `credentials` (SME-242), `egress` (SME-243) and `limits` (SME-245) are **not fields yet** — writing them is a parse error. So this ticket's files carry no `credentials`/`egress`/`limits`, intended values included.
- The grammar (`src/personas/rules.rs`): `class: all | no-destructive | read-only` (default `all`); `allow`/`deny` pattern lists; a pattern has 0 or 1 `/`; a server segment never holds `*`; empty parts and a pattern in both lists are errors. Specificity: level 1 exact, 2 tool wildcard, 3 `<server>/*`, 4 the ceiling; most specific wins, deny wins a tie. Server names match **exactly** (`pattern_server == server`), so patterns must carry the configured name with its case. `*` in a tool segment matches any run without `/`.
- This deployment's configured MCP servers are `Github`, `exa` and `linear.app` (every conversation sees them as `mcp__Github__…`, `mcp__exa__…`, `mcp__linear.app__…`). None contains `/` or `*` (241 refuses such new names), so all are pattern-namable. The design's examples use lowercase `github/…`/`linear/…` — illustrative only; the files below use the real names, or `list_personas`/`start_agent` report the patterns as naming no configured server (never an error, and a stale pattern can never widen past the ceiling).

- MCP tool classes come from annotations, **unannotated means destructive**. Neither this seat nor CI can read GitHub's/Linear's annotations, so the rules below are written so that every MCP tool that matters is decided by a **level-1 or level-2 pattern** (a pattern decides whatever the class turns out to be) and only never-used tools fall to the ceiling. The design's worked example shows exactly this (`github/create_pull_request_review` unannotated, allowed by an exact allow).
- Chains compose: a child's effective rules are its persona's **and** every ancestor's (`agents.rule_chain`, fixed at start; conjunction). So every `allow` a seat needs must also be allowed by the persona of whoever starts it. The plan's sets below honour that floor.
- Nesting is **not** blocked: `DEFAULT_AGENT_DEPTH = 5` (`SMELT_AGENT_DEPTH`, SME-241) — PM at depth 1, seats at 2, a seat's Code Reviewer at 3 fits. The ticket's note about "the default depth of 2" predates 241 (the user raised it to 5 on 2026-10-23); SME-245 will add per-persona limits.

## Decision 1 — which personas get files, and where the prose lives

**Recommendation: all seven**, not five. The ticket's Done-when says "Every persona in `docs/personas/README.md` has a persona file that smelt's parser accepts", and the design counts "SME-247's seven" files. The five seat personas (planner, developer, code-reviewer, integrator, facilitator) are where the rules matter; project-manager and architect files are instructions-only and cost ~1 KB each.

File names match the README rows and each other: `project-manager.md`, `architect.md`, `planner.md`, `developer.md`, `code-reviewer.md`, `integrator.md`, `facilitator.md` (all valid `name` shapes, and `name` equals file name as the parser requires).

One source of truth, per persona, with a clean division:

- **Role prose** — responsibilities, statuses moved, seat rules — stays in `docs/personas/<name>.md`, unchanged in substance. No prose is copied into the file.
- **Machine facts** — the `description` one-liner and the tool rules — live only in `.agents/personas/<name>.md`. (The README table's "Works on"/"Moves the ticket" columns stay as they are: they are summaries that already exist, not copies of a file field.)
- **Pointers added (the doc changes the user approves at plan time, per the confirm-before-change rule):** `docs/personas/README.md` gets a short paragraph under the table — every persona has a persona file at `.agents/personas/<name>.md` with its tool rules; `.claude/agents` is a symlink so the same files are Claude Code subagents; under smelt a seat is started with `start_agent`'s `persona` parameter (shown `smelt:<name>`), and under Claude Code the file's smelt rules, model and credentials do not apply. ## Decision 2 — the rules per role, against the real process and grammar

Principles the table follows:

1. Ceiling `read-only` for every seat: it leaves everything a seat does **inside its pod** (terminals, files, clone, gate runs, web reads, reports) allowed, and refuses by class anything reaching out that isn't named — including `start_agent` (writing), an unannotated MCP tool, and `http_request`'s `POST`/`DELETE`. Only `project-manager` gets no rules at all, for the chain reason in its row.
2. Where a seat's outward effect is wanted, name it exactly (level 1) — that works whatever the MCP class turns out to be. Where the process forbids an effect that an allow-list neighbour could otherwise reach, deny it exactly, even when the ceiling already refuses it: a deny survives a future `mcp_tool_classes` override (SME-240) marking that tool read-only, and it says so in the file.
3. The **chain floor**: a seat's `allow` must be a subset of what its starters allow. Developer's and Integrator's sets are written to be supersets of Code Reviewer's (they start it); PM's has no rules so it floors nothing.

## Decision 3 — self-consistency: the lint rides this ticket

The Done-when already requires it ("a test in `src/repo_lints.rs` (or beside the parser) parses every persona file in the repo"), so it rides. New submodule `src/repo_lints/personas.rs` (the module's existing shape: `cluster_lock`, `components`, `links`; `repo_lints` is `cfg(all(test, feature = "server"))` and compiles in the server tests `check.sh` runs), one `mod personas;` line in `src/repo_lints.rs`:

1. **Parse every tracked file directly under `.agents/personas/`** (`tracked_files()` filtered) through `crate::personas::parse` — the same entry the server uses, so CI agrees with the runtime parser. An assertion failure prints the parse error naming the file.
2. **Native patterns must name real tools:** for each persona's parsed `tools`, every pattern without `/` and without `*` must equal a name in the tool `REGISTRY`; every native wildcard pattern must match at least one registry name. A small local matcher suffices (the rules' `glob` is module-private; these patterns hold at most one `*`). This is what catches `merge_pull_request` written without the server part, and a registry rename. MCP patterns are **not** checked against server lists — that's deployment config in the database, not the repo; the runtime reports cover it.
3. **README ↔ files parity:** the seven names in the `docs/personas/README.md` table each have `.agents/personas/<name>.md`, and every persona file has a table row.
4. **The symlink is tracked and right:** `.claude/agents` is in `tracked_files()` and `read_link` says `../.agents/personas`.

No CI check can verify the configured server *names* (`Github`, `linear.app`) — that stays a deployment property; `list_personas` already prints the unmatched-pattern report SME-241 shipped.

## Decision 4 — Claude Code usability

**Same files, no copy step** — that is what the chosen format is for. `.claude/agents -> ../.agents/personas`, a relative symlink (spike S1: it loads as a subagent beside the built-ins, the unknown `smelt` frontmatter key is ignored with one debug-log warning, and a relative body link is followed). Claude Code reads `name`/`description`/body and nothing smelt-specific; no Claude Code keys (`tools`, `model`, `disallowedTools`) are written into the files.

One blocker this plan found and fixes: **`.gitignore` ignores `.claude/`**, and git cannot re-include a file under an excluded directory. So `.gitignore` changes: `.claude/` becomes `/.claude/*` plus `!/.claude/agents` (root-only, everything else under `.claude/` stays ignored) — and the lint (item 4) asserts the symlink is actually tracked, so a re-ignored symlink fails CI rather than silently vanishing from fresh clones.

The live Claude Code load with these files can't be re-run from this seat (no `claude` CLI); the mechanism is S1-proven. Recommend the full per-persona check (smelt starts and Claude Code load alike) ride **SME-248**, the project's Done-when run; this ticket's PR spot-checks two personas on its check server (below).

## Decision 5 — rollout: the PM switches seat dispatch to `persona:`

A process change, no code. After this merges to `main`:

- The PM dispatches seats as `start_agent(brief, repo: "/workspace/smelt", persona: "<name>")` (shown `smelt:<name>`) instead of prose briefs that name the role. The persona is read from the **child's** checkout at the child's ref — the child clones at the parent's commit by default, so once the PM's clone is at/after this merge every seat finds its file; before that a seat's start fails with "no file for persona …", which is the safe direction.
- **Brief shape:** ticket id, its Linear link, the branch (and worktree, or conversation+clone for a sandbox seat), the PR where one exists, and only what is specific to the ticket — the user's answers, what a stopped seat already did. Role prose and doc pointers drop out: the persona body's links and the repo's AGENTS.md carry them. This makes "a brief points at the rules; it doesn't restate them" (SME-257, proposal 3) structural rather than a habit.
- Unchanged: the Linear `started`/`finished` comments (`conversation <id>, clone <path>` shape), the seat's report through `finish`, ownership reconstructable from comments.
- The Facilitator keeps its current seat (Claude Code sub-agent started by the PM's session) unless the user says otherwise — see Questions 1.
- Depth is fine: default 5 (SME-241) covers PM(1) → Developer(2) → Code Reviewer(3).

## Trade-offs to flag

- **Rules are about effects outside the pod.** The Code Reviewer's `write_file`/`edit_file` denies state its contract, but bash writes the same paths; the design says so, and the real walls for that are SME-242/243. Don't read the deny list as sandboxing.
- **Server names are deployment config.** The files name `Github`/`linear.app` because that is what this deployment configures; another deployment with other names gets the unmatched-pattern report and ceiling-only rulings — never wider. A rename here silently weakens the rules until someone reads the report: that is 241's chosen trade, restated.
- **The PM file has no rules** by necessity (chain composition is a conjunction; a guarded PM would strangle its own seats). Guarding the PM itself waits for credentials (242).
- **The Facilitator's reads collide with 243's "never smelt"** (its job reads smelt's API over HTTP). 243's Planner must decide that persona's egress; until then smelt's fetchers check no addresses and it works.
- **A seat's persona is snapshotted at start:** editing a file mid-ticket changes no running seat (by design); after merge, the *next* dispatch picks the new rules up.
