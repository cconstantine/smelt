## What

The model gets `create_volume(name, mount_path)` and `delete_volume(name)`: claims owned by its conversation, mounted in its pod (and its children's) on top of each conversation's own `/workspace` claim. `start_agent` gains an optional `volumes` list; a parent can pass only volumes it holds (created or mounted to it), so a child never gets more than its parent. A volume is deleted with the conversation that created it, and a startup sweep cleans a cut-off delete. The system prompt's Environment section lists the conversation's volumes with who owns them, as global volumes are listed today.

Why (scope item 3): without it each child re-clones and rebuilds, minutes each on this repo.

## Criticals carried from the stopped pass (still true at `4d004ed`)

- The Sandbox volumes page's `create_volume`/`delete_volume` are server functions in `src/api/sandbox_volumes.rs` calling `sandbox::create_volume`/`delete_volume` (`src/sandbox/manager/volumes.rs:65`/`:93`). The tool registry is a separate namespace and the model's tools are new functions in `crate::agents`. **Nobody unifies the names.**
- The tool classes are fixed by the design (`docs/design/personas/tool-rules.md` has the rows already): `create_volume` writing, `delete_volume` destructive.
- `src/sandbox/adopt.rs` needs no change: the adoption pass lists only `!{INSTANCE_LABEL}` objects (`adopt_unlabelled_objects_with`, `:102`), and these claims are created labelled — a labelled agent-volume claim is left alone until the sweep runs, as the stopped pass said to check.

## Decisions this plan makes (the design leaves them open)

- **Names stay unique across everything one conversation mounts.** The design's `UNIQUE (owner_conversation_id, name)` is uniqueness per *creator*. A parent can also hold volumes it was passed, and two of its mounts can share a name (grandparent's `cache` passed down, plus the parent's own `cache`) — then `start_agent(volumes: ["cache"])` is ambiguous. `create_volume` therefore also refuses a name already taken by any volume this conversation mounts (an EXISTS check in the tool, not a new constraint). Trade-off flagged.
- **`/run/docker-sock` joins the reserved mount paths.** The design refuses at/under `/workspace`, `/etc/smelt` (`POD_GIT_DIR`, `src/git/server/keys.rs:9`), the system dirs (`/etc /usr /bin /lib /proc /sys /dev /var/lib/docker`), a global volume's path, or another of this conversation's mounts — but the pod also mounts the Docker socket at `DOCKER_SOCK_DIR` (`src/sandbox/spec.rs:329`), and a volume over it would break the pod's Docker. Added to the refusal list. Trade-off flagged.
- **The live-pod sentence is a pure function over a db read** (`list_sandbox_pods`, no cluster): both tools' results say the volume mounts from the *next* pod when the conversation has a live pod; smelt never restarts the pod itself (design).
- Passing lookup is by name over the parent's `conversation_volume_mounts` join, inside `create_child`'s transaction, `FOR SHARE OF v` on the `agent_volumes` rows — the design's lock against a concurrent `delete_volume`. `delete_volume` locks the same row `FOR UPDATE` for its refuse-check-plus-delete, in one transaction; the claim goes after the commit (best-effort; the sweep catches a crash). Duplicate names in one `start_agent` call are deduplicated.

## How

**Schema** (`migrations/20261025180000_agent_volumes.sql`), exactly the design's two tables:

```sql
CREATE TABLE agent_volumes (
    id BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    owner_conversation_id BIGINT NOT NULL REFERENCES conversations(id) ON DELETE CASCADE,
    name TEXT NOT NULL CHECK (name ~ '^[A-Za-z0-9_-]{1,64}$'),
    mount_path TEXT NOT NULL,
    created_at TIMESTAMP NOT NULL DEFAULT now(),
    UNIQUE (owner_conversation_id, name)
);
CREATE TABLE conversation_volume_mounts (
    conversation_id BIGINT NOT NULL REFERENCES conversations(id) ON DELETE CASCADE,
    volume_id BIGINT NOT NULL REFERENCES agent_volumes(id) ON DELETE CASCADE,
    PRIMARY KEY (conversation_id, volume_id)
);
```

## State model

Record: one `agent_volumes` row, plus `conversation_volume_mounts` rows (the owner first, then every child it's passed to), plus the claim `agent-volume-<id>` labelled `smelt/instance` and `smelt/agent-volume-owner`.

**States of the record:** created (row + owner mount + claim) · row-without-claim (crash between row commit and claim create, or a cluster rebuild — every `create_pod` for a mounting conversation re-creates the claim, the global `ensure_volume_claims` shape) · passed (mount rows for descendants) · owner-deleted-rows-gone (claims gone by the delete or awaiting the sweep) · claim-orphan (owner gone, claim left by a cut-off delete — the sweep's only job).

**Writers (each path that creates, changes or finishes it):**
- `create_volume` tool: row + owner mount in one tx; claim after the commit, rows rolled back if the claim create fails (the global `manager/volumes.rs:65` shape); a crash between commit and claim leaves row-without-claim, re-created by the next pod start.
- `delete_volume` tool: refuse-check + row delete in one tx under the row's `FOR UPDATE`; claim delete after the commit, best-effort — failure leaves the claim for the sweep.
- `start_agent` → `create_child`: child mount rows under `FOR SHARE OF v` on the volume rows.
- `delete_subtree`: rows go by FK cascade from `conversations`; claims deleted after teardown (commit 5) — a crash leaves them for the sweep.
- `create_pod_attempt_unspanned` → `ensure_agent_volume_claims`: claim writer only (create-if-missing; `NotOurs` refuses the start, like a foreign global-volume claim).
- The startup sweep: claim writer only (delete, uid-preconditioned, instance-scoped).
- The migration: creates the tables.

No other path writes rows: the user's volumes page (`api/sandbox_volumes.rs`), the chat UI, and the persona machinery never touch these tables.

**Readers and what each does with a value another just wrote:** `create_pod_attempt_unspanned` reads mounts once per start (a create/delete during a start: the pod gets what was committed when it read; smelt restarts nothing); `start_agent`'s name lookup reads under the `FOR SHARE` lock (a `delete_volume` begun meanwhile waits — either it sees the child, `starting`, and refuses, or it commits first and the lookup finds no row and refuses); `delete_volume`'s check reads mount+state in its own tx; the system prompt re-gathers every turn (a volume created mid-turn appears in the next turn's prompt, and the tool result already said it); `start_agent`'s reply names what it passed from what it just committed. No reader caches any of it.

**Races:**
- `start_agent` vs `delete_volume` on one volume: the `FOR SHARE`/`FOR UPDATE` pair on the row serializes them; both outcomes are consistent (see the design; that is what the lock is for).
- two `start_agent` calls passing the same volume: both take `FOR SHARE` — compatible; mount rows are keyed by child, distinct.
- `start_agent` vs subtree delete: the existing conversation-row locks already exclude them (create_child takes the caller row `FOR NO KEY UPDATE`; the delete marks under the root's lock and refuses later starts).
- own `delete_volume` while the owner's pod is (re)starting: the start read its mounts earlier; the claim delete is accepted while that pod still mounts it — `pvc-protection` completes it when the pod ends. The volume row is gone either way, so the leftover is garbage the design accepts; noted in the tool copy.
- sweep vs a fresh `create_volume`: the sweep lists claims then live conversations; an owner conversation that exists at listing time is not swept.

**In flight when the setting changes:** a running pod keeps its mounts until its next start (the tool says so — Kubernetes cannot add a volume to a live pod); a child whose start committed mount rows keeps them even if the parent deletes the volume afterwards (the delete refuses while the child is `starting`); the prompt of a turn already running is unchanged (it was built at turn start). The record of what a pod actually mounted is its pod spec (`kubectl`/Tempo), not a smelt row.

**After a restart:** rows in Postgres, claims in the cluster — both survive; mounts still take effect only at the next pod start. A cluster rebuild re-creates claims at the next pod start with empty content (same as global volumes today).

**What each caller does in each state:**

| Caller | no volumes | own volume, live pod | own volume, no pod | volume passed to it | row, claim missing | owner gone |
| -- | -- | -- | -- | -- | -- | -- |
| `create_pod` | globals only | globals + own + passed mounts | same | mounts at the volume's path | claim re-created at start | n/a |
| `create_volume` tool | — | ok; result adds the next-start sentence | ok; sentence omitted | — | — | — |
| `delete_volume` tool | "no volume … you created" | rows now, claim after; pod unmounts next start | same | refused (not the creator) | claim 404 = fine | refused (row gone) |
| `start_agent(volumes)` | none asked | mount rows recorded | same | re-passable (holds it) | child mounts; ensure re-creates | refused |
| `delete_subtree` | — | lists before cascade, claims after teardown | same | only its mount row goes | claim delete 404 = fine | sweep deletes |

## Trade-offs to flag

- **The name-collision rule** (see Decisions) is this plan's one addition to the design's schema behaviour: `create_volume` refuses a name already taken among everything the conversation mounts. The alternative (allow it, qualify names when passing) widens the tool's input grammar for a case the design never uses.
- **`/run/docker-sock` is added to the design's reserved list** — the design listed `/var/lib/docker` (the sidecar's data dir) but not the socket dir; a volume over the socket breaks the sandbox's Docker. A user-typed global volume can still take that path today (unchanged there — this check is the model tool's).
- **`delete_volume` can unmount under a live pod:** the claim delete is accepted while the owner's running pod still mounts it; `pvc-protection` completes it at the pod's end, so files stay readable there until then. The tool result says the next start is where it changes.
- **`src/sandbox/claims.rs` grows to ~31,700 B** — over the 30,000 B aim, under the ceiling. A split is not planned (no forced trigger: the aim is enforced for test files); flag for the next ticket that grows it.
- **No user-facing surface** for model volumes: the Sandbox volumes page stays the global table (separate tables by design). A page or panel section showing model-created volumes is a reasonable follow-up, deliberately not in this ticket.
- **The spec split is a ~10-minute gate cost up front** to avoid the SME-179 shape; the alternative (grow `spec.rs` to ~40 KB) leaves no room for review fixes.
- **One claim per volume, mounted in every mounting pod at once** — RWO across pods on one node (spike S2), smelt's single-node k3s requirement; a multi-node cluster would need pinning or RWX. Written into the tool descriptions and docs, as for global volumes.
