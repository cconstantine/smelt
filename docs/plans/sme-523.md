- **SME-346 has shipped nothing.** It is a Backlog idea for HTTP providers' KV cache, in `providers/limiter.rs`. This plan borrows its idea (prefer the warm cache) for the gate's release order only, and doesn't touch the limiter.

## 1. The cache TTL: evidence, and what's left to measure

**Documented:** Claude Code's prompt-caching page (https://code.claude.com/docs/en/prompt-caching, "Which TTL each request gets") says that on a Claude subscription, within the plan's included usage, the main conversation gets the **one-hour** TTL, and that includes non-interactive `-p` runs. Once the subscription draws on usage credits, it drops to five minutes. `CLAUDE_CODE_PROMPT_CACHE_TTL=5m|1h` pins it (v2.1.242+; smelt pins 2.1.318 in `Dockerfile:73`), and `FORCE_PROMPT_CACHING_5M=1` overrides everything. Anthropic's prompt-caching docs (https://platform.claude.com/docs/en/build-with-claude/prompt-caching) say a cache hit refreshes the entry's lifetime at no extra cost, and that the lifetime counts from the **start** of the request that reads or writes it. Pricing: 1 h writes cost 2× base input, 5 min writes 1.25×, reads 0.1× (0.05× on Opus 5.5, $0.20 against $4/MTok).

**Captured:** every captured CLI stream in `src/claude_cli/fixtures/*.jsonl` (CLI 2.1.319, captured through the real subscription for SME-430/431/444) reports its cache writes as `ephemeral_1h_input_tokens` (1,108, 923, 900, 621, …), and `ephemeral_5m_input_tokens` is 0 in all 65 usage blocks. So the CLI asks for the 1 h TTL here.

**Not yet measured:** whether a wake after a 5–60 min gap actually reads the cache. **M1 is the Developer's first step, before any code.** The Developer can't run it from a seat (no production database), so the Ticket Driver asks whoever has read access to production's database (the Deployer or the user) to run this read-only query:

```sql
WITH c AS (
  SELECT m.input_tokens i, m.cache_read_input_tokens r, m.cache_creation_input_tokens w,
         m.created_at - lag(m.created_at) OVER (PARTITION BY m.conversation_id ORDER BY m.created_at) gap
  FROM model_call_usage m JOIN inference_providers p ON p.id = m.provider_id
  WHERE p.kind = 'claude_cli' AND m.kind = 'turn' AND m.created_at > now() - interval '4 days')
SELECT CASE WHEN gap < interval '5 min' THEN '1 <5m' WHEN gap < interval '55 min' THEN '2 5-55m'
            WHEN gap < interval '65 min' THEN '3 55-65m' ELSE '4 >65m' END AS bucket,
       count(*), round(avg(r::numeric / nullif(r + w + i, 0)), 3) AS read_share
FROM c WHERE gap IS NOT NULL GROUP BY 1 ORDER BY 1;
```

`created_at` is when a call was recorded, at its end, so a gap includes the next call's own generation time. Expected (a prediction): `read_share` stays high (>0.8) in buckets 1 and 2 and falls sharply in bucket 4. If bucket 2 is low, the TTL is 5 min in practice: the Developer reports it to the Ticket Driver before going on, and the constants in §3 change (`RESEED_AFTER` 4 min, and re-seeding is likely not worth it; see Q5). The result goes into `docs/setup/claude-code.md`.

### Results (the Developer, 2026-11-14)

- **M1, run by the Deployer on production (the ticket's comment):** the TTL is 1 h in practice. Every call after an idle gap of 5–55 min read the cache, and the drop comes at about 1 h. So §3's constants stand as written (`RESEED_AFTER` 50 min), and re-seeding goes ahead.
- **P1–P4 need a real subscription**, which no seat's sandbox has (no `~/.claude` credentials, no `CLAUDE_CODE_OAUTH_TOKEN`): they move to Hands-on, after the deploy. What a seat could check, against the pinned CLI 2.1.318 in the image: `--no-session-persistence` ("sessions will not be saved to disk and cannot be resumed (only works with --print)") and `--fork-session` are both in `claude --help`, and `--max-turns`, which `--help` doesn't list, is in the binary and already in production use: `claude_cli::once` passes `--max-turns 1` for every summary. So P1's primary path and its fallback both exist; which one holds the `.jsonl` byte-identical is P1's live check.

## 2. Part 1: the usage gate

### Projection (Q1)

The gate reads the newest `five_hour` window seen from any Claude Code provider. They all share the server's one `CLAUDE_CODE_OAUTH_TOKEN`, so they share one subscription (SME-486's first trade-off). It projects **as of now**, using the window's average pace:

- `start = resets_at − 5 h`, and `e = clamp((now − start) / 5 h, 1/7, 1)`. The floor of 1/7 is SME-486's first-seventh rule: before ~43 min, one burst would project wildly.
- `projected = u / e`. This is the utilization at the reset if the average rate so far holds.
- **Hold** when `projected ≥ 0.95`, or when the window's status is `rejected`. Otherwise **open**.
- A hold ends at `release_at = start + 5 h × u / 0.95`, which is when `u / e` falls back under 0.95 with no new usage, or at `resets_at` for `rejected` or `u ≥ 0.95`. The release time is computed, not polled, so the UI can say "resumes about 14:20".
- A reading whose `resets_at` has passed, or that has no `resets_at`, or no reading at all, is **open** (fail open: SME-486's verdict treats unknown the same way, and a missing reading must never stop every Claude Code call for good).

This is "spend the window evenly". The alternative, a rate over the last N minutes, needs a history of readings smelt doesn't keep. With every call stalled, no new readings arrive, so that rate decays to zero after N minutes whatever the real use is, and the gate would release in bursts. Q1 asks the user to choose.

### Where readings come from

- `usage::seen` (called by `run/read.rs` and `once.rs` as each event streams) also calls `gate::observe(&reading)`. That keeps one process-wide `five_hour` window, newest `seen_at` wins, so the gate sees a reading **as the call streams**, not after it records. `run/read.rs` and `once.rs` aren't edited.
- At startup (`main.rs`, beside the idle passes), `gate::load(pool)` seeds it from `db::newest_claude_code_five_hour(pool)`: a new query in `src/db/provider_usage.rs` (2,020 B) that joins `inference_providers` on `kind = 'claude_cli'`. A failed load logs and leaves the gate open.

### What is gated (Q2)

**Every Claude Code API call smelt makes**: both sites in `turn/call.rs`, and the re-seeds of part 2 (which never wait; see §3). The gate sits **between** calls: a call already streaming is never stopped. A mid-turn call waits with the CLI Parked, the turn holding its CLI process and its provider slot, if its provider has a limit. With the alternative, gating only new turns, one agentic turn of a hundred calls would run straight through a hold. Q2 asks.

`gate::wait(conversation_id)` is called first thing in `call_claude_cli` and in `stream_for_kind`'s ClaudeCli branch, before `usage::discard`. That adds about 200 B to `call.rs`.

### Release order (Q3)

Waiters sit in one process-wide list. Each entry holds the conversation, when it began waiting, and whether its cache is **warm**: its last gated call passed less than `WARM_FOR` = 55 min ago, from an in-memory map `last_pass` that `gate::wait` writes as it lets a call through. When the gate opens:

1. Warm waiters go first, oldest wait first. A warm call costs a cache read, a cold one a full prefill, so the same 5-hour budget buys more warm calls. This is SME-346's idea.
2. Then cold waiters, oldest first.
3. Coming out of a hold, one waiter passes every `RELEASE_SPACING` = 15 s, and each one re-checks the latest reading before it goes. A call that never waited, because the gate was open and no one was queued, passes at once. Without the spacing, twenty seats released at the same instant would all send before the first one's reading came back.

The mechanics: a `Mutex<GateState>` holds the reading, the waiters, `last_release` and `last_pass`. A `tokio::sync::Notify` is signalled by `observe` and by each pass. Each waiter loops: compute the verdict; if it's held, sleep until `release_at` or a notify; if it's open, pass when it's at the head of the order and `last_release + RELEASE_SPACING ≤ now`, else sleep until then or a notify. A `Waiter` guard removes its entry on drop, so a Stop or a dropped turn leaves no ghost, and it publishes the clear.

### What a held conversation shows (Q4)

- A new `ConversationEvent::UsageHold { until: Option<i64> }` (Unix seconds; `None` clears it) is published when a call starts waiting and when it stops. It's regenerable: a new `#[get] get_usage_hold(conversation_id) -> Option<i64>` in `src/api/usage_windows.rs` (2,310 B) reads the waiters list, and the chat fetches it where it fetches the turn state on select.
- `ConversationState` (`frontend/pages/chat/state.rs`, 30,053 B; about 200 B added, and its tests already live in `chat/tests/`) gets `usage_hold: Option<DateTime<Utc>>`.
- The working line (`chat/streaming.rs`, 1,529 B) reads **"Waiting for the Claude 5-hour usage window · resumes about 14:20 (in 23 min)"** while it's set, in the viewer's local time (part 3's helper), instead of "Working… 1m 20s". Stop works as before: it drops the turn, and the waiter with it.
- **Where it sits:** in the working line's own place, at the foot of the transcript above the composer. It's the same element at every width, so it covers nothing new. At phone width the text wraps under the existing working-line rules. The narrowest case is a phone (360 px) with the text at its longest, `(in 4 h 59 min)`. The browser check runs there.
- Sidebar: nothing is added. SME-513 reworks the sidebar next, so a held badge there can wait for it (see Trade-offs).

## 3. Part 2: re-seeding the cache of conversations expected to wake

### When a conversation is a candidate

An in-memory `reseed::Candidates` map (conversation → last call start, provider id, re-seeds this idle spell) is written by `gate::wait` as it lets a **turn** call through (the start time; a compaction summary doesn't count, since it isn't the session's prefix). A real call sets the re-seed count back to 0.

A loop, `turn::reseed::watch(pool)`, spawned in `main.rs`, wakes every 60 s. For each candidate whose last start + `RESEED_AFTER` (50 min, against a 60 min TTL) has passed, it re-seeds only if all of these hold:

1. **No turn is running** in the conversation (the turn state's existing running check, read only: `turn/state.rs` is 39,982 B and isn't edited).
2. **The cache is still alive:** last start + 60 min > now + 2 min. Otherwise it's too late, and the candidate is dropped.
3. **A wake is expected:** a new `db::expects_wake(pool, id)` in `src/db/sandbox/commands.rs` (19,264 B). It is true when any of these holds:
   - a `terminal_commands` row for the conversation has `status = 'running'`;
   - an `agents` row whose conversation's `parent_id` is this one is `starting` or `active`;
   - this conversation has a `pending_questions` row with `asked_of = 'parent'` (a child waiting on its parent's answer).
   A conversation waiting on the **user** (`ask_user`) or with nothing pending isn't re-seeded.
4. **Fewer than `RESEED_CAP` re-seeds this idle spell** (6, about 5 h of keeping warm; Q5).
5. The conversation's model still resolves to a ClaudeCli provider, the same provider, and it has a `claude_cli_sessions` record for that provider.
6. **The gate is open with no waiters** (`gate::try_pass`): a re-seed never queues. If the gate is held, the re-seed is skipped. The next tick tries again only while condition 2 still holds, so a hold longer than the TTL means a cold wake, which is the gate's to decide.
7. If the provider has a request limit, a slot is free right now (try, never wait).

When one of these fails for good (conditions 2, 4 and 5), the candidate is dropped. Condition 3 failing also drops it: no wake source left means no expected wake, and when a command or agent later finishes, its notice wakes the conversation, which starts a new spell anyway.

### What a re-seed sends

The goal is to read the exact prefix the wake will send, so that the cache entry's lifetime is refreshed, without changing the session the wake resumes.

- **Request:** `turn::reply::build_request(pool, id, turn_model, None, &[], false, 0)`, the same builder a turn uses. It gives the system prompt and tools the wake would send now. If the prompt has changed since the last call (the date rolled over, a repo was attached), the wake misses the cache either way.
- **Launch:** `claude -p` with the turn's arguments (`process::cli_args`), the same model and effort, the same `--system-prompt-file` contents, and the MCP config from `bridge().register(&request.tools)`, so the tools list matches. Plus `--max-turns 1`. Session: `--resume <session> --no-session-persistence` (new `SessionArg::ResumeUnsaved`), so the CLI loads the session and writes nothing back. **P1** checks that this leaves the session's `.jsonl` byte-identical and creates no new session file. If it doesn't, the fallback is `--resume <session> --fork-session`: read the fork's id from the `system`/`init` line and delete its file with `files::forget_session`.
- **Message:** one user line, `Reply with only the word ok.` The reply is read through `message_stop`, then the process group is killed. The reply is never saved to the conversation.
- **Code:** `once.rs` (9,875 B) gets its launch inputs as a parameter, `OnceLaunch { effort, mcp_config_file, session }`, and the summary passes today's values. A new `claude_cli/reseed.rs` builds the re-seed's inputs and calls it. `run.rs` (38,280 B) isn't touched.
- **Recorded:** a `model_call_usage` row of the new kind `reseed` (a migration, `20261114120000_model_call_kind_reseed.sql`, widening the CHECK; it sorts after `20261113120000`). That puts the cost in the conversation's spend and in the M2 numbers. `usage::record` records its reading, and its `seen` feeds the gate.
- **P2:** the re-seed's `cache_read_input_tokens` ≈ the last turn call's `cache_read + cache_creation`, and its `cache_creation` is small (only the one-line message). **P3:** a wake 70+ min after the last real call, but under 60 min after a re-seed, shows a high cache read. This is the Done-when "a measurement shows the cache hit on the wake", done hands-on after the deploy if no seat has the subscription (see Hands-on). **P4:** `--max-turns 1` with the bridge's tools registered: if the model calls a tool anyway, the kill at `message_stop` lands before the CLI calls the bridge, or the bridge's parked call goes away with the run (check that `RunBridge`'s drop does that).

### The cost (Q5)

Take a cached prefix of N tokens on Opus 5.5 (API prices as a proxy; the subscription's weighting isn't published):

- one re-seed ≈ 0.05·N to read, plus a few tokens written and output;
- a cold wake ≈ 2·N to write, against 0.05·N to read.

So keeping warm pays for itself as long as k re-seeds × 0.05·N < 1.95·N, which is k < 39, about 39 h. The cap of 6 (~5 h) is far inside that. It's set lower because a wake gets less likely the longer a conversation waits, and because the subscription's 5-hour accounting of cache reads isn't documented. **M2**, after the deploy: the `five_hour` utilization step across a lone re-seed, against a cold wake's step. It's recorded in What shipped, and the cap is revisited if the step is larger than expected.

## 4. Part 3: reset times in local time

- New `frontend/timezone.rs`: a hook `use_local_zone() -> Signal<LocalZone>`, with `LocalZone { offset_minutes: i32, label: String }`. It's read once per page load through `document::eval`: the offset as `live.rs` reads it, and the label from `new Intl.DateTimeFormat([], {timeZoneName: 'short'}).formatToParts(new Date())` (for example `PST`). SSR, and an eval that fails, give UTC with the label `UTC`. `chat/live.rs`'s `use_timezone_offset` keeps its signal and calls the shared reader, so there's one place that reads the zone.
- `reset_text(window, now, zone)`: `resets 06:00 PST` within a day, else `resets Tue 16:00 PST`, with the day computed in local time. It's used by `SubscriptionUsage`, `usage_title` (the context bar's hover) and part 1's working line. `ProviderUsageSuffix` shows no time. `smelt-api` and the CLI output stay UTC.
- One offset per page load: a reset on the far side of a DST change shows an hour off until the page reloads (see Trade-offs).

## 5. State model

**Gate reading** (one, process-wide). It is **none** at start, then **loaded** (from the DB at startup), then **live** (each `observe`). Writers: `gate::load` once, and `gate::observe` from every Claude Code call's stream (turn calls, summaries, re-seeds). Newest `seen_at` wins, so an older reading arriving late is ignored. A restart loses nothing that matters: the DB has the last recorded reading.

**Gate verdict**, which is derived and never stored: **open**, or **held until T**. It moves to held on a reading or on the clock passing a line. It moves to open as the clock passes T, at a reset, or on a reading. Readers: each waiter, `try_pass` (re-seeds) and `get_usage_hold`.

**Waiter** (per gated call), states and events:

| state \ event | verdict held | verdict open, head of order, spacing passed | open, not head | new reading | Stop / turn dropped | server restart |
|---|---|---|---|---|---|---|
| (new) | waiting; publish `UsageHold{until}` | pass at once if no others wait | waiting, publish | n/a | n/a | n/a |
| waiting | update `until`; publish if it changed | pass, set `last_release`, `last_pass`; publish clear | keep waiting | re-check | guard drops: removed; publish clear | lost with the turn; the turn's restart rules apply (an owed answer re-wakes it), and it meets the gate again |
| passed | n/a | n/a | n/a | n/a | the call itself handles it | n/a |

A failed publish is fire-and-forget, as for every event, and a tab regenerates it from `get_usage_hold` on select. Other conversations see the waiters list only through their own order. Other tabs of the same conversation see the event.

**Re-seed candidate** (per conversation, in memory): **absent**, then **idle** (written when a turn call passes), then **re-seeding** (a launch in flight), then back to **idle** with count + 1 and start = the re-seed's start, or **dropped**. A failed re-seed (spawn error, nonzero exit, silence) logs and drops the candidate: its cache state is unknown, so the conservative move is a cold wake. A real call passing the gate meanwhile overwrites the entry, and a re-seed finishing afterwards must not move `start` back. It sets `start = max(start, its own)`. A conversation deleted mid-re-seed: the launch fails when its work directory goes, it's logged, and the candidate is dropped. A restart loses every candidate, so there are no re-seeds until each conversation's next call (see Trade-offs).

**Writers and readers:**

- `last_pass`: written by `gate::wait`; read by the release order.
- Candidates: written by `gate::wait` (on a turn call) and `reseed::watch`; read by `reseed::watch`.
- `claude_cli_sessions`: read only by the re-seed. Its writers (`run::call`) are unchanged. A re-seed reading a record that a turn starting at the same moment deletes (`run::call` sets it aside first) gets none, so that tick skips the conversation, since condition 1 can't see a turn that is only just starting. If both do run, the re-seed's process doesn't persist, so the session is untouched (P1). The cost is one wasted re-seed at most.
