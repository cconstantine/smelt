## What happened, and the mechanism

The signature: `test_pyright_from_the_catalog_answers` fails at
`cluster.rs:350` with `The install didn't finish within 10 minutes` and an
empty log. Seen twice: a seat's cold gate (pre-#300 code), and PR #302's CI
run 42495207518 (`5ff50ed3`, which has #300 and not #304).

**Mechanism: npm bounds no part of opening a connection.** It has no bound
on the DNS lookup, the TCP connect, or the TLS handshake. All three run inside
`@npmcli/agent`'s `connect()` (`agents.js:105–162`), and its connection
timeout is hard-coded to 0 (`options.js:28`: `connection: 0`; npm has no
config key that reaches `timeouts`, since `fetch-timeout` flattens only to
`timeout`). npm's `fetch-timeout` covers none of it:

- `minipass-fetch` starts its request timer on the request's `socket`
  event (`index.js:105–112`). With an async `createConnection` that comes
  only after `connect()` resolves, so only after the TLS handshake.
- The agent's idle timeout (`socket.setTimeout`) is set after the connect
  too (`agents.js:155`).

So a connection that opens and then goes quiet before TLS completes holds npm
until the kernel gives up. With a live peer that never answers TLS, that's
never. With a path that goes dark after the SYN-ACK, it's TCP's
retransmission limit (`tcp_retries2=15`, about 15 minutes). npm logs a fetch
only when it ends, so the log stays at **0 bytes**, at `loglevel=http` too.
The pod is Running, and every exec read returns `Ok`. That is CI's
signature exactly, and on today's main it's the same signature plus #304's
diagnostics.

`NPM_STALL_BOUNDS` (#300) bounded what comes after the socket. #300's
measurement used a plain-`http` tarpit, where the socket exists as soon as
TCP connects, so the handshake gap never showed. The real registry is
`https://registry.npmjs.org`.

## What was checked and ruled out (this round, against the code as it is now)

- **"The message proves the pod was Running": verified (traced).**
  `start_with` reaches `wait_installed` only after `wait_running`
  returned `Ok` on `phase == "Running"` (`pods.rs:227–234`, `:333`), and
  `install_interrupted` ends the wait at once if the pod stops or is
  deleted. CI's events back it: `Started container server` for
  `lsp-3008114318-pyright`. Test start 15:38:24 → failure 15:48:36 is
  612 s, so `wait_running` took ≤ 12 s of it.
- **Image pull: ruled out.** Since SME-391 (`590d3c92`, an ancestor of
  both sightings' bases) `k3s-bootstrap` pre-pulls `node:22-slim`, and
  the failure fails bootstrap if it can't. CI's events: `Container image
  "node:22-slim" already present on machine`. A pull would also fall
  inside `wait_running`'s own bound, not the install's.
- **Scheduling / Pending: ruled out.** The server pod sets `nodeName`, so
  there's no scheduler, and Pending would end at `wait_running`, before the
  install bound starts.
- **LimitRange / SME-314: ruled out.** The pod sets explicit requests and
  limits (`64Mi`/`50m`, the config's limits; `pods.rs:144–147`).
- **The shell that opens the log: ruled out (traced).** `( install ) >
  install.log` is opened by the shell before npm runs. On main a missing log
  reads `missing` and an empty one `0 bytes`, and the reds show `0 bytes`
  with `npm install` alive. So the shell ran, and npm was running and
  silent.
- **The exec path, (B)/(B′): closed by #304**, and not this. Red 1
  made 547 record reads with no failed read, and a refusal would read
  `couldn't be read N times`.
- **CPU: ruled out.** The install alone takes 7 s in a hand-made copy of
  the pod (`added 1 package in 6s`, tarball 4.9 s; measured), and 16.9 s
  through the test. Round 2 showed CI's node was idle for the last 5 m 19 s.
- **Fetch stalls: bounded by #300** (X2a above). **DNS:** round 2's
  measurement (`EAI_AGAIN` at 71/111 s) was not re-run. The fix's bound
  covers the lookup anyway, since `tls.connect` resolves inside it.

## The fix

**A bound on every TLS connect a node-based installer makes, inside the
install only.** The pod script writes a small preload and runs the install
with `--require` of it added to `NODE_OPTIONS`. The preload wraps
`tls.connect`: if the connect has neither reached `secureConnect` nor closed
within `CONNECT_BOUND` (30 s), it destroys the socket with an error whose
`code` is `ECONNECTIONTIMEOUT`.

- **npm retries that error** on a fresh connection: it's in
  `make-fetch-happen`'s list (`remote.js:13–27`), and anything but a
  `request-timeout` is retried. Each try is logged at `loglevel=http`
  (`attempt N failed with ECONNECTIONTIMEOUT`), and the last ends in npm's
  own `npm error … TLS connect to <host> didn't finish within 30000 ms`.
  So a transient stall rides through (green above, 62.6 s), and a dead path
  fails in about 150 s with its reason in the log, both inside the 10
  minutes.
- **The bound covers the DNS lookup, the TCP connect and the handshake
  alike**, since the timer starts at the `tls.connect` call.
- **Worst case per request:** 4 tries × (30 s connect + 30 s fetch) + 3 ×
  10 s backoff = 270 s, under the 600 s bound. The existing
  `test_npm_gives_up_on_a_stalled_registry_inside_the_install_bound`'s
  doc comment gains the connect term. Its arithmetic test stays as it is:
  it reads env only.

### `pod_script`'s shape (the prototype's, as measured)

```sh
cat > /tmp/smelt-connect-bound.js <<'SMELT_EOF'
<connect_bound.js, the bound filled in>
SMELT_EOF
mkdir -p "$HOME" && ( [ -f /tmp/smelt-connect-bound.js ] && \
  NODE_OPTIONS="${NODE_OPTIONS:+$NODE_OPTIONS }--require=/tmp/smelt-connect-bound.js" && export NODE_OPTIONS; \
  <install> ) > /tmp/install.log 2>&1; echo $? > /tmp/install.rc; \
trap 'exit 0' TERM; while :; do sleep 1 & wait; done
```

- **The install alone gets it.** `NODE_OPTIONS` is set inside the
  install's subshell, so the language server itself, started later over
  `pods/exec` with the container's env, never loads the preload.
- **A user's own `NODE_OPTIONS`** (a config's `env`) is kept, with the
  `--require` added after it.
- **If the file can't be written,** the install runs as it does today:
  no `--require` of a missing file, which would fail every node start.
- **Images without node, or installs that don't use it** (`go install`,
  `curl`, `rustup`) ignore `NODE_OPTIONS`. The delimiter `SMELT_EOF` is
  quoted, so the shell expands nothing inside it. The preload has no line
  that is `SMELT_EOF`, and T1 asserts it.
- The pod's PID 1 is still the script, so `PROCESS_LISTING` still skips
  it.

### State model / callers

There's no new persistent state. The preload lives in the pod's `/tmp`,
rewritten by each pod's start, and goes with the pod. A saved config gets it
at its next start, since it's in `pod_script`, not in the config.

| Caller | Before (main) | After |
|---|---|---|
| `start_with` → `wait_installed` (the test; production's `start_language_server` → `manager::start`) | a stalled connect: waits the full 600 s, then the timeout error with an empty log | a transient stall: the install finishes on npm's retry. A dead path: `The install failed (exit 1)`, with npm's logged attempts and error, in ≈ 150 s (≤ 270 s worst) |
| `list_with` | unchanged (`Installing` until the record says otherwise) | unchanged; the install ends sooner |
| A server already running when this deploys | unchanged (the install is done) | unchanged; only a new pod's install has the preload |

## Trade-offs to flag

- **A connect that takes over 30 s now fails and retries** instead of
  waiting. A real handshake takes well under a second. A path that slow
  would have been a failure anyway.
- **It's a preload in every server pod's install.** It's scoped to the
  install's subshell and added after the user's own `NODE_OPTIONS`. A future
  node that changes `tls.connect`'s shape would make the wrapper a no-op,
  not an error, since it only adds a timer around the original call.
- **(A)'s trickle is not covered.** A server sending a byte every < 30 s
  still holds npm. It needs the server itself to cooperate in being slow, and
  it hasn't been seen. #304's listing tells it apart from a connect stall.
- **T2 adds ≈ 75 s of mostly-idle time** to one test thread in the gate.

The prototype preload (the reds' green run and X3; the Developer writes the
real one to this plan, with the host:port in its message):

```js
'use strict'
const tls = require('tls')
const ms = 30000
const connect = tls.connect
tls.connect = function (...args) {
  const socket = connect.apply(this, args)
  const timer = setTimeout(() => {
    const e = new Error(`TLS connect to ${socket.servername || socket.remoteAddress || '?'} didn't finish within ${ms} ms`)
    e.code = 'ECONNECTIONTIMEOUT'
    socket.destroy(e)
  }, ms)
  timer.unref()
  const done = () => clearTimeout(timer)
  socket.once('secureConnect', done)
  socket.once('close', done)
  return socket
}
```
