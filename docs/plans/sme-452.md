# SME-452 recurrence plan (2026-11-08)

**Branch:** `cconstan/sme-452-recurrence`, from `origin/main` `5ff50ed3`.

SME-452's first fix (PR #300, `6db16e1909d8`) bounded npm's fetch stalls
and made a timed-out install carry its log tail. The flake came back on
PR #302's CI (run 42495207518, `server` job 128775997746, head `08be3abd`):

```
started: "The install didn't finish within 10 minutes. Its output so far:\n"
```

Nothing came after `so far:`. This plan explains why the log was empty. It
reproduces that empty-log signature on demand, settles whether production
is exposed, and fixes what can be fixed. It also makes the next
occurrence name its own cause.

**In short:** the evidence can't pin one mechanism. Two code paths give
this exact message, and both are still open on main:

- **(A)** npm is still running, silent.
- **(B)** the wait loop reads an exec the kubelet refused as "still
  running", and reads that exec's empty stdout as an empty log.

This plan closes (B) and the never-started case (C) for good. (A) is made
self-attributing: a timed-out install names the process still running. The
plan also gives (A) a hermetic reproducer that turns the exact CI signature
red every time. **Part 3 is instrumentation, not a fix of (A)'s trigger.**
The trigger, whatever made npm slow on that runner, stays unknown until the
next occurrence names it.

## 2. The candidates, measured or traced

Measurements M1–M3 ran in `node:22-slim` (npm 10.9.9, node v22.23.4) with
SME-452's `NPM_STALL_BOUNDS` exported, using the scripts in the Planner's
scratch directory. Results:

1. **CPU starvation of the pod: ruled out.** The pod's request is
   `cpu: 50m` (a tiny CFS weight), and the gate's load was real (the 1 s
   probe timeouts). But the timeline gives the pod **at least 5 m 19 s
   alone on an idle node** (15:43:17 to 15:48:36; no pod events after
   15:42:12). The same install takes 3.2 s alone (M1) and about 14 s
   through the test. Starvation could delay it, but it can't keep it
   unfinished on an idle node.
2. **DNS hanging outside npm's bound: ruled out.**
   - M3: with a nameserver that drops every packet, npm failed at **71 s**,
     writing `npm error code EAI_AGAIN … getaddrinfo EAI_AGAIN
     registry.npmjs.org` to the log.
   - With a pod-style `resolv.conf` (three search domains, `ndots:5`), the
     same failure came at **111 s**.
   - Either way the result is a logged error well inside 600 s, not
     silence. glibc's resolver always gives up, and npm's 30 s
     `fetch-timeout` timer runs while the lookup is pending.
3. **A registry request that never answers, or a body that stops: ruled
   out** by part 1's bounds. Round 1 measured both: at most 150 s per
   request, ending in a logged npm error (`network timeout`,
   `EIDLETIMEOUT`).
4. **npm writes nothing until it ends (M1): measured, and it's why the log
   says nothing.** A real `npm install --prefix /tmp/home/lsp
   pyright@1.1.414` into a non-TTY file wrote its first byte at **3,058 ms
   of 3,160 ms**: 23 bytes, `added 1 package in 3s`. So at every moment
   before the end, an npm install's log is empty. An empty log can't tell
   "npm never started" from "npm is 9 minutes in". With
   `npm_config_loglevel=http` (M4), npm logs each fetch as it completes:
   four lines, 373 bytes, first byte at 719 ms (`npm http fetch GET 200
   https://registry.npmjs.org/pyright 292ms (cache miss)`, …, the tarball
   at 1,889 ms).
5. **(A) npm alive but silent past the bound: possible, and reproduced
   (M2).** npm has no total-time bound. Its 30 s timeouts are idle times
   (round 1 measured this). A registry that answers the packument with
   `content-length` set, one byte every 20 s, keeps `npm install` running:
   **still running at 660 s, 0 bytes of log**, through part 1's bounds.
   That is the CI signature exactly. M2's container showed the processes
   (`/proc/*/status`, `/proc/*/cmdline`):
   `31 [S (sleeping)] npm install trick@1.0.0` (npm sets its own process
   title) and `22 [S (sleeping)] node /tmp/registry.js`.
   **Whether this was the trigger is not shown.** The runner's other
   downloads finished at the same time (gopls's `go install` at 15:40:53).
   But a slow path to `registry.npmjs.org` alone, about 6 MB of tarball
   arriving at under 10 KB/s, fits it.
6. **(B) The wait loop misreading: a real, open code path.**
   - `src/sandbox/exec.rs`'s `extract_exit_code` returns **0** for any
     terminal `Status` with no `ExitCode` cause.
   - The kubelet's exec server writes exactly such a status when the
     container runtime couldn't run the command: `newInternalError(err)`
     (`Failure`, reason `InternalError`, message `error executing command
     in container: …`, no causes). See
     [`cri-streaming/…/remotecommand/exec.go`](https://github.com/kubernetes/kubernetes/blob/master/staging/src/k8s.io/cri-streaming/pkg/streaming/remotecommand/exec.go).
   - `install_rc` then sees exit 0 with empty stdout, which is `Ok(None)`:
     "still running". It isn't counted as a failed read, and isn't logged.
   - `install_log` returns the same refused exec's empty stdout as `Ok("")`.
   - So an exec path into the pod that stayed refused in-band for the whole
     window gives **this exact message, even for an install that finished
     in 3 s**. Nothing in the job log rules it in or out: the kubelet logs
     the refusal (`runtime.HandleError`), and CI doesn't dump kubelet logs.
   - *Expected (unmeasured; my k3s here couldn't pull its pause image):*
     an exec of a binary that doesn't exist, on k3s's containerd, comes back
     as such an `InternalError` (`… OCI runtime exec failed: … executable
     file not found in $PATH`). The Developer captures it live as T2's
     fixture.
7. **(C) The install never started, or its log was never opened: closed by
   tracing, except one blind spot.**
   - The pod script is `mkdir -p "$HOME" && ( {install} ) > /tmp/install.log
     2>&1; echo $? > /tmp/install.rc`. The shell opens the log before the
     install runs.
   - A failed `mkdir` skips the install but still writes rc 1, which reads
     as "The install failed (exit 1)", not a timeout.
   - The container Started, and `sh` is PID 1.
   - The blind spot: a missing log reads as an empty one, because `tail`'s
     exit status is ignored. Part 2 closes it.
8. **Output written somewhere the tail doesn't read: same as 4.** npm's
   stdout and stderr both go to the log. Its debug log goes to
   `$HOME/.npm/_logs`, but only at exit.
9. **(B′) One exec hanging for minutes: open, unmeasured.** `exec_with` has
   no bound of its own. A record read that hangs holds the loop, and the
   message reads the same either way. Part 3 records the slowest read.

**What this leaves:** (A) or (B)/(B′). The evidence that exists can't pick
between them, so the plan doesn't pretend to.

## 3. Production exposure: **yes**

The model's `start_language_server` reaches the same loop:

- `src/lsp/manager.rs:131` `start` (the tool, and the test's `start` too)
  → `:157` `pods::start_with`
- → `wait_running` → `wait_installed`
- → `wait_installed_within(…, INSTALL_TIMEOUT = 600 s)`
- → `timed_out`.

So a user's call can block for 10 minutes and come back with `The install
didn't finish within 10 minutes. Its output so far:` and nothing after it,
by (A) or (B). (B) reaches further: every `exec_with` and `PodShell::run`
caller reads a refused exec as success with empty output. For example,
`lsp/manager/pod_files.rs`'s `head -c` read would see an empty file.

## 4. The fix

### Part 0: split (a move only)

`src/lsp/pods.rs` is 30,664 B, over the 30,000 B aim (round 2's nit 3:
"split out `pods/install.rs` when it next grows"). Move the install wait
into **`src/lsp/pods/install.rs`**:

- `INSTALL_TIMEOUT`, `InstallWatch`, `wait_installed`,
  `wait_installed_within`, `install_log`, `LOG_READ_TIMEOUT`,
  `bounded_read`, `install_rc`;
- `pods.rs` gets `mod install; use install::*;` (or re-exports), so
  `start_with`, `list_with` and the tests' `super::super::*` still see
  them.

This is a move only: no behaviour changes, and both builds and the test
build pass.

### Part 1: a refused exec is a failure (closes B everywhere)

In `src/sandbox/exec.rs`:

- `extract_exit_code`:
  - `status == "Success"` → 0;
  - an `ExitCode` cause → its code (as today);
  - **any other status** (a `Failure` with no `ExitCode` cause, such as
    `InternalError`) → **-1**, like no status at all.
- `exec_with`: for such a status, append `exec failed: <reason>: <message>`
  to `stderr`, so callers that show `stderr` say why.

Every caller treats a nonzero code as failure, so the change only moves
callers in the safe direction. `list_with`'s `install_rc` `Err` arm
already keeps `Installing` and logs. Update the doc comment's SME-7 note
("no exit code at all (implying 0)") to say that only `Success` implies 0.

### Part 2: the install wait counts a refused read, and says when the log is empty or missing

In `src/lsp/pods/install.rs`:

- `install_rc` becomes the exec plus a pure **`rc_of(ExecResult) ->
  Result<Option<String>, String>`**:
  - exit `-1` → `Err(stderr, or "the exec ended without a status")`, which
    the loop counts with `rc_read_failed`;
  - exit 0 with a non-empty stdout → `Some(rc)`;
  - any other exit (`cat`'s 1 while the record doesn't exist yet) →
    `Ok(None)`, as today.
- `install_log` becomes the exec plus a pure **`log_of(ExecResult) ->
  Result<String, String>`**: a nonzero exit is `Err("tail exited N:
  <stderr>")`. This was round 1's waived Low 4. The failure path's
  `unwrap_or_default()` keeps reading it as empty there.
- `timed_out`: `Ok(log)` with an empty `log.trim()` gives **`. It wrote no
  output.`** instead of a bare `Its output so far:`. This was round 2's
  waived Low 1.

### Part 3: a timed-out install names what was still running (attributes A and B′)

This part is instrumentation. It doesn't fix (A)'s trigger.

- **Each record read is timed.** `InstallWatch` keeps `rc_reads: u32` and
  `slowest_read: Duration`. `timed_out` adds `; N record reads, the slowest
  S s`. One read hanging for minutes (B′) shows up as a huge `S` and a
  small `N`; a healthy loop shows about 600 reads under 1 s each.
- **A process listing at timeout.** Before `start_with` deletes the pod,
  `wait_installed_within` runs one more exec, bounded by `LOG_READ_TIMEOUT`
  like the log read. It's a POSIX `sh -c` script that needs only `/proc`,
  `tr`, `sed` and `head`, so it works in `node:22-slim`, busybox and Alpine
  images. It lists:
  - whether `/tmp/install.rc` exists, and what it holds;
  - `/tmp/install.log`'s size in bytes (`wc -c`);
  - each process except PID 1 (the pod script, whose text is the install
    command itself) and the script's own shell: `pid [State]` plus the
    **first two words** of its command line (`npm install`, `curl -fsSL`,
    `go install`). `environ` is never read, and the listing is capped at
    2,000 bytes.

  M2's state gives `31 [S (sleeping)] npm install` and `22 [S (sleeping)]
  node /tmp/registry.js`. The message gains `; still running then: <the
  listing>`, or `(its processes couldn't be read: …)`. If the exec path is
  what's broken (B), this exec fails too. Since part 1, that failure is
  named (`exec failed: InternalError: …`) rather than read as empty.
- **npm logs each fetch.** Add `("npm_config_loglevel", "http")` to
  `NPM_STALL_BOUNDS` (Q1). Every finished registry request writes a line,
  so a log tail that stops after the packument says the tarball was in
  flight, and a log with no lines at all points to the first request. The
  user's own `env` still wins, by the existing filter.

### How the next occurrence reads, by cause

| Cause | The message after this fix |
|---|---|
| (A) npm slow or silent | `It wrote no output` (or `npm http fetch …` lines), `still running then: … npm install`, about 600 fast reads |
| (B) exec refused in-band | `its record couldn't be read N times (last: exec failed: InternalError: …)` and `(its processes couldn't be read: exec failed: …)`; an install that had finished reads as its rc instead, on the first read that gets through |
| (B′) one read hanging | `N record reads, the slowest S s` with `S` in minutes |
| (C) never started | `(its output couldn't be read: tail exited 1: … No such file …)`, no `install.rc`, no install process |

## 7. State model

The record is `/tmp/install.rc` and `/tmp/install.log` in the server pod,
written by the pod script only. They're lost with the pod, which
`start_with` deletes on any failure. The new reader is the timeout's
process listing, which only reads `/proc`.

What each reader does with each result of a record read:

| Read gives | wait loop, today | wait loop, after | `list_with`, today | `list_with`, after |
|---|---|---|---|---|
| exit 0, `0` | Ok (Ready) | same | Ready | same |
| exit 0, `N≠0` | fails with log | same | Installing | same |
| exit 1 (no record yet) | still running | same | Installing | same |
| no status, or refused (-1 after part 1) | **still running, silent** | a failed read, counted and named at timeout | **Installing, silent** | Installing, logged (existing `Err` arm) |
| upgrade failed (`Err`) | counted | same | Installing, logged | same |

Work in flight: a start already waiting when the deploy rolls out goes with
the old process. Nothing persists.

**Error text reaching a new sink** (the tool result the model reads):

- the process listing: a process's first two words only, never `environ`
  and never PID 1's script;
- the runtime's refusal message (container ids, the command's first word);
- `tail`'s `stderr`.

None of these quotes the config's `env` values. T5's listing is in the
real caller's shape, through `wait_installed_within`.

## Trade-offs to flag

- **(A)'s trigger is still not fixed.** A truly slow registry path still
  fails the install at 10 minutes. Afterwards it says so (the process
  listing and npm's fetch lines) instead of failing silently. The catalog
  tests stay end-to-end against the real registry. Making them hermetic
  (an npm cache in the image, or a local mirror) is a different change.
- **npm installs log more.** With `loglevel=http` a failed npm install's
  message carries one line per fetch (4 lines for pyright, M4) before
  npm's error. That's within the 4,000-byte tail.
- **Part 1 changes every exec caller.** A refused exec now fails where it
  used to "succeed" with empty output. That's the correct reading, but a
  caller that today silently gets `""` (`pod_files`' read, say) will
  surface an error instead.
