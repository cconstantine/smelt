# SME-457 — the browser tier's `== web bundle` hang

**Branch:** `sme-457-dx-bundle-hang` (pushed; from `origin/main` 5ff50ed3)
**Ticket:** SME-457 (team Smelt Agent, project "Test reliability"). Planner plan.

## What

`scripts/browser-tier` hangs forever at `== web bundle`: `dx build --platform web`
prints its client line, then nothing, while its child
`cargo +nightly rustc --unit-graph … --profile server-dev` sits at ~0% CPU (4h45m
observed on SME-441's round-tip gate). The mechanism is found and reproduced on
demand; this plan fixes it at the mechanism, bounds the step loudly, and pins both
with shell tests that run in `check.sh`.

## Mechanism (found, reproduced)

1. `scripts/browser-tier:80` runs `dx build --platform web` **unwatched**.
2. dioxus-cli 0.7.9's build path calls `get_unit_count_estimate`
   (`build/request.rs:1030` → `:2331` → `:2353`), which spawns
   **`cargo +nightly rustc --unit-graph -Z unstable-options …`** (`:2360`) — the
   exact stuck child in the ticket. A failing estimate is swallowed by design
   (`if let Ok(count)`, `:2333`): it's only a progress count.
3. The smelt stack image has **stable only** (probe below). `cargo` is rustup's
   shim, and rustup **auto-installs a missing toolchain from the network**
   (`RUSTUP_DIST_SERVER`). The download has no timeout.
4. On a TCP path that accepts but never answers (sandbox networking's stall
   mode), rustup blocks forever: state `S`, `wchan=futex_wait`, ~0 jiffies CPU,
   and the child's fds show the tell — `…/usr/local/rustup/tmp/<rand>_file`
   plus a socket. `dx` waits on the child forever. Whichever profile's estimate
   hung first decides whether the last log line is the client-completed one
   (SME-441) or silence before it (our repro, where both profiles' estimates
   hang). `check.sh` itself never runs `cargo +nightly`, so it stays green —
   exactly the observed pattern.

**Why now.** SME-385 made the full chain run at every push point, and every
push point now runs `dx build`, i.e. rolls the rustup-network coin every time.
There is no cargo-registry or rustup volume in `docker-compose.yml`:
`/usr/local/rustup` lives in the image layer, so a fresh `docker compose run`
container has no nightly and tries the download again. It succeeds (costing
minutes, unnoticed) or, rarely, stalls — hours, at 0% CPU. CI's SME-67 hang
("the server half sometimes hangs without logging a line, after the client
bundle is written") is *very likely the same coin on a runner* — unverified,
CI logs weren't kept; the fix removes it there too.

**The Driver's lock candidates, examined.** Holding cargo's build-directory and
package-cache locks does also stall `dx build` silently (probe 4), but cargo
then prints `Blocking waiting for file lock` / `(Try N) Taking a while…` within
seconds — SME-441's log had none — and a lock waiter has no rustup tmp fd or
socket. Shared `target/` between check.sh and browser-tier is **not** the
mechanism; leftover lock-holders remain possible-but-unobserved stalls, and the
bound below caps them too.

## Evidence (live probes, this sandbox, compose stack, 2026-11-08)

1. **Red, on-demand:** with `RUSTUP_DIST_SERVER` pointed at a TCP listener that
   accepts and sleeps (python3, port 8123), `dx build --platform web` hangs;
   recipe in **Hand-check**. Observed: `rc=124` at a 120 s guard; stuck child
   `cargo +nightly rustc --unit-graph -Z unstable-options --config
   profile.server-dev.strip=false … --profile server-dev …`, state `S`,
   `wchan=futex_wait`, cputimes 1 jiffy, `fd 6 -> /usr/local/rustup/tmp/…_file`,
   `fd 7 -> socket[…]`. Signature matches the ticket.
2. **Green, same stack:** `RUSTUP_AUTO_INSTALL=0 cargo +nightly --version` →
   `error: toolchain … not installed`, rc=1, **9 ms**. With it exported, a full
   `dx build --platform web` completes green, warm, in **14.4 s** — dx swallows
   the failed estimate exactly as its source says.
3. **Image facts:** fresh container has no nightly toolchain; its rustup
   honours `RUSTUP_AUTO_INSTALL` (probes 1–2 are the A/B on the same image).
4. **Lock alternative:** `flock` on `target/debug/.cargo-lock` +
   `/usr/local/cargo/.package-cache` + `dx build` → `rc=124` at 90 s with cargo
   `(Try 42) Taking a while…` warnings in the log. A real stall, a different
   mechanism, named in its own log — absent from SME-441's.

## Fix

At the mechanism, plus a bound that fails loudly. The bound alone is not the fix.

1. **`scripts/ci-web-bundle`: `export RUSTUP_AUTO_INSTALL=0`** for the watched
   dx child. Every caller of the watched bundle build inherits it; `cargo
   +nightly` now fails fast, the estimate is ignored, dx builds. Header comment
   cites SME-457 and notes SME-67's hang as the same mechanism (hypothesis).
   Same posture as `CARGO_NET_OFFLINE=true` (SME-442): the gate makes its
   network behaviour deterministic instead of hoping.
2. **`scripts/browser-tier`: run the bundle step through `scripts/ci-web-bundle`
   under a hard cap**:
   `timeout -k 30 "${SMELT_BROWSER_TIER_BUNDLE_TIMEOUT:-1800}" scripts/ci-web-bundle >"$log" 2>&1`;
   rc 124 → tail the log and fail naming the step, the cap, and what was waited
   on (`dx build --platform web` — a stalled toolchain download or cargo lock;
   pointer to docs/testing.md), rc≠0 → today's "dx build failed" path, rc 0 →
   continue. `ci-web-bundle`'s TERM trap + process-group kill mean the cap
   leaves nothing running. Post-client silence passes with SME-67's warning —
   correct here: the tier serves `target/dx/smelt/debug/web/public` and builds
   its own server with `cargo test`, same reasoning as CI (ci-web-bundle
   header). The cap is needed because ci-web-bundle deliberately leaves
   *pre-client* silence to "the step's timeout" — a seat has no step timeout.
   1800 s is ~5× a cold in-stack bundle (warm rerun 14 s; SME-67's note says the
   server half normally ends ~40 s after the client; the first-ever run adds
   wasm tooling and a full server build — minutes). Chosen, not measured; overridable.
3. **`scripts/check-server`: add `RUSTUP_AUTO_INSTALL=0` to the `dx serve`
   env** (the overrides array at its `exec setsid env "${overrides[@]}" dx serve
   …`, line ~518). `dx serve` shares the estimate path; today it can hang the
   same way, and its hangs survive the run.
4. **Tests** (both files already run in `check.sh`'s list — no `check.sh` change):
   - `scripts/test-ci-web-bundle`: a fake dx asserting the child sees
     `RUSTUP_AUTO_INSTALL=0` (exits 7 when it doesn't).
   - `scripts/test-gate-scripts`: a new case — a stubbed bundle dx that logs
     nothing and sleeps, run through browser-tier with
     `SMELT_BROWSER_TIER_BUNDLE_TIMEOUT=6 CI_WEB_BUNDLE_DX=…` under the case's
     own `timeout 90`: browser-tier must exit non-zero naming `web bundle`.
     Also fix the existing CALLS expectation for the new call shape (expected:
     `dx build --platform web --verbose unlocked` — a prediction, the
     Developer records the actual).
5. **Docs**: `docs/testing.md` — browser-tier section gains the watcher/cap,
   the SME-457 signature, how to diagnose (stuck-child fds) and reproduce.
   `docs/setup.md` — a few lines: stack toolchain env posture (file is at
   36,600 B, ~3.4 KB under the ceiling — keep the addition under 1 KB).
   `docs/process/rules-commits.md` — no change: the push-point chain itself is
   unchanged; behaviour lives in testing.md.

## Hand-check (this is also the on-demand hang reproduction — red on the unfixed scripts)

```bash
# silent TCP sink on the compose network (the stack image has python3):
docker compose run -d --name sme457-hole --no-deps --entrypoint python3 smelt -c \
  'import socket,time
s=socket.socket(); s.setsockopt(socket.SOL_SOCKET,socket.SO_REUSEADDR,1)
s.bind(("0.0.0.0",8123)); s.listen(128)
while True: time.sleep(60)'
hole=$(docker inspect -f '{{range .NetworkSettings.Networks}}{{.IPAddress}}{{end}}' sme457-hole)

# RED (unfixed scripts): hangs; rc=124 under the guard. Observed today: rc=124,
# child cargo +nightly rustc --unit-graph … S/futex_wait/0 CPU.
docker compose run --rm --no-deps -T smelt bash -c \
  "timeout 120 env RUSTUP_DIST_SERVER=http://$hole:8123 dx build --platform web; echo rc=\$?"

# GREEN (fixed): the watched step through ci-web-bundle (or with
# RUSTUP_AUTO_INSTALL=0 exported) completes; observed warm: 14.4 s.
docker compose run --rm --no-deps -T smelt bash -c \
  "RUSTUP_DIST_SERVER=http://$hole:8123 scripts/ci-web-bundle"

# check-server: start one with RUSTUP_DIST_SERVER pointing at the sink —
# it serves; the estimate fails fast. Clean up: docker rm -f sme457-hole.
```

Full-gate check: `scripts/check.sh` green; `scripts/browser-tier` completes its
bundle step; a deliberately hung stub fails in ≤ cap + 30 s with the named
message (the gate-scripts case automates this).

## Trade-offs

- dx's progress display shows unit counts as unknown in the stack (the estimate
  is cosmetic; this is already its behaviour whenever the estimate command
  fails — nightly was never installed deliberately).
- The browser tier inherits SME-67's pass-on-post-client-silence (with a
  `::warning::` line): a stall that leaves the client bundle finished no longer
  fails the tier, it warns; the tier's real server comes from `cargo test`.
- A seat that genuinely wants nightly installs it into the image (or unsets the
  variable per call); the gate never downloads a toolchain mid-run.
- The 1800 s cap bounds unknown stalls (including leftover cargo-lock holders —
  probe 4) at the cost of a slow failure that names itself; a red on it is
  always a hung gate, never a merely slow one, if the cap stays ≥5× the cold run.
