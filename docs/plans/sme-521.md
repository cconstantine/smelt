**Evidence:** traced in code at `fdf9474`. Steps that depend on live facts are marked **[live]** and written with both branches.

## What, and why

Today the storage-grace pass (SME-345) is **row-driven**. It picks conversations whose latest `sandbox_pods` row has `quietly_stopped_at`, and only `PodEnd::Quiet` (idle stop, finish stop) sets that. Every other end leaves claims for good: `terminate_pod`, a lost pod, a failed create, a finished agent whose pod was already gone, rows from before `20261102120000`, and the user's Stop. A claim with no row at all is never looked at.

This plan makes the pass **claim-driven**. The pass lists this instance's conversation claims in the cluster. For each conversation that holds claims, one rule (`grace::fate`) decides from the database whether its storage is live, kept, or due, and when. The clock is the latest row's `terminated_at`, whatever ended it, or the claim's own creation time when there is no row. So:

- Every way a pod ends gets a clock (item 1), with no per-path marking to forget. A new end path added later is covered too.
- Old rows need no backfill write (item 3): `terminated_at` is already set on every ended row.
- A claim with no row is seen, because the claims are the input (item 4).
- The same rule feeds the Pods page's counts (item 6), so the page and the pass can't disagree.

The grace is chosen per conversation (item 2), in this order:

| # | Conversation's state | Grace | Setting (default) |
|---|---|---|---|
| 1 | Latest row live | none: in use | — |
| 2 | Sub-agent whose `agents.state` is `finished`, `stopped` or `failed` | short | `SANDBOX_AGENT_STORAGE_REMOVAL_DAYS` (1) |
| 3 | Latest row ended by the user's Stop (`stopped_by_user = true`) | long, or kept | `SANDBOX_USER_STOPPED_STORAGE_DAYS` (30, Q1) |
| 4 | Latest row ended before this change by something other than a quiet stop (`stopped_by_user IS NULL AND quietly_stopped_at IS NULL`): its end can't be told | as row 3; row 5 when row 3's setting is 0 | — (Q3) |
| 5 | Any other end: quiet stop, `terminate_pod`, lost pod, failed create | default | `SANDBOX_STORAGE_REMOVAL_DAYS` (7, unchanged) |
| 6 | No pod row at all | by rows 2/5 on the claim's `creationTimestamp` | — |

`0` on rows 2, 3 or 5's setting means "kept until removed by hand" for that class. `SANDBOX_STORAGE_REMOVAL_DAYS=0` stays the whole pass's off switch, as today. All three settings are whole days from 0 to 365 and are parsed by the existing `storage_removal_days_from` shape. They're read once at startup.

## How

### Data model

New migration `migrations/20261115120000_sandbox_pods_stopped_by_user.sql`. It sorts after the latest one, `20261114120000_model_call_kind_reseed.sql`:

```sql
-- SME-521: whether the user's Stop ended this pod (true), or something
-- else did (false). NULL: still live, or ended before this column
-- existed, when a Stop and a terminate_pod looked the same. The
-- storage-grace rule reads it to pick the grace (docs/plans/sme-521.md).
ALTER TABLE sandbox_pods ADD COLUMN stopped_by_user BOOLEAN NULL;
```

No backfill `UPDATE`: the rule reads `terminated_at`, which every ended row has. `SandboxPod` (`SELECT *` / `RETURNING *`) ignores the extra column, as it already ignores `quietly_stopped_at`.

`db::terminate_sandbox_pod_as` (`src/db/sandbox/mod.rs`) writes it in the statement that closes the row:

- `Plain` sets `stopped_by_user = COALESCE(stopped_by_user, false)`. It must not turn a Stop into a non-Stop: `create.rs`'s failure paths run `Plain` on a row the user's Stop may already have closed (SME-122's B1 window).
- `Quiet` sets `false`. It only closes a live row.
- `ByUser` sets `true`, and keeps clearing `quietly_stopped_at` as today.

`quietly_stopped_at` stays as it is: still stamped by quiet stops and cleared by the pass, the Stop and the user's removal. Only row 4 and the Pods page's "quiet" wording read it now. Dropping it isn't worth the churn, and keeping it keeps a rollback to `fdf9474` working.

### The rule: `src/sandbox/storage_grace/rule.rs` (new, pure)

```rust
pub(crate) struct GraceSettings { pub default_days: u32, pub agent_days: u32, pub user_days: u32 }
pub(crate) struct GraceInput {            // one conversation, from the database
    pub latest: Option<LatestPod>,        // None: no pod rows
    pub agent_done: bool,                 // agents.state IN ('finished','stopped','failed')
}
pub(crate) struct LatestPod { pub pod_id: i64, pub terminated_at: Option<NaiveDateTime>,
                              pub stopped_by_user: Option<bool>, pub quiet: bool }
pub(crate) enum Fate { Live, Kept, RemovesAt { at: NaiveDateTime, days: u32, class: GraceClass } }
pub(crate) fn fate(input: &GraceInput, oldest_claim: NaiveDateTime, s: &GraceSettings) -> Fate
```

`Due` is `RemovesAt` with `at <= now`, compared by the caller on the database's clock (SME-354 B14's rule). `GraceClass` (`Agent`, `UserStop`, `Unknown`, `Default`, `NoPod`) is there for the notice text, the Pods page and the logs. It goes in its own file so the Pods page (`api/pods.rs`) and the pass share it, and its tests need no database.

### Settings: `src/sandbox/storage_grace/settings.rs` (new)

`storage_removal_days()` moves here unchanged. Next to it go `agent_storage_removal_days()` and `user_stopped_storage_days()`, each with the same `OnceLock` and parser: `days_from(name, setting, default)`, generalized from `storage_removal_days_from`, which stays a thin wrapper so its tests keep their names. Then `grace_settings() -> GraceSettings`.

### The pass: `src/sandbox/storage_grace/mod.rs` (was `src/sandbox/storage_grace.rs`)

The first commit is a pure move: `storage_grace.rs` becomes `storage_grace/mod.rs`, so the diff of the rewrite reads clean.

`remove_expired_storage_once_with(pool, settings, removal_timeout, list, remove)` gets an injected `list` beside the existing injected `remove`. The real `list` is `list_stored_claims(client, instance)`, which reads the claims with the Pods page's selector (`smelt/conversation`, `smelt/instance=<ours>`). It returns `StoredClaims { by_conversation: BTreeMap<i64, ClaimSet> }`, where `ClaimSet` has the names, the oldest `creationTimestamp` among claims not being deleted, and whether every claim is deleting. Tests pass a fixed snapshot, so the pass's tests still need no cluster.

One pass:

1. `list()`. On an error, log a warning and skip this pass. Skip conversations whose claims are all deleting already.
2. Make one database read for those ids: `db::storage_grace_inputs(pool, &ids)`. For each conversation it returns whether it exists, its latest row (`DISTINCT ON (conversation_id) … ORDER BY id DESC`), whether its `agents.state` is done, and `now()`.
3. Gone conversations are counted as `orphaned` and left to the startup sweep (`sweep_orphaned_conversation_claims`), as today. Each of the rest gets its `fate`.
4. **Log one line every pass:** `info!(stored, live, kept, waiting, due, orphaned, removing, "storage grace pass")`. This is item 6's log half.
5. Take the due ones, oldest `at` first, **at most `STORAGE_REMOVALS_PER_PASS = 20` conversations** (40 claims) per hourly pass. That bounds the first pass after deploy, and the local-path helper pods each delete starts (see Trade-offs).
6. For each one, keep today's settle shape: skip while its turn runs, `between_turns`, `try_lock` its start lock, then re-check under both locks. The re-check is `db::storage_grace_input(pool, id)` plus `fate` again, and it must still be due **with the same latest pod id (or still none)**. A pod started since the list, a conversation woken from `finished` to `active`, or one deleted, each skips it.
   - **Row case:** same as today. `start_storage_removal(pod_id)` (B13), the bounded `remove`, then settle: `forget_storage_removal_attempt`, the notice, then `clear_pod_quiet_stop_mark`. That clear is now only bookkeeping: once the claims are gone the conversation isn't listed again.
   - **No-row case (item 4):** the bounded `remove`, with no attempt record and **no notice**: no pod ever ran, so the model has nothing it lost. A failure or a claim left behind is retried next pass, as today.
7. The notice text takes the class's days: "after {days} days stopped". For an agent it says "after {days} day(s) finished".

`remove_conversation_storage_locked` (`manager/storage.rs`) is unchanged. It already stops what mounts the claims (its live rows, its language-server pods), waits for them to go, and deletes the two claims by name and uid, keeping only claims labelled as ours.

## State model

**Records:** a conversation's claim pair (in the cluster), its latest `sandbox_pods` row (`terminated_at`, `stopped_by_user`, `quietly_stopped_at`, `storage_removal_started_at`) and its `agents.state`.

**Writers of the row fields:**

| Field | Writers |
|---|---|
| `terminated_at` | `Plain` (overwrites: `terminate_pod`, `watch::close_if_gone` → `force_terminate_pod`, each `create.rs` failure path, the removal's `force_terminate_pod`); `Quiet` (live rows only); `ByUser` (`COALESCE`) |
| `stopped_by_user` | `Plain` → `COALESCE(x, false)`; `Quiet` → `false`; `ByUser` → `true` |
| `quietly_stopped_at` | `Quiet` sets it; `ByUser`, the pass's settle and the user's removal clear it |
| `storage_removal_started_at` | the pass (start, forget, clear); the user's removal (clear) |
| `agents.state` | `finish`, `stop_agent`, failure, and `message_agent` waking it (`active`) — all under the guarded `UPDATE … WHERE state = …` |

**Readers:** the pass's list read and its locked re-check, the Pods page (`stored_storage`), and the prompt (settings only). The pass decides twice: once from the list and once under both locks. Between the two, a pod start makes a newer row, a wake sets `active`, or a delete removes the conversation, and the re-check skips all three. After the re-check nothing can change under it: a start needs the start lock, which the pass holds, and a wake that comes after the re-check queues on the turn lock, then finds the claims gone and gets the notice. That's today's SME-345 race, unchanged.

**Per conversation, state × event:**

| State ↓ / event → | pod starts | pod ends (any way) | agent finishes | agent woken | grace passes (pass runs) | user removes storage | conversation deleted |
|---|---|---|---|---|---|---|---|
| no claims | claims made → Live | — | — | — | not listed | no-op | — |
| claims, **no row** (item 4) | row made → Live | — | class Agent | class Default | removed, no notice | removed | teardown / startup sweep |
| **Live** | refused (one live pod) | → Waiting (clock = `terminated_at`) | still Live | still Live | skipped | pod stopped, claims removed | teardown |
| **Waiting** (clock running) | → Live (newer row) | (Plain on an old row moves the clock forward; harmless) | grace → agent days | grace → default/user | not due: counted | removed, marks cleared | teardown |
| **Due** | → Live, re-check skips | — | — | re-check reads new state | removed (cap 20/pass), notice for row case | removed | re-check skips |
| **Kept** (class days 0) | → Live | — | may become Due (agent days) | — | counted as kept | removed | teardown |

**Failure partway, per transition:**

- **List fails:** the pass is skipped and logged. Nothing is changed.
- **Inputs read fails:** same.
- **Re-check fails:** that conversation is skipped (as today).
- **`start_storage_removal` fails:** skipped, nothing deleted (as today).
- **Removal times out, errors, or leaves a claim:** the claims or the attempt record stand, there's no notice, and the next pass lists the claims again and retries (as today; SME-350's silent case is unchanged and stays its own ticket).
- **Removal fine, `forget` or `clear` fails:** the next pass doesn't list the conversation, because its claims are gone, so nothing is retried and the stale `storage_removal_started_at` stays harmless. That's an improvement: today it re-settled. Note that the B13 notice-on-retry path needs the claims listed. Today a given-up attempt whose deletes landed already ends unannounced (SME-350), and this keeps exactly that.
- **No-row removal partway:** retried next pass while any claim remains. No notice either way.
- **Writing `stopped_by_user` fails:** that's the same statement that closes the row, so the row isn't closed and the pod is still live (today's rule in `terminate_pod_as`).

**What each caller does in each state:**

| Caller | Live | Waiting | Due | Kept | No row | Orphaned |
|---|---|---|---|---|---|---|
| Pass | skip | count | remove (cap) | count | remove when due, no notice | count; startup sweep deletes |
| Pods page | "running" | "removed in N days" | "removed within the hour" | "kept until you remove it" | "never started · removed in N days" | not shown (no title), counted in summary |
| User's Remove | removes | removes | removes | removes | removes | — |

**Work in flight:** the settings are read once at startup. A restart with new values applies at the next pass. A removal already running keeps the timeout and days it read, and the notice names those days.
