# SME-465 — deployer `terraform init` GitHub release-asset 504 stalls

**Branch:** `cconstan/sme-465-deployer-terraform-init-stalls-on-github` (pushed; from `origin/main` `b3f947e50cb3`)
**Ticket:** SME-465 (team Smelt Agent, project "Test reliability", Urgent). Planner plan; Driver is the ticket's authority (no PM above it).

## What

A fresh Deployer seat's step-2 `terraform init -input=false` fails — repeatedly, for
tens of minutes — because some of this repo's providers ship as **GitHub release
assets** and GitHub's release-asset download path intermittently answers **504 for
hours**. Two deploys ate it: `6db16e1909d8`'s ("about 20 tries over about 20 minutes",
SME-326 comment `08d3a73f`) and SME-447's (3 failed inits, worked around with a
hand-built verified mirror, comment `23b9290a`). The fix is to **pre-provision that
mirror in the deploy procedure itself** — homelab's `smelt-deployer/DEPLOY.md` gains a
script that builds a `zh:`-verified local provider mirror *before* init, and a CLI
config that forces `terraform init` to use it for exactly the GitHub-hosted providers.
Retry-until-green stays ruled out; the lockfile's checksum verification stays live and
is what makes the mirror trustworthy.

**Proven already by a seat (this planning sandbox, 2026-11-09, live incident partly
still up):** the mirror route end-to-end under a simulated 504 host — and the exact
tamper that must make init fail — see Evidence.

## Mechanism (measured, 2026-11-09)

- Root `.terraform.lock.hcl` pins seven providers; **three** download from
  `github.com/.../releases/download/...`: `gavinbunney/kubectl` 1.19.0,
  `ryanwholey/pihole` 0.2.0, and — not named in the ticket, same exposure —
  `cloudflare/cloudflare` 5.28.1. The four `hashicorp/*` come from
  `releases.hashicorp.com` and were observed installing fine *during* the live 504s.
- `github.com/.../releases/download/...` 302s to `release-assets.githubusercontent.com`
  (measured `location:` head). During the incident the 504 came from the
  `/releases/download/` redirector (`504 Gateway Timeout returned from github.com`
  in terraform's own error, measured in-seat while writing this plan); `api.github.com`
  answers fine, and its **asset octet-stream endpoint** —
  `GET /repos/<owner>/<repo>/releases/assets/<id>` with `Accept: application/octet-stream`
  — delivered all three full zips in-seat today.
- **`zh:` in the lockfile is the sha256 of the distribution zip**: measured
  `sha256(kubectl linux_amd64 zip) = dd7dd18f1f82…` and `sha256(pihole) = a6e23c12…`
  and `sha256(cloudflare) = 2ae20048…`, each present in that provider's `zh:` set.
  So a mirror builder can authenticate every download against the lockfile alone —
  no extra trust, no published-SHA256SUMS dependency.
- Terraform 1.15.9's filesystem **packed layout** (`<mirror>/registry.terraform.io/
  <ns>/<type>/terraform-provider-<type>_<version>_<target>.zip` — the release asset's
  own filename) installs with `terraform init` verifying against the lockfile.
  A filesystem mirror skips the publisher *signature* check (installs print
  `(unauthenticated)`); the lockfile checksum set is the verification, and it is
  **live** — see the swap-tamper probe.
- **A loose mirror config is not enough** (measured): `filesystem_mirror { path }` +
  `direct { }` with no include/exclude still queried the origin registry for a
  mirrored provider during the live 504s and failed; and at full-repo init terraform
  installed a mirrored provider *from direct* when it happened to answer
  (`self-signed, key ID` instead of `(unauthenticated)`). The config must pin the
  choice: `filesystem_mirror { path, include = [mirrored…] }` plus
  `direct { exclude = [mirrored…] }`. With that, init passed through a 504-everything
  on github.com proxy. (SME-447's seat used a loose config under a mostly-healthy
  host, so its success does not contradict this.)
- `terraform init`'s own retry is bounded ("the request failed after 2 attempts");
  the 20-minute stalls were seats re-running init by hand — exactly what the
  mechanism removes from the path.

## Fix

### 1. homelab: `smelt-deployer/tf_provider_mirror.py` (new, stdlib-only Python 3)

Run from the repo root (DEPLOY.md's step 2 cwd). Behaviour:

1. Parse `.terraform.lock.hcl` (its format is terraform-generated and stable): for
   each `provider "<source>" { version = "<v>" hashes = [… "zh:<hex>" …] }` block,
   the source address, version and set of `zh:` hashes. Never writes the lockfile.
2. For each provider, `GET https://registry.terraform.io/v1/providers/<ns>/<name>/
   <version>/download/linux/amd64` (probe-confirmed shape: returns `download_url`
   and `filename`). If `download_url`'s host is **`github.com`**: parse
   `owner/repo/tag/filename`, `GET api.github.com/repos/<owner>/<repo>/releases/tags/
   <tag>` to find the asset id by name, `GET api.github.com/repos/<owner>/<repo>/
   releases/assets/<id>` with `Accept: application/octet-stream`, follow the redirect,
   stream to a temp file. Non-github providers are left alone (direct handles them;
   releases.hashicorp.com held up through the incident).
3. **Verify `sha256(zip) ∈ zh:` before placing anything**; mismatch or any fetch
   failure → delete temp, print the provider and reason, exit non-zero. Place at
   `<mirror>/registry.terraform.io/<ns>/<name>/<filename>` (packed layout), staging
   via temp + rename.
4. Idempotent: an existing mirrored zip whose sha256 is still in the lockfile's `zh:`
   set is kept without re-fetching (re-runs in the same seat are free).
5. Write `~/deploy.tfrc` **last, atomically**: `provider_installation` with
   `filesystem_mirror { path = "<mirror>", include = [<exactly the providers mirrored>….] }`
   and `direct { exclude = [same…] }` (the strict pin — see Mechanism; this is the
   form measured green under the 504 proxy). `include`/`exclude` are generated from
   what the script classified, so a future lockfile that adds another GitHub-hosted
   provider is covered by re-running it, and a lockfile version bump re-fetches.
6. Defaults `--mirror ~/tf-mirror --config ~/deploy.tfrc --target linux_amd64`.
   No secrets read or sent (the GitHub API route is unauthenticated; ≈6 calls per
   cold build against a 60/h/IP core limit — the deployer seats share one egress IP,
   so watch it in Trade-offs). No `-lock=false`, no lockfile writes, no network
   beyond registry.terraform.io + api.github.com, and no fallback to the flaky
   `/releases/download/` path: if the API route fails the script fails loudly and
   DEPLOY.md says stop-and-report.

### Why not bake the mirror into the sandbox image

- The smelt sandbox image is the **product** image (tagged off smelt's agent sources
  / smelt sha); provider zips belong to **homelab's lockfile**, which bumps
  independently — a baked mirror is stale the moment the lockfile moves, and a stale
  zip is worse than none (init fails checksum and the seat has no idea why).
- It grows every seat's image ~100 MB+ (the three zips are ~110 MB, cloudflare's
  alone ~65 MB) for one persona's step 2.
- The script re-derives from the lockfile per seat, so provider bumps and future
  additions need no image change, and homelab remains the single source of the
  deploy procedure (the seat's `git pull --ff-only` already pulls it fresh).
- DEPLOY.md's own posture is step-2 installs (kubectl, terraform) per sandbox; the
  mirror joins that set, not a new layer.

## State model

Actors: **Driver** (pin, dispatch), **Deployer seat** (one conversation, fresh pod),
**`tf_provider_mirror.py`**, **terraform**, hosts (`registry.terraform.io`,
`api.github.com`, `github.com` release path, `release-assets.githubusercontent.com`,
`releases.hashicorp.com`).

Seat from first command to init done, under a broken release-asset host:

| state | mover | what's true / can fail |
|---|---|---|
| fresh sandbox | seat | nothing under `~/`; step 2 installs kubectl+terraform (`dl.k8s.io`, `releases.hashicorp.com` — unaffected hosts); failure = report (unchanged) |
| repo at master | seat | `git checkout master && git pull --ff-only` (step 2) — after the pin push this carries the new DEPLOY.md *and* the script; a seat pinned at an old sha reads the old text and behaves exactly as today |
| mirror: cold | script | 3 providers × (tag lookup + asset download) + 7 registry lookups; every placed zip `zh:`-checked at placement; mid-way failure deletes temp, exits non-zero → **stop-and-report** (mirror may hold earlier zips; safe: each is `zh:`-valid or absent, re-run skips-or-redoes per provider) |
| mirror: warm | script | zips whose sha256 ∈ `zh:` kept, no network for them; a lockfile bump or mismatched stale zip → refetch, never install the mismatch |
| tfrc | script | `~/deploy.tfrc` exists **iff** the script's *last completed run* succeeded (written last — a failed later re-run, the pin-shrink guard included, leaves the earlier tfrc standing); a completed re-run overwrites it whole; no default `~/.terraformrc` exists in seats |
| init | terraform | mirrored 3 install from disk `(unauthenticated)`, verified against the lockfile's recorded checksums (swap-tamper proves refusal); the other 4 install direct as today; module fetch (`git::https://github.com/cconstantine/smelt.git`) and backend are **not** on the release-asset path — the incident never broke them, this fix does not cover them |
| init done | seat | plan/apply as today; `TF_CLI_CONFIG_FILE` matters only for init |
| pod death | — | `~/bin`, `~/tf-mirror`, `~/deploy.tfrc`, `.terraform/` all lost together; a recreated seat rebuilds from step 2 (DEPLOY.md's pod-recreate ban stands; this row is only why there is no cross-seat mirror state to reason about) |

Writers of the mirror are one seat's script (per-pod `$HOME`, no sharing). Readers:
only that seat's `terraform init`. The lockfile has exactly one writer class (humans
recording version bumps in homelab PRs); this mechanism never joins it. A deploy in
flight while the tooling commit lands on master: only step 6's pin push can feel it
(`git push origin HEAD:master` refuses non-ff) — sequencing below minimizes it, and
DEPLOY.md's existing "refused → report the commit" rule catches the residue.

## Appendix A — `proxy504.py` (the demo simulator, verbatim as measured)

Lives at `<scratchpad>/sme-465/proxy504.py` (not committed); the Developer starts it
with `python3 proxy504.py 8443` and points terraform at it with
`HTTPS_PROXY=http://127.0.0.1:8443`. It answers `504 Gateway Timeout` to `CONNECT
github.com` / `CONNECT www.github.com` and tunnels every other host untouched —
exactly the incident's shape (asset redirector down; `api.github.com`,
`release-assets.githubusercontent.com`, `registry.terraform.io`,
`releases.hashicorp.com` live).

```python
#!/usr/bin/env python3
"""Forward proxy: 504 on CONNECT github.com, tunnel everything else."""
import socket, sys, threading
from http.server import BaseHTTPRequestHandler, ThreadingHTTPServer

BAD = {"github.com", "www.github.com"}

class H(BaseHTTPRequestHandler):
    protocol_version = "HTTP/1.1"
    def do_CONNECT(self):
        host, _, port = self.path.partition(":")
        if host in BAD:
            self.send_response(504, "Gateway Timeout")
            self.send_header("Content-Length", "0")
            self.end_headers()
            return
        try:
            up = socket.create_connection((host, int(port)))
        except OSError as e:
            self.send_error(502, str(e)); return
        self.send_response(200, "Connection Established")
        self.end_headers()
        cli = self.connection
        def pipe(a, b):
            try:
                while True:
                    d = a.recv(65536)
                    if not d: break
                    b.sendall(d)
            except OSError: pass
            finally:
                try: b.shutdown(socket.SHUT_WR)
                except OSError: pass
        threading.Thread(target=pipe, args=(cli, up), daemon=True).start()
        pipe(up, cli)
    def log_message(self, fmt, *args):
        sys.stderr.write(fmt % args + "\n")

if __name__ == "__main__":
    port = int(sys.argv[1]) if len(sys.argv) > 1 else 8443
    ThreadingHTTPServer(("127.0.0.1", port), H).serve_forever()
```
