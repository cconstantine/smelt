# SME-240 plan — the user can override an MCP tool's class on the MCP server's settings page

**Branch:** `sme-240-mcp-tool-class-override` (made in the planning seat's clone from `origin/main` at `b151495`, SME-237's merge; exists as of this plan)

## What

On an MCP server's edit page, list the server's tools with the class SME-237 gives them and where it came from — the server's annotations, the unannotated default (destructive), or the user's override — and let the user set or clear an override per tool. The override is stored in a new `mcp_tool_classes` table keyed by the server's id, and wins over the annotations at every place a class is read: today that is the one read inside `call_tool_classed` (SME-237 review 1), and from SME-241 on, the class SME-241 refuses by.

Why: many servers don't annotate; everything of theirs is destructive, so a read-only persona couldn't use, say, GitHub's `get_pull_request` until the user fixes it once per tool (design: `docs/design/personas/tool-rules.md#mcp-tools`).

## Current state (read from main at b151495)

- `ToolClass` (read-only < writing < destructive) is `pub(crate)` in `src/anthropic/tools/class.rs`; it has `as_str()` and no parser.
- An MCP call's class is read in `call_tool_unspanned` (`src/mcp/call.rs`): after `ensure_connected`, under one `REGISTRY` guard it takes the connection's `service` and `listed_class(&conn.tools, tool_name)` (`src/mcp/tools.rs`: `class_from_annotations`, unlisted → destructive), and hands the class to `on_class` just before sending. `anthropic::tools::execute_uncapped` passes a `record` closure that writes `smelt.tool.class` on the `tool` span. A call that fails before sending records no class.
- `tool_definitions_for` (the offered list) carries no class — `ToolDefinition` has no class field; nothing filters by class yet (SME-241).
- The edit page (`McpServerEdit`) shows the tool list only as bare names inside the Status section, from `McpConnectionStatus::Connected { tool_names }` (`connection_check` returns names, dropping annotations).
- **Probed live from the planning seat (2026-10-23, curl against `EXA_MCP_URL`):** Exa's `web_search_exa` *is* annotated — `"annotations":{"readOnlyHint":true,"destructiveHint":false,...}` — so the built-in server's page will show `read-only · from the server`, and the Playwright check below exercises override → persistence → clear → back-to-annotation on it.
- `mcp_servers` is keyed by a BIGINT identity `id`; `update_mcp_server`/`delete_mcp_server` call `mcp::evict(id)`.

## Schema

New migration `migrations/20261023220000_mcp_tool_classes.sql` (sorts after `20261023180000_agent_messages_and_pause.sql`; check against `migrations/` at develop time and renumber if a later one has merged):

```sql
CREATE TABLE mcp_tool_classes (
    server_id  BIGINT NOT NULL REFERENCES mcp_servers(id) ON DELETE CASCADE,
    tool_name  TEXT   NOT NULL,
    class      TEXT   NOT NULL CHECK (class IN ('read-only','writing','destructive')),
    created_at TIMESTAMP NOT NULL DEFAULT now(),
    updated_at TIMESTAMP NOT NULL DEFAULT now(),
    PRIMARY KEY (server_id, tool_name)
);
```

Keyed by `server_id`, exactly as `tool-rules.md#mcp-tools` prescribes: renaming a server keeps its overrides; deleting the server cascades. `class` is TEXT with a `CHECK`, the `auth_mode` precedent (the DB is the source of truth for valid values).

## db functions (`src/db/mcp.rs`)

- `set_mcp_tool_class(pool, server_id, tool_name: &str, class: ToolClass)` — `INSERT ... ON CONFLICT (server_id, tool_name) DO UPDATE SET class = excluded.class, updated_at = now()`.
- `clear_mcp_tool_class(pool, server_id, tool_name) -> bool` — delete; `false` when nothing matched.
- `list_mcp_tool_classes(pool, server_id) -> Result<Vec<(String, String)>>` — raw class text, `ORDER BY tool_name` (the endpoint sorts).
- `get_mcp_tool_class(pool, server_id, tool_name) -> Result<Option<String>>` — the call path's one-row PK read.

`src/anthropic/tools/class.rs` gains `ToolClass::parse(text: &str) -> Option<ToolClass>` (the three `as_str()` names only) — used by the POST endpoint's validation and the API; the call path matches the text inline and treats an unknown text (unreachable under the CHECK) as destructive with a warn — fail-closed toward what SME-241 will enforce.

## The class at the call (`src/mcp/call.rs`)

In `call_tool_unspanned`, after `ensure_connected` succeeds and before the `REGISTRY` lock:

```rust
let override_class = crate::db::get_mcp_tool_class(pool, config.id, tool_name).await
    .map_err(|e| CallFailure::Failed(format!("couldn't read {tool_name:?}'s class override for {:?}: {e}", config.name)))?;
```

then, under the existing guard, `let class = override_class-else-`listed_class`; `on_class(class)`. Ordering notes:

- Reading *after* `ensure_connected` keeps SME-237 review 1's guarantee (a failed connect says why; no lookup of its own hides it) and keeps the read off `REGISTRY`'s guard (it's a DB query, not connection state).
- A DB failure fails the call before it is sent rather than falling back to the annotations: the override is the user's answer to untrustworthy annotations, and a silent fallback would drop it exactly where SME-241 is about to enforce on the same read. This is a new refusal — see Trade-offs; its message names server and tool only (both already on the `mcp call` span), never tool output.
- `call_tool_classed`'s doc comment and `docs/mcp.md` change with it. `anthropic::tools::mod.rs` is untouched (the `on_class` contract is unchanged).
- No cache: the override is re-read at every call, so a save on the page takes effect at the next call with no `evict` and no stale window.

## MCP list-for-the-page (`src/mcp/tools.rs`)

`pub(crate) async fn tool_class_report(pool, config) -> Result<Vec<McpToolClassInfo>, crate::mcp::CheckError>` with `pub(crate) struct McpToolClassInfo { pub name: String, pub server_class: ToolClass, pub annotated: bool }`. Flow mirrors `check_connection`: `ensure_connected(pool, config, Attempt::Always)` (the user asked), then one `REGISTRY` read mapping each `McpTool`: `server_class = class_from_annotations(...)`, `annotated = read_only_hint.is_some() || destructive_hint.is_some()` (a title-only annotation counts as unannotated → default). `connection_check` itself stays as it is (the badge needs only names).

## API (`src/api/mcp.rs`)

```rust
pub struct McpToolClassRow {
    pub tool_name: String,
    pub server_class: Option<String>,   // None: tool not in the current live list (unreachable or gone)
    pub override_class: Option<String>,
    pub listed: Option<bool>,           // None: server unreachable, so the live list is unknown
}
pub struct McpToolClasses { pub rows: Vec<McpToolClassRow>, pub server_note: Option<String> }
```

- `#[get("/api/mcp-servers/{id}/tool-classes")] get_mcp_tool_classes(id)`: load the row (same "no MCP server config with id" error as siblings); for `auth_mode == "oauth"` with no grant, return `server_note = "Not connected — connect this server first"` with rows from the stored overrides (`listed: None`). Otherwise call `tool_class_report`: Ok → one row per listed tool (`server_class Some`, `listed Some(true)`) merged with stored overrides whose name isn't listed (`server_class None`, `listed Some(false)`) — listed rows in the server's own order first, then stale ones by name; Err → rows from stored overrides only, `server_note` "Unreachable: {error}" or "Sign-in expired: {error}" mirroring `McpConnectionStatus`'s texts. The merge is a pure `merge_tool_class_rows(listed: Vec<McpToolClassInfo>, saved: Vec<(String, String)>) -> Vec<McpToolClassRow>` so it's testable without a connection.
- `#[post("/api/mcp-servers/{id}/tool-classes")] set_mcp_tool_class(id, tool_name: String, class: Option<String>)`: server row must exist (same error text); `tool_name` must not be blank ("a tool name is required"); `class: Some(text)` → `ToolClass::parse` or "unknown tool class {text:?}: expected read-only, writing or destructive" → `set_mcp_tool_class`; `None` → `clear_mcp_tool_class`, error "no override was saved for {tool_name}" when it matched nothing. No `evict` — nothing caches a class. An override may be saved for a tool the server doesn't currently list (the design keeps those); the page only ever offers live names and saved names, so no free-text input reaches it.
- Unit tests in `api/mcp.rs`'s existing `mod tests` (precedent: the status round-trip and `is_navigable_authorization_url` tests): `merge_tool_class_rows` ordering/None-ness, `ToolClass::parse` table, row JSON round-trip.

## State model

Record: one row per (`server_id`, `tool_name`) → class; the *absence* of a row means "the server's answer".

- **States:** absent | present(read-only) | present(writing) | present(destructive).
- **Transitions and who makes them:** absent → present (user, POST); present → present-with-another-class (user, POST upsert); present → absent (user selecting "Server's answer", POST with `class: None`); any → gone (server delete cascading). Nothing else writes rows: no model path, no startup path, no background writer.
- **Partial failure:** the upsert and the clear are one statement each — a failure leaves the row exactly as it was and the page's error + next GET show truth; the cascade is part of the server's own `DELETE` transaction (`delete_mcp_server_config`), so no half state. A GET is read-only.
- **Readers and what each does with a value another just wrote:** `call_tool_unspanned` reads per call (sees whatever committed before its read); `get_mcp_tool_classes` reads per page load; both re-read, so neither can act on a stale copy. No process caches a class, so an override change needs no `evict` and nothing goes stale after a restart; rows live in Postgres and survive everything.
- **In-flight work row:** a turn whose MCP call has already reached `on_class` keeps that class for the call in flight even if the user saves or clears an override while it waits (up to `CALL_TIMEOUT`, 120 s, for an MCP call); the next call reads the new value. The record of what a call actually used is its `tool` span's `smelt.tool.class` (Tempo), unchanged by this ticket.
- **Races between the two writers (the page's two actions, two tabs):** both write the one row; the last commit wins; there is no read-modify-write to lose (the class is set whole). A set racing a clear on one key ends in one of the two, and both tabs' next GET show it.
- **Override vs connection list:** when an override exists, the connection's list decides nothing about the class; when none does, `listed_class`'s current rules (including "unlisted → destructive") are unchanged.

**What each caller does in each state:**

| Caller | server reachable, row absent | row present | server unreachable | server deleted |
| -- | -- | -- | -- | -- |
| `call_tool_unspanned` | annotation/default class as today | the override, at call time | fails in `ensure_connected` as today (the DB read never runs; no class recorded) | `resolve` says the server is gone before this path |
| DB read in the call | reads no row | reads the row | — | the call was refused above it |
| `get_mcp_tool_classes` | rows for listed tools, note None | rows with override origin | stored overrides + note; `listed: None` | "no MCP server config with id {id}" |
| the page | renders and saves | renders and saves | renders overrides + note; still clearable | route has no server to load (today's behavior) |
| SME-241 (later) | judges by the combined class — that's why the combine sits inside the call, where `on_class` is the refusal seam SME-237's What shipped names | | | |

## Trade-offs to flag

- **One small PK read per MCP tool call** instead of caching the override on the connection: no staleness, no evict plumbing, one extra Postgres round-trip (indexed, sub-ms locally) against a call that costs a network round-trip.
- **If the override row can't be read, the call fails before sending** (new refusal): falling back to annotations would silently drop the user's override, and SME-241 will enforce at this same read. Its message carries server name, tool name and Postgres's text only — same class of text the page already shows from Postgres (database.md's duplicate-key precedent); nothing of the tool's input or output.
- **`docs/current-state/features.md` sits 1,916 B under the size ceiling.** This plan adds one ~160-byte clause (it fits, the SME-177 "one or two lines fit" rule), but the file needs a split ticket before anything else grows it — the Planner is naming it rather than expanding this ticket; the Project Manager may want to file it.
- **"Annotation vs default"** is decided by whether the tool carries either hint: a title-only annotation counts as unannotated (default destructive), matching the spec's defaults.
- **The page's two resources each attempt a real connection** (status + classes) on an unreachable server: up to two serialized `CONNECT_TIMEOUT` waits (15 s each) per load; correct, just slow, and the same as opening that page twice today.
- **No new browser-tier scenario** (fixture cost above); the Playwright check stands in, per the ticket's either/or.
