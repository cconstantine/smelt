# SME-309 plan — The model picks the wrong server's tool

**Branch:** `sme-309-tool-server-labels` (worktree `/workspace/sme-309`, cut from `origin/main` at `b56ff56`; `git worktree list` confirmed on 2026-10-28).
**Ticket:** [SME-309](https://linear.app/smelt-agent/issue/SME-309). Planner seat 2294639414, 2026-10-28. No code — the Developer implements.

## 1. What and why

With ~100 tools offered (smelt's ~50, Linear ~45, GitHub ~20, exa), seats pick the wrong tool by meaning: `message_agent` ("send a message to your parent") and Linear's `save_comment` ("create or update a comment") are neighbours, and seats wrote ticket comments instead of reporting to their parent. They also hallucinated crossed names — `mcp__linear.app__add_issue_comment`, a GitHub verb under the Linear prefix — and slipped letters (`todosote`).

The user's two fixed decisions stand and are not revisited here: **seats keep the full tool list**, and **the model stays the cheap local one**. The harness must make ownership legible in what the model sees.

**One fact anchors the design:** the system prompt *already* says "MCP servers: … (their tools are named `mcp__<server>__<tool>`)" (`src/turn/history.rs`, the Environment section) — and the seat hallucinated a name anyway, with that line in front of it. A naming *convention* stated far from the choice point demonstrably doesn't carry; what the model reads when choosing is the tool's own description. That is where the label has to be.

## 3. The decision: both — the prefix at the choice point, the block for what only prose can say

**Description-prefixing and a prompt block are not rivals here; they answer different bullets of the Done-when and fail differently.**

- *Prefix only* can't say "a Linear comment is a ticket record, not a message" — that's a relation between two tools no single description can own, and Done-when's second bullet demands the prompt say it directly.
- *Block only* puts the server identity far from where the model chooses, and relies on the model maintaining a name→server map over ~65 names — exactly the cross-reference SME-286 proved the deployed model fails at (it composed `mcp__linear.app__add_issue_comment` while the Environment line already stated the `mcp__<server>__<tool>` convention; see §2).

So: **prefix every offered MCP tool's description with its server** (composed at offer time, survives a server adding or renaming tools — it reads the config's name every turn), **and extend the system prompt** with (a) a per-server purpose line, said *once per server* rather than repeated per tool, and (b) a static section naming the confusions directly. Cost, measured: ~15 bytes of prefix × ~66 MCP tools ≈ 1 KB, plus a ~1 KB prompt section and ~200 B of environment lines — roughly 2% of today's prompt. The fixed decision (harness makes the choice clearer) is the decision to pay that; §Trade-offs keeps it honest.

Rejected variants:

- **Purpose text inside every prefix** (the ticket's literal "Linear issue tracker: …"): Exa's own one-line description is 82 characters; ×65 tools ≈ 5 KB repeated every call, and a server that sends no description gets nothing. The purpose goes in the environment block once instead (§4.2), which still satisfies Done-when bullet 1's "either … or … or both" split across prefix (which server) + block (what it's for). It is the user's call whether to instead pay the repetition — Question 1.
- **Prefix smelt's ~50 native tools too**: churn across 9 files for no recorded confusion; smelt's own tools are the labelled-by-absence default, and the four tools that were actually confused carry an explicit `[smelt]` label instead (§4.4).

## 4. Design

### 4.1 The `[server] ` prefix — `src/mcp/tools.rs`

`mcp_tool_to_definition` (line 130) copies the server's description verbatim today. New pure function, so it is testable without connections:

```rust
/// The description as the model sees it: the owning server leads, so a
/// hundred-tool list says which room each tool is in. Skips the label when
/// the description already leads with the server's name — no double label.
pub(crate) fn labelled_description(server_name: &str, description: &str) -> String {
    if description.to_lowercase().starts_with(&server_name.to_lowercase()) {
        description.to_string()
    } else {
        format!("[{server_name}] {description}")
    }
}
```

and `mcp_tool_to_definition` uses it. Notes:

- One composition point for every provider kind: every turn goes to a provider's `/v1/messages` with the same `ToolDefinition`s (`src/providers.rs` header; `anthropic::tools::server::tool_definitions` assembles natives + MCP), so labelling here covers Anthropic, llama.cpp, Ollama and Other alike.
- Case-insensitive leading-name match because the deployed GitHub server is configured as `Github` — the same lesson SME-286's `similar` ranking learned.
- Today's real lists: no deployed description leads with its server name, so nothing is skipped in practice; the rule guards future servers (the no-double-label Done-when bullet; §6 test B).
- Names are already bounded by `check_server_name`, so no length guard is needed.
- `mcp__<server>__<tool>` naming and dispatch are unchanged — text is the only change; tool count and order are untouched, so no prompt-cache churn beyond what MCP configuration already causes (SME-93's note).

### 4.2 What each server is for — `src/mcp/mod.rs`, `src/turn/history.rs`

Servers describe themselves at `initialize`, and smelt throws it away. **Live-probed 2026-10-28** (curl against keyless `https://mcp.exa.ai/mcp`, the server smelt ships by default): its `serverInfo` carries `"title": "Exa"` and `"description": "Exa web search, page fetching and research-agent tools for AI agents over MCP."`, and the result carries an `instructions` field ("Only use tools returned by tools/list. …"). rmcp 3.1.2 exposes this on `RunningService::peer_info()` (verified on docs.rs), whose `InitializeResult.server_info` (`rmcp::model::Implementation`) has the `title`/`description` fields.

- `Connection` (`src/mcp/mod.rs:139`) gains `purpose: Option<String>`, set where it is built (line ~414) from `peer_info()`: `description` → `title` → `None`. Sanitize to one line (control chars and runs of whitespace collapse to a single space — precedent: `crate::git::plain_path_text` guards on the prompt's other free-text fields) and truncate at 200 chars.
- `crate::mcp::prompt_servers(pool) -> Vec<PromptMcpServer { name, purpose }>`: `db::list_mcp_server_configs` joined against `REGISTRY` — same shape `prompt_environment` already builds from the DB. A never-yet-connected server gets `purpose: None`, same as an unlisted tool list; connecting stays the tool path's business (`prompt_environment` must not start connecting — a prompt build can't wait 10 s per server).
- `PromptEnvironment.mcp_servers: Vec<String>` becomes `Vec<PromptMcpServer>`; the Environment section grows from the one line
  `- MCP servers: {} (their tools are named mcp__<server>__<tool>)`
  to a lead line plus one line per server:
  `- MCP servers (their tools are named mcp__<server>__<tool>, and every description starts [server]):` / `  - Github — <purpose>` … / `  - linear.app — <purpose>` / `  - exa — Exa web search, page fetching and research-agent tools for AI agents over MCP.` (no purpose → name alone). Empty list still drops the line.

The history.rs edit is confined to the `PromptEnvironment` struct, the `system_prompt()` MCP loop, and `prompt_environment()`'s `mcp_servers` read — see §11 for the SME-242 note.

### 4.3 The disambiguation section — `src/turn/system_prompt.md`

New static section, placed after the opening (the tools are "the tools below", so their ownership says so early). Draft prose — the Developer may tune wording, tests assert against its stable phrases:

```markdown
# Tools and their owners

The offered list is roughly a hundred tools: smelt's own, plus every configured MCP server's. What you see names who each belongs to:

- An MCP tool's name is mcp__<server>__<tool> and its description starts `[server]`. A description with no bracket label is smelt's own.
- Reporting between agents is smelt's own work: `message_agent` sends a message into another agent's conversation (your parent, or one of your agents), `finish` is your final report to your parent, `ask_parent` waits on a question from it. These are the only ways to reach an agent. A comment tool on an MCP server writes a record on a ticket in the user's tracker — never a message, never a report: do not write a Linear or GitHub comment to say what you did.
- A tool that isn't in the offered list doesn't exist, however plausible its name reads: a GitHub verb under the Linear prefix, or any other blend you assembled, names nothing. Call only names exactly as offered, label and all.
```

Backtick rule: `test_system_prompt_only_names_real_tools` fails the base prompt naming any backticked lowercase/underscore word that isn't a native tool. The section backticks only `message_agent`, `finish`, `ask_parent` (all real). **Keep it that way** — refer to MCP tools unbacktickicked ("a comment tool on an MCP server"); if a future edit backticks `save_comment` or `add_issue_comment`, they'd have to join `NOT_TOOLS`, and that's a smell to avoid, not a licence.

### 4.4 smelt's side — `src/anthropic/tools/agents.rs`, `src/anthropic/tools/questions.rs`

The four confused tools get a `[smelt] ` label (matching §4.1's form) and one clause making the "not a tracker" reading impossible:

- `message_agent` (agents.rs): `"Send a message to your parent…"` → `"smelt agent message: send a message into another agent's conversation — your parent (to: \"parent\") or one of the agents you started — at any time. Nothing leaves smelt: this is how agents report to each other; a comment in an issue tracker is a ticket record, not a message. It arrives…"` (rest as today).
- `finish`: leads `"smelt agent report: "`; keep its body.
- `ask_parent`: leads `"smelt agent question: "`; keep its body.
- `ask_user` (questions.rs): leads `"smelt: "`; its body already says the user answers on a card in the chat.

Descriptions stay well under any cap; only these four, not every native tool (§3).

## 8. State model (the only new state: the in-memory purpose)

Per-server, in `REGISTRY`, exactly like the tools list: absent before first connect → `name` alone in the environment; set at connect from `initialize`; dropped by `evict` (edit/delete/disconnect) and rebuilt on the next connect; never persisted, nothing to migrate; a restart re-derives it. A server reachable but silent (no description/title) shows name only, forever, harmlessly. A turn's first request can precede the first connect → its prompt lists the name alone and later requests carry the purpose; the prompt already changes mid-conversation with server connect/evict (SME-93 handles the thinking-binding consequence).

## 9. Threat note

The purpose string is third-party text entering the system prompt. It joins text from the same source that is *already* in the model's view (the servers' own tool descriptions) and the server list is user-configured, so no new trust boundary — but §4.2's single-line sanitization and 200-char truncation bound it, and `docs/mcp.md` says so.
