## What

A repo's remote reaches the user unchecked in four places (ticket lists three; the trust card's question line is the fourth and it is the moment of granting), and the same untrusted string is the key `settle` decides on. Fix both ends, the SME-271 way for paths:

1. **Refuse at record time** (the strong half): `parse_remote` refuses a url holding any `not_plain` character — the SME-276 predicate (controls, line breakers, bidi controls, default-ignorables). No new row can hold a remote that differs from another only invisibly, and the trust key inherits the guarantee (the key is host+path of a checked url). The two "isn't a git URL smelt can clone" messages quote the url through `plain_multiline_text` and say why when characters were hidden.
2. **Escape at every showing** (the display half, and the answer for rows recorded before the fix): all four sinks show the remote through `crate::git::plain_multiline_text` with `hidden_text_note`'s wording where a notice fits — the same rule and wording SME-273/276/277 already use, so the sinks can't drift.

No migration: recorded keys stay as recorded (decision below).

## The display-vs-refuse decision, and the migration story

**Recommended: both, exactly as above.** Refusing only (no display escape) leaves rows recorded before the fix rendered raw — a ready repo is never re-listed, a `repo_trust` row outlives every conversation, and a pending trust card recorded before deploy is answered after it. Displaying only (no refuse) leaves the trust key itself forgeable — two rows the user cannot tell apart, one of which they can grant. SME-271 shipped exactly this pair for paths (refuse at record + render-side treatment of old rows), and SME-273 shipped the display half for the panel.

**Why no migration for rows already recorded.** `remote_key` is a trust *identity*: `get_repo_trust` matches it by exact string, `lock_remote_trust` hashes it for the advisory lock, `settle` guards on `repo.remote_key != remote_key`, and Forget round-trips the stored string from `/git`. Rewriting stored keys — to escape or delete them — could merge two keys that differ only in invisibles into a PK conflict, or silently re-point a repo row's decision at another remote's row: a worse trust bug than the display one this ticket fixes. So: keys and urls stay byte-for-byte as recorded; the display escape neutralizes any old value (a `repo_trust` row whose escaped key the user Forgets still deletes the stored key, because the button sends `decision.remote` raw — display-only escape keeps that exact); `conversation_repos` rows age out with their conversations, and `repo_trust` rows are one Forget away from being asked again. If the user instead wants old keys cleaned, that is a migration sorting after SME-239's `20261027120000_agent_volumes.sql`, updating `conversation_repos.remote_key` and `repo_trust.remote_key` in lockstep with one escaped mapping — the plan advises against it and its size (~2 tables + a fixture decision + trust-merge semantics) is why.

## State model

The state that matters is one bit per row, new: a recorded `url`/`remote_key` is **plain** (every row from this change on) or **legacy** (recorded earlier; can hold invisibles/reordering characters — never line-breakers, `178b8a6`). It changes no status transition; `cloning/ready/failed` and SME-86's `attempt` rules are untouched.

## Trade-offs to flag

- Refusal is a behaviour change for copy-pasted urls: today a url with an invisible character clones; from now on it's refused with a message showing the escape. That's the point (the user sees why), but a user who pasted a poisoned url from a page and *wanted* that repo will have to retype it. This mirrors SME-271's refusal at record time.
- Legacy rows keep their keys and are escaped at showing, not cleaned — a deliberate pass on a migration, with the trust-identity argument above. A legacy dirty url also now fails a child's inherited clone at `clone_into_pod` rather than cloning; only possible for rows recorded before the fix.
- The `/git` row and the panel tooltip put their count notice in a hover `title` — unreadable at phone width (SME-273 accepted the same); the escapes themselves carry the fix at every width. The card and the context view get visible notice lines, per their panes' shapes.
- `docs/current-state/features.md` sits 3,086 B under the ceiling at head; this plan adds ~250 B to its git bullet and takes no split (the SME-239 branch adds no features.md row; any other ticket touching it within 2 KB needs the split conversation first — rules-commits).
- Trust notices and the system-prompt line keep the raw stored url (model-facing, never a line-breaker per the evidence header; invisibles are what the model is *meant* to see). If the user wants the transcript's notice text escaped too, that is ~4 more `format!` sites in `git/server/trust.rs` + `instructions.rs` — not in this plan.

## Open questions for the user

1. **Take the refuse-at-record + escape-at-display pair, and leave rows recorded before the fix as they are (no migration, display escape covers them)?** *Recommendation: yes — it is SME-271's shipped shape for paths, and rewriting trust keys risks re-pointing a decision at another remote (the migration story above).*
2. **Should the model-facing strings that quote a repo's url (trust notices in the transcript, the system prompt's Repositories line) also escape, for pre-fix rows only?** *Recommendation: no — a recorded url has never been able to hold a line-breaker, the model reads characters by design, and every row from this change on is plain; say so and leave them.*
