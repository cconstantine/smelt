# SME-493 plan: a persona's token ceiling compacts a seat before its next call

Ticket: SME-493 (Linear). **Branch:** `cconstan/sme-493-claudecode-seats-compact-on-their-own-at-a`, from `origin/main` at `4cc7caef3022`. This file is the plan (the ticket's `## Plan` holds a summary and this link; Trade-offs stay in the ticket). **It is removed before the PR merges** (a commit `git rm docs/plans/sme-493.md` before the merge, as for every `docs/plans/` file).

## What and why

The retro (SME-477, proposal 1) found that no ClaudeCode Developer ever compacted. The automatic trigger fires only near the model's window (1M on ClaudeCode), and every step re-reads the whole context. This ticket adds a **persona ceiling**, `smelt.compact_at: <tokens>`. Once a conversation's next request would pass it, the conversation compacts before that model call, over the same `compact` path SME-482's on-demand compaction uses. Then it goes on. The values are the agreed ones: `smelt:developer` 200000 and `smelt:ticket-driver` 120000.

## Decisions (Planner), for the Driver to confirm or overrule

**D1. The ceiling lives only in the persona. There is no provider default.** `smelt.compact_at` is a positive integer of tokens. YAML 1.2's core schema reads `200_000` as a string, so it must be written `200000`. Anything else is the file's parse error, naming the file and line like the other `smelt` fields: `0`, a string, or a negative number. There is no floor: a tiny ceiling can't loop (D5). A provider-level default would mean a new `provider_models`/`inference_providers` column, a migration, a provider-form field and its validation. It would also reach the user's own non-persona chats, which the ticket doesn't ask for. The ticket's cost is per role, and the role is the persona. A provider default can be its own ticket if one is wanted. No number appears in code: `compact_at` is read from the file, and the window trigger is unchanged.

**D2. It applies on every provider kind, and the lower trigger wins.** On ClaudeCode's 1M window, 200k fires long before the window does. On a 200k HTTP model the window trigger (`compaction_ceiling(window)`) fires first, so a ceiling at or above it is inert. On a large-window HTTP model it saves what it saves on ClaudeCode. The check runs only when the window trigger said `Go` (D4), so the effective trigger is `min(window trigger, compact_at)` by construction.

**D3. How the ceiling reaches a conversation: from its frozen persona snapshot, read once per turn.**
- *Parse:* `personas::parse` gains `compact_at` (`Persona.compact_at: Option<u64>`, `SmeltSettings.compact_at: Option<NonZeroU64>` with `#[serde(default)]`, so `0` is refused by serde at its line).
- *Snapshot:* `agents::persona::snapshot` adds `"compact_at": persona.compact_at` to `persona_settings`. One function serves both a child's start (`agents/start.rs:367` → `agents.persona_settings`) and a top-level set (`agents/top_level.rs:65` → `top_level_personas.persona_settings`).
- *Read:* a new `db::persona_compact_at(pool, id) -> Result<Option<u64>, sqlx::Error>` in `src/db/agents/grants.rs`, beside its twin `persona_credential_names`. It runs the same `agents UNION ALL top_level_personas … LIMIT 1` query, takes `persona_settings->'compact_at'` and reads it `as_u64`. No row, no key, or a JSON null all mean `None`.
- *When:* `run_turn_loop` reads it once at the turn's start, next to `get_conversation_usage` (`run.rs:242`), and an error propagates like that read's. It is handed to the progress record (`set_ceiling`, D5). The snapshot is frozen for the conversation's life (as `credentials` is, SME-242's "frozen at start"), so reading per turn and reading at set give the same value. Per turn costs one indexed read and needs no new cache to keep true.
- *Child seats:* each child runs under its own persona's ceiling. Nothing is inherited down the chain: a Planner started by a Driver doesn't get 120k. A child with no persona, and every top-level conversation without one, has no ceiling.
- *Seats already running:* their snapshots were taken before the merge and have no `compact_at`, so they keep today's behaviour until a new seat starts. Editing a persona file changes only seats started after the edit.

**D4. The path: SME-482's `compact_on_request`, with a new asker, at the window trigger's own call site.**
- *Where:* in `run_turn_loop` (`src/turn/run.rs`), the `CompactionStep::Go` arm of the proactive check (`run.rs:368`). That is before `build_request_with_room`, and so before this iteration's model call. It runs after the slot was refreshed (`run.rs:352`), and the last saved message is a user message, notices or the previous pass's tool results. That is the same safe boundary the window compaction already relies on at this site, and `compact` re-checks it (`is_safe_compaction_boundary`).
- *What it calls:* a new `compact_at_ceiling` in `src/turn/on_request.rs`, the sibling of `compact_if_asked`. It calls **`compaction::compact_on_request(pool, conversation_id, turn_model, slot.held(), Asker::Ceiling(ceiling), None)`**. That runs `in_compaction_span` → `compact`, the very function the window, endpoint and model compactions run. So every safeguard holds unchanged:
  - the user's and the parent's words quoted verbatim (`typed_user_text`, `unanswered_user_text`/`cap_unanswered`);
  - the pinned todo list (`get_conversation_todos` → `compaction_messages`, SME-462);
  - the unread results (SME-414);
  - the summary cut-off guard (`summarize`'s one continuation, SME-443);
  - the summary-overflow retry (SME-73);
  - `clear_conversation_usage`;
  - ClaudeCode's session restart from the summary (`claude_cli::session::reset`, SME-431).
- *On success:* the same bookkeeping the window arm does. `with_compaction_progress(id, |p| p.compacted(window))` (so SME-414's thrash count sees it), then `note_thrash`, then `compacted = true` and `last_known_usage = None`. `compact_at_ceiling` returns whether it compacted, and run.rs sets those two locals from it.
- *The divider:* `Asker` gains `Ceiling(u64)` (still `Copy`). `Asker::reason` returns a `String`, and `compact_on_request` drops its `.to_string()`. The divider reads "Conversation compacted: it passed its persona's 200,000-token ceiling", grouped with `overflow::grouped`.
- *On failure* (`compact_on_request` returns `Err`): the turn carries on, as SME-482's model compaction does (its round 1 L1). This request still fits the window, so the ceiling is a saving, not a need. `tracing::warn!` names it, and the compaction span is already marked failed by `in_compaction_span`. **No notice is saved**: the model didn't ask, nothing changed for it, and a notice each turn on a lasting failure would be noise in the history. The record turns the ceiling off for the rest of this turn (`ceiling_failed`), so one turn pays for at most one failed summary. The next turn tries again.
- *`compact_context` stays independent:* a ceiling compaction doesn't spend the model's once-per-turn. This happens rarely, and the model asks for its own reasons, such as a Driver after a merge.
- *Why not fold it into `CompactionProgress::step`:* step's `Compact` arm is the window's path, whose failure fails the turn (SME-18), and step's tight/at-limit judgements are measured against the window. The ceiling needs neither.

**D5. No loop: the ceiling is *spent* while compacting can't get under it.** The record is `CompactionProgress`, the conversation's in-memory runtime record, which every compaction kind already updates. It gains:

```rust
/// The persona's ceiling (SME-493) and whether it's worth compacting at.
#[derive(Clone, Debug, Default)]
struct Ceiling { at: Option<u64>, spent: bool, failed: bool }
```

Its methods:
- `set_ceiling(at)` — at the turn's start, beside `turn_started`. It stores `at` and clears `failed`.
- `ceiling_due(projected) -> bool` — true only when all of these hold:
  - `at` is set;
  - not `spent` and not `failed`;
  - `projected >= at` (`projected` being `Some`);
  - `steps_since_compaction >= 2`.
- `ceiling_failed()` sets `failed`.
- `measured` (existing): when it records a post-compaction `after` (that is, `awaiting`, before the `guess` early return), it sets `spent = after + MIN_ROOM_TO_WORK > at`. That reuses the window trigger's own "left room to work in" margin, 4,096 tokens, so no new number is added.
- `sync` (a window change) keeps `at` and clears `spent`, as it keeps `on_request`.

Why each piece:
- **The summary leaves the context over the ceiling.** The first reply after that compaction measures `after ≥ at − 4,096`, so `spent` is set and no later step compacts at the ceiling. The window trigger still guards the window.
- **Re-arm.** `spent` clears when a later compaction of *any* kind (window, on request, endpoint, refusal) measures under `at − 4,096`. It also clears on a window change or a restart. Without a re-arm, a seat whose floor sits above its ceiling simply runs as it does today, which is no worse than now.
- **The two-step rule.** A compaction with exactly one step since the last is the shape SME-414's `thrash` counts, and at `END_AT` that ends the turn. Without the rule, a seat taking 100k-token steps under a 120k ceiling could have the *ceiling* end its turns, though the window had plenty of room. With it, a ceiling compaction always comes at least two steps after the last compaction, so `compacted()` resets `thrash` instead of counting it. A real window loop is unaffected: the window's `Compact` arm runs before the ceiling is asked.
- **Before the next call.** `projected` is `None` straight after any compaction (usage is cleared), so the call right after a ceiling compaction never compacts again. That holds whatever `spent` says.

*Restarts:* the record is memory only, like everything else in `CompactionProgress` (its doc's "a restart or a delete: all of it goes"). After a restart `at` is read again at the next turn's start, `spent` is false and `steps_since_compaction` is 0. The worst case is one extra ceiling compaction per restart, at least two steps in, which then measures and sets `spent` again. Persisting `spent` would need a column, or deriving it from `model_calls`. That isn't worth one bounded summary per deploy, and it is listed under Trade-offs.

**D6. What "context" is measured as:** `projected_input(last_known_usage, estimate_tokens(pending_new_content))`, the very number the window trigger reads (`run.rs:366`). That is the last reply's `input_tokens + cache_creation_input_tokens + cache_read_input_tokens + output_tokens`, plus a 4-chars-a-token estimate of what was saved since. In other words, the size of the request about to go. Claude Code's per-API-call usage carries all three input counts (`src/claude_cli/fixtures/window_stop.jsonl`), and that sum is the meter's fill, the 653k/572k the ticket cites. The no-loop judgement reads `measured`'s `after`, which is input + cache creation + cache read without the output, as the window's tight rule does. A server that reports no usage measures nothing, so the ceiling never fires there. That is the window trigger's own limit.

**D7. Which personas get a ceiling:** only the two the user agreed, `developer: 200000` and `ticket-driver: 120000`. The retro measured Developers at ~80% of ClaudeCode tokens, and Drivers are the other long-lived seat. The Planner, Code Reviewer, Integrator and Deployer are short seats that rarely near 200k. The Project Manager and Facilitator already compact themselves at their pass boundaries with `compact_context` (SME-482). Ceilings for them would be a new product choice, so they go under Trade-offs, not into this change.

## State model

`CompactionProgress.ceiling`, one per conversation, in its `ConversationRuntime`. All writes run under the turn lock, like the rest of the record.

| From | Event (writer) | To |
|---|---|---|
| none | turn start reads a snapshot with `compact_at` (`set_ceiling`, `run_turn_loop`) | armed (`at` set) |
| armed | a step with `projected ≥ at`, ≥2 steps since the last compaction (`ceiling_due`) | compacting |
| compacting | summary saved (`compacted`) | armed, awaiting a measure |
| compacting | summary failed (`ceiling_failed`) | off for this turn |
| armed, awaiting | first reply measures `after + 4096 > at` (`measured`) | spent |
| armed, awaiting | measures under it (`measured`) | armed |
| spent | any later compaction measured under (`measured`), a window change (`sync`), a restart | armed |
| off this turn | next turn's start (`set_ceiling`) | armed (or spent, as it was) |

Other writers of the same record touch only their own fields: the window compaction (`compacted`/`measured`), the endpoint's `compact_now`, the model's `compact_if_asked`, and refusal recovery. Each of them can *re-arm* a spent ceiling through `measured`, and none can arm a ceiling the persona hasn't set. No other conversation or tab sees the record. The divider and the `compaction` model-call row are the visible trail, live through `record_saved`, like every compaction. Nothing lives in the pod.

**Partway failures:**
- *The summary call fails:* nothing is saved, `failed` is set and the turn goes on.
- *A save fails after the summary* (`create_message` or `clear_conversation_usage`): `compact` returns `Err`, handled as above. Any divider rows already saved stay, as on every compaction path today (`compact`'s existing behaviour). Usage not cleared means `projected` stays over `at`, but `failed` blocks a retry this turn.
- *A Stop mid-compaction:* drops the turn future as on the window path. The next turn starts with `failed` cleared and tries again if still over.

**What each caller does in each state:**

| State | turn step (`run_turn_loop`) | window trigger | `compact_context` / endpoint |
|---|---|---|---|
| none | never compacts at a ceiling | unchanged | unchanged |
| armed, under `at` or <2 steps | goes on | unchanged, asked first | unchanged |
| armed, over, ≥2 steps | compacts, then calls | already said `Go` | unchanged; may re-arm via `measured` |
| spent | goes on | still fires at the window | its measure under `at` re-arms |
| off this turn | goes on | unchanged | unchanged |

**Work in flight:** the snapshot can't change under a running turn, and the turn reads `at` once at its start. A window learned mid-turn (`sync`) keeps `at` and drops `spent`, so the next qualifying step may compact once, then measure.
