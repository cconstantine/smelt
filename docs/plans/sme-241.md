## What

A persona file's `smelt.tools` (grammar: [tool-rules.md#the-grammar](https://github.com/cconstantine/smelt/blob/main/docs/design/personas/tool-rules.md#the-grammar)) decides which tools the persona's conversation is **offered** (`tool_definitions`) and which it may **call** (refused as a tool error naming the rule), enforced server-side from one evaluation function. A child's rules are narrowed by its parent's: `start_agent` stores a **rule chain** (JSONB `agents.rule_chain`, the parent's chain plus the child's own persona rules) and evaluation walks it — nothing is re-read from files, so a later persona edit changes nothing and the tool list is stable within a conversation (prompt caching holds). `start_agent` becomes an ordinary writing tool under the rules: the root-only offer goes, replaced by a depth check (`SMELT_AGENT_DEPTH`, default **5**) that stays until SME-245. MCP server names refuse `/` and `*` going forward; existing ones are reported; `list_personas` and `start_agent` report rule patterns that match no configured server.

Rules about what bash can reach (credentials, egress) are SME-242/SME-243, not here.

## Threat model

- **Inherited overrides for a replaced tool** (Code Reviewer's finding F5 on SME-240's PR #185, carried here per the ticket's comments): `mcp_tool_classes` rows key on `(server_id, tool_name)`, and both the settings page's "no longer lists" marker and `call_tool_unspanned`'s fresh reads match by *name* — so if a server replaces a tool and re-lists a **different** one under a name the user once overrode, that new tool silently inherits the user's class. Today that only changes what the page shows and what a span records; **from this ticket it decides what a persona may call**, so an override set for a harmless tool can mark a later destructive one read-only and let a `read-only` persona through. The class is read fail-before-send at exactly the point the rules are enforced (`src/mcp/call.rs:129–167`), so this ticket cannot make it worse; it makes it matter. Whether the row should carry the annotation it was set against, or be dropped when the server's tool list changes, stays open — a question below, recommendation: a follow-up ticket, not this one.
- **Stale patterns never widen:** after a server rename, its patterns match nothing and the tools fall to the class ceiling — never wider than the ceiling ([tool-rules.md edge cases](https://github.com/cconstantine/smelt/blob/main/docs/design/personas/tool-rules.md#the-grammar)), and they're reported.
- **Fail-closed reads:** the override read already fails the call before send if Postgres can't read it; the rule-chain read is smelt's own JSONB written by typed serde — an unreadable chain falls back to allow-all with a warning (fail-open) *only* on a corrupt store, and a corrupt store also means `execute`'s chain read sees the same corruption: the offer/call pair stays consistent. (Alternative — fail-closed — would strand every tool in the conversation on a bad row; the row is written once by smelt itself.)
- **Depth:** with the root-only rule lifted, unbounded nesting needs a cap now — hence `SMELT_AGENT_DEPTH` (default 5, user's raise from the design's 2, 2026-10-23) in this ticket; SME-245 adds persona limits.
- **`http_request` method-override headers** (SME-237 review finding): a `POST` carrying `X-HTTP-Method-Override: DELETE` is classed writing today, though some frameworks honour it as a delete. Decision below (Questions 1).

## How

### Grammar, in the persona module

`SmeltSettings` gains `tools` (its comment already reserves it — "Later tickets add `tools` (SME-241)"), and `src/personas/` grows a submodule `rules.rs` (the grammar types + evaluation; `mod.rs` stays the format). Typed serde with `deny_unknown_fields` as everywhere; errors name the file (`{path}: …`, like the existing ones):

- `Ceiling`: `all` (default) / `no-destructive` / `read-only` — a serde enum on exactly the design's spellings; an unknown class is a serde error naming the file.
- `Pattern`: parsed from one string — 0 or 1 `/` (more than one is an error); the server segment (when present) contains no `*` (`*/get_*` is an error: "a pattern's server is always named"); an empty pattern is an error; `*` in the tool segment matches any run of non-`/` characters. A no-`/` pattern names a smelt tool; a `/` pattern names a server that may not be configured (not an error — reported elsewhere).
- `ToolRules { class: Ceiling, allow: Vec<Pattern>, deny: Vec<Pattern> }`; a pattern text in both lists is an error naming the file (the design's "a name in both lists").
- Specificity is computed, not stored: level 1 exact, level 2 wildcard in a tool name, level 3 `<server>/*`, level 4 the class ceiling.

`Persona` gains `tools: Option<ToolRules>`; `persona::snapshot` puts it into the settings JSONB (`{"model": …, "tools": …}`) so the snapshot carries it to the chain assembly (below). No other read of `persona_settings` changes.

### One evaluation, for offer and call

`rules.rs` (with `ToolClass` from `anthropic::tools` — already shared):

```rust
pub(crate) struct RuleChain(Vec<ToolRules>);           // deserialized from agents.rule_chain
impl RuleChain {
    /// Called at the tool's class: allowed iff every entry allows it.
    /// Entry: most specific level with a matching pattern decides;
    /// deny wins a tie at that level; no match → class within the ceiling.
    pub(crate) fn allows_at(&self, tool: ToolRef, class: ToolClass) -> Result<(), String>; // Err names the rule
    /// Offered: allowed at *some* class the tool can have.
    pub(crate) fn allows_any(&self, tool: ToolRef, classes: &[ToolClass]) -> bool;
}
```

`ToolRef` is either `Native(name)` or `Mcp { server, tool }` — the same name split `crate::mcp::parse_tool_name` already does. The refusal message names the rule and the tool: `"{name} is denied by this conversation's tool rules (deny pattern \`{pattern}\`)"` / `"(class ceiling {ceiling} doesn't allow a {class} tool)"`. Only `http_request` has more than one class (`Class::can_be`, sitting `#[expect(dead_code)]` in `class.rs` with the reason "SME-241 offers tools by it" — this plan un-dead-ens it), so a `read-only` persona is offered `http_request` and its `POST`/`DELETE` calls are refused.

### Where it's read and enforced

- **Offer** — `anthropic::tools::tool_definitions(pool, conversation_id)` (called from `turn/reply.rs` per model call and from `api/chat.rs`'s context-detail; signature unchanged): read the chain (new `db::agent_rule_chain`, one indexed query; no `agents` row or NULL → allow-all) → filter `REGISTRY` by `is_offered(offer, has_parent) && chain.allows_any(Native(def.name), tool.class.can_be())` → pass the chain to `mcp::tool_definitions_for`, which keeps a server's tool only when `chain.allows_at(Mcp{…}, class)` where `class` is the user's override row if any (`db::list_mcp_tool_classes`, one read per connected server, same source of truth as the call path) else the annotations of the connected server's own list.
- **Native call** — `execute_uncapped`, right where it records `registered.tool.class.of_call(input)`: `chain.allows_at(Native(name), class)` → refuse before `run` runs, naming the rule. Same fail-before-any-side-effect posture as `offered_to`'s existing checks.
- **MCP call** — `call_tool_classed` gains a check: `on_class` becomes `check_class: impl FnOnce(ToolClass) -> Result<(), String>` (the caller records the span *and* evaluates). `call_tool_unspanned` calls it after the override read + `listed_class`, under the same REGISTRY guard — the read SME-240 established at `src/mcp/call.rs:129–167` — and a refusal returns a `CallFailure::Failed` naming the rule **before** `service.call_tool(request)` is sent, keeping the "no class, no send" contract. `test_a_tool_call_that_succeeds_leaves_its_span_unmarked` and the classed-span tests keep their assertions; a refused call records its class and marks the span failed with the rule text (never the input, SME-137).

### Narrowing and storage

- Migration `20261026120000_agents_rule_chain.sql`: `ALTER TABLE agents ADD COLUMN rule_chain JSONB;` — the column the `20261023120000_child_agents.sql` comment and docs/database.md already reserve ("SME-241 and SME-242 add `rule_chain` and `credentials`"). The chain is a JSONB array of `ToolRules` entries, child's own last; **re-check `ls migrations` at commit time** — `20261026120000` sorts after SME-244's `20261025120000` and SME-239's `20261025180000` too.
- `create_child`: with the caller's row locked (already `FOR NO KEY UPDATE`), read its `agents` row's `depth` and `rule_chain`. Child: `depth = caller.depth + 1` (was the literal `1`), `root_id = caller.root_id` (was the caller), `rule_chain =` the caller's chain (a conversation without an `agents` row: depth 1, `root_id` = caller, chain NULL = allow-all). Refused when the caller is an agent at `depth == SMELT_AGENT_DEPTH`: `"start_agent can't go deeper than {N} levels of agents (you're at depth {d})"` — replaces the `ROOT_ONLY` arm (const and message go). A caller with `parent_id` but no `agents` row (a test artifact of the existing `bare_child` helper, never a real conversation) keeps a refusal: `"this conversation has a parent but no agent row, so its depth is unknown — start_agent needs a conversation smelt started"`.
- `SMELT_AGENT_DEPTH`: read in `agents::start_agent` (the env-var pattern of `sandbox/idle_notice.rs`: unparseable → default 5 with a warning), passed into `db::NewChild` as `max_depth` so `db` tests set it directly — never by env in tests.
- `complete_start`: when the persona's snapshot settings carry `tools`, **append** that entry to the stored chain (read-modify-write of the JSONB inside the existing transaction — the child row's chain is its parent's as of `create_child`; nothing can race it: the parent's chain is immutable once its own start completed, and the child takes no turn until `active`). A persona with no `smelt.tools` (or no persona) leaves the parent's chain as the child's own — no entry, allow-all.
- The chain is written exactly twice (create, complete) and never again: a persona-file edit, a server rename, or `stop`/`reactivate` change nothing (Done-when: "a later edit to a persona file changes nothing"). `agents.rule_chain` is immutable while the agent is `active`.

### `start_agent` as an ordinary tool

`Offer::Root` disappears: `start_agent`'s registry entry becomes `Offer::All`, the `Offer` enum loses the variant, `is_offered`/`offered_to`/`tool_definitions`' match arms go. So it's offered to every conversation (under its class — `writing` — hence denied outright by a `read-only` persona, per the design's worked example), and the depth check is the only structural limit. This changes what agent conversations are offered at deploy (they gain `start_agent`): one cached-prompt rewrite per live agent conversation, said in the PR (rules-commits.md's tool-list rule).

### Reports

- **Patterns matching no configured server:** `personas::rules` gains `unmatched_servers(&self, server_names: &[String]) -> Vec<String>`. `list_personas` (`git::server::personas::persona_entry`) reads `db::list_mcp_server_configs` once per listing and adds a `"rules"` note naming them ("pattern `gh/create_*` names no configured server"); a renamed server's stale patterns surface here (the design's rename edge case). `start_agent` does the same after the persona snapshot during `prepare` and folds the note into the existing `parent_notice` channel (the model-not-found notice's mechanism), so the parent is told at the child's done step.
- **Server names:** new `crate::mcp::check_server_name` (refuses `/` and `*`, naming both rules) called from `create_mcp_server` and `update_mcp_server`. Existing offending names are reported, not broken: `McpServerSummary` gains `name_unrulable: bool`, and the edit page shows a line under the name field — "this name contains `/` or `*`, so its tools can only be ruled on by class; rename it to rule on them". No DB CHECK (existing rows must survive).

## State model

`agents.rule_chain` (JSONB array of rule entries, oldest first):

| State | Meaning | Who moves it there | Who else sees it |
| -- | -- | -- | -- |
| no row (not an agent) | user's own conversation: allow-all | — | `tool_definitions`, `execute` read NULL → allow-all |
| NULL chain, agent row `starting` | child's chain = parent's, own rules not yet read | `create_child` (copies parent's chain) | no turns are admitted while `starting`, so nobody evaluates it yet |
| chain entries, `active`/`finished`/`stopped` | effective rules, fixed at start | `complete_start` appends the persona's entry — the only writer after create | `tool_definitions` (every model call), `execute` (every call), `tool_definitions_for` |
| corrupt/unparseable chain | smelt-written JSON that won't deserialize | — (shouldn't happen) | allow-all + warning, both offer and call — consistent pair |

Transitions that can fail partway: `create_child`'s insert is one transaction (chain or nothing); `complete_start`'s append is in its existing transaction, and `Ok(false)` (child stopped/deleted meanwhile) writes nothing including the chain — the failed/`stopped` child is never evaluated. A start that fails before `complete_start` leaves chain = parent's on a `failed` row nobody runs. In-flight rows at deploy: every existing agent row gets `rule_chain` NULL → its parent's allow-all-equivalent (no entries) → today's behaviour; a turn in flight keeps its already-built tool list and its calls see an empty chain → allowed, as today.

Readers of shared state and what another caller can change under them: the chain is immutable after start, so the only cross-writer pair is `create_child` (parent's chain read) vs `complete_start` (child's own write) — the child id is created under the parent's row lock, and the persona entry comes from the snapshot taken during the start, not re-read. A parent's `stop_agent`/delete doesn't touch chains. MCP server renames/deletes change only the *report*, never a stored chain.

Per-caller table — what each caller does when the chain is absent / empty / present / corrupt: `tool_definitions` → filter (absent/empty/corrupt = offer all as today); `execute` native → allow (same) or evaluate → refuse naming the rule; `call_tool_classed` → only refuses at the same three states as `execute` (same function); `list_personas`/`start_agent` → report only; `create_child` → depth check only.

## Trade-offs to flag

- Deploy rewrites the offered list of every live agent conversation once (`start_agent` joins it; `Offer::Root` goes) — one cache miss per agent, said in the PR.
- The chain is evaluated per model call and per call from one indexed read each — an extra query per tool call, same order as the existing `conversation_links`/override reads.
- A corrupt chain falls open (with warnings) rather than stranding the conversation; the store is smelt-written and checked by typed serde at write.
- `list_personas` now reads `mcp_servers` (the report needs it); a listing of a persona whose rules name no server is informational only — patterns are never fatal by design.
- The depth refusal is at the call, not the offer (a depth-5 agent is still *offered* `start_agent`): keeps the offered set a function of rules alone, and the refusal copy explains the limit; hiding it by depth would change an agent's tool list at no rules-change and complicate the caching story.
- `start_agent`'s description text is unchanged, so no other conversation's cache sees a reword.
- Three open branches (`sme-239-model-volumes`, `sme-279-trust-repo-without-agents-md`, `sme-244-group-spend`) share 4–6 of these files; whoever rebases second absorbs the `server/tests.rs` split. See Overlap verdict.

## Questions for the user

1. **`http_request` method-override headers:** class a call by the method a `X-HTTP-Method-Override` / `X-HTTP-Method` / `X-Method-Override` header names (so a `POST` + `…Override: DELETE` is destructive), or refuse only by the literal method? **Recommendation: class it by the header-named method** — it's ~15 lines in `class.rs` + tests (commit 8), and the alternative leaves a hole exactly where the design says the class scale must hold ("an HTTP DELETE" is destructive; a framework honouring the header makes it one).
2. **`mcp_tool_classes` staleness for a replaced tool** (Threat model, first bullet): should an override row carry the annotation it was set against, or be dropped when the server's tool list changes? **Recommendation: neither this ticket** — one threat-model sentence lands here; file a follow-up in the personas project so the row-vs-tool identity question gets its own review.
