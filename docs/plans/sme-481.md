## What and why

Today only a child has a persona: `start_agent` snapshots it into the child's `agents` row (`persona_*`, `rule_chain`, `credentials`), and every reader of a persona reads that row. A top-level conversation has no `agents` row, so it's allow-all, holds the git key whenever one is stored, holds no named secret and has no `# Persona` section. A Ticket Driver or Project Manager started by the user, or by a PM through the API (SME-460), gets its persona only from prose in its brief.

This ticket lets a top-level conversation be **set to a persona once, after its repo is attached and before its first message**. From then on it runs under that persona's instructions, tool rules (`own:` included), credentials and `smelt.model`, as a child with that persona does. There are two differences, both narrower than a child gets, never wider: there is no parent chain to narrow it (the user's own conversation, the root, is allow-all, so a child of the root gets the same), and the model resolves only on the provider the conversation is already on.

## Decision: set after attach, before the first message (not `POST /api/conversations`)

`POST /api/conversations/{id}/persona` with `{"persona": "<dir>:<name>"}`. `POST /api/conversations` stays as it is.

Why:
- **The persona is read from the conversation's own checkout,** as a child's is from its own (persona-files.md, "Read from the child's own checkout"). A checkout exists only once the attach's clone finishes, and that clone is asynchronous and keeps running if the tab closes (SME-225). Putting the persona in `POST /api/conversations` would need a `starting` state for top-level conversations plus a background start with a failed state and a restart sweep, which is `agents.state`'s whole machinery for a row that isn't an agent. A set on a `ready` checkout is synchronous and simple.
- **It is the PM's existing sequence:** create, attach, set the model, *set the persona*, send. The UI uses the same calls.
- **"Started" has one server-side check** (next section) that both the UI and the API go through.

## Security: how each property holds

### "Started", exactly, and where it's enforced

A conversation has **started** once any of these is true:
1. it has a row in `messages` (a user send, a saved notice, a reply);
2. a turn holds or is queued on its turn lock;
3. a turn has been admitted (`turn::turn_running`, which counts an admitted turn still waiting for the lock: the Developer confirms against `TurnInFlight::start_by_user` and records it).

The invariant: **no model call, tool call or saved message in the conversation comes before the persona is fully applied, and nothing changes the persona after it's applied.** It is enforced in one server function, `agents::top_level::set_persona` (new), which runs everything inside `turn::between_turns(id, wait = false, …)`:
- Lock held or queued → refused: "this conversation has started".
- `turn_running(id)` → refused, same text.
- In the transaction: `lock_remote_trust(remote_key)` first (the lock order `create_child` uses), then `SELECT parent_id, deleting_at FROM conversations WHERE id = $1 FOR NO KEY UPDATE`. Refused if the conversation is gone, has a parent ("an agent's persona is set by start_agent"), is being deleted, has any `messages` row, or already has an **applied** `top_level_personas` row.
- The apply (insert, pod reconcile, mark applied) finishes **before the turn lock is released**. So a send admitted during the set saves its message and makes its first call only after the persona is applied. A send admitted while an unapplied row exists is refused by the admission gate (below).

**Swapping:** no endpoint unsets or replaces an applied persona. A second set is refused whether or not a message exists. The only replace is a set over an **unapplied** row (left by a failed apply, below), and no turn can have run under one of those. Recommendation: keep it this way (Decided (Driver) D3).

**The admission gate (new),** for the window a restart can leave: `agents::admit_user_turn` (the user's send and their question answer, `turn/questions.rs:170`), `confirm_user_turn` and `admits_notices` refuse a conversation with an unapplied `top_level_personas` row ("this conversation's persona is still being applied; try again, or start a new conversation"). The read sits in the existing `db::agent_state` call. That is one query: an `agent_state_or_persona` returning the agent state, or a synthetic `persona-pending` for an unapplied top-level row, so the existing match grows one arm. `admit_user_turn` already fails closed on a read error. `admits_notices` falls open on a read error, as today (trade-off T3).

### 1. The trust gate

- **Listing** (`GET /api/conversations/{id}/persona`) lists personas only for a `ready` repo whose remote is trusted, read under `lock_remote_trust`. It is the same gate `list_personas` uses (`git::server::personas::gated_listing`), refactored to return structured rows so both share it. An undecided remote's row says "trust this repo (Work on a repo trusts it) to use its personas", and a declined one says its personas aren't available. No description, setting or parse error from an untrusted file reaches the response.
- **Setting:** the file is read from the conversation's pod before the transaction, as a child's is read after its clone (`agents::persona::snapshot`, reused as is through `checkout_for(id)`). Then the transaction re-reads `repo_trust.trusted` under `lock_remote_trust` and refuses anything but `Some(true)`. A revoke between the read and the transaction lands before or after the lock: before means refused, after means applied. Afterwards the snapshot stands, as a child's does (persona-files.md step 4).
- `POST /repos` ("Work on a repo") trusts the remote it attaches. Through the API that means the caller's attach is the trust decision (trade-off T1).

### 2. Credentials: what the persona lists, nothing more

A child of the user's root gets Rule G (`git-ssh`): `create_child` seeds the root's bit, and `prepare` narrows it to what the persona asks for (`narrow_agent_credentials`), so the child gets the key iff the persona lists `git-ssh` and a key is stored. It gets Rule S from its own snapshot's names, each backed by the store.

A top-level persona conversation is given **the same two answers, computed the same way**:
- `top_level_personas.credentials TEXT[]` is `['git-ssh']` iff the snapshot lists `git-ssh`, else `'{}'`. Rule G (`credentials::git_ssh_granted`) reads it like a child's column (`Some(list)`), so a persona that doesn't list `git-ssh` loses the key the persona-less root had. Today's "no row means the key if one is stored" now applies only to a top-level conversation with **no** persona.
- Rule S (`db::persona_credential_names`) reads `persona_settings.credentials` from `agents` **or** `top_level_personas`. There is no other path. No ancestor exists, and nothing reads the PM's or another conversation's names.
- **The pod:** the attach's clone ran with the key installed, as a child's clone does. After the row commits, `credentials::reconcile_pod(pool, id, Some(&snapshot))` (the child's call, unchanged) removes `/etc/smelt/keys/*` and the `IdentityFile` lines unless `git-ssh` is granted, and writes the granted secrets. This happens while the turn lock is still held, so no command of the model's runs while the pod holds more than the grant. Installs read the committed, narrowed row before writing, under the per-pod install lock (`with_install_lock`). So an install that read before the commit writes before the reconcile, which then corrects it, and one that starts after the commit reads the narrowed grant.
- **Children of a top-level persona** narrow from it as from any agent. `create_child`'s caller branch reads `top_level_personas` when the caller has no `agents` row: the child's chain is `for_child(top-level chain)`, and its `git-ssh` seed is the top-level bit. Without this, a top-level persona with `credentials: []` could start a child that holds the key (a new grant for being top-level), so it is tested (C3).

So a top-level `smelt:deployer` gets `deploy_kubeconfig`, `git-ssh` and `claude_oauth_token`, each backed by the store, and nothing else: exactly what `start_agent(persona: "smelt:deployer")` from the user's root gets (C1 asserts the equality).

### 3. Self-scoped rules (`smelt.tools.own`, SME-322)

The stored chain for a top-level persona is `[<its tools entry, own included>]`. That is the child's chain from an allow-all root, which `complete_start` builds as `[] || tools`. `RuleChain::allows_at` already applies each entry's `own`, and the one reader, `db::agent_rule_chain`, now reads `agents.rule_chain` or `top_level_personas.rule_chain` (one `UNION ALL`, primary key both sides). Every enforcement point goes through that reader: the offer (`tool_definitions`), the native and MCP call paths (`call_rule_chain`), the question tools (`question_allowed`) and script MCP calls (`script_mcp/mod.rs:401`). The Developer re-greps `agent_rule_chain` and `rule_chain` to confirm the list. A child of the top-level persona gets `for_child(chain)`, which strips `own`, through the `create_child` change above. So `own` binds the top-level conversation and not its agents, and the cascading part binds both.

### 4. Not after it has started

See "Started" above. The tests are S1–S4.

## Model: how `smelt.model` resolves at the top level

**Rule:** a top-level persona's `smelt.model` resolves **only on the provider the conversation is on at the set**: its chosen provider (`conversations.provider_id`, set by the picker or `POST /model`), else the default model's provider. It is matched in `provider_models` (provider, model), the test `db::provider_for_model` already uses.
- **The provider lists the model:** the conversation is pinned to `(that provider, the model)` in the set's transaction. A persona saying `claude-opus-5-5` on a conversation the user put on ClaudeCode runs `claude-opus-5-5` on ClaudeCode.
- **The provider doesn't list it:** **refused, loudly**, with nothing written: "persona `smelt:x` asks for model `M`, which `<provider>` (this conversation's provider) doesn't list; providers that do: `<names>`. Pick one of those first (the model picker, or `POST /api/conversations/{id}/model`), or use a persona without `smelt.model`." There is no fallback to the default's provider or to the others by name. That fallback is exactly how a ClaudeCode user would land on the paid Anthropic API (SME-460).
- **No provider at all** (`NoProviders` or `NoDefault` with no chosen model): refused, "pick a model first".
- **No `smelt.model`:** the conversation's model is untouched.
- **After the set,** the picker still works: the user, or the API caller, may change the model, as the user can in a child. The model isn't a security boundary. The persona's model is the starting model, and `conversations.provider_id/model` records what runs. A turn in flight keeps what it read: `resolve_turn_model` runs per turn, the same as today.
- **For the API caller,** "the provider the user picked" is whatever it set with `POST /model` before the persona, else the default. docs/api.md says to set the model first.

Children are unchanged: parent's provider, then the default's, then by name (`provider_for_model`). That fallback can also land a child on another provider silently. See D6.

Implementation: a new `db::provider_lists_model(pool, provider_id, model) -> bool`, and the refusal text built from `provider_models` joined to `inference_providers`. `agents::persona::persona_model` stays the child's.

## Data model

Migration `migrations/20261111120000_top_level_personas.sql`. It sorts after main's newest, `20261110130000_report_owed_wake_index.sql`. SME-480 adds one too: whichever merges second renames its own to sort after main's newest.

```sql
CREATE TABLE top_level_personas (
    conversation_id BIGINT PRIMARY KEY REFERENCES conversations(id) ON DELETE CASCADE,
    persona_name TEXT NOT NULL,
    persona_path TEXT NOT NULL,          -- absolute, /workspace/<dir>/.agents/personas/<name>.md
    persona_commit TEXT,
    persona_body TEXT NOT NULL,          -- links made absolute, as a child's
    persona_settings JSONB NOT NULL,     -- {"model", "tools", "credentials"}, as a child's
    rule_chain JSONB,                    -- [tools] or NULL when the persona has no smelt.tools
    credentials TEXT[] NOT NULL,         -- Rule G's bit: '{git-ssh}' or '{}'
    created_at TIMESTAMP NOT NULL DEFAULT now(),
    applied_at TIMESTAMP                 -- NULL until the pod matches the grant
);
```

Why a table of its own rather than an `agents` row with depth 0: about 47 queries in nine files read `agents` as "this conversation is a child" (statuses, `finish`, `report_owed`, the stuck-turn notice to a parent, the sweeps, usage's group root, deletes). A root row there would need every one audited, and one missed is a parent notice to nobody or a `finish` offered to the user's conversation. The table holds only what the persona governs, and the six readers listed below read it beside `agents`. Code decides `parent_id IS NULL` under the row lock. No trigger: the set is the only writer.

## State model

**`top_level_personas` row:** none → *unapplied* (inserted) → *applied* (`applied_at` set). Then gone by the conversation's cascade delete. There is no other transition: no unset, no swap.

| Step | What happens | If it fails partway |
| -- | -- | -- |
| read (before the transaction) | the persona file from the conversation's pod, at the checkout's recorded commit; parse; resolve the model | nothing written; the error is returned |
| insert (one transaction) | trust lock, row lock, the checks, insert unapplied (or replace an unapplied row), pin the model | rolled back; nothing written |
| reconcile | `reconcile_pod` to the persona's grant | the compensating delete of the row, still under the turn lock, then a best-effort `reconcile_pod(id, None)` back to the persona-less grant; error returned. A failed delete leaves the row unapplied: turns refused, a retried set replaces it, the startup sweep deletes it |
| AGENTS.md | `load_agents_md` as a child's start does, if the attach didn't already load it (the Developer checks `attach_repo`) | same as reconcile |
| mark applied | `UPDATE … SET applied_at = now() WHERE conversation_id = $1 AND applied_at IS NULL` | same as reconcile |
| request dropped | the set runs in a spawned task the handler awaits (the SME-354 B7 pattern), so a hung-up client can't stop it between steps | — |
| smelt restarts mid-set | the turn lock is gone; the row is unapplied | `agents::sweep::startup_sweep` deletes unapplied rows first, before anything wakes, and best-effort reconciles each pod back; the gate refuses turns until then |

**Every writer:** the set (insert, replace-unapplied, mark applied, compensating delete), the startup sweep (delete unapplied), the conversation delete (cascade). That's all.

**Every reader, and what it does with a row:**

| Reader | Unapplied | Applied |
| -- | -- | -- |
| `db::agent_rule_chain` (offer, calls, questions, script MCP) | rules apply | rules apply |
| Rule G `git_ssh_granted`, Rule S `persona_credential_names` (new pod's install, live install, reconcile, prompt) | narrowed grant | narrowed grant |
| `turn::history::agent_prompt` / `persona_section` | no turn runs | `# Persona` section; the heading text says "read when this conversation was set to it" |
| `db::conversation_tree` (sidebar) | label shown | label shown |
| `admit_user_turn` / `confirm_user_turn` / `admits_notices` | refused / refused / not admitted, the notice saved | admitted |
| `create_child` (the caller is top-level) | no turn, so no `start_agent` | child chain `for_child`, bit seeded |
| `GET …/persona` | "being applied" | the label, commit, model |

**Who sees a change:** the set publishes `ConversationsChanged`, so every tab's sidebar and start screen refetch. Repo updates (`ReposUpdate`) also refetch the start screen's options, so a clone finishing shows its personas. Other conversations: none. The pod: credentials, as above. A pod restart re-installs from `for_conversation`, which reads the row, so the pod comes back with the same grant.

**In-flight work:** nothing is in flight, by construction: the set refuses a conversation with a turn.

## API shape

New `src/api/personas.rs` (server functions; `src/api/chat.rs` is 29,232 B):
- `get_top_level_persona(id)` → `GET /api/conversations/{id}/persona` → `TopLevelPersona { set: Option<SetPersona { label, path, commit, applied, model }>, can_set: Option<String> /* why not */, options: Vec<PersonaOption { label, description, error }>, repos_waiting: Vec<RepoNote> }`. Options are listed only when the persona can be set. This reads the checkout on every call, as `list_personas` does.
- `set_top_level_persona(id, persona)` → `POST /api/conversations/{id}/persona` → `SetPersona` or a `ServerFnError` with the refusal text above. `persona` takes the scoped name only (`<dir>:<name>`): with one attached repo a bare name would work, but `start_agent` refuses a bare one without `repo` (SME-368), and one spelling is simpler.
- docs/api.md gets two table rows, and docs/api/agents.md gets the section on the sequence (create, attach, model, persona, send), "started", the model rule and every refusal.

## UI

**Where:** the start screen (`transcript.rs`'s `conversation-empty` block), directly under `RepoAttach`, shown only while the start screen shows (no messages). It is a new component, `PersonaPicker`, in `src/frontend/pages/chat/persona_picker.rs`:
- **No ready, trusted repo with personas:** nothing shown, or one muted line, "Start as a persona: attach a trusted repo with `.agents/personas/`", when a ready repo has none or isn't trusted.
- **Options:** a `<select id="persona-picker">` of `<dir>:<name>` plus "No persona", the chosen option's description under it (clamped to two lines), and a "Start as this persona" button. A file that doesn't parse is a disabled option with its error as its title.
- **After the set:** the picker is replaced by "This conversation runs as `smelt:ticket-driver` (`<model>` on `<provider>`)". A refusal shows in the picker's error line, the `ErrorText` style.
- **Requests:** both `spawn`s (the GET, refetched on `ConversationsChanged` and `ReposUpdate` for the open id, and the POST) live in `PersonaPicker`, which is shown under the start screen's own condition. The POST's result can hide the picker, so it is kept in a signal on the component's parent row, `ConversationState` (`state.rs`, 30,053 B, about +200), rather than in the picker (SME-57).
- **Sidebar:** a top-level row shows the persona as an agent's row does: the second line holds the label alone, with no status, since a top-level conversation has none. `tree.rs:191`'s `persona: None` path is where the Developer checks a top-level node is drawn.

**Layout:** at laptop width the select and the button sit on one line (`flex-wrap: wrap`), the description below. At phone width (360px) the button wraps under the select, and the select takes `max-width: 100%`. **Narrowest:** the transcript column at 721px with the sandbox panel and a todo list open (the SME-144 measure). The widest content is a 64-character name with a 10-character dir, ellipsised in the select, and a 1,024-character description clamped. It covers nothing: it is in the flow of the start screen, below the attach form and above the example asks. CSS goes in `assets/css/07-pages.css` (24,866 B, about +600).

## Docs: what changes in the design, and what still holds

New page `docs/design/personas/top-level.md`, linked from index.md and from agents.md's "The `agents` row is separate…" paragraph.
- **What changes:** "personas are only sub-agents" was true because the only way to read and snapshot a persona was a child's start. Now a top-level conversation can be set to one once, after attach and before its first message. Why: a PM-started Driver must be top-level (one tree per ticket, SME-460), and its rules, credentials and model were prose until now.
- **What still holds:** the trust gate at the read. The snapshot is frozen, so a persona can't widen itself by editing its file. Rule G narrows down the line, and Rule S comes from the persona alone. `own` binds only its own conversation. Rules and credentials can never be set or swapped once the conversation has started. A top-level persona gets nothing a child of the root wouldn't, and its model resolves only on its own provider. It is also the table, "started", the state model and the readers.
- tool-rules.md "Narrowing": "the user's own conversation, at the top, has allow-all" becomes "…has allow-all, unless it was set to a persona (top-level.md), in which case its chain is that persona's one entry". persona-files.md `model` gets a sentence on the top-level rule.

## Decided (Driver): please confirm

## Trade-offs to flag (copied into the ticket)

- **T1. The trust gate binds files, not API callers.** `POST /repos` trusts what it attaches, and smelt's API is unauthenticated. So any caller that can reach it (a sandbox's `curl`) can attach a repo and set a persona from it. That includes minting a top-level `smelt:deployer` with `deploy_kubeconfig`, which `start_agent(persona: "smelt:deployer")` from any conversation can already do (Rule S is persona-only). This ticket adds no reach beyond what the API already allows. SME-460's allowlisted client and SME-243's egress rules are the guard.
- **T2. A failed attach that saves a notice in the conversation counts as "started",** so it can't take a persona then. Start a new conversation.
- **T3. `admits_notices` falls open on a database read error,** as today. With an unapplied row, the window is only between a restart and the startup sweep. The sweep runs before anything wakes, and a live set holds the turn lock anyway.
- **T4. The GET reads the checkout on each call** (like `list_personas`), only while the start screen shows.
