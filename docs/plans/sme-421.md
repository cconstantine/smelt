# SME-421 plan: an overstated undercount makes the floor refuse a compacted retry that fits

**Branch:** `cconstan/sme-421-an-overstated-undercount-makes-the-floor` (from `origin/main` 127bc232, fetched).
This file lives on that branch only — **it is removed before the PR merges**; the ticket's `## Plan`
keeps the record. All line numbers were re-read at 127bc232 (the ticket's "Where:" line had moved).

## What

When a request is refused as too big, `overflow::recover` learns how far short the token estimate
fell: `undercount = refusal's input count − estimate_request_tokens(refused)`
(`src/turn/overflow.rs:107`), and adds that absolute number to the retry — both the fallback
projection (`src/turn/reply.rs:47-48`) and the `size` handed to `before_sending`
(`src/turn/reply.rs:86`). The correction exists on purpose (SME-386 final review: without it the
retry's budget is refused again on every send), but it is measured against the **pre-compaction**
request. When the retry answers the refusal by compacting, the content the estimate missed (a
base64/CJK tool output) was just summarized away, and the surviving request is charged for an error
it no longer has. The floor (`room::before_sending` → `CompactionProgress::floor_fired`) then
refuses the retry, sets `stuck`, and poisons `CompactionProgress::after` with the overstated size
(`floor_fired`'s `after.get_or_insert(size)`) — which keeps `fits` false and `why_stuck` quoting a
phantom size. A user send escapes it (`user_wrote` → `try_anyway`, and a plain send never reaches
the floor because `room_only` is off); a child stays stuck through its parent's wakes — the ticket's
complaint.

Ticket scenario, verified against today's code (llama.cpp `n_ctx` 32,768; tool output 31k real
tokens estimated 10k; `alone` ≈ 4.5k): refused estimate ≈ 14.5k, `undercount` ≈ 21.5k; after
compaction the retry is projected at ≈ 7k + 21.5k ≈ 28k — over the floor line
(`window − COMPACTION_SAFETY_BUFFER − MIN_USEFUL_REPLY` = 32,768 − 4,096 − 1,024 = 27,648) — so
`budget_within_room` gives < 1,024, `floor_fired` sets `stuck`, and the ~7.5k real request never goes.

The fix: **keep the correction, scale it to what survives compaction.**

## Fix: scale the undercount to `alone`'s share

A refusal names one number; the undercount cannot be attributed to a part of the request from it.
But compaction only shrinks the messages: what survives untouched is `alone` — `refused` with its
messages emptied (`without_messages`, already computed in the named branch, `overflow.rs:48`) — and
a fresh summary. The surviving estimate error is therefore *at most* the error of the refused
request attributable to `alone`'s proportion, plus the summary's own error. The summary is smelt's
own summary prose — plain text `estimate_tokens` (chars/4) fits well, the same assumption every
SME-386 budget already makes, with `COMPACTION_SAFETY_BUFFER` as its cover. So:

```
scaled_undercount = undercount × alone_estimate / refused_estimate      (saturating; used when the
                                                                     request went through compaction)
```

Properties that matter:

- **Uniform estimate error (the SME-386 regime, and escape.rs's single ratio): exact.** With
  estimate = `r ×` real: refused estimate = `rR`, `undercount = R(1−r)`, so
  `scaled = R(1−r) · alone_est/(rR) = alone_est(1−r)/r` — exactly the surviving fixed part's own
  shortfall (and the summary, fresh prose, needs no correction). The correction does what its
  comment promises, on the
  request it is added to.
- **Self-attenuating:** `alone ≤ refused_estimate`, so `scaled ≤ undercount` always — this fix can
  only shrink the correction, never grow it — and when compaction shrinks nothing (a request that
  is all `alone`), `scaled = undercount`: the SME-386 protection stands in full exactly where it
  was earned.
- **`refused_estimate == 0` (unreachable — `build_request` always puts a system prompt on the
  request)**: fall back to the full undercount, so the SME-386 protection is the default.

Ticket scenario under the fix: `scaled ≈ 21.5k × 4.5/14.5 ≈ 6.7k`; projected ≈ 7k + 6.7k ≈ 13.7k,
well under 27,648 → `before_sending` sends with a real budget; no `stuck`, no poisoned `after`.
Acceptance bar (1) ✓. A request that truly doesn't fit is still refused: `floor_fired`, `after`,
`try_anyway`, `at_limit`/`MAX_AT_LIMIT`, `too_small`, `MAX_REFUSAL_COMPACTIONS` and the SME-414
thrash bounds are untouched — bar (2) ✓.

**Why not the ticket's other options.** *Let that floor send at `MIN_USEFUL_REPLY`:* that makes the
floor send on every NoRoom — real non-fits included — turning each wake into a paid server call and
weakening escape invariant 2 (wakes stop spending) for the same phantom-size class of bugs; it also
masks the wrong number instead of fixing it. The `MIN_USEFUL_REPLY` escape stays where SME-386 put
it: `try_anyway`, paid for by a user write. *Apply it only to `alone`'s share (literal):* that is
this formula — "share" taken proportionally, not literally adding only an `alone`-sized term, which
would drop the SME-386 protection whenever the system prompt/tools themselves are the
undercounted part (shared tool descriptions, long server names).

## Where the choice lives: a tiny `Undercount` value

`undercount` is consumed in exactly two places (`reply.rs:48` fallback projection — reached only
when `last_known_usage` is `None`, i.e. post-compaction; `reply.rs:86` `size` — used by
`floor_fired` only when `compacted`) — but there are **two** paths to a compacted retry: recover
compacts before calling `build_request_with_room` (`overflow.rs:73-81`), and the floor compacts
*inside* its loop (`reply.rs:99-105`, review L-2's case). Scaling once in `recover` would leave the
second path absolute. So carry the pair and choose per loop pass:

`src/turn/room.rs` (the file of plain room decisions the escape test already drives directly):

```rust
/// A refused request's estimate shortfall, and what may still be true of a
/// request built after a compaction of it (SME-421): the part the estimate
/// missed sat in the history the summary replaced, so a compacted request
/// is charged only `alone`'s share of it — what no compaction shrinks.
#[derive(Clone, Copy, Debug)]
pub(super) struct Undercount { full: u64, refused_estimate: u64, alone: u64 }

impl Undercount {
    pub(super) const fn none() -> Self { … }                       // full 0 — a turn's normal steps
    pub(super) fn from_refusal(input: Option<u64>, refused_estimate: u64, alone: u64) -> Self { … }
    pub(super) fn for_request(self, compacted: bool) -> u64 {
        if !compacted || self.refused_estimate == 0 { return self.full; }
        self.full.saturating_mul(self.alone) / self.refused_estimate
    }
}
```

- `overflow.rs`: hoist `let alone = estimate_request_tokens(&without_messages(refused));` above the
  `named` match (the guess branch needs it too — a refusal can name a count without a window), and
  replace `:107` with `Undercount::from_refusal(overflow.input_tokens, estimate_request_tokens(refused), alone)`.
  `recover`'s signature is unchanged.
- `reply.rs`: `build_request_with_room` takes `undercount: Undercount`; the loop starts
  `let correction = undercount.for_request(*compacted);` and passes `correction` to `build_request`
  (which keeps its plain `undercount: u64` — `named_refusal.rs:99` and any test calling it are
  unaffected) and to `size`. Fix the doc-comment at `:67-68`. `BeforeSending::Compact` re-loops →
  the scaled number is picked up on the very next pass.
- `run.rs:374`: the turn loop's `0,` becomes `Undercount::none(),` (one line; sits amid SME-414/455
  churn, see blast radius).

### T2 — escape.rs: per-part estimate error + a third invariant

Today's `World` has one ratio (`estimate_percent`, 85–115) for the whole request, so the undercount
is a flat ≤ ~18% of the refused request and both existing invariants survive the bug (the ticket's
trace: the floor falsely refuses once, then a user send
sails past the floor because `room_only` is off). The model must widen before any invariant can see
this. Exact model change:

- New `World` parts: `blob: u64` (real tokens of a base64/CJK-style tool output sitting in the
  history) and `blob_percent: u64 = rng.range(20, 60)` (under-estimates 2–5×).
- `real()` = `fixed + history + blob`. Whole-request estimate becomes per-part:
  `estimate_request()` = `(fixed + history)·estimate_percent/100 + blob·blob_percent/100`.
  The old proportional `estimate()` stays for *new* content (pending/typed/`fits_a_short_reply`'s
  compacted hypothetical — no blob there).
- `compact()` sets `blob = 0` along with the summary+quote history — a summary keeps a base64 blob's
  gist in plain words, not its bytes. This is the whole point: the undercounted part's estimate
  share collapses at compaction while the refusal's count still carries it.
- Wherever the turn grows `history` (the typed send; the step-to-step `pending` growth), with
  chance ~30% also `blob += rng.range(200, 30_000)`. The event mix's `estimate_percent` branch keeps
  its range and gains a `blob_percent` re-roll beside it.
- `World::recover` / `World::build` take room.rs's `Undercount` directly and apply
  `for_request(*compacted)` at the fallback projection and `size` — a line-for-line mirror of
  reply.rs (escape.rs already imports from `super::*`).

Third invariant (the ticket's bar 1 as a property): when `recover` answers a refusal that **named
its count** by compacting, record `expect_send = Some(scaled)` — the surviving share the correction
will add. In `build`'s `BeforeSending::Refuse` arm, if
`real().max(estimate_request()) + expect_send_bound + COMPACTION_SAFETY_BUFFER + MIN_USEFUL_REPLY ≤ window`
holds — the retry fits, with room to spare, even after the fix's deliberately conservative surviving
share — push a fault: `"the floor refused a compacted retry that fits: real …, est …, bound …,
window …"`. `check()` fails when `world.faults` is non-empty (report the first, keep
`SME386_ESCAPE_DUMP` writing every failing case's log, plus the new fault). The oracle reads only
the server-truth size, the estimate and `alone` — never today's `full` — so it cannot pass by
construction. A mid-loop compaction only shrinks `real`/`estimate_request()` with the bound fixed,
so the invariant stays required after such a compaction too.

**Expected red (a prediction):** with today's code, ≥ 1 of the 20,000 seeds fails with the new
fault (the bug's shape — dominant blob, named refusal, compact, floor — is common once blobs exist;
if a run shows zero, raise the blob chance to ~50% and widen `blob_percent` down to 10 before
touching the invariant). **Expected green after the fix:** no fault at all, and both original
invariants ("a fitting send reaches the server within 3 sends", "wakes stop spending") hold on all
20,000 seeds — the widened world is exactly where invariant 2 must keep paying: refusals still
count into `MAX_REFUSAL_COMPACTIONS`, stuck wakes still stop spending, `try_anyway` still gives the
user their way out. **Which part it needs:** red with `for_request` stubbed to ignore `compacted`
(== today's behavior); green with the scaling. Record that stub-run output next to the prediction.

## State model (the numbers this fix feeds)

- `undercount`/`Undercount`: lives only between a refusal and the retry's build — never persisted,
  never crosses a turn. Writers: `recover` only (a turn's normal `build_request_with_room` passes
  `none()`). Readers: `build_request`'s fallback projection and `before_sending`'s `size` — both
  reachable only on a compacted request.
- `CompactionProgress::after`: today a false floor records the overstated size here
  (`floor_fired`'s `get_or_insert`) and keeps `fits` false across every later wake; it is replaced
  only when a reply measures post-compaction (`measured`), cleared on window change (`sync`) or a
  user write (`user_wrote`, via `stuck`/`try_anyway` only). The fix removes this corruption path's
  main trigger; nothing about its transitions changes.
- `stuck`: same setters (real `at_limit`×3, `MAX_REFUSAL_COMPACTIONS`, `too_small`, floor NoRoom
  on a real size), same clearers (`user_wrote`; `sync` on window change). Bar (2) rides on this:
  real non-fit refusal semantics are bit-for-bit unchanged — only inputs shrink.
- Partial failures mid-transition: unchanged (a summary already paid for when the floor refuses
  stays paid, `refusal_compacted` already counted — SME-386 round 2 M4; the fix does not move any
  `?`). Race with a window learned mid-recovery (`learn`): `sync` still resets all of it — the
  scaled number was computed from `refused` and the learned window, same as today's.

## Trade-offs

1. **Proportional attribution over-corrects when the error is concentrated:** after the fix the
   correction can still exceed the true surviving error by up to `alone_est × (server count/estimate
   − 1)`. With an unusually large `alone` and a ≥3× blob under a small window the floor may still
   refuse once. Accepted: the exact per-part error is not knowable from one aggregate count, the fix
   is monotone (`scaled ≤ full` always), and the user escape (`try_anyway`) is unchanged.
2. **The summary's own estimate error is not corrected** (fresh prose, chars/4, `COMPACTION_SAFETY_BUFFER`
   as cover) — the same assumption the SME-386 budgets and the escape model already make.
3. **T2's oracle uses the surviving bound the fix computes** — the strongest fit claim a sizing
   heuristic can make: the floor must never refuse a compacted retry that fits *by its own most
   conservative estimate*. An exact oracle would need per-part counts no provider returns.
