# SME-482 plan: compact on demand

**Branch:** `cconstan/sme-482-compact-on-demand-the-user-the-api-or-the` (from `origin/main` 41e8c5c, worktree `/workspace/smelt-worktrees/smelt-sme-482` in the Planner's sandbox). Trade-offs and questions are in the ticket. This file goes before the PR merges (development-process.md).

## What and why

Today smelt compacts only on its own: proactively before a request that wouldn't fit (`run.rs`'s `CompactionStep::Compact`), at the floor inside `build_request_with_room`, and after an overflow refusal (`overflow.rs`). A long-running Project Manager carries every past ticket until the window fills, and pays for that history on every turn. This ticket adds three triggers. Each one goes through the **same** `compact` body in `src/turn/compaction/mod.rs`, so every safeguard holds with no new code: the verbatim user and parent messages (SME-367), the pinned todo list (SME-462), the unread-results naming (SME-414), the summary's cut-off and empty refusal (SME-443), the overflow retry inside the summary (SME-73), and the Claude Code session reset (SME-431).

1. **The user:** a "Compact" button in the chat header opens a small popover with an optional note ("what to keep") and **Compact now**. It calls the endpoint below.
2. **The API:** `POST /api/conversations/{id}/compact`, body `{"note": string|null}`. It runs between turns, and is **refused** while a turn runs or is queued (Q1).
3. **The model:** a tool, `compact_context`, with an optional `note`. The call records a request. The turn compacts at the **end of that tool pass**: after every result of the reply is saved and before the next model call, or before the turn returns when the pass ends the turn. It happens **at most once per turn**, and a second call in the same turn is refused with a result that says so.
4. **The PM persona** carries the compaction points: one short section in `docs/personas/project-manager.md`, and one line in `.agents/personas/project-manager.md` pointing at it. One line goes in `docs/personas/ticket-driver.md` too (after a merge). That one is the Planner's call per the brief; Q6 lets the Driver drop it.

No migration. The divider's reason rides on the existing `CompactionSummary.refused` field (serde-default JSON in `messages.content`), so nothing in the schema changes.

## How

### The shared core (`src/turn/compaction/mod.rs`, 23,450 B → about 25,000)

- `compact` gains a `note: Option<&str>` parameter and returns `Compacted` (`Done` | `Skipped(Skip)`, where `Skip` is `Empty` | `UnsafeBoundary`) instead of `()`. Today's two silent `return Ok(())` no-ops become `Skipped(..)`. `compact_conversation`'s signature and behaviour stay as they are for its three callers (`run.rs`, `reply.rs`, `overflow.rs`) and the test callers (`tests/spans.rs`, `tests/tools.rs`): it passes `None` and maps `Compacted` to `()`.
- A new `pub(super) async fn compact_on_request(pool, conversation_id, turn_model, slot, by: Asker, note: Option<String>) -> ServerFnResult<Compacted>`, in the same `compaction` span. `Asker` is `Model` | `Request` (the endpoint, whether the chat or a script called it: one route, no trustworthy way to tell them apart, see Q2). It passes the divider's reason as `refused` (it is "why this compaction happened", and the transcript already renders it after "Conversation compacted: "). The reason is `"the model asked for it"` or `"on request"` (Q2). A summary request that overflows keeps that reason (the existing `refused.or_else(..)`).
- `summarize`'s prompt gets one more paragraph when a note is given, after the live state: `"Whoever asked for this compaction asks the summary to keep: {note}"`. `COMPACTION_SYSTEM_PROMPT` does not change.
- `types.rs`: the doc comment on `CompactionSummary.refused` now says it is the reason for any compaction that isn't the plain proactive one (a refusal, or an on-demand one). The field name stays (Q7). 26,132 B, so a comment edit only.
- `continuation.rs` (23,030 B): `unread_tool_results` skips `compact_context`'s own result. It is read by definition, and naming it as unread would tell the model to re-run it. Sibling results stay named, since they really were covered unread.

### The request record (`src/turn/compaction_progress.rs`, 22,797 B → about 24,500)

`ConversationRuntime` lives in `src/turn/state.rs`, which is **39,960 B, 40 bytes under the ceiling**. Nothing goes there. The record goes inside `CompactionProgress`, which is already the conversation's and is reached through `with_compaction_progress`:

```rust
/// A compaction the model asked for this turn (SME-482).
#[derive(Clone, Debug, Default)]
struct OnRequest { pending: Option<Option<String>>, spent: bool }
```

- `request(note) -> Result<(), &'static str>`: refused when `spent` ("already compacted once this turn") or when `pending` ("already asked for in this reply"). Otherwise it sets `pending`.
- `take_request() -> Option<Option<String>>`: takes `pending` and sets `spent`.
- `turn_started()`: clears both. It is called at the top of `run_turn_loop`, under the turn lock.
- **`sync` keeps `on_request`** when it resets everything else for a new window. A window learned mid-turn must not hand the turn a second compaction (T6).

The on-demand compaction then calls `p.compacted(window)`, as the proactive one does. The next reply measures the room it left, and it counts toward SME-414's thrash count the same way. That bounds a model that compacts on every wake with one step between (see the state model).

### The model tool (new `src/anthropic/tools/compact.rs`, about 3,500 B; `tools/mod.rs` 25,727 B, +2 lines)

- `Registered { offer: Offer::All, class: Class::READ_ONLY }`. Every conversation is offered it: top-level, child and linked. Every persona's chain lets it through, since all of them have `class: read-only` or the `all` default, and none denies it (checked against `.agents/personas/*.md`; T17). It is READ_ONLY in the same sense as `todowrite` and `notify_user`: it changes smelt's own record of the conversation, not the sandbox or anything outside.
- Input: `{ "note": string? }`. The note is trimmed, and empty means none. It is refused over 2,000 characters, or when it holds control characters other than `\n` (the `git::not_plain` family, minus newline).
- `run`: `crate::turn::request_compaction(conversation_id, note)` returns `Ok("This conversation will be compacted once this tool pass ends, before your next model call: you'll go on from a summary, with the user's and parent's messages and your todo list kept word for word.")` or the refusal as an `Err`.
- Description (draft): *"smelt: compact this conversation's context now, to save tokens: smelt summarises the history and you continue from the summary, with the user's and parent's own messages and your todo list kept word for word. Use it at a natural break (a task finished, before starting an unrelated one), not mid-task. Before calling it, record what you'll need in a durable place (your todo list, the ticket); the summary is a narration, not a record. Call it on its own: other calls' results in the same reply are summarised before you read them. Once per turn; `note` says what the summary must keep."*

### The safe point (new `src/turn/on_request.rs`, about 7,000 B; `run.rs` 28,701 B → about 29,300; `reply.rs` 26,452 B → about 27,300)

- `reply.rs::run_tools`: when a reply has a question (`ask_user`/`ask_parent`, recorded) **and** a `compact_context` call, the compact call is refused: `"compact_context can't run in the same reply as a question: call it after the answer"`. The reason is that the question's `tool_use` has no result until the answer turn, and a summary covering it would leave the answer's `tool_result` orphaned, which Anthropic refuses outright. That refusal sits next to the existing question pre-pass, so the order is fixed: questions are recorded first, and then `compact_context` is checked against `asked`.
- `run.rs`, after the tool pass's results and any correction notice are saved and `streak.after_calls` is settled, and **before** `if ends { return }`: `on_request::compact_if_asked(pool, conversation_id, turn_model, slot.held(), &mut last_known_usage, &mut persisted, &mut pending_new_content).await?`. That function:
  1. `take_request()`. With none, it returns at once.
  2. `compact_on_request(.., Asker::Model, note)`. The last saved message is the pass's tool results, so the boundary is always safe. An `Err` (SME-443's empty or still-cut-off summary, a second overflow) **fails the turn** exactly as a proactive compaction's failure does, and the history stays as it is.
  3. `p.compacted(window)`, `*last_known_usage = None`, `pending_new_content.clear()` (the continuation is now the request's tail; it is estimated whole, as after any compaction), and `note_thrash(..)`.
  - The turn then loops, and the next iteration's drains (notices, agent messages) land **after** the continuation, where the model reads them word for word. If `ends`, it returns.
- `run_turn_loop`'s start: `with_compaction_progress(id, CompactionProgress::turn_started)`.
- **Claude Code:** nothing kind-specific is added. `compact` already calls `claude_cli::session::reset`, which sets the reset mark. The turn's next `call_run` takes it, ends the parked run (the CLI still waiting on its `compact_context` MCP call, whose result `turn_cli.hold_results` held), and starts a new session seeded from the summary. That is the B2 row that `test_a_full_tool_loop_compacts_and_goes_on_in_a_new_session` already covers for the proactive trigger. When the pass ends the turn, `turn_cli.close()` answers the held calls, and the next turn's first call takes the mark (its `cli.run` is `None`) and starts fresh from the row-less session. T15 proves both.

### The endpoint (new `src/api/compaction.rs`, about 2,500 B; `api/mod.rs` +1 line)

It goes in a file of its own, not `api/chat.rs` (29,232 B), which SME-481 is adding `POST /api/conversations` to.

```rust
/// Compacts the conversation now, between turns (SME-482).
#[post("/api/conversations/{id}/compact")]
pub async fn compact_conversation_now(id: i64, note: Option<String>) -> ServerFnResult<()>
```

It calls `crate::turn::compact_now(db::get(), id, note)` in `on_request.rs`, which works like this:

1. Validates the note (the same rule as the tool). Refuses a conversation that doesn't exist, with the existing `conversation_not_found()`.
2. `tokio::spawn`s the work and awaits the handle. A client hanging up drops only the await, never the compaction halfway through its three inserts (the `after_turn_state_write` pattern, SME-219 review 1).
3. Inside: `between_turns(id, /*wait*/ false, || ..)`. `None`, meaning the lock is held or queued for, refuses with *"A turn is running in this conversation: compact it once the turn ends, or ask the model to call compact_context."* Holding the lock:
   - Refuses a pending question row (`db::get_pending_question`, which covers `ask_user` and `ask_parent` through `asked_of`): *"This conversation is waiting on a question: answer it first."* That is the orphan rule again.
   - Refuses *"Nothing new since the last compaction."* when nothing but that compaction's continuation follows the latest `CompactionSummary`.
   - Resolves the model (`providers::resolve_turn_model`; its error goes through), takes a `TurnSlot` (`TurnSlot::acquire`), and calls `compact_on_request(.., Asker::Request, note)`. `Skipped(Empty)` gives *"Nothing to compact yet."*. `Skipped(UnsafeBoundary)` (a stopped turn left calls with no results) gives *"The last reply's tool calls have no results yet: send a message first, then compact."*
   - On `Done`: `p.compacted(window)`. No usage event is published: usage is cleared to none, and `ContextUsageUpdate` carries a `TokenUsage`, not an `Option`. The clicking tab refetches `get_context_usage` after the call returns (see UI). Other tabs' meters catch up at the next reply (a trade-off).
4. `between_turns` releases the idle turn state, as the quiet stop's callers do.

## State model

**`OnRequest`** (memory, in the conversation's `CompactionProgress`; lost on restart):

| state × event | `compact_context` call | end of tool pass | window changes (`sync`) | turn starts | Stop / turn dropped | restart / delete |
|---|---|---|---|---|---|---|
| idle (`None`, !spent) | → pending; result Ok | — | idle | idle | idle | gone |
| pending | 2nd call in the reply: refused ("already asked for"), stays pending | compact → spent (on Err: spent, turn fails) | **stays pending** | cleared → idle | stays until the next turn's start clears it | gone (that turn is gone too) |
| spent | refused ("once this turn"), stays spent | nothing | **stays spent** | cleared → idle | stays until the next start | gone |
| pending + question in the same reply | the compact call is refused in `run_tools` before `request` runs, so this cell can't be entered | — | — | — | — | — |

**Every writer:** the tool's `run` (`request`), the turn loop's end of pass (`take_request`), and the turn loop's start (`turn_started`). All three run under the conversation's turn lock, since tools run inside the turn. No other caller writes it. The endpoint never touches it: its compaction is outside any turn and doesn't spend the model's once.

**What a failure partway leaves:** `compact` saves the summary, the divider and the continuation as three inserts, then clears usage, then resets the Claude Code session. A Stop, or an insert error, between those inserts leaves part of a divider. That already holds for every compaction trigger today. The endpoint's spawned task means a client hang-up can't cause it. A Stop can't either, since the endpoint isn't a turn. Only a restart can. On the model path a Stop mid-compaction drops the turn as it does today (`docs/api/events.md`: "A stop drops the turn wherever it's waiting … a compaction"). Summary call failures (SME-443's empty or cut-off, a second overflow) happen **before** any insert, so the history stays as it is, and the turn fails with the notice, or the endpoint returns the error.

**Compaction record (`CompactionProgress`) per trigger:**

| trigger | `compacted(window)` | `thrash` | `stuck`/`thrashing` checked first |
|---|---|---|---|
| proactive / floor / refusal (today) | yes | yes | yes, at `step` |
| model tool | yes | yes: one accepted step between two compactions grows it, as today | no: at most one summary a turn, and the next iteration's `step` ends the turn if armed |
| endpoint | yes | yes | no: a deliberate act by the user or the PM |

So a model that calls `compact_context` on every wake, with exactly one step between compactions, is ended by the existing `END_AT` (12). One with two or more steps per wake isn't counted. It pays one summary per wake that something real caused (a command finishing, a message). That is a trade-off in the ticket.

**What each caller does in each conversation state:**

| conversation state | model tool | endpoint (user/API) |
|---|---|---|
| idle, nothing new since the last compaction | n/a (in a turn, the reply itself is new) | refused: nothing new |
| idle, with history | n/a | compacts (holds the lock and waits for a provider slot) |
| turn running, or a turn queued for the lock | compacts at end of pass, once | refused at once (no wait) |
| question pending (`ask_user`/`ask_parent`) | the call can't be in the question's reply; refused there | refused: answer first |
| last reply's calls have no results (stopped mid-tool) | n/a (a turn answers them in its request first) | refused: send a message first |
| paused (after a Stop) | n/a | compacts; doesn't end the pause or wake it |
| `stuck` / `thrashing` armed | the turn ends at `step` before any call, so no tool runs | compacts (counts as a compaction) |
| conversation deleted mid-compaction | the insert errors, the turn fails (as today) | the insert errors, Err returned, the idle state released |
| Claude Code | session reset, the next call starts from the summary (mid-turn: the parked run ends) | session reset, the next turn starts a new session |

**Who else sees each change:** the divider is published to every tab live (`record_saved` → `MessagesAppended`), and the sidebar reorders (`ConversationsChanged`), as for any compaction. A send that arrives while the endpoint holds the lock is admitted and queues behind it (`TurnPlace`), so it runs on the compacted history (T13). A Stop sent meanwhile drops that queued send, not the compaction. A wake queues the same way.

**Work already in flight:** the endpoint resolves the model when it takes the lock. A model change made during the summary call applies from the next turn, as everywhere (SME-72). A model-tool compaction uses the turn's own `turn_model` snapshot, including a window learned earlier in the turn.

**Provider slot:** the endpoint waits for a slot on the conversation's provider while holding the turn lock. On a one-slot server that is busy with another conversation's turn, it waits out that whole turn (SME-343's slot is held per turn). That is in the trade-offs.

## PM persona compaction points

**`docs/personas/project-manager.md`** gets a new `## Compacting your context` section at the end (about 900 B):

> A long-running PM keeps its context small by compacting (`compact_context`, SME-482) at these points, and only after recording the board first (open slots, the Drivers running and their conversations, pins, retro counts) on the "Next retrospective" ticket or in its todo list, so the summary is never the only copy: after a ticket reaches Done and its retro count is taken; after a retrospective closes; and before starting a new Driver when its context is past about half the window.
