# SME-335 plan: the sandbox-pod-max LimitRange declares its own defaults — plan convergence, schedulable init containers

**Branch:** `cconstan/sme-335-limitrange-default-removal-is-a-provider-no` — the ticket's Linear `gitBranchName`, off `origin/main` at `bad67245`, pushed; this file is its first commit

**Repo:** this one — `terraform/smelt/` is the module homelab consumes at `?ref=main` (the ticket's "Repo: cconstantine/homelab" is wrong: homelab has no LimitRange of its own, only the module call). The fix lands here; the Deployer later applies it there.

## What and why

The module's `kubernetes_limit_range_v1.sandbox_pod_max` declares only `max` (SME-77: memory ceiling, never a `cpu` entry). The Kubernetes API server then fills every unset `default` **and** `defaultRequest` of a LimitRange item **from `max`, on every write**, and re-fills `default` on writes that omit it. Everything in this ticket follows from that one mechanism, probed live on a throwaway k3d running `rancher/k3s:v1.34.6-k3s1` (the version `docs/setup.md` / `src/bin/sandbox_image_import.rs` pin, via the `terraform/test-cluster/` recipe) whose node reports **62.8Gi allocatable — smaller than the 64Gi default, so the scheduling symptom reproduces by itself**:

1. **Perpetual plan drift.** `terraform apply` reports `kubernetes_limit_range_v1.sandbox_pod_max` updated (`0 add / 2 change`), yet every subsequent `terraform plan` re-proposes the identical change. Two plans back-to-back after a successful apply were byte-identical:

   ```
   ~ limit {
       ~ default         = { - "memory" = "64Gi" -> null }
       ~ default_request = { - "memory" = "64Gi" -> null }
   Plan: 0 to add, 2 to change, 0 to destroy.
   ```

   Why: the kubernetes provider (`3.3.0`, the test-cluster lock file's version) updates with a merge patch, and a merge patch cannot remove server-filled keys — and even a write that omits them gets `default` re-filled from `max` by the API server. **No provider version converges a config that leaves the fields out; the ticket's "provider no-op" is right about the symptom, but this is API-server defaulting, not a provider bug — a provider upgrade cannot fix it, and `lifecycle.ignore_changes` only hides it (probe below).**
2. **Scheduling bug (the 2026-11-06 escalation).** The module's own `database-is-ready` init container (server.tf) declares no resources, so admission gave it `requests: {"memory":"64Gi"}, limits: {"memory":"64Gi"}` — read off the admitted pod — and the server pod sat `Pending` with `FailedScheduling: 0/1 nodes are available: 1 Insufficient memory` on the 62.8Gi k3d node. Same mechanism as e458d346's homelab note (only ryzen's 98Gi could take it) and the 62Gi test-node block. The rest of this repo already works around the fill-in with small explicit resources (`src/bin/sandbox_image_import.rs:173` loader pod; `src/sandbox/pod_lifecycle_tests/storage.rs:88` "no test node here can fit" (SME-341); the LSP holder fixtures) — this fix makes the *namespace* stop punishing containers that name nothing.
3. **Lowering the max fails at apply.** With the as-is module, as-is state, and server-filled live state (`default`/`defaultRequest` = 64Gi), `terraform apply -var sandbox_pod_memory_max=32Gi` fails, verbatim:

   ```
   Error: Failed to update limit range: LimitRange "sandbox-pod-max" is invalid:
   [spec.limits[0].defaultRequest[memory]: Invalid value: "64Gi": default request
   value 64Gi is greater than max value 32Gi, ...]
   ```

   The patch can't un-fill the 64Gi `defaultRequest`, and the API refuses the lower max against the retained request — exactly the 2026-11-06 report. `lifecycle.ignore_changes` does **not** rescue this (probe D below): it hides the plan while leaving live `defaultRequest` at 64Gi, and lowering max fails the same way.

The consequence the ticket names — homelab master permanently plan-dirty, training the eye past DEPLOY.md's clean-plan gate — plus a latent "no node under 64Gi can ever take the server" bug, are all reproduced on the k3d.

## How (the fix)

**F1 — `terraform/smelt/rbac.tf`.** Declare the defaults the API server has been filling in, and zero the request:

```hcl
  spec {
    limit {
      type = "Container"
      max  = { memory = var.sandbox_pod_memory_max }

      # (comment: API server fills these from max when unset (SME-335) — a
      # plan that omits them can never converge, and every container naming
      # no memory of its own reserved the whole ceiling. default mirrors max
      # exactly: an un-capped container's limit stays what it has always
      # effectively been, and lowering sandbox_pod_memory_max moves both
      # together, so lowering the ceiling keeps applying. default_request is
      # zero: naming nothing reserves nothing (the SME-77 intent, extended to
      # containers that name nothing). Containers that DO name their memory —
      # every container smelt builds, `requests.memory: 0` included — are
      # untouched by either field.)
      default = { memory = var.sandbox_pod_memory_max }

      default_request = { memory = "0" }
    }
  }
```

**F2 — `terraform/smelt/server.tf`.** The `database-is-ready` init container gets its own small resources — 32Mi request, 64Mi limit — taken verbatim from the user's own unmerged fix commit `e458d346` (branch `cconstan/init-container-memory`), comment included. A pod should never depend on a namespace default to be schedulable (a namespace can carry more than this LimitRange; the module may one day meet a different one).

**F3 — `k8s/smelt-park-rbac.yaml`.** Both LimitRange documents (`smelt-park`, `smelt-park-test`) gain `default: {memory: 64Gi}` and `defaultRequest: {memory: "0"}` (the `0` quoted — quantities are strings), and the big comment (which today *describes the fill-in as the design*) is rewritten to the explicit shape. rbac.tf's header binds them: "if the yaml ever changes, this must change with it" — they change together. The compose `k3s-bootstrap` applies this yaml to the dev cluster, so the dev k3s converges on its own next bootstrap (`kubectl apply` replaces the whole atomic `limits` list — the explicit `"0"` lands; the Developer re-apply check below covers it).

**F4 — `terraform/test-cluster/`.** `main.tf`'s header gains `./check-limitrange.sh` alongside `check-secret-env.sh`, and the new script (Tests, below) checks the fix against the same k3d.

`terraform/smelt/README.md`'s "What it makes" bullet gains half a sentence ("…a LimitRange capping sandbox pod memory **and declaring `default`/`defaultRequest` explicitly (SME-335)**"), and SME-77's homelab patch recipe (its ticket's `kubectl patch … limits/0 → {type,max}` form) is now wrong — noted here so the Deployer never re-applies it; the module (or the three-field patch) is the way.

**No new variables.** `default` is welded to the existing `sandbox_pod_memory_max` input, and `default_request` is a constant `"0"`: a consumer that ever set a `sandbox_pod_memory_default_request` above its max would reproduce symptom 3 through the module's own door. (Decided 2.)

## Why this shape is safe (probe facts, k3s v1.34.6)

- The API server **accepts** `defaultRequest: {memory: "0"}` and **keeps it** — a hand-written LimitRange and the terraform apply both read back `"0"`; it only fills fields that are *absent*.
- A container that sets `requests.memory: 0` explicitly — every sandbox container, via `memory_only()` (SME-77) — is **left alone** by any `defaultRequest`: probe pod `{requests: 0, limits: 8Gi}` read back unchanged after the fix. **A non-zero `defaultRequest` could never turn smelt's own pods into reservers, and the zero one can't either** — the brief's "must not schedule sandbox pods against each other" constraint holds a fortiori, because defaults only touch containers that leave the field out.
- After the fix, a brand-new container that declares nothing gets `limits: {memory: 64Gi}, requests: {memory: 0}` — the ceiling it always effectively had, and **schedulable** (probe pod went `Running` on the 62.8Gi node).
- The recreated server pod scheduled and went `Running 1/1` with `database-is-ready` at `requests: {"memory":"0"}` — the fix, live on a node where the as-is pod could never schedule.

## State model

The live object's three relevant fields and what each apply does:

| State | Who puts it there | Exit |
|---|---|---|
| server-filled (`default`=max, `defaultRequest`=max, config omits both) | any write from an as-is config (the fill-in runs on create *and* update) | F1 apply: one in-place update, `default` unchanged (config `default` == the filled 64Gi), `default_request` → `"0"` — the change homelab sees |
| explicit (config == live) | post-F1 apply; survives re-plan, re-import, lower/raise of the max, and hand-apply of the yaml | only hand edits (then it's drift, *visible*, no ignore_changes) |
| partially fixed (e.g. `default` only) | a failed/aborted apply | next apply converges (merge patch re-sends both explicit keys) |

New pods pick the new defaults at admission; already-running pods (sandboxes included) are untouched. A mid-apply failure leaves the object in a state the next apply converges — no hand repair. On homelab the transition is **two in-place LimitRange updates plus one in-place Deployment update** (the init resources), then empty plans — SME-77's never-hand-patch discipline is preserved because the module now writes the whole intended object every apply.

## Decided (Driver)

1. **`default` mirrors `sandbox_pod_memory_max`; `default_request` is `"0"`.** Converges (probe), keeps today's effective limit semantics (no cap change for any container that omits limits), keeps lowering the ceiling a one-variable edit, and reserves nothing from containers that name nothing. The alternatives probed: 16Mi (needless reservation), 1Gi default (re-caps forgetful containers — rejected), ignore_changes (masks drift; lowering still fails — rejected), init-resources-only (insufficient — the whole ticket's list of symptoms needs the LimitRange fixed).
2. **No new module variables** — a knob a consumer could set above `max` would reopen symptom 3; welding `default` to the max takes away that footgun at zero cost.
3. **F2 is in** (init resources, user's own `e458d346` values 32Mi/64Mi): pods declare their own resources as policy; the probe shows it makes the server pod schedulable even with an unfixed LimitRange. One extra in-place Deployment update on deploy is the cost.
4. **The red-first artifact is the throwaway-k3d check script, not a Rust test** — the thing that broke is what `terraform apply` leaves in a cluster; nothing in `src/` observes the LimitRange's `default` fields, and `test_create_applies_the_memory_limit_and_reserves_nothing` only passes because pods declare their own (which they still will). The test-cluster root is the module's existing harness (SME-438), and `scripts/` is off-limits.
5. **SME-77's intent, kept exactly:** 64Gi max stays, no `cpu` entry ever, sandbox containers keep their explicit zero request and are untouched by the new defaults (probe), and the plan-file claim "`defaultRequest` cannot make sandbox pods reserve against each other" is verified at the pod level (fact 2 above), not reasoned.
6. **Homelab needs no hand work**: `?ref=main` picks the module up; the two Deployer-visible facts (expected diff, empty plan after) are in the deploy section.

## Trade-offs (also in the ticket)

- `default` welded to the max means lowering the ceiling also lowers the default *limit* — but that is what the API server has been doing unasked on every write all along; the fix makes it visible and keeps lowering applicable (verified both directions).
- The server pod rolls once at deploy time (init resources; Recreate, ~2 min per README).
- A hand-created container in these namespaces that names no resources now *reserves* nothing and (if it names no limits) is capped at 64Gi — exactly the old live behavior minus the reservation; the only "regression" is for something that was relying on a 64Gi *reservation*, which by definition could never schedule on any node here.
