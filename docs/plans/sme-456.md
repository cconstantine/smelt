# SME-456: bound `go install`'s and `curl`'s stalls inside the install bound

**Branch:** `cconstan/sme-456-go-curl-stall-bounds`, from `origin/main` `944b95d0` (SME-452's PR #307 merge).
Planner seat: one clone in a conversation sandbox, so there's no linked worktree (rules.md, "Working from a conversation sandbox").

## What and why

SME-452 bounded npm's stalls inside `INSTALL_TIMEOUT` (600 s): `NPM_STALL_BOUNDS` and the `connect_bound.js` preload. Two catalog installers still have no stall bound of their own:

- `go install` (gopls; `pkg:golang`).
- `curl -fsSL` (every `pkg:github` server: rust-analyzer, actionlint, …).

When either meets a stalled registry, it runs into the 600 s bound and ends as `The install didn't finish within 10 minutes`. **This plan bounds each one at its mechanism, well inside 600 s, so the installer's own error comes back.** The fix lives in the server pod's install script, not in the catalog's suggested commands. So saved installs, edited ones included, get the bounds without any re-deriving. `INSTALL_TIMEOUT` is unchanged.

## Mechanism, measured

**Setup** (seat sandbox, Docker):

- `golang:1` is go1.27.3 and `buildpack-deps:trixie-curl` is curl 8.14.1, the catalog's images.
- `stall.py` (below) has four modes on its own ports: **tarpit** (accepts TCP, never answers the ClientHello), **header** (TLS done, request read, no reply), **trickle** (200 with `Content-Length: 50000000`, then 1 byte every 20 s), **bodystall** (200 headers and 1,000 bytes, then nothing).
- curl ran `curl -fsSL -o /dev/null https://stall:<port>/x` with `CURL_CA_BUNDLE`.
- go ran `GOPROXY=https://stall:<port> GOSUMDB=off GOFLAGS=-x go install golang.org/x/tools/gopls@v0.20.0` with `SSL_CERT_FILE`.
- Each run was capped by `timeout 700`. All runs went in parallel. Scripts: `measure.sh`, `measure_fixed.sh`, `proto.sh` (seat scratch `/workspace/scratch/sme-456/`, quoted below).

### Today (`base`)

| stall | curl | go |
|---|---|---|
| tarpit (TCP up, TLS never) | **301 s**, rc 28 `curl: (28) Connection timed out after 300269 milliseconds` | **10 s**, rc 1 `net/http: TLS handshake timeout` |
| header (no reply) | **> 700 s** (killed, rc 124) | **> 700 s** (killed), 4 parallel `# get …info` lines, never answered |
| trickle (1 B / 20 s) | **> 700 s** | **> 700 s**, after `# get …: 200 OK (0.082s)` |
| bodystall | **> 700 s** | **> 700 s**, after `200 OK (0.020s)` |

**curl:**

- Its default connect timeout (300 s) covers TCP **and** the TLS handshake: the tarpit ended at 301 s with error 28. That's under 600 s by itself, but it takes half the bound.
- No bound at all after the connection is up: no response-header wait, no idle body, no total. A header stall, a trickle or a mid-body stall holds curl forever.
- In the catalog's `curl … | tar -xz` shape the pipeline waits with it.

**go** (source: `src/cmd/go/internal/web/http.go` on `release-branch.go1.27`):

- `get` uses `securityPreservingDefaultClient` = a copy of `http.DefaultClient`: no `Timeout`. The 5 s `impatientInsecureHTTPClient` is used only for `GOINSECURE` https.
- So `http.DefaultTransport`'s bounds apply, and only those: a 30 s dial and a 10 s `TLSHandshakeTimeout` (the measured 10 s). There's no `ResponseHeaderTimeout` and no body bound.
- cmd/go doesn't retry a proxy fetch.
- So a stall after the handshake (no response header, a trickle, a body that stops) holds `go install` forever, silent: without `-x` it writes nothing until it ends.
- The same holds for the checksum database (`sum.golang.org`, same client) and for a `direct` fallback's `git`.
- `-x` prints `# get <url>` before each fetch and `# get <url>: 200 OK (…s)` once headers arrive (`fetch`/`get` above).

**pip and cargo are bounded** (SME-452's sweep: 15 s × 5 retries, 30 s × 3) and stay out of scope.

### Fixed (`proto.sh`, the plan's wrapper prototyped, same stalls)

|---|---|---|
| tarpit | **30 s** `curl: (28) Connection timed out after 30001 milliseconds` | **10 s** (unchanged, Go's own) |
| header | **60 s** `curl: (28) Operation too slow. Less than 1024 bytes/sec transferred the last 60 seconds` | **125 s**, rc 143, log ends with the four `# get …info` lines, then `smelt: go wrote nothing and received under 1 KB/s for 120 s, so it was stopped` |
| trickle | **60 s**, same message | **125 s**, same |
| bodystall | **60 s**, same message | **125 s**, same |

- curl's low-speed check also covers the wait for response headers: the header stall ended at 60 s.
- `.curlrc` through `CURL_HOME` works with curl 8.14.1, in both `golang:1` and `buildpack-deps:trixie-curl`.

**Real installs through the wrapper still succeed:**

- `go install golang.org/x/tools/gopls@latest` at `--cpus 1`: rc 0 in 123 s, 44 MB binary. The `-x` log is 1,184,242 bytes.
- The actionlint v1.7.7 `curl … | tar -xz` install: rc 0 in 1 s, `actionlint -version` prints `1.7.7`.

**How quiet a real go install gets, to size the watchdog** (`real_go.sh`: `GOFLAGS=-x`, each line timestamped):

## The fix

All of it goes in the server pod's install script (`pod_script`), next to SME-452's preload and scoped the same way: to the install's subshell, never the language server (started later over `pods/exec`), never the user's command text.

**Part 0, a move only (own commit, proved by script):**

- `CONNECT_BOUND`, `CONNECT_BOUND_JS`, `pod_script` and `NPM_STALL_BOUNDS` move, with their doc comments, from `src/lsp/pods.rs` (27,079 B) to a new `src/lsp/pods/script.rs`.
- `pods.rs` goes to about 21.5 KB. This part would otherwise take it past the 30,000 B aim.
- Visibility: `pub` stays `pub` through a `pub use script::{CONNECT_BOUND, NPM_STALL_BOUNDS};` re-export. `pod_script` is `pub(super)`.

**Part 1, curl's bounds, `CURL_STALL_BOUNDS`:**

- A new `src/lsp/pods/curlrc` (included with `include_str!`, like `connect_bound.js`):

  ```
  connect-timeout = 30
  speed-limit = 1024
  speed-time = 60
  ```

- `pod_script` writes it to `/tmp/smelt-curl/.curlrc` with the same heredoc pattern. Inside the install's subshell it sets `[ -n "$CURL_HOME" ] || { CURL_HOME=/tmp/smelt-curl; export CURL_HOME; }`, so a `CURL_HOME` in the config's `env` wins.
- The command line wins over a `.curlrc` too, so a user's own `--connect-timeout` or `--speed-time` beats these, and `curl -q` skips the file.
- `connect-timeout = 30` matches `CONNECT_BOUND`. Every connection counts separately, including the redirect hop to `objects.githubusercontent.com`.
- `speed-limit`/`speed-time` is an idle-style bound, not a total cap: under 1 KB/s for 60 s in a row. A slow but moving download is never cut. A 1 KB/s link couldn't fetch rust-analyzer (about 15 MB) inside 600 s anyway.
- Worst case per curl: 30 s, or 60 s after the connection is up. The catalog's command runs one curl per install.

**Part 2, go's bound, `GO_IDLE_BOUND` (120 s):**

- **`GOFLAGS="${GOFLAGS:+$GOFLAGS }-x"`** in the install's subshell. go then logs each fetch (`# get <url>`) and each build step. That makes go's log a progress signal, and a stall names its URL.
- **An idle watchdog**, a new `src/lsp/pods/go_idle.sh` (included with `include_str!`, `__GO_IDLE_S__` filled in like `__CONNECT_BOUND_MS__`). It runs next to the install, which `pod_script` now starts in the background and `wait`s on. Every 5 s it checks:
  - whether a process whose `/proc/*/comm` is `go` is running (only then does idle time count);
  - whether the install log grew;
  - whether the pod received at least 5 KB since the last check (`/proc/net/dev`, every interface; the pod's network namespace holds only the install's traffic at that point, and loopback is counted so the hermetic tests' local servers count).
- After 120 s with a `go` running, no log growth and under 1 KB/s received, it appends `smelt: go wrote nothing and received under 1 KB/s for 120 s, so it was stopped` to the log and `kill`s (TERM) those `go` processes. The install then fails with its own exit status (143 for a bare `go install`) and its own log, which ends with the stalled `# get <url>`.
- It exits once the install does.
- The script is the prototype in `proto.sh` (below), tidied.

**Part 3, the log is opened for append.** `: > /tmp/install.log` first, then the subshell `>> /tmp/install.log 2>&1`. Otherwise the watchdog's appended line is overwritten by the install's next write (its shell's `Terminated`), since the install's descriptor holds its own offset.

**How the go choice meets SME-452's Q3** (no blanket `timeout` around installs):

- This is an idle bound, not a total one. It fires only on no progress, at about 125 s, leaving about 475 s.
- It kills only `go` processes, never the install's shell, so the install's exit status and log still arrive, plus a line saying why.
- A go install that keeps logging or receiving is never stopped, however long it takes.
- Q3's worry was killing what the timeout's process listing needs. This ends far before the 600 s listing, so a go/curl stall never reaches it.

**The options weighed for go:**

| option | verdict |
|---|---|
| `timeout` wrapper (total) | No: SME-452 Q3, and it cuts a slow, healthy install. |
| A bounded local GOPROXY in the pod | No: needs a proxy program in every image; `golang:1` has python3, but a user's image might not. |
| A Go env or `GODEBUG` knob | None exists for client timeouts (`net/http` has none; cmd/go reads none). |
| TCP keepalive / `tcp_retries2` | No: a peer that ACKs and sends nothing stays alive; `tcp_retries2` isn't a safe sysctl. |
| `SIGQUIT` for a goroutine dump | No: hundreds of lines; the 4,000-byte tail would show only its end. `-x`'s `# get` line names the URL better. |
| **Idle watchdog with `-x`, go only** | **Yes.** Covers connect, header, trickle and body stalls, and `git` under `direct`. Names the URL. Measured. |
| The same watchdog for every installer | No (Q4): `cargo install` compiles a big crate silently with no network, and npm has its own bounds. |

**Why config, not the command text:**

- `rederived_install` (SME-386 A3) only rewrites a pre-SME-360 single-arch command into the catalog's exact suggestion, and `manager::start` looks a server up in mason's registry only when `is_single_arch_github_install` holds.
- Putting curl's flags into `github_download` would need a third derivation (per-arch without flags → per-arch with), a registry lookup at the start of every existing `pkg:github` server, and a write to each saved config. It would still miss every edited command.
- In the pod script, the catalog's suggestions don't change by a byte (every exact-string test in `catalog/tests.rs` stays as it is, untouched, which is the guard), and every saved install (old text, per-arch, edited) gets the bounds as it is. `rederived_install` and `config.rs` are untouched. T7 tests that explicitly.

## State model

- **New state, all in the server pod's `/tmp`, gone with the pod:**
  - `/tmp/smelt-curl/.curlrc`, written once by the pod script before the install.
  - The watchdog subshell, alive while the install runs.
  - Its idle counter, in memory.
- **Writers of `/tmp/install.log`:** the install's subshell (now `O_APPEND`) and the watchdog, with one line when it fires.
- **Readers:** `install_log` (`tail -c 4000`, on failure and on timeout). With `-x`, a go install's log is about 1.2 MB, so the tail shows its last lines: the `# get` lines and the smelt line on a stall, go's own error on any other failure.
- **`/tmp/install.rc`:** still written once, after `wait`, by the pod script.
- **Each caller in each state:**

  | install state | `wait_install` | `PROCESS_LISTING` at timeout | watchdog |
  |---|---|---|---|
  | running, making progress | polls | – | resets idle |
  | go stalled < 120 s | polls | – | counts |
  | go stalled ≥ 120 s | sees rc 143 + log, fails at once | not reached | appends its line, kills `go`, keeps watching until the install exits |
  | curl stalled | sees curl's/tar's rc + log within 30/60 s | not reached | idle (no `go`) |
  | other installer stalled (npm…) | as before (SME-452 bounds) | as before | idle (no `go`) |
  | install done | reads rc | – | exits within 5 s |

- **Work in flight:** a pod already installing keeps the script it was created with. Only pods created after the deploy get the bounds. Nothing is persisted.
- **Failure partway:**
  - If `.curlrc` can't be written (`/tmp` full), curl runs unbounded, as today. Same for the preload.
  - If `/proc/net/dev` can't be read, `rx` reads 0, and only log growth counts as progress. A go install keeps logging every few seconds under `-x`, so that's still safe.
  - If `kill` fails (go already gone), nothing.

## Trade-offs to flag

- **A stalled go or curl now fails fast instead of waiting** (curl 30 s or 60 s, go about 125 s), with no retry. Today neither recovers from a stall on its own (measured: over 700 s, or 301 s for curl's handshake), so the only case that loses is a server that would have woken up between 60 s and 600 s in.
- **Every install's curl gets `.curlrc` bounds,** including curl inside a user's own script. A link under 1 KB/s for 60 s in a row fails it, unless the user passes their own flags (the command line wins) or sets `CURL_HOME`.
- **go installs log every step (`-x`):** about 1.2 MB of `/tmp/install.log` for gopls, about 13,800 lines. Only its last 4,000 bytes are ever read.
- **A user's go command that runs a long, silent, offline program** (`go run` of a quiet generator that runs over 120 s without output or network) would be stopped, with the smelt line saying why. No catalog install does that.
- **T5 and T6 add about 3.5 minutes** of mostly-idle time across test threads.

## Questions for the Driver (none needs the user)

1. **Bounds in the pod script, not in the catalog's commands?** Recommended **yes**: the suggestions don't change, so saved and edited installs get the bounds with no re-deriving, no registry lookup at start, and no write to saved configs. The command-text route adds a derivation to `rederived_install`, a lookup per `pkg:github` server, and still misses edited commands.
2. **curl's values: `connect-timeout 30`, `speed-limit 1024` over `speed-time 60`?** Recommended **yes**: measured 30 s and 60 s, matching `CONNECT_BOUND`, and idle-style.
3. **go's watchdog: 120 s with no log growth and under 1 KB/s received, while a `go` runs?** Recommended **yes**: about 13× the largest gap at 0.5 CPU (9.2 s). 60 s would also fit the measurements, with less margin under load.
4. **The watchdog for go only, not every installer?** Recommended **yes**: cargo compiles quietly with no network, and npm already has its own bounds.
5. **Add curl `--retry`?** Recommended **no**: curl can't rewind a stream it already piped into `tar`. A stall fails in 60 s with curl's own error, and SME-452's message carries it.
6. **Commits 2a/2b rather than one?** Recommended **2a/2b**.

## Appendix: the scripts (seat scratch, `/workspace/scratch/sme-456/`)

`stall.py` (modes tarpit/header/trickle/bodystall, optional TLS) and `measure.sh` are as described above. Results: `out/base-*.txt` and `out/fixed-*.txt`. `proto.sh`, the wrapper prototyped:

```sh
LOG=${LOG:-/tmp/install.log}; GO_IDLE=${GO_IDLE:-120}
mkdir -p /tmp/smelt-curl
: > "$LOG"
cat > /tmp/smelt-curl/.curlrc <<'SMELT_EOF'
connect-timeout = 30
speed-limit = 1024
speed-time = 60
SMELT_EOF
( CURL_HOME=/tmp/smelt-curl; export CURL_HOME
  GOFLAGS="${GOFLAGS:+$GOFLAGS }-x"; export GOFLAGS
  "$@" ) >> "$LOG" 2>&1 &
install=$!
(
  idle=0; last_log=-1; last_rx=0
  rx() { awk 'NR > 2 { sub(/^[^:]*:/, ""); s += $1 } END { print s + 0 }' /proc/net/dev 2>/dev/null || echo 0; }
  gos() { for p in /proc/[0-9]*; do [ "$(cat "$p/comm" 2>/dev/null)" = go ] && echo "${p#/proc/}"; done; }
  while kill -0 "$install" 2>/dev/null; do
    sleep 5
    log=$(wc -c < "$LOG" 2>/dev/null || echo 0); now=$(rx)
    running=$(gos)
    if [ -z "$running" ] || [ "$log" != "$last_log" ] || [ $((now - last_rx)) -ge 5120 ]; then idle=0; else idle=$((idle + 5)); fi
    last_log=$log; last_rx=$now
    if [ "$idle" -ge "$GO_IDLE" ]; then
      echo "smelt: go wrote nothing and received under 1 KB/s for $GO_IDLE s, so it was stopped" >> "$LOG"
      kill $running 2>/dev/null; idle=0
    fi
  done
) &
wait "$install"; rc=$?
```

The real version keeps the user's `CURL_HOME` (`[ -n "$CURL_HOME" ] ||`), keeps SME-452's `NODE_OPTIONS` line, and writes `$rc` to `/tmp/install.rc` before the idle loop.
