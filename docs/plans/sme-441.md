# SME-441 plan: the sidebar shows when an idle conversation has a terminal command running

**Branch:** `cconstan/sme-441-the-sidebar-shows-when-an-idle-conversation` (from `origin/main` at `bad67245`).

This plan file is the full plan (the ticket's `## Plan` links it); it is removed before the PR merges, per [development-process.md](https://github.com/cconstantine/smelt/blob/main/docs/development-process.md).

## What

A conversation whose model turn has ended while a terminal command still runs looks idle in the sidebar. Give it a marker next to the green pod dot: a pulsing dot, coloured distinctly, whose hover title counts the commands ("1 command running"). It updates live on the channel the green dot already uses, and it shows on child-agent rows too. Decided (Driver), 2026-11-07: a running turn wins — the marker shows only while the conversation is not busy; the look is a pulsing dot distinct from the pod green; the hover title is count-based. No open questions for the user (the Driver decided what the user would have been asked).

## How

### 1. What "a command is running" means, and its query

**Marker predicate:** conversation `c` gets a marker when at least one `terminal_commands` row has `status = 'running'` and its terminal's pod is live (`sandbox_pods.terminated_at IS NULL`). Rows carry `conversation_id`, but the marker is counted through the pod join on purpose: a pod stop marks the pod's running commands `lost` (`close_pod_terminals`), and if that marking ever loses a race or errors, the marker still cannot outlive the pod — a marker can never sit on a row with no green dot, which is the ticket's "pod stop must clear it", structurally. This mirrors `list_live_pods`' `running_commands` subquery (`src/db/sandbox.rs` ~125) exactly, so the sidebar count and the Sandboxes page count can never disagree; both mirror `POD_BUSY` (~158) and `FINISH_RUNNING_COMMANDS_SQL` (`src/db/agents/mod.rs` ~256, SME-389 B's finish gate) too — four readers, one predicate.

New in `src/db/sandbox.rs`, beside `conversations_with_live_pods` (~311), which it mirrors in style:

```rust
/// The conversations with at least one running terminal command on a
/// live pod, with the count — the sidebar's markers (SME-441). Same
/// predicate as `list_live_pods`' `running_commands` and `POD_BUSY`.
pub async fn running_command_conversation_counts(
    pool: &PgPool,
) -> Result<Vec<(i64, i64)>, sqlx::Error> {
    sqlx::query_as::<_, (i64, i64)>(
        "SELECT p.conversation_id, COUNT(*)::BIGINT
           FROM sandbox_pods p
           JOIN sandbox_terminals t ON t.pod_id = p.id
           JOIN terminal_commands tc ON tc.terminal_id = t.id
          WHERE p.terminated_at IS NULL AND tc.status = 'running'
          GROUP BY p.conversation_id
          ORDER BY p.conversation_id ASC",
    )
    .fetch_all(pool)
    .await
}
```

**No migration.** The table keeps its finished rows; this query's shape (live terminals of live pods, few rows each, joined to `terminal_commands` by `terminal_id` with `status = 'running'`) is the same one `list_live_pods` already runs per live pod on every `/pods` request, served by `idx_terminal_commands_terminal_running` (`terminal_id` partial on `status = 'running'`, migration `20260812041850`). `idx_terminal_commands_conversation_running` (`conversation_id` partial on `status = 'running'`, migration `20261105200000`) is what `FINISH_RUNNING_COMMANDS_SQL` and `idle_agent_without_report` use; ours groups by the *pod's* conversation, so the terminal-partial index is the one it rides, as `/pods` already does. No new index.

**API — new server function, not a widened fetch.** `get_live_pod_conversations` (`src/api/pods.rs` ~522, `GET /api/pods/conversations`, the green dot) stays as it is: a plain id list refreshed by `PodsChanged`. The marker needs a count and refreshes on a different, ~100× more frequent event (every command start and finish, not just pod create/stop); widening the dot's endpoint would re-run the dot query on every command and couple two independent lifecycles. New, next to it:

```rust
/// A conversation's running terminal commands, for the sidebar's markers.
#[derive(Clone, Debug, Serialize, Deserialize, PartialEq)]
pub struct RunningCommands {
    pub conversation_id: i64,
    pub running_commands: i64,
}

/// Which conversations have running terminal commands on a live pod,
/// and how many — the sidebar's command markers (SME-441).
#[get("/api/pods/commands")]
pub async fn get_running_command_conversations() -> ServerFnResult<Vec<RunningCommands>> { … }
```

(`db::running_command_conversation_counts` mapped to rows.) Route shape follows `/api/pods/conversations`: a literal segment beside `{pod_id}` routes, which that route already proves works.

### 2. Live updates: one new event, both relays

New app-wide event `AppEvent::CommandsChanged` (unit variant, like `PodsChanged`) in `src/events/mod.rs`, with the matching relayed variant `ConversationEvent::CommandsChanged {}` (empty struct — internally-tagged enums can't serialize tuple variants, the `MessagesAppended` comment says why; copy `PodsChanged {}` exactly). "Carries nothing: listeners refetch" — `api::chat::conversation_relay` (`src/api/chat.rs` ~556) gets the branch relaying `AppEvent::CommandsChanged` to `ConversationEvent::CommandsChanged {}` like its `PodsChanged` branch, so **both** sidebar connections carry it: the app-wide stream (`use_sidebar_app_events`, `src/frontend/pages/chat/live.rs` ~317) when nothing is selected, and the selected conversation's stream relay (SME-269) when one is.

**Publish sites — every production path that flips a conversation between "has a running command" and not** (all verified in `origin/main` at `bad67245`; `db::create_terminal_command` has exactly one non-test caller):

| Transition | Site | Publish |
| -- | -- | -- |
| record (`running` row appears) | `src/sandbox/files.rs::run_command` ~216, after the awaited `db::create_terminal_command` returns — the only creator (via `run_terminal_command`, `src/anthropic/tools/pods.rs` ~460; script MCPs run their scripts *as* such commands) | `publish_app(AppEvent::CommandsChanged)` next to the existing per-conversation `publish_command_update(…, "running")` (~226, SME-144) |
| send failed → `lost` | same fn ~234, in the `Ok(())` arm after `mark_terminal_command_lost` | there, next to the existing `"lost"` `publish_command_update` |
| finish (agent reports exit) | `src/sandbox/agent.rs::handle_agent_message` Exit branch ~798, only when `mark_terminal_command_finished` returned Ok — restructure the current `if let Err(e)` into a match so the publish rides the Ok path | there, next to the existing finished `SandboxCommandUpdate` |
| pod closed with running commands → `lost` | `src/sandbox/watch.rs::close_pod_terminals` ~263: set a `marked_lost` bool where `mark_terminal_command_lost` returns Ok; publish once at the end if set | covers **all** pod-loss paths in one site: user Stop (`stop_pod_for_user`, `src/sandbox/manager/teardown.rs` ~191), Remove volumes (`src/sandbox/manager/storage.rs` ~98), the crash pass (`handle_crash_cleanup`), the gone-pod pass (`watch.rs` ~208), and the quiet stop (`src/sandbox/quiet_stop.rs` ~326, which never marks — a busy pod is never quiet-stopped — but is covered by the same join) |

Publish *after* the awaited write commits, never before: a refetch can then only start after the commit it reports, so the last event's refetch can never miss it (two commands finishing at once just cost one extra refetch; the final state is read last). `events::publish_app` is a synchronous broadcast — no subscribers, no cost; a publish with nobody listening is a no-op, and the reconnect's one-shot reconcile (next item) covers anything published while a tab was down. `terminate_pod_as`' `PodsChanged` (`src/sandbox/manager/terminate.rs` ~196) stays as it is: it moves the green dot, and the sidebar refetches both resources on it anyway — no change needed.

Consumers of the new event:

- `src/frontend/pages/chat/live.rs::use_sidebar_app_events`: new `commands_changed: Signal<u64>` parameter, a match arm bumping it, and — like the other four — one bump in the connect-time one-shot reconcile (~347) so a stream that reconnects resyncs the markers. `AppEvent::Unknown` already means "stale bundle → offer reload": see the old-bundle note below.
- `src/frontend/pages/chat/state.rs`: `EventEffect::CommandsChanged` (~122, beside `PodsChanged`) and the `apply_event` arm (~283).
- `src/frontend/pages/chat/live.rs::use_conversation_events`: `EventEffect::CommandsChanged => *commands_changed.write() += 1` (~238).
- `src/frontend/pages/chat/mod.rs::Chat`: a `commands_changed` signal with a comment like `pods_changed`'s (~144), passed to `ConversationSidebar` and `ChatPanel` exactly like `pods_changed` (~163-164).

**Not changed: the Sandboxes page.** `src/frontend/pages/pods.rs::use_pods_changed` gets no `CommandsChanged` arm: every command start would make that page re-read Kubernetes usage for every pod, for a count it already refreshes on a 30 s tick. The sidebar's marker and the `/pods` count share a predicate, not a refetch trigger. (It can be a follow-up ticket if the Driver wants it; the `match` has a `_ => {}` arm, so it compiles either way.) `src/frontend/notifications.rs`' match also keeps its `_ => {}` — a command is not something the user is *needed* for; the notifier stays out.

**Old bundles (SME-43):** `AppEvent`/`ConversationEvent` are `#[serde(tag = "type")]` with `#[serde(other)] Unknown`, so an old bundle decodes the new event as `Unknown` and offers a reload (the sidebar and the pods page already do exactly that for every event added since — `ProvidersChanged`, `ConversationsChanged`) rather than breaking. The web bundle ships with the server, so this only matters across a reload window. `src/events/wire_tests.rs` pins the tagged-object wire form — add both variants to its round-trip lists (that test is why SME-269's unit variant had to stay plain).

### 3. How it looks, and how it composes (Decided (Driver))

**The running turn wins.** One row, one mark: `ConversationRow` (`src/frontend/pages/chat/sidebar/mod.rs` ~290) already draws the pulsing busy spinner from `row.node.busy` (~359 — that's `crate::turn::busy_conversations()`, a turn running or queued, `src/api/agents.rs` ~85; an agent whose turn ended but whose `agents` row is still `active` is *not* busy, which is precisely this feature's case) and the green pod dot from the pods resource (~369). The command marker sits beside them, shown only when neither the turn nor the row is busy. The derivation is a pure fn so the rule is unit-testable:

```rust
/// The sidebar's command marker's title: `Some` when the conversation
/// isn't running a turn (the busy mark wins — Decided (SME-441)) and has
/// running commands on its live pod. The count is the whole title: no
/// command text reaches the DOM (see the plan's hover-title rule).
fn command_marker(running_commands: i64, busy: bool) -> Option<String> {
    match (running_commands, busy) {
        (0, _) | (_, true) => None,
        (1, _) => Some("1 command running".into()),
        (n, _) => Some(format!("{n} commands running")),
    }
}
```

`ConversationSidebar` adds the resource next to `live_pods` (~47):

```rust
let live_commands = use_resource(move || {
    let _ = commands_changed();
    crate::api::pods::get_running_command_conversations()
});
```

and per row passes `running_commands: running_commands_for(row.node.id)` (a lookup in the fetched rows, `0` on no data, following `has_live_pod` ~51). A failed fetch means `0` for every row — no marker, no error line (the dot's fetch behaves the same).

`ConversationRow` gains the `running_commands: i64` prop and draws, right after the `live_pod` span (~369):

```rust
if let Some(title) = command_marker(running_commands, row.node.busy) {
    span { class: "live-command-dot", role: "img", title: "{title}", aria_label: "{title}" }
}
```

**Agents too:** child-agent rows *are* the same `ConversationRow` — the tree row is keyed by conversation id, an agent's commands are recorded under the agent's own `conversation_id` (the tool runs in its conversation), and its pod is its own — so an agent idling on a finished-notice-wait gets its own marker with no extra code. The scenario below covers it explicitly.

**CSS** (`assets/css/07-pages.css`, right after `.live-pod-dot` ~64; that file is 23,840 bytes):

`var(--warn)` is the theme's amber token (`assets/css/01-base.css` ~21, dark-mode value ~43 — it recolors like the MCP page's amber does, `05-mcp.css` ~357); `turn-working-pulse` is the very animation `.conversation-busy` uses (`07-pages.css` ~254), so the marker says "alive, waiting" in the sidebar's own motion language, in a colour that is neither pod-green nor accent-blue.

**Hover title / untrusted text:** count-only — the marker's `title` and `aria_label` contain a number and fixed words; no model-controlled text reaches the attribute at all. Dioxus escapes attribute values the way the sidebar already escapes `title: "Sandbox running"` and `waiting_count`'s counts (`sidebar/mod.rs` ~403), and the browser scenario reads both back. If a later ticket adds the command line to the title, it must isolate it like `CommandIndicator::title` does (`\u{2068}…\u{2069}`, `indicators.rs` test ~45); that is deliberately out of scope here.

**Where it sits, and widths:** in the row's mark run, after the pod dot, before the age — same 8×8px flex-shrink:0 box as `.live-pod-dot`, so a row with both dots is exactly as wide as one with busy + pod dot + waiting could already be (the busy dot and the command dot never coexist). The sidebar column is fixed (272px, the `07-pages.css` header comment); below 720px the sidebar is the phone strip, where the rows keep that width and fold behind "Conversations" (SME-40/41) — unchanged. Worst-case content (long title + "?" + both dots + age + armed Delete's long confirm) is the width SME-236 already holds at 390px; the scenario adds this marker's content to that exact check.

## State model

The marker is **derived, not stored**: no table, no column, no cache — "at least one `running` row on a live pod" evaluated at fetch time. A pod's Docker daemon dying with the pod, a server restart mid-command — those end in the same transition (mark `lost`) or in the join excluding a dead pod.

**One `terminal_commands` row:** `running` → `finished` (with exit code) | `lost` (never an exit code). Every writer (production only; tests drive the same fns):

| Transition | Writer | When | Fails partway |
| -- | -- | -- | -- |
| — → `running` | `sandbox::run_command` (`src/sandbox/files.rs` ~216), reached only from `run_terminal_command` (`src/anthropic/tools/pods.rs` ~460); one in-flight command per terminal enforced before the insert | after the stale-terminal refuse and the busy check | insert fails → error to the tool, no row, no publish |
| `running` → `finished(code)` | `handle_agent_message` Exit (`src/sandbox/agent.rs` ~798) | the sandbox agent reports the exit | mark fails → logged, marker stays (the row *is* running as far as the database says); a later `lost` mark or reload settles it |
| `running` → `lost` | (a) `run_command`'s send-failure path (`files.rs` ~234) — if *this* mark fails, the row stays `running` and the tabs' earlier "running" stands, as the code comments already decide; (b) `close_pod_terminals` (`watch.rs` ~263): user Stop, Remove volumes, crash cleanup, gone-pod pass, quiet stop | the send failed; the pod is gone | each `let _ =` keeps today's tolerate-and-continue; with the join, a `lost`-mark miss still shows no marker once the pod row closes |
| rows deleted | conversation delete cascade (`terminal_commands.conversation_id` FK) | user deletes | no CommandsChanged — the row's gone and `ConversationsChanged` rebuilds the list anyway |

**Readers of the same predicate:** the new `GET /api/pods/commands` (new, per-event + connect-reconcile refresh); `/pods` rows' `running_commands` (`list_live_pods`, 30 s tick + `PodsChanged`); `POD_BUSY` (idle-pass never stops a command-busy pod); `FINISH_RUNNING_COMMANDS_SQL` (SME-389 B refuses a first `finish` with commands running); `terminal_command_is_running` (tool busy check). All read at query time, none caches; this ticket adds a reader, no new writer race. Commands a seat detached (`&`, nohup, `finish`'s own rule) make no rows and never mark — the marker says "a command smelt tracks", same as the finish gate.

**Turn start/end and pod stop** (the ticket's explicit cases): a turn start moves no row; the tree's `busy` hides the marker (the turn wins). A turn end moves no row; `TurnsChanged` refetches the tree and the marker reappears if the count still stands — the count never went stale, because CommandsChanged refetches the count even while busy (the resource is sidebar-wide, not row-gated). A pod stop marks the pod's running rows `lost` and publishes `CommandsChanged` + `PodsChanged` → both dots clear within a couple of seconds, live; with an old bundle, the reload offer instead. Server restart with commands in flight: rows stay `running` until crash recovery/reconnect marks them `lost` (same window as today's `/pods` count — no new staleness), and every tab's connect-reconcile refetches regardless. A tab that missed events while disconnected refetches on connect (the reconcile bump), the established broadcast-no-replay answer (`live.rs` ~343).

**What each caller does:**

| Caller | none running | running, not busy | running, busy (a turn) | pod stops with one running |
| -- | -- | -- | -- | -- |
| Sidebar row, every tab (home tab: app stream; conversation tab: the relay) | no marker | amber pulse + green dot; hover "N command(s) running" | busy spinner only (amber hidden) | both dots gone in seconds, no reload |
| Home page `/` sidebar (SME-269 app stream) | same | same | same | same |
| Sandboxes page `/pods` | its own count column | its own count column (30 s tick, unchanged today) | n/a | row disappears (`PodsChanged`) |
| Notifier / title counts | untouched (`_ => {}` arm) | untouched — a running command is not "needs the user" (the idle-notice feature owns that, SME-377's note about a model waiting on its own commands) | | |
| Web bundle predating the variant | n/a | sees `Unknown` → reload offered (SME-43) — the standing behaviour for every added event; until reload, no marker | | |
| SSR first paint / mid-turn reload | no marker | marker in the first render (both resources load during it, like `live_pods`) | spinner | no marker |

- **Two files end within ~2,000 bytes of the 40,000 ceiling:** `src/db/sandbox.rs` (37,898 → ~38,500; headroom ~1,500) and `src/sandbox/agent.rs` (38,554 → ~38,700; headroom ~1,300). plan.md's rule would split them first; measured, this ticket adds ~550 and ~150 bytes — a review fix of that size fits, and splitting two of the hottest sandbox modules (and re-gating twice) costs more than the risk buys. The Developer keeps any review additions inside the headroom; the Driver should file the split of `src/db/sandbox.rs` (its terminal-commands section → `src/db/sandbox/commands.rs`) as its own Backlog ticket now, before anything else lands on these files (rules-commits: split before adding).
- The marker counts *tracked* commands: `&`/`nohup`-detached processes make no rows and mark nothing — the same rule the finish gate and the pod idle-stop rules use, stated so the user reads "a command smelt can see".
- The `/pods` page deliberately does not refetch per command (its usage re-read from Kubernetes per event outweighs a fresher count it already refreshes every 30 s); so a /pods count can lag the sidebar by up to its tick.
- The hover title is the count, not the command line (Decided (Driver)) — that also keeps all model-written text out of the attribute; isolating command text there would need `CommandIndicator::title`'s isolates.
- Between the `CommandsChanged` refetch and the `TurnsChanged` tree refetch landing, a row can show the marker for a turn that just started, or hide it for one that just ended, for the round trip (~a fetch) — bounded by whichever lands last; the busy spinner and amber dot are mutually exclusive in the same row either way.
- Crash-window staleness is unchanged from today's `/pods`: a row stays `running` until crash recovery marks it `lost` (or the live-pod join hides it); no new window is opened.
