# SME-244 plan — a parent conversation shows the cost of itself and every agent under it

**Branch:** `sme-244-group-spend` (cut from `origin/main` at `4d004ed` on 2026-10-25 and pushed; this file is its first commit.)

## What and why

The context detail view's "Spent so far" section sums one conversation's `model_call_usage` rows (`db::get_conversation_spend`). A group's root should show the whole group's spend — its own plus every agent under it, deleted children included — next to its own; an agent's own context view should show its spend as today plus its group's, labelled with the group's root. Scope item 7, and it creates `model_call_usage.group_root_id`, the column SME-245's per-call budget check reads (design: `docs/design/personas/agents.md#limits-sme-245`, the Budget row at `:149`).

## Migration — `migrations/20261025120000_group_root_id.sql` (new)

Newest on `main` at cut time is `20261023180000_agent_messages_and_pause.sql`; SME-240's planned one is `20261023220000_mcp_tool_classes.sql` and SME-239's will be ≥ `20261023230000` — all sort before this. Re-check `ls migrations/` at develop time; the name must not already exist. No renumbering dependency either way: this file only touches `model_call_usage` and reads `agents`, both long on `main`, so it stays correct if a later-timestamped migration lands first.

```sql
-- SME-244: cost groups. Each model call carries the id of the conversation
-- its spend belongs to: itself, or for an agent the conversation at its
-- group's root (`agents.root_id`, set at the start, so the group query
-- needs no recursion). No foreign key by design: a deleted child's spend
-- must keep counting in its group while `conversation_id` SET NULLs
-- (docs/design/personas/agents.md#limits-sme-245, the Budget row).
ALTER TABLE model_call_usage ADD COLUMN group_root_id BIGINT;

CREATE INDEX model_call_usage_group_root ON model_call_usage (group_root_id);

-- Rows predating this migration: an agent's rows to its root (agents exist
-- since SME-236), every other conversation's to itself. Rows whose
-- conversation was already deleted keep no group, as they join no
-- conversation's spend today.
UPDATE model_call_usage m
   SET group_root_id = COALESCE(
       (SELECT a.root_id FROM agents a WHERE a.conversation_id = m.conversation_id),
       m.conversation_id)
 WHERE m.group_root_id IS NULL AND m.conversation_id IS NOT NULL;
```

sqlx's Postgres migrator runs each file in one transaction, so the column, the index and the backfill land together or not at all. Migrations run at startup, before any turn records a call, so the backfill never races the fill.

## The fill — no Rust change to the record path

`record_model_call_if_current` (`src/db/usage.rs:112`) is the **only** production writer of `model_call_usage` — one call site, `src/turn/call.rs:161`, covering turn and compaction kinds alike; the `#[cfg(test)] record_model_call` (`:97`) goes through the same INSERT, so tests exercise the fill as written. Add the column after `cost_usd`; no new binds:

```sql
INSERT INTO model_call_usage
     (conversation_id, provider_id, model, kind, input_tokens, output_tokens,
      cache_creation_input_tokens, cache_read_input_tokens, cost_usd, group_root_id)
 VALUES ((SELECT id FROM conversations WHERE id = $1 FOR NO KEY UPDATE),
         (SELECT id FROM inference_providers WHERE id = $2 FOR KEY SHARE),
         $3, $4, $5, $6, $7, $8, $9,
         COALESCE((SELECT root_id FROM agents WHERE conversation_id = $1),
                  (SELECT id FROM conversations WHERE id = $1)))
 RETURNING conversation_id
```

Why it's right at every moment:

- *Child:* `create_child` inserts the child's conversation row and its `agents` row (`root_id NOT NULL`) in one transaction, and commits before the brief's first turn runs (`src/db/agents/start.rs:39–100`), so every child call records with the real root.
- *Top-level conversation:* no `agents` row → the fallback subselect → its own id; a top-level that's gone → both NULL (the fallback re-reads `conversations`; its `FOR NO KEY UPDATE` was already taken by the first VALUES expression, left to right).
- *Delete races:* a conversation's (or an ancestor's cascade) delete takes that conversation row's lock; the record takes it first too, so it sees either wholly-before (agents row present, root read) or wholly-after (agents cascade-gone, fallback NULL) — never a half state, and the FK can't fire because both columns come from subselects.

## State model

The state here is one column, `model_call_usage.group_root_id`, written once per row and never updated after.

Writers:
- the INSERT in `record_model_call_if_current` — the only production write; one call site (`src/turn/call.rs:161`), turn and compaction alike, finished and unfinished calls alike (an unfinished call is in its group like it's in its conversation's spend);
- the migration's backfill UPDATE — at startup, once, in the migration transaction, before any turn can record.

Readers:
- `context_detail()` per dialog open — `get_group_root` + `get_group_spend`; a value another conversation just changed (a child's call landing while a root's dialog sits open) is not seen until the next open, which refetches by design (`context.rs:541–562`) — that ends at the next click, not "briefly".
- the providers page (`model_spend_since`) and the conversation's own `get_conversation_spend` — unaffected, they don't read the column.
- SME-245's budget check (later) will read it per call; no reader today sums across conversations except the context dialog.

Transitions and failures:
- Row recorded while its conversation is live: `group_root_id` names the live root (itself for a root; an agent's root via the committed `agents` row).
- Row recorded after its conversation's delete committed (the SME-178 case): NULL conversation, NULL group — in no conversation's spend and no group's, still in the providers page's 30 days, as today.
- Rows of a child deleted after they were recorded: conversation_id SET NULLs, `group_root_id` stays — the root's group still counts them (the ticket's Done-when; test 2).
- Deleting the whole root: its `agents` rows and descendants cascade; its usage rows keep `group_root_id` pointing at the dead root — no live conversation queries that key, so those rows join no shown group (the design counts group spend only for a live root's group).
- Fill races: none beyond the above — the record's first VALUES expression holds the conversation's `FOR NO KEY UPDATE` before the `agents` read, and `create_child` commits conversation + `agents` in one transaction before the agent's first turn, so the fill never sees half a start.
- A failed migration leaves the column, index and backfill all absent together; the server restarts and retries — no partial column state.

## Trade-offs to flag

1. **A parent in the middle of a tree shows the whole group's number, not its own subtree's.** `group_root_id` keys every row to the tree root by design; a subtree total needs a recursive walk of `conversations.parent_id` per call. The ticket says leave it out; the copy ("In <root title>'s group") says whose number it is, so the middle parent isn't misread as its own descendants' total.
2. **A root's group line appears only when an agent's call has been recorded** — a child mid-turn isn't counted until its record lands, the same moment the providers page would see it. Shown always, a root with no agents would show its own figure twice.
3. **A call whose record commits after its conversation's delete has no group** (and no conversation), as today for conversation spend; it still counts in the providers page's last-30-days.
4. **`docs/api/events.md` is already past the 30,000-byte aim** (30,440): this ticket adds ~300 B and repairs its already-stale struct line. If it ever needs splitting, that's its own ticket.
5. `get_group_root` + `get_group_spend` add one round trip and one indexed aggregate per context-detail open (a hand-opened dialog, refetched per open) — not per turn.

## How it will be checked by hand (after merge, on a scratch database)
