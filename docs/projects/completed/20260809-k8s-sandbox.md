# K8s sandbox lifecycle

**Branch:** `k8s-sandbox` · **Idea:** `projects/ideas/coding-session.md` (kept — sandboxing was one piece of it; tool-wiring, streaming, and persistence still to come) · **Plan:** `projects/plans/k8s-sandbox.md` (removed)

## What shipped

The sandboxing phase of the coding-session idea, scoped to just the
lifecycle primitive: create, exec, delete — proven against a real cluster,
not wired to any tool yet.

- **`src/sandbox.rs`** (`server`-only): `Sandbox` (a live pod handle —
  `exec`, plus a `Drop` that queues cleanup) and `SandboxManager`
  (`create`/`delete`, owning the `kube::Client` and the cleanup queue's
  background drain task). `create` is get-or-create: a `Running` pod
  found under the deterministic `sandbox-{session_id}` name is reused
  rather than recreated, which is what makes an active conversation's
  sandbox survive a smelt server restart with no persistence code at all.
- **Test infrastructure**: `docker-compose.yml` gained `k3s`
  (`rancher/k3s`, pinned to match the real `homelab` cluster) and
  `k3s-bootstrap` (a one-shot `scripts/k3s-bootstrap.sh` run via
  `bitnami/kubectl`) services, making the sandbox tests hermetic — they
  hit a cluster `docker compose up` provides, not a specific reachable
  home network, matching how the existing Postgres tests already work.
  `k8s/smelt-park-rbac.yaml` is the first versioned copy of the `park`
  service account's RBAC scope (the real `homelab` copy predates this
  file and was created by hand).
- **Dependencies**: `kube` 4.2, `k8s-openapi` 0.28 (`v1_34`), and `rustls`
  (explicit `ring` provider install in `main.rs` — kube's own rustls-tls
  stack only auto-installs a default when built with its `aws-lc-rs`
  feature, which this project doesn't use).
- **5 tests**, all against a real cluster: clean-slate `create`, reuse-on-
  `Running`, `exec` capturing stdout and a non-zero exit code, `delete`
  confirming the pod is actually gone, and the Drop path (drop without
  `delete`, poll for the background drain task to clean it up).

Explicitly not done (per the plan's own scope): wiring any tool through
`anthropic::tools::execute`, streaming `exec` output to the browser,
`git clone`/credential wiring, an idle-timeout reaper for orphaned pods,
RuntimeClass/NetworkPolicy (both cluster-admin/deferred decisions, not
code).

## Retrospective

**What worked:**
- **Spiking against a real cluster settled several design questions that
  would otherwise have been guesses.** The plan's own "spike the riskiest
  assumption first" rule earned its keep twice: once confirming `kube-rs`
  could actually create/exec/delete against real RBAC before writing any
  production code, and again when a small throwaway Rust probe (not just
  `kubectl`) revealed the exact shape of the k8s exec protocol's exit-code
  encoding (`Status.details.causes[].reason == "ExitCode"`,
  `message` = the code as a string) — nothing in the docs spelled this out
  plainly, and guessing at it would have shipped a subtly wrong
  `extract_exit_code`.
- **Building the compose test infrastructure by hand-replaying it with
  `docker run` (since `docker compose` isn't installed in this dev
  container) caught real bugs before they reached the committed YAML**:
  `fs.inotify.max_user_instances` exhaustion killing k3s within seconds of
  boot, `bitnami/kubectl`'s non-root user unable to read/write the shared
  volumes, and `rancher/k3s`'s own bundled `kubectl` subcommand being
  broken in this version. All three would have been discovered by the user
  instead, on their first real `docker compose up`, if the plan had merely
  described the design without anyone actually running it.
- **Splitting `Sandbox` (passive handle) from `SandboxManager` (active,
  confirmable lifecycle operations)**, arrived at through the plan
  conversation rather than the initial draft, made the Drop-vs-explicit-
  delete distinction fall out naturally instead of needing an `Option`
  disarm dance on `Sandbox` itself.

**What caused friction, surprise, or rework:**
- **A default `DeleteParams` grace period silently broke two different
  tests' assumptions** — `sleep infinity` doesn't trap `SIGTERM`, so a pod
  deleted with Kubernetes' default (commonly 30s) grace period sits
  `Terminating` well past a short test timeout. Discovered by a genuinely
  confusing test failure (the Drop-path test timed out, but `kubectl get`
  showed the pod correctly `Terminating`, not stuck) rather than anything
  the plan anticipated. Fixed by a shared `immediate_delete_params()`
  (`grace_period_seconds: Some(0)`) used everywhere the module deletes a
  pod, including test cleanup.
- **This dev container's own nesting (docker-compose's `docker` DinD
  sidecar) meant `docker compose` itself isn't installed here**, so the
  actual `docker-compose.yml` changes could be proofread and individually
  spiked (via direct `docker run`/`docker network create` against
  `DOCKER_HOST`) but not run end-to-end from inside the session. **Closed**:
  the user ran `docker compose up -d k3s k3s-bootstrap` then `docker
  compose up -d` (recreating `smelt` itself) for real from their host —
  `smelt`'s `KUBECONFIG` came up pointing at a real, bootstrap-generated
  `/etc/smelt/k3s/park-kubeconfig.yaml` with `server: https://k3s:6443`
  exactly as designed, and the full test suite (94 tests, including all 5
  sandbox tests) passed against it with no changes needed.
- **`kube`'s rustls-tls stack needing an explicit crypto provider install**
  (`rustls::crypto::ring::default_provider().install_default()` in
  `main.rs`) was invisible until a standalone probe binary panicked on its
  first TLS connection — kube only auto-installs one when built with its
  `aws-lc-rs` feature, which conflicts with matching `reqwest`'s existing
  `ring`-based rustls-tls setup.

**What to change (proposals):**
- Consider adding `docker compose` (the CLI plugin, not just the `docker`
  binary) to the dev image — its absence is what forced every piece of
  this project's infrastructure to be validated by hand-replaying
  individual `docker run`/`docker network` commands instead of just
  running the actual compose file, which is real, avoidable friction for
  any future compose-file change.
