# Web fetch tools (webfetch, http_request)

**Branch:** `webfetch` · **Idea:** `projects/ideas/webfetch.md` (removed) · **Plan:** `projects/plans/webfetch.md` (removed)

## What shipped

Two native tools for two different jobs, sharing one SSRF guard.

### `webfetch`

One new native tool, `webfetch(url)`, that navigates a real headless
browser (`chromiumoxide`/`chrome-headless-shell` over CDP — the same
dependency `src/browser_tests.rs` already used for its own test tier, now
also a genuine runtime dependency of the app itself) to a URL and returns
its rendered, readable text (`document.body.innerText`) — independent of
whatever's reachable from inside the model's sandbox pod, and unlike a
plain HTTP GET, works on JS-rendered pages since the page is actually
executed, not just downloaded.

- Runs from smelt's own server process, not the sandbox pod — no
  dependency on a live pod existing, since this is a general lookup tool,
  not a sandbox-specific one.
- A process-global, lazily-launched shared browser
  (`tokio::sync::OnceCell<Browser>`), launched on first `webfetch` call —
  a server that never uses it never pays for a running Chrome process.
- Every request the page makes — the top-level navigation, any redirect,
  subresources, JS-initiated `fetch()`/`XHR` calls — is checked against an
  SSRF guard (`is_safe_fetch_addr`: refuses loopback/link-local/private
  (RFC 1918)/unspecified/multicast addresses, checked against the actual
  resolved `IpAddr`, not the hostname string) via the CDP Fetch domain's
  request-interception mechanism, not just the URL the model asked for —
  necessary specifically because a real, JS-executing browser can issue
  requests a plain HTTP client never would.
- `websearch` (the idea's other half) was split into its own idea
  (`docs/projects/ideas/websearch.md`) rather than scoped into this plan —
  it needs a paid third-party search API and a provider choice only the
  user can make, a meaningfully different dependency than "fetch a URL,"
  which needs nothing new.

### `http_request`

Added after the user pointed out that a full headless browser is real
overkill for hitting a JSON API or a static endpoint — slower, and
`innerText` extraction is a poor fit for JSON. `http_request(url, method?,
headers?, body?)` is a plain HTTP client (`reqwest`, no browser, no JS) for
exactly that case, much cheaper than `webfetch` whenever real page
rendering isn't needed.

- Reuses the *exact same* SSRF guard as `webfetch` — extracted into a new
  shared module, `src/fetch_guard.rs` (`is_safe_fetch_addr`,
  `parse_fetch_target`, `is_request_allowed_with`, `truncate`), so SSRF
  logic has one source of truth rather than two copies that could drift
  apart. `webfetch.rs` was updated to use the same shared module.
- `reqwest`'s own automatic redirect-following is disabled; redirects are
  followed manually, one hop at a time, re-checking each target against
  the SSRF guard — unlike `webfetch`, there's no CDP interception layer to
  lean on here (a plain HTTP client never executes page JS), so the guard
  has to sit at the redirect-loop level instead.
- A non-2xx status (404, 500, ...) is returned as normal data, not a tool
  error — that's real information the model should see, the same way
  `curl` itself doesn't fail on a 404.
- Needs no `chrome-headless-shell`, no browser lifecycle, no
  `browser-test` feature — its tests are plain, always-on `#[tokio::test]`s
  against a local fixture server, same as most of this codebase's other
  async tests.
- Interactive/multi-step browsing (visiting a page, clicking links,
  navigating a session across several tool calls) was explicitly scoped
  out of both tools — a meaningfully bigger addition (a stateful browsing
  session, not "fetch once and return") — and left for a future idea.

**Verification:** 285 `cargo test --features server` tests passing (up
from 257 before this project started), both build targets clean, and two
real end-to-end passes against real `chrome-headless-shell`
(`browser_tests::test_end_to_end_browser_scenarios` and
`webfetch::browser_tests::test_fetch_scenarios`, run together via `cargo
test --features "server browser-test" -- --ignored --test-threads=1`) — a
real page's rendered text comes back correctly, navigating straight to a
loopback address is refused, and a page-initiated JS `fetch()` to a
private address gets blocked (the case a plain top-level-URL check
couldn't have caught). `http_request`'s own 11 tests (redirect-target
resolution, method parsing, a real local-server round trip, redirect
following with the SSRF guard re-checked at each hop, a non-2xx response
returned as data) all run in the default, always-on tier — no real
browser needed for any of them.

## Retrospective

**What worked:**
- **Extracting the SSRF guard into `fetch_guard.rs` paid off immediately
  for the second tool.** `http_request` needed the exact same
  loopback/private/link-local check, the exact same "test needs a relaxed
  predicate since every locally-reachable address in this dev container is
  unsafe by the real rule" seam, and the exact same truncation shape —
  all reused verbatim rather than re-derived or copy-pasted. The one
  genuinely new piece (manual redirect-following, since a plain HTTP
  client has no CDP interception layer to check each hop through) went
  smoothly and all 11 of its tests passed on the first real run — no
  browser needed for any of them, so they're plain always-on
  `#[tokio::test]`s rather than another `#[ignore]`d, `browser-test`-gated
  tier.
- **The user's own suggestion to research first** ("look online for a
  tool/crate that can be used like a browser for AI") surfaced that
  `chromiumoxide` — already vendored in this exact codebase for
  `src/browser_tests.rs`'s own test tier — was a strictly better fit than
  the plan's original `reqwest`+`html2text` design: real page rendering
  (the actual thing being asked for), no new external dependency, and no
  third-party data flow (unlike a hosted alternative like Jina AI Reader,
  which would mean sending every looked-up URL through someone else's
  infrastructure).
- **Verifying the CDP Fetch domain's types against the vendored
  `chromiumoxide_cdp` source before committing to the interception
  design** (confirmed `fetch::EnableParams`/`EventRequestPaused`/
  `ContinueRequestParams`/`FailRequestParams` all exist, with the right
  shapes) meant the plan's most novel piece was de-risked before writing
  any code, not discovered to be infeasible partway through.
- **A dependency-injection seam for the SSRF predicate**
  (`fetch_with_guard`/`is_request_allowed_with`, parameterized on
  `fn(IpAddr) -> bool`) made the guard's actual blocking behavior
  testable in a dev container where *every* locally-reachable address is
  either loopback or RFC1918-private — without ever weakening the real
  production `fetch`'s default guard, which always uses the strict
  `is_safe_fetch_addr`.
- **Splitting pure logic from the browser glue** kept the SSRF-relevant
  logic (`is_safe_fetch_addr`, `parse_fetch_target`,
  `is_request_allowed_with`, `truncate_text`) strict-TDD-able — 17 unit
  tests, no real browser needed — while the browser-driving glue itself
  followed a spike-first approach (per `development-process.md`'s "spike
  the riskiest assumption first" rule), proven against a real
  `chrome-headless-shell` before being considered done.

**What caused friction, surprise, or rework:**
- **A redundant `wait_for_navigation()` call caused an indefinite hang.**
  `chromiumoxide::Page::goto`'s own doc comment says it "resolves directly
  after the requested URL is fully loaded" — an extra
  `wait_for_navigation()` call after it waits for a *second* navigation
  event that never comes, hanging forever. Found only by actually running
  it against a real browser, not by reading the method signature alone;
  the doc comment that would have caught it was right there, one line
  away from the code that ignored it.
- **Chrome's own stdout inheritance made a genuinely-finished test look
  hung.** `chromiumoxide` only pipes the spawned `chrome-headless-shell`
  process's stderr, not stdout — so a long-lived shared browser (by
  design, reused across calls) keeps holding a shell pipeline's stdout
  pipe open indefinitely, even after the actual Rust test process has
  cleanly exited, if that pipeline includes something like `| tail` that
  waits for real EOF. Cost real debugging time chasing "is my code
  actually hung" before the real cause (a shell-pipeline artifact, not a
  code bug) became clear; the practical fix was procedural — redirect
  test output to a real file instead of piping through another command.
- **Hit the exact `OnceLock`/`OnceCell`-across-separate-runtimes hazard
  `testing.md` already documents for `PgPool` — for a second resource
  type.** Each `#[tokio::test]` fn gets its own independent tokio runtime;
  the shared browser's background handler task is tied to whichever
  runtime first launched it, so a later test reusing the same static from
  a *different* runtime fails once the first test's runtime tears down
  ("send failed because receiver is gone"). The first draft split the
  browser tests into three separate `#[tokio::test]` fns before hitting
  this; fixed by consolidating into one, mirroring `browser_tests.rs`'s
  own already-documented reasoning for the identical hazard — should have
  been recognized from that existing doc before writing three separate
  tests, not after.
- **A missing `#[ignore]` attribute silently dropped the new test from a
  "full tier" verification run.** `cargo test ... -- --ignored` only runs
  tests marked `#[ignore]`; the new `test_fetch_scenarios` wasn't marked,
  so a first "run the whole tier" pass reported success while having
  silently skipped it entirely — caught only by checking the actual test
  *names* in the output, not just the exit code.

**What to change:**
- **Confirmed and applied**: extended `testing.md`'s existing
  `OnceLock`/`OnceCell`-across-separate-runtimes callout (previously
  written specifically about `PgPool`, now retitled and led with a general
  statement of the hazard) to name it as a general hazard for *any*
  process-global resource whose correctness depends on a background task
  that outlives a single `#[tokio::test]` function —
  `chromiumoxide::Browser` is a second concrete instance now, named
  alongside `PgPool` with a pointer to check for this before adding a
  third.
- **Confirmed and applied**: added a `testing.md` note that piping
  `cargo test`'s output through another command (`| tail`, `| grep`, ...)
  can make a genuinely-finished test run look hung if anything the test
  spawned (a long-lived subprocess like a shared browser) inherits and
  holds the same stdout pipe open — redirect to a real file instead when a
  test launches a long-lived child process. Not unique to
  `chrome-headless-shell`; written generally.
