# OAuth authentication for MCP servers

**Branch:** `mcp-oauth` · **Plan:** `projects/plans/mcp-oauth.md` (removed)

From `projects/ideas/mcp-oauth.md`: extends `/mcp-servers`
(`docs/projects/completed/20260817-mcp-servers.md`) with a second auth mode
alongside static headers — the user clicks Connect, approves smelt at the
MCP server's own OAuth provider, and lands back on smelt already connected,
with an expired access token refreshing itself automatically. The user
picked GitHub's hosted MCP server as the live verification target ("github's
mcp is advertised as having oath, so we can use that").

## What shipped

- **`rmcp`'s `auth` feature** (`rmcp::transport::auth`) does essentially all
  of the OAuth/PKCE mechanics — RFC 9728/8414 discovery, dynamic client
  registration, PKCE, token exchange, refresh — so this project is almost
  entirely wiring, not a from-scratch OAuth client. The de-risking discovery
  that this existed (found by reading `rmcp`'s own source, not assumed) is
  what made the rest of the plan tractable in one pass.
- **`mcp_servers`** gained `auth_mode` (`static_headers`/`oauth`,
  DB-`CHECK`-enforced), `oauth_credentials` (a JSONB blob storing `rmcp`'s
  own `StoredCredentials` serialized as-is — no hand-modeled token schema),
  and `oauth_client_id`/`oauth_client_secret` (added mid-project — see
  below).
- **`src/mcp_oauth.rs`** (new, server-only) — `PgCredentialStore` (a
  `CredentialStore` impl persisting tokens to Postgres so they survive a
  smelt restart, unlike `rmcp`'s in-memory default), a `PENDING` registry
  holding one in-flight `OAuthState::Session` per server between "Connect"
  and the callback, `start`/`handle_callback`/`disconnect`, and the plain
  Axum `callback_handler` (`/oauth/mcp-callback/{id}`) — deliberately *not*
  a Dioxus server function, since it's hit by a real browser redirect from
  the OAuth provider and must respond with an HTTP redirect, not JSON.
- **`src/mcp.rs`'s `connect()`** gained an OAuth branch: fetch a fresh
  access token (auto-refreshing via the stored refresh token, persisting
  the refresh) and feed it into the *existing* `Authorization: Bearer`
  header path static-header mode already used, rather than wiring `rmcp`'s
  `AuthClient`/`AuthorizedHttpClient` into the transport's HTTP client
  directly — lower risk, reuses already-proven code.
- **`connect`/`ensure_connected`/`tool_definitions_for`/`connection_check`/
  `call_tool`/`PgCredentialStore`** all take their Postgres pool as an
  explicit parameter rather than reaching for `db::get()` internally — the
  same testable-all-the-way-down convention the rest of the codebase
  already follows, needed so `PgCredentialStore` could be pointed at a
  `#[sqlx::test]` throwaway database instead of the real one.
- **`/mcp-servers` UI**: an auth-mode radio on the new-server form (static
  headers / OAuth, static headers remains the default); in OAuth mode, an
  optional pre-registered client ID/secret pair (see below) and, on the
  edit page, a connection panel (Connect/Reconnect/Disconnect,
  `NotConnected`/`Connected`/`Unreachable` status) replacing the header
  editor. `auth_mode` and the pre-registered client fields are fixed once a
  server is created — no in-place mode switch, matching the "delete and
  recreate to change" escape hatch already used elsewhere in this UI.
- **The redirect_uri's base URL is derived from the incoming request's
  `Host` header** (`X-Forwarded-Proto` deciding scheme, defaulting to
  `http`) by default — the user's initial choice over adding a new env var.
  A real deployment surfaced the need for an override after all (a
  proxy/tunnel whose forwarded `Host` isn't one a browser/OAuth provider
  could reach), so `SMELT_BASE_URL` was added as a follow-up, same
  set-but-empty-is-unset rule every other env var here follows — set, it
  wins outright; unset, the `Host`-derived guess is unchanged. See
  [setup.md](../../setup.md).
- **Tests**: a hand-built mock OAuth authorization server (axum, real HTTP,
  implementing just `/register` and `/token` — no `/.well-known/...`, since
  omitting it exercises `rmcp`'s legacy-endpoint fallback for free) drives
  `start` → `handle_callback` → a fresh `AuthorizationManager` end-to-end,
  including a deterministic refresh (the mock's initial token response sets
  `expires_in: 0` so the very next `get_access_token()` call is forced
  through the refresh path, no sleep needed). 205 tests total, both build
  targets clean.

## A real gap found only by live-clicking Connect against GitHub

The plan's live-verification target (GitHub's hosted MCP server) doesn't
just lack OAuth discovery metadata — `https://api.githubcopilot.com/.well-known/oauth-protected-resource`
and `https://github.com/.well-known/oauth-authorization-server` both 404 —
it also **rejects Dynamic Client Registration outright**. The first live
Connect attempt (dynamic-registration-only, as originally planned) failed
end-to-end with a real, correctly-surfaced error: *"Registration failed:
Dynamic client registration not supported."* This wasn't something source-
reading `rmcp` could have caught — it's a fact about GitHub's own OAuth
implementation (a legacy, pre-DCR provider requiring an OAuth App
registered by hand), not a bug in the discovery logic, which correctly fell
back to synthesized legacy endpoints and then correctly got rejected at
`/register`.

Flagged to the user mid-implementation rather than silently worked around;
the user chose to extend scope immediately rather than defer. Added
`oauth_client_id`/`oauth_client_secret` (the latter write-only, same
precedent as header values) to `mcp_servers`, exposed as optional fields on
the new-server form, and wired into `AuthorizationRequest::with_preregistered_client`/`with_client_secret`
— `rmcp`'s own priority order already prefers a pre-registered client over
DCR whenever one is present, so this was a small, targeted addition, not a
redesign.

Re-verified live with a placeholder client ID: Connect now produces a real,
correct `https://github.com/login/oauth/authorize` URL — GitHub's actual
login/consent redirect, carrying the pre-registered `client_id`, a real
PKCE `code_challenge`/`code_challenge_method=S256`, `state`, and an RFC
8707 `resource` parameter identifying the MCP server. This is as far as
live verification could go without a real GitHub account: completing the
actual consent screen needs a real, user-owned GitHub OAuth App and a real
login, which the agent has no way to do on the user's behalf. **The final
consent → callback → persisted-token step is unverified against the real
GitHub flow** — everything up to and including building the correct
authorization URL is proven; the token exchange this triggers is proven
separately, against the mock server, but not chained to a real GitHub
`code`. The user should do one real Connect click themselves (with a real
GitHub OAuth App's client ID/secret) before relying on this for a
GitHub-backed conversation.

## Retrospective

**What worked:**
- Reading `rmcp`'s `auth` module source before planning (not just its
  Cargo feature list) found a fully-built OAuth client already sitting in
  an existing dependency, changing the whole shape of the plan from
  "implement OAuth" to "wire up rmcp's OAuth." Worth doing this kind of
  source dive *before* committing to a plan whenever a "build vs. use
  what's already there" question is even plausible.
- Threading `pool: &PgPool` through `mcp.rs`'s previously pool-free
  functions, rather than reaching for the global `db::get()` from the new
  `PgCredentialStore`, cost a mechanical refactor but paid for itself
  immediately — the resulting mock-server test suite needed no special
  scaffolding to point at a `#[sqlx::test]` throwaway database.
- The mock OAuth authorization server ended up smaller than expected:
  omitting `/.well-known/...` entirely (rather than implementing it) was
  the right call, since it exercises `rmcp`'s real legacy-fallback code
  path instead of a path this project would otherwise never test.
- Live browser verification against GitHub's real MCP server caught the
  DCR gap that no amount of source-reading or mock-server testing would
  have — the mock server, built to be "reasonably complete," implemented
  exactly the endpoints a compliant server would have, which is precisely
  what let it miss the one specific way GitHub is *non*-compliant.

**What caused friction, surprise, or rework:**
- The original plan (per `rmcp`'s general MCP-spec-first design) assumed
  DCR-or-bust would cover "some MCP servers need OAuth" broadly enough for
  a first pass, with GitHub as the live-verification target already
  believed to be a real, working example. It wasn't — the one server this
  project had lined up to prove the design against needed the one thing
  the design didn't yet support. `dx serve`'s dev-mode hot-reload also
  turned out to rebind the actual listening port away from the one passed
  on its own command line (`--port 8080`) at least once during this
  session — the redirect_uri captured in the live-verification screenshot
  shows `0.0.0.0:33471`, not `8080`, a dev-environment artifact rather than
  an application bug, but worth knowing about if a future live check looks
  like the wrong host got used.

**What to change:**
- None proposed to `development-process.md` this time — the existing
  "flag before silently expanding scope" rule is what correctly triggered
  a stop-and-ask when the DCR gap surfaced, and it worked as intended.
