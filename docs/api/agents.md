# Child agents

Part of [api.md](../api.md). How a conversation's model starts agents, hears from them, writes to them and stops them (SME-236, SME-238). The design is [docs/design/personas/agents.md](../design/personas/agents.md); the code is `src/agents/` (the lifecycle), `src/anthropic/tools/agents.rs` (the tools), `src/db/agents/` (the rows) and `src/git/server/child_ref.rs` (the child's checkout).

A child agent is a whole conversation with a `parent_id`: its own transcript, model, streaming, Stop, usage and sandbox, which the user can open and write in. Its lifecycle is `agents.state`: `starting`, `active`, `finished`, `stopped` or `failed` (see [database.md](../database.md)).

## The tools

Six tools, at the end of the registry so every older tool keeps its place in the request. A tool's `Offer` says who is given it — every conversation, every conversation but callable only by one with a parent or agents of its own, or only an agent (`Offer::All` / `Linked` / `Child`) — `tool_definitions(pool, conversation_id)` leaves the others out and `execute` checks them again from the database, so a call from an older history is refused too. On top of that, since SME-241 the conversation's stored **rule chain** speaks at both places: it filters the offered list and refuses a call as a tool error naming the rule ([Tool rules](#tool-rules)).

| Tool | Offered to | What it does |
| -- | -- | -- |
| `start_agent(brief, repo?, ref?, persona?, volumes?)` | every conversation (`Offer::All` since SME-241; a rule chain whose ceiling excludes `writing` hides it and refuses the call), and `execute` refuses one whose depth has run out | Records the child (`starting`) with its depth, group root and rule chain, its brief as its first message, with `repo` its copy of that checkout as `cloning` and with `volumes` its mount rows for the volumes it names (SME-239), in one transaction; spawns its start and returns the child's id at once. |
| `list_agents()` | every conversation | Its own children only, newest first: id, title, persona (`<dir>:<name>`), status, when it started, its last message, how many agents it started. Status is the first that holds of `starting`, `failed`, `stopped`, `running` (a turn in flight), `waiting for the user` (an unanswered `ask_user` question or an AGENTS.md card), `waiting for its parent` (an unanswered `ask_parent`, SME-238), `finished`, `idle`. |
| `stop_agent(id)` | every conversation | One of its own children and its whole subtree set `stopped` (state first), then each one's turns stopped (`turn::stop_conversation`). Pods and terminals are left alone. Any other id is refused. |
| `finish(report)` | an agent | The child `finished` and its report queued to its parent in one transaction, then the parent woken. A successful `finish` ends the child's turn as `ask_user` does (`run_tools`), and that turn's end stops the child's sandbox pod (SME-78, below). A second one is refused, and so is one while a message to the child is unread or an answer to its question untaken (SME-238): it reads that first. |
| `message_agent(to, text)` | every conversation (`Offer::Linked`, so the tool list doesn't change when a conversation starts its first agent), but `execute` refuses one with neither a parent nor agents of its own | SME-238: `text` (1–30,000 characters) queued to the caller's parent (`to: "parent"`) or one of its own children (its id), and the recipient woken. See [Messages and questions](#messages-and-questions). |
| `ask_parent(question)` | an agent | SME-238: handled by `run_tools` with `ask_user` (one question of either kind per reply); the question recorded and queued to the parent, and the child's turn ends waiting. |

**`start_agent`'s checks**, all before anything is written: `brief` 1–30,000 characters; `repo` a `/workspace/<dir>` that is one of the caller's `ready` checkouts; `ref` a plain ref (`git::validate_ref`: no whitespace or control characters, no `..` or `@{`, not starting with `-`, not ending in `/` or `.lock`); `persona` a valid persona name, needing `repo`. Without `ref`, the parent's checkout must be on a commit its upstream has (after a `git fetch` in the parent's pod), the upstream a branch on `origin`, with no uncommitted changes to tracked files (`git::parent_commit`; a detached HEAD, no upstream or one that isn't on origin, unpushed commits or a dirty tree is refused, saying what to do; the commit and branch it reports are checked as a commit id and a plain ref), and the persona must be in it now. In the transaction: the remote's trust lock, then the caller's row `FOR NO KEY UPDATE`; the caller must exist, not be `deleting_at`, not be a `stopped` agent, and — SME-241 — be shallower than `SMELT_AGENT_DEPTH` (`agents::agent_depth`, read once per call in the `sandbox::idle_notice` pattern: unparseable warns and takes the default 5, and `db::NewChild.max_depth` carries it in so the db tests set it directly, never through the environment): an agent at that depth is refused "start_agent can't go deeper than N levels of agents (you're at depth D)". A caller with a `parent_id` but no `agents` row — never a conversation smelt started, only a test artifact — is refused too, its depth and chain unknown. The depth check is at the call, not the offer: an agent at the limit is still *offered* `start_agent`, so the offered set stays a function of the rules alone. The remote must be trusted (`repo_trust.trusted`): undecided also records the repo's own trust card first — an `instruction_requests` row at the sentinel path `''`, one per checkout row — committed with the refusal, whose copy says a card is asking the user in this conversation, and the tool then publishes the conversation's repos so the card reaches open tabs (SME-279); declined is refused without a card. The child's row is then written with `depth` = the caller's + 1 (1 for a conversation with no `agents` row), `root_id` = the caller's group root (the caller itself at the top), and `rule_chain` = the caller's chain ([Tool rules](#tool-rules)); SME-239 adds its volume mounts to the same transaction: `volumes`'s names, deduplicated, are looked up over the caller's `conversation_volume_mounts` with the `agent_volumes` rows taken `FOR SHARE` — the pair to `delete_volume`'s `FOR UPDATE`, so a pass and a delete exclude each other and one of the two refuses — and a name the caller doesn't hold is refused ("you don't hold a volume named …: `create_volume` makes one, and you can pass only volumes you hold").

## Tool rules

SME-241. What an agent may be offered and call is decided by its **rule chain**: the JSONB array on its `agents` row (`rule_chain`), the parent's chain followed by its own persona's `smelt.tools` entry — a class ceiling plus allow/deny patterns over smelt tool names and `<server>/<tool>` MCP names, the grammar being `personas::rules::check` (every error names the persona file) and the semantics [design/personas/tool-rules.md](../design/personas/tool-rules.md#the-grammar). Evaluation is a conjunction over entries (`RuleChain::allows_at`): the most specific matching pattern decides, deny wins a tie at that level, nothing matching leaves the class against the ceiling, and no entry can be undercut by a later one — so a child is never wider than any ancestor. A conversation with no `agents` row (the user's own) has no entries: everything, as before.

The chain is read by `db::agent_rule_chain` (one indexed query) in the two places it matters, per model call and per tool call: `tool_definitions` filters the registry by `is_offered(offer, has_parent) && chain.allows_any(name, tool.class.can_be())` and hands the chain to `mcp::tool_definitions_for`, which keeps one of a server's tools only when the chain allows it at the class that server's call would be judged by — the user's saved override if any, else the annotations of the connection it lists (`mcp::tools::judged_class`, the same function the call path uses, so a tool is offered under exactly the class it is ruled at). `execute_uncapped` asks the same chain for a native call's class and refuses it before `run`, and for an MCP call the chain travels in as `call_tool_classed`'s `check_class`, consulted after the override read and the listed class and **before** `service.call_tool` is sent, so a refused MCP call never reaches the server and its span records the class and is marked failed with the rule's text. A refusal is a tool error naming the rule, in one of these two shapes:

```text
github/merge_pull_request is denied by this conversation's tool rules (deny pattern `github/*`)
start_agent is denied by this conversation's tool rules (class ceiling read-only doesn't allow a writing tool)
```

The context detail view shows the same filtered list (`api/chat.rs`'s call needs no change). `http_request` is the one native tool with more than one class, so a `read-only` ceiling is offered it and refuses its `POST`; a method-override header naming a method raises its class (never lowers it), which is what makes a `POST` with `X-HTTP-Method-Override: DELETE` a destructive call.

The chain is written twice and never again: `create_child` copies the parent's, and `complete_start` appends the persona's entry, read from the snapshot the start took, not from the file. A later persona edit, a server rename or a stop changes nothing for a live agent, which is also what keeps its offered list — and its cached prompt — stable within a conversation. An absent row, NULL, or JSON that won't parse falls open with a warning, identically in the offer and the call: the column is smelt-written by typed serde, and failing closed would strand every tool in the conversation on a bad row.

Two reports say when rules name nothing. `ToolRules::unmatched_servers` lists patterns whose server isn't configured — a renamed server's leftovers, which fall to the class ceiling rather than widening — and `unmatched_note` puts it in one sentence: in `list_personas`' `rules` field, and in `start_agent`'s notice to the parent at the child's done step. And `mcp::check_server_name` refuses `/` and `*` in a new MCP server name (a pattern's server part is exact), while a server named that way before is reported with `McpServerSummary::name_unrulable` and a line on its edit page; its tools can be ruled on only by class. See [mcp.md](../mcp.md#tool-classes).

## The start

A spawned task (`agents::run_start`) per child, holding `StartExit`, whose cleanup runs on every way out (done, failed, stopped, deleted, the task dropped): it runs the credentials exit SME-242 fills and, unless the start is done, deletes any AGENTS.md trust card in the child (a done start's load made none, and its first turn may already have asked about another file). With a repo, its pod work goes through `ChildCheckout` (`PodCheckout` in production; tests register a fake per parent):

1. **Clone** (`git::clone_child_repo`): the default branch into the child's pod, then `checkout_ref`: a branch is checked out tracking the remote's, a tag or a commit id detached, a commit no ref reaches fetched by id; without a `ref`, the parent's commit on a branch named as its upstream.
2. **Trust again**, under the trust lock: a remote forgotten while it cloned fails the start.
3. **AGENTS.md**: the checkout's top-level one is loaded (`request_or_load`); a card instead (the remote forgotten since step 2) fails the start.
4. **Persona**: `.agents/personas/<name>.md` read in the child's checkout (symlink-safe), parsed, its relative links made absolute (`personas::links::absolute`), and kept as a snapshot. Its `smelt.tools`, if it has any, are checked against the grammar during this step (`persona::snapshot`), so a bad rule fails the start with the persona file named.
5. **Model**: the persona's `smelt.model` on the first provider that has it (the parent's, the default's, then by name); none has it, the child keeps its parent's model and the parent is told.
6. **Done** (`db::complete_start`): `active`, `started_at`, the snapshot and the model, the persona's rules appended to the child's `rule_chain` ([Tool rules](#tool-rules)), and a notice to the child itself, which its first turn drains; then `Notice::Wake`. The parent's own notice, when it has anything to say, is one message covering both the persona's model not being found and its rules naming no configured MCP server. A child no longer `starting` (stopped or deleted meanwhile) is left alone, chain included.

A step that fails ends the start through `fail_start`: the child `failed`, the error queued to the parent as its report and saved in the child's own transcript. Nothing makes a failed child `active` again.

No turn runs in a child while it's `starting`: the user's send or answer is refused ("This agent is still starting."), a wake is a no-op and a delivered notice is only saved (`admits_notices`). A `stopped` or `failed` child is treated the same way for wakes and notices, so it stays quiet even after a restart loses the Stop's pause (review 1). The user's send or answer in a `finished` or `stopped` child that had started makes it `active` (`admit_user_turn`); one in a `failed` child, or one stopped during its start, is refused (an answer before it's recorded). Once the turn is counted the state is read again (`confirm_user_turn`), so a parent's `stop_agent` landing in between refuses the send; and a user's turn that queued behind a turn which called `finish` makes the child `active` again once it holds the turn lock (`resume_finished`), so it can report again.

## The queue

Reports and notices reach a conversation through `agent_messages`, never `Notice::Deliver`: `drain_agent_messages` runs beside the two command drains at every iteration of `run_turn_steps`, so a busy parent takes a report between a tool result and its next call, and several arrive in one model call, in the order they were queued. Each row is saved as one `user` message (`Report from agent #12 (smelt:developer):` + the report, `Message from agent #12 (smelt:developer):` or `Message from your parent:` + a message, `Question from agent #12 (…), which waits for your answer (reply with message_agent to 12):` + a question, or `Notice: …`) and marked delivered in one transaction (`db::deliver_agent_message`). `db::wake_has_work` counts undelivered rows. Every writer queues in the transaction of the state change it reports, then wakes the recipient (`Notice::Wake`):

- `finish` (report), a failed start (report), the start's done step (a notice to the child itself; and to the parent when the persona's model wasn't found);
- the user's Stop on an `active` child not already paused (`agents::user_stop`, a notice to its parent); a Stop on a `starting` child is refused;
- a child's last turn ending while it's `active` with nothing to wait on (no unanswered question, card, running command or live agent of its own) and not paused (`agents::after_last_turn`, a notice with the first 500 characters of its last reply, and the failure when the turn failed); not after a stop, nor a wake that did nothing;
- deleting a child (a notice to its parent, in the delete's own transaction);
- `message_agent` and `ask_parent` (SME-238, below).

**At startup** (`agents::startup_sweep`, after the clones a restart cut off are failed): every child still `starting` fails with "smelt restarted during the start", every agent `active` and not paused whose last message is a turn's with no reply after it (a tool result, a row the queue delivered, or the model's tool call whose tool was still running; not a notice saved while it was idle, nor the user's own message) and which isn't waiting on a question is queued `smelt restarted during your turn; carry on` (once, however many restarts), and every conversation with undelivered rows, or an agent with an answer it hasn't taken, that isn't a `stopped` agent nor paused is woken. The pause after a Stop is stored (`conversations.paused_at`, SME-238) and restored by `turn::restore_pauses` in `main` before the pod watch, the idle-command watch and this sweep start, so a conversation the user stopped stays quiet across a restart.

## Messages and questions

SME-238. **`message_agent`** resolves `to` (`parent`, or an id that must be one of the caller's children; anyone else is refused as `stop_agent` refuses one, without saying whether it exists), then in one transaction (`db::message_agent`): both `conversations` rows `KEY SHARE` in ascending id; the recipient's `agents` row `FOR NO KEY UPDATE` (a root parent has none), so a `stop_agent`, a `finish` or a delete's marking lands wholly before it or waits; refused if the recipient is `deleting_at`, `stopped` or `failed`; a `finished` child made `active`; then, for a child waiting on its parent whose question the parent has read (its `question` row, which shares the question's `created_at`, is delivered), the reply is written as the question's answer (`UPDATE … WHERE asked_of = 'parent' AND answer IS NULL`) and nothing is queued; else a `message` row is, so a message the parent sent before reading the question isn't taken as the answer (review 1). After the commit the recipient is woken: an idle one runs a turn, a busy one reads it at its next step, a paused one (the user's Stop) waits for the user, and a `starting` one reads it in its first turn. A message to a child that was `finished` is read by the woken child, which can `finish` again.

**`ask_parent`** (`db::ask_parent`): the child's `agents` row `FOR SHARE` must be `active`, and the parent neither being deleted nor a `stopped` or `failed` agent; then a `pending_questions` row `asked_of = 'parent'` (header "Question for your parent") and a `question` row to the parent, in one transaction, and the parent woken. No question card or sidebar mark appears. The child's woken turn takes the answer through `take_answer_or_wait`, and the call's result is `Your parent answered:` + the reply. If the user writes in the child first, their message takes the question with `questions::NOT_ANSWERED_BY_PARENT`, and the parent's later reply arrives as a plain message; the parent isn't told the user stepped in. A child waiting on its parent gets no "ended without a report" notice.

## Deleting

`delete_conversation` deletes the whole subtree (`agents::delete_subtree`): transaction A locks the group root's row (the lock `start_agent` takes) and marks the subtree `deleting_at` and its agents `stopped`, so a `start_agent` after it is refused; every turn and browsing session in the subtree is stopped and its pods listed; transaction B locks the deleted conversation's parent (shared) and the subtree (for update) in ascending id, queues the notice to the parent, and deletes, the cascade removing the subtree; then each conversation's pods are torn down and its turn state and event channel forgotten. The sidebar's armed Delete says how many agents go with it ("Delete + 2 agents?").

**A finished child's pod (SME-78).** When a turn ends with the child `finished`, `after_last_turn` calls `sandbox::stop_finished_agent_pod`: no live pod (the seat ran `terminate_pod`) is a no-op; otherwise it waits for the child's turn lock and then its pod-start lock, re-checks in one statement (live, still `finished`, no repo cloning, no command running) and stops the pod quietly with a saved notice. `/workspace`, Docker's data and mounted volumes are kept; no volume or mount row is touched. A command left running keeps the pod, and the idle pass's backstop stops it within a minute of the command ending. A `message_agent` racing the stop is decided by the turn lock: one that made the child `active` before the re-check keeps the pod; one after it finds the pod stopped, and the woken turn reads the notice, then the message, and starts a pod on the same claims if it needs one. A pod counts as a finished agent's only while nothing used it after the finish (review 1, A2). It must have been started at or before the finish, no command may have started in it since, and its last flushed note must be no later than the finish plus two passes (`FINISHED_GRACE_SECS`, which covers the finish turn's own note and one pass of flush lag). A pod the user started or used after the finish (Work on a repo, a preview) falls back to the idle rule, while a command left running that ends after the finish doesn't. A child stopped by `stop_agent`, or failed, keeps its pod until the idle stop.
