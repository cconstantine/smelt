# Scheduling and capacity

Part of [Setup & Running](../setup.md#deploying): where sandbox pods go on a cluster of several nodes, and what the memory they reserve costs (SME-484).

**Sandbox pods spread over the nodes** (SME-484). Every sandbox pod carries a soft `topologySpreadConstraint` over `kubernetes.io/hostname`: at most one more of this instance's sandbox pods on a node than on the emptiest, with `whenUnsatisfiable: ScheduleAnyway`, so it never keeps a pod from starting. Before it, every new pod went to the node that already held the multi-GB sandbox image. It counts only this instance's sandbox pods (its instance label, and the conversation label language-server pods don't carry); language-server pods still follow their sandbox's node. **A tainted node is left out of the spread:** the rule honours taints (`nodeTaintsPolicy: Honor`) and sandbox pods tolerate none, so a node tainted for other work (on homelab, ryzen runs the inference engine and needs the whole machine) is never a place to spread to, nor counted as an empty one. `SANDBOX_NODE_SELECTOR` narrows the nodes the same way. The rule shapes only where a conversation's *first* pod goes: its claims then pin every later pod to that node (see [Deploying](../setup.md#deploying)).

**Personas reserve memory, and an idle pod holds its reservation.** A persona's `smelt.resources` gives its pods requests ([persona-files.md](../design/personas/persona-files.md)); smelt's own ask for 12Gi of Docker memory for the personas that run the gate (developer, code-reviewer, integrator, planner, deployer) and 1Gi for the rest, plus a small request for the sandbox container (256Mi, the deployer's 1Gi). The scheduler places a pod only on a node whose allocatable memory, less the requests already placed there, holds the new pod's: requests count, not use. A pod keeps its request from its start until it stops, and an idle pod stops only after `SANDBOX_IDLE_STOP_MINUTES` (60 by default), so plan for every live seat, idle or not, holding its whole request: a 31 GiB node holds two gate seats, a 63 GiB one four (five 12.25 GiB pods would leave nothing for the node's other requests). Memory used outside the cluster's pods isn't counted, so a node whose other work leaves little free can still be offered a pod it can't really hold. A pod no node has room for stays Pending: its sandbox panel shows the scheduler's reason (`Unschedulable: 0/3 nodes are available: … Insufficient memory`) while it waits, and if the start times out (`SANDBOX_RUNNING_WAIT_TIMEOUT_SECS`), the model's error leads with it (`no node can take it now (the scheduler: …)`). A conversation pinned to a full node waits for room there.
