# Phase 1: Plan
Part of the [development process](../development-process.md).


**Do this before writing any code, any tests, or any files other than the plan itself.**

1. Read the user's request carefully
2. Read the ticket, and the **Current state** docs, to understand the request and the current codebase
3. Ask clarifying questions if the request is ambiguous — do not assume (a Planner writes them as the plan's open questions instead; see [Personas](../personas/README.md))
4. **If the work depends on an outside service or tool, check it before presenting options.** For each claim a choice rests on (whether it's still available, pricing and free tiers, what signup or access it needs, the API's request and response shape), check the provider's current docs and cite them. Don't answer from memory with a general "worth checking" caveat. Also look at how a comparable tool solves the same problem, in its source rather than its marketing. On `websearch`, provider answers from memory had three wrong or stale claims, and a three-provider plan was written on top of them. Reading opencode's source then showed Exa's keyless MCP endpoint, which cut the project to about 60 lines. **When the plan changes a value smelt sends to a provider** (a larger `max_tokens`, a new thinking setting), check each provider kind's limit on that field and every `stop_reason` the change can make reachable, and cite them in the plan. On SME-111 the plan let Other ask for up to half the window, though Claude, behind a gateway, refuses a `max_tokens` above its cap; and its cut-off notice covered only `max_tokens`, while bigger replies made Claude's `model_context_window_exceeded` reachable (round 1's medium finding). **A claim about what a tool does counts as one of these claims, even when the tool is local and free to probe.** A plan said dockerd's `--mtu` is the default for any bridge that doesn't set its own; it is the default for the *default bridge* only, and user-defined bridges — what a compose project makes — need `--default-network-opt` (SME-157). The plan was hours of work and the wrong claim sat in it unnoticed until a test measured it. **When a probe measures a pathological input** (deep nesting, a huge file, a long line), it also times the library call at each size it measures, not only the shape of its output: a fix that bounds the output can leave the call's own cost unbounded. On SME-174 the Planner's probe measured how deep syntect's scopes nest at each depth, but not how long its parse took; capping the spans fixed the crash, but the parse is roughly quadratic in depth (about 70 s at 32,000 levels in a debug wasm bundle), and the tests had to be scoped down to 8,000 mid-build. One timing line in the probe would have shown it at plan time.
5. Create a branch in a worktree of its own: `git branch <short-slug> main`, then `git worktree add ../smelt-<ticket> <short-slug>`, and work there (a Planner branches from a freshly fetched `origin/main` into `~/smelt-worktrees/smelt-<ticket>`; see [Personas](../personas/README.md)). Never `git checkout` in the main checkout: the user's dev server may be serving it. On SME-43 this step said `git checkout -b`, and following it switched the user's checkout. A new worktree needs no image build when the cluster already has the one named after its agent sources (`scripts/sandbox-image-ref`, SME-102); `scripts/cluster-doctor` says when it doesn't.
6. Write the plan into the ticket's description, under a `## Plan` heading after the idea's own text (create a ticket first if the work has none). The plan contains:
   - **Branch:** the branch name created in step 5
   - **What** is being built and why
   - **Which files** will be created or modified (be specific). When the change gives a function a new need (a database row, a config, a running server), find the tests that reach it by grep, `#[ignore]`d ones included, not by reading alone: on SME-167 the plan's list of tests that needed a server row, made by reading, missed the `#[ignore]`d live Exa test. When the change removes a crate's last use in a file, list that crate's `Cargo.toml` comment too if it names the file, and say that the edit renames the sandbox image (`Cargo.toml` is an agent source, see [rules-commits.md](rules-commits.md)), so the Developer batches it with any other agent-source edit. On SME-168 the callback's `?oauth_error=` encoding went, `Cargo.toml`'s comment on `percent-encoding` still named it, round 1 found it, and the one-line fix cost an image build before its gate. **Give each changed file's size** against the 40,000-byte ceiling ([rules-commits.md](rules-commits.md)), and plan a split first, as its own commit, for any file within about 2,000 bytes of it. On SME-179 `src/turn/run.rs` was 132 bytes under the ceiling after the planned changes, found only when round 1's fix crossed it, and a move commit and a history rewrite followed. **A plan that adds tests to a file already over the 30,000-byte aim, or that takes it there, moves the module's tests to `foo/tests.rs` as its first commit** (a move only, checked by a build of every target), rather than waiting for the ceiling to force it mid-review. On SME-182 `src/lsp/catalog.rs` was 23 KB with about 10 KB of tests planned; round 1's fifth fix crossed the ceiling, and the fix had to be set aside, the move made, and the fix reapplied.
   - **How** it will be implemented: data model, API shape, UI flow. For a split of a component, list each request (`spawn`) that moves and the condition its new component is shown under: a request in a component its own result hides is dropped (SME-57, see [frontend.md](../frontend.md#calling-server-functions))
   - **State model**, for a feature that keeps state (database rows with a status, files in the sandbox, decisions the user makes): each record's states, what moves it between them (the user, the model, a Stop, a restart, a retry, a timeout, another conversation), and who else sees each change (other conversations, other tabs, the pod). For state in the sandbox, say what survives a pod restart and what's lost. For each transition, also say what happens if the operation that makes it fails partway: a delete that errors after the mark is set, a send that fails after the event was taken. For a record that several callers write, also list every writer: each path that creates, retries or finishes it (a retry and a fresh request for the same thing, a failure path as well as success). Each listing or refresh path that writes the record is a writer of its own, even when two of them call the same function: on SME-111 the plan named the provider page's `/props` refresh as the writer of a model's reported window, and the picker's quick listing, which skips `/props`, wrote it too (round 2's medium finding). The races sit between writers. List every caller that reads shared state too (a remembered setting, a cached decision), and what each does with a value another caller just changed: on SME-93 all three review rounds found their bug at a reader of the remembered per-provider thinking choice, not at a writer. When the state is a credential bound to something (an address, a client, an instance), list every reader that hands the credential out, not only its writers, and say how each checks the binding: on SME-166 the plan listed the writers of an MCP server's grant and the readers of its URL, and round 2 found `PgCredentialStore::load` handing the grant to a connection manager built for the old URL. For each check a caller makes before acting on a record (is it waiting? is it answered?), also say what can change between the check and the act, and who can change it: on SME-34 a turn checked a pending question when it started and again only when calling the model, and an answer recorded in between was neither waiting nor taken (round 1's high finding). A tool's own scratch resources count as records here too (a helper pod, a lock file, a temporary name): on SME-102 both review rounds found the image import's loader pod, whose fixed name let one run delete another's mid-import, because the state model listed the images but not the tool's own pod. The tests then cover each transition, not just the happy path. On SME-32 none of this was written down: a re-clone step was built and then thrown away when the user asked why `/workspace` didn't outlive the pod, and ten code-review rounds found about 45 bugs, most of them transitions nobody had listed (retry, interrupt, trust given from another conversation), several made by the previous round's local fixes. On SME-53 the plan listed a torn-down mark's transitions but not a teardown that fails after setting it, and a failed pod delete left a live pod refusing every connect. On SME-86 the plan had a repo row's states but not its writers, and both review rounds found another writer racing the retry it fixed: a fresh clone into the same directory, and a failed attempt's error path. For a record keyed by an id that events arrive for (a stream's content blocks, a tool call, a pod), write the states and events as a small state × event table: every event in every state, including a repeat of the event that created the record (a second start for one still open). On SME-112 the plan listed a delta for a block already finished but not a start for a block still open, and round 2's finding sat in exactly that cell: llama.cpp's final chunk can resend a tool call's start, which split one call in two. When the plan adds a shared resource to prevent a race (one cache, one manager, one lock), it names the second user that makes the race possible: a test can only fail once that user exists, so the resource and that user land in one commit. On SME-113 one OAuth manager per server could only be tested together with the status check, its second user. For each skip or failure outcome in the table, also say what happens to the other records chosen together with that one: on SME-134 the plan had "a pod's delete is refused (409) → skipped", but not what then happens to the claims chosen because of that pod, and round 2 found them deleted from under the pod made again. When the change wraps another command (a lock, a timeout, a supervisor), the state model has a row per way the wrapper and its command can end: a signal to the wrapper alone, a signal to the process group, SIGKILL, a stopped command, a command reading the terminal, and what each does to the command's own children. On SME-100 the plan decided that the locked command wouldn't inherit the lock without listing these, and round 2 found three bugs in exactly those cells: a terminal read stopped the command while the holder spun holding the lock, `kill -9` of the holder left an orphaned test binary running with the lock free, and Ctrl-C no longer ended the calling script. **When the fix moves when a value is taken or cleared** (a generation, a kept error, a pause), the state model adds one table for that value: a row per kind of caller (on a turn: a message, an answer, a notice, a wake), a column per way the caller can end (stopped while queued, not found, failed before or after saving its input, nothing to do, done), and in each cell what the value is afterwards. On SME-179 the plan listed the turn generation's writers per field but not this table, and both review rounds found cells of it, each fix opening the next: an answer turn with nothing to do cleared the user's kept error, round 1's fix then made an answer turn failing before it saved the answer keep nothing, and round 1's delete guard was fooled by a fresh lock. **When the change moves several writes into one transaction,** the state model lists each writer's row locks and the order it takes them in, foreign-key cascades included: an `ON DELETE CASCADE` locks the child rows in physical order, not id or index order, and a row that's been rewritten (asked for again, loaded again) has moved. Prefer locking the parent rows up front, in a fixed order (by id), over matching the cascade's order table by table. On SME-181 the plan called a conversation delete "one statement (FK cascade)" and harmless because it took no lock, and both review rounds found a decision deadlocking against it: round 1's fix matched the cascade's order across tables, round 2 found the order within a table differs once a row has moved, and the fix was to share-lock every affected conversation's row first, in id order.
   - **Commits, when the plan splits one fix into tests for a new helper and for its caller:** say whether the helper has a non-test caller on its own. If it doesn't, the helper and its caller land in one commit, each test still seen red first: a helper with no caller warns as dead code in the server build, and `check.sh` fails on the warning. On SME-168 the plan's test order suggested a commit for the callback-error store and another for its wiring into the handler, and the store-only commit couldn't pass the gate.
   - **A prediction of what a red test will show is marked as one** ("expected: …"), never written as fact, and the Developer records the actual red output next to it. Tests assert the behaviour, not the prediction. On SME-169 the plan predicted two U+FFFD per split character; the real red had three, since `from_utf8_lossy` makes one for an incomplete lead sequence and one more for each stray continuation byte, so a test counting two would have failed for the wrong reason.
   - **Which part each test needs, when the fix has several parts:** for each test, the part of the fix it must fail without, and what it shows with only the other parts in. A test that is red on the unfixed code and green on the whole fix can still pass on a half-fix, and then says nothing about the part it was meant for. The Developer checks each claim against a build with that part stubbed out (see "Check that a fixture set bites" in [tdd.md](tdd.md)). On SME-172 the plan predicted only unfixed against fixed for a two-part fix (re-sync the open files; sync and ask again in a rename), and the B16 test's terminal change, an append, moved no position: it passed with the rename part stubbed out, and review round 1 found it.
   - **Where new UI goes,** for anything new on screen (a banner, a panel, a button): where it sits at a laptop width and at a phone width, and what it may cover. On SME-43 the plan placed a reload banner "at the top"; on a phone it covered the Conversations button, found only by a screenshot. A UI fix's plan also names each layout the fix depends on (laptop and phone widths, which side panels are open, where they sit) and what the fix does in each. On SME-75 the fix for text moving under the pointer had to hold with the side panels open and at phone width, which the plan hadn't listed. For each layout, also compute the narrowest width the new element gets, with every panel that can sit beside it, and test there with the widest content it can show. On SME-144 the checks used 900px with no todo list, where the terminal card is about 316px wide; at 721px beside a todo list it's 137px, and a `running` pill pushed the connection pill out of the card. Round 1's fix was then checked at 740px with the narrowest label (`lost`), and round 2 found 721–739px with the widest one still broken.
   - **Every source of error text, when the change sends it somewhere new** (a span, a shipped log, the UI): each source that reaches the new sink, and what each can quote (a URL with its query, a server's reply body, the tool's input). The tests put a marker into each source and assert it never reaches the sink, at least one per source in the real caller's shape, not only through a helper. On SME-137 the plan listed what a span never holds but not what reaches `mark_error`: round 1 found four sources (reqwest's URL with its query, the request guard's URI, an MCP tool's error output, JSON-RPC errors) and round 2 a fifth, an rmcp transport error quoting the server's reply body.
   - **An outside program's parser, when the fix depends on how that program reads data:** read how it finds and splits a unit (where it starts and ends, line breaks, odd bytes), not only the function that makes the decision, and specify the code to match. On SME-165 the plan cited Chrome's keep-alive decision (`IsKeepAlive`) but specified a reply-head reader (an `HTTP/1.` prefix, `\r\n\r\n`) that Chrome doesn't match, so the Developer read `http_util.cc` mid-build.
   - **What a tightened shared check protects at each caller,** when the plan makes a check stricter and several callers run it: say per caller what the tightening stops there. A caller where it stops nothing keeps the old behaviour, through a parameter if needed. On SME-173 the plan refused `Sec-Fetch-Site: same-site` everywhere and wrote the model's browser's cost down as a trade-off, but there `same-site` can only be the sandbox itself, so the cost bought nothing and broke the system prompt's own advice ("publish the port and use `localhost` instead"); review 1 caught it, and the fix added a `Destination` argument. **When a trade-off depends on a header or policy, list every value that triggers it,** not only the one measured: that plan named `Referrer-Policy: no-referrer`, but `same-origin` (Django's default) drops the `Referer` the same way, so the cost was larger than written.
   - **What each caller does with a new refusal, when the fix adds a refusal or error to a path:** follow each caller's handling of that error to its side effects (a delete, a retry, a cleanup, a fallback) and say whether each still holds when the refusal is true, since the error now means something it couldn't before. On SME-180 the plan said a refused key install "fails the new pod's start, which then deletes the pod it just made", but the refusal meant the pod by that name was now another database's, and `create.rs`'s delete by name would have deleted that pod (round 1's finding, fixed by holding each `Sandbox` delete to its pod's uid).
   - **What each check reads, and when, before calling one check "subsumed" by another:** for each, the value it compares and the moment that value was read (built once, loaded per request, read inside the transaction). Two checks on the same row can read it at different moments, and then neither covers the other. On SME-177 the plan said a whole-grant compare-and-set subsumed the client-id condition, but the grant came from the refresh's own load of the current row while the client id came from the manager's build, so after a new sign-in an old manager could match the new grant with its old client; the Developer caught it while writing the code and kept both.
   - **A failure's status, captured live, when the plan reports a failure from a Kubernetes status field** (a reason, a phase, an exit code): capture the failure at plan time, once per phase of the workload that can change the field (before and after the pod's own signal handler is set, say), and write the captured fields into the plan. rules-code.md's [fixture real artifacts](rules-code.md) rule asks for one live fixture by the time the code is written; this asks for it before the plan relies on it, and in each phase. On SME-171 the plan assumed an evicted pod reads a pod-level `Evicted`. It took one capture per review round to learn that it doesn't after the install (the pod's TERM trap exits 0, so the pod reads Succeeded, its container `Completed`), and that it does during the install, where the trap isn't set yet; round 1's capture covered only the later phase, and its test fed that state to the install path.
   - **A threat list for a new service with a web UI** (a compose service such as Grafana): what an unauthenticated visitor, or another site through DNS rebinding, can make it do (add a data source, send a webhook or an alert, install a plugin, answer to another Host name), and the setting that turns each off. It is the plan-time half of the security-boundary rule under [Phase 2](tdd.md) ("write down what it does *not* cover"). On SME-137 Grafana took two review rounds: an anonymous Admin reachable by DNS rebinding, then an Editor's alerting webhooks to any host on the compose network.
   - **What each caller does in each state,** as a small table: for every state (none, starting, ready, broken...), what each caller of it does (waits, fails fast, starts it, retries, gives up). The states and transitions alone don't say this. On SME-35 the plan listed a language server connection's states, and "an edit never starts a server", but not that an edit must never *wait* for one to connect. Most of its 15 review findings were at those cells: a failed start left running, an edit waiting two minutes, a spent retry budget that a restart didn't reset, a "connecting" message repeated forever. For a caller that queues behind a slow step (a lock, a connect in flight), the cell says what it waits out: the whole step, its retries included. When the step's result can be refused at the end (an edit came in during it), say how the step stops its own retries once refusal is certain. On SME-167 a connect refused after an MCP server edit still retried the old settings, so the old server got a second request and a status check queued behind it waited out both attempts, up to 30 s (round 1's medium finding).
   - **A row for work already in flight.** For any setting a running operation reads (a turn's model, a pod's limits), say what the operation in flight does when the setting changes under it (keeps what it read, or picks up the change, and when), and which record says what it actually used. On SME-72 the plan had the model's states but not this, and the first review's top finding sat exactly there: the switch point for a model's signed reasoning was recorded when the user picked a new model, while a turn still running kept writing for the old one past it.
   - **How it will be checked by hand,** when the Definition of done calls for a hands-on check: the steps, and which settings make the case happen. Before calling a check impractical, look up the real floor or ceiling of each setting that would trigger it, in the code and the UI, not from memory. On SME-126 the plan called a cut-off-mid-tool-call check impractical because the reply budget is "never below 16,384 tokens", but the provider's "Max reply tokens" goes down to 1,024; the Developer found that and the check took two minutes.
   - **The size of the change a trade-off avoids, when the plan keeps the trade-off because a file is at its size ceiling:** write the change down and measure it. A change of a line or two fits under the ceiling and goes in; only one that needs the file split goes to a split ticket. On SME-177 the plan left a status check reading Unreachable after a lost refresh, because `src/mcp.rs` was near its ceiling, though `docs/mcp.md` already said the check retried; review 1's fix was one match arm, 156 bytes (the split is SME-205).
   - **Questions for the user**, in their own section at the bottom of the ticket (see [Questions for the user](../personas/rules.md)), and **trade-offs** you want the user to see, in a section of their own. When a tradeoff says "only X sees the difference", name a real X and check it before writing it down. On SME-90 the plan stopped at "only header-less clients see the difference" without asking who they are; review found webhooks to production's https previews refused. When a yes to a question would widen the ticket, say by how much next to it: the files and sites it adds, and any toolchain, image or CI change. On SME-95 the plan asked whether to lint `expect()` with clippy without saying a yes meant 36 more sites in 15 files, clippy added to the image and a CI step, so the user chose without seeing the size.
7. Show the plan to the user (link the ticket) and **stop**. A Planner moves the ticket to **Planned** instead, and the user approves by moving it to Todo (see [Personas](../personas/README.md))
8. **Wait for explicit approval** — a response like "looks good", "yes", or "go ahead". The user may also leave feedback as comments on the ticket.
9. Once approved, move the ticket to **Todo**; move it to **In Progress** when implementation starts
10. Do not write any implementation code or tests until you receive that approval

If the user requests changes to the plan, update the ticket's plan and show it again. Repeat until approved.
