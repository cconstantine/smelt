# Feature checklist: Dev tooling and operations
Part of the [Feature checklist](index.md).

CI, connection limits, check servers, the cluster lock, sandbox images, traces.

| Ticket | Feature | How to check in the browser |
| -- | -- | -- |
| SME-14 | CI | Not web-checkable (every PR's CI) |
| SME-129 | A check server's scratch database is cleaned up | Not web-checkable (a dev script): `scripts/check-server stop` deletes exactly the scratch database's own pods and claims before it drops it — retrying until the cleanup succeeds — and `sandbox_instance_cleanup --list` prints the namespace's pods and claims grouped by `smelt/instance`, which is how a stranded instance is found |
| SME-27 | Connection limits | A watching tab streams the reply; reloading mid-reply shows the text so far; the sender sees its message once |
| SME-115 | A scratch-database server leaves the dev server's sandboxes alone | Restart the dev server onto the fix; a conversation with a sandbox from before it keeps its `/workspace` files and its sandbox panel still connects. Then `CHECK_SCRATCH_DB=1 scripts/check-server start` from a worktree with the fix (a scratch database by default since SME-226 — pass the flag anyway, as a checkout cut before that merge runs an older copy of the script that defaults to the dev one — and no cluster lock needed since SME-100), ask for a sandbox in a new conversation there, delete that conversation there, and `scripts/check-server stop`: back on the dev server, every conversation's sandbox and files are still there. `CHECK_SCRATCH_DB=1 scripts/check-server start 98a8e67` is refused, naming SME-115. Not web-checkable: each pod and claim carries `smelt/instance`, and the scratch server's conversation ids start above 2,000,000,000 (real-cluster tests in `src/sandbox/tests.rs`) |
| SME-117 | A check server's log records what it deleted | `CHECK_SCRATCH_DB=1 scripts/check-server start` with no `RUST_LOG` set: it prints `logging at RUST_LOG=info (check-server's default)`. On "Sandbox volumes", add a volume and delete it; start a conversation and delete it in the sidebar; then `scripts/check-server stop`, which prints the log's path. `grep -E 'smelt instance\|swept\|adopt\|deleted (pod\|claim\|volume claim)\|tearing down'` on that log shows the instance, "nothing to adopt", the sweep's summary (`listed=0 deleted=0`), "deleted volume claim" with the claim's name and uid, and "tearing down a conversation's sandbox" with the conversation's id; smelt's lines have no colour codes. A conversation that had a sandbox adds "deleted pod" and two "deleted claim" lines, each with a uid. Not web-checkable: the level chosen from an override, the environment or `.env` (`scripts/test-check-scripts`), and the sweep's and teardown's lines against real pods and claims (`sandbox::claims::log_tests`, `sandbox::adopt::log_tests`) |
| SME-100 | The scripts take the cluster lock themselves | Not web-checkable (developer tooling). From a worktree with `scripts/with-cluster-lock`: `scripts/check.sh` with nothing wrapping it builds, lints and compiles the tests while another session's gate holds the lock, then prints `waiting for the cluster lock (held by pid …, …, in <its worktree>)` and runs only the tests under it; `smelt-cluster-lock.log` in the repository's git common dir gains a line with its `waited=` and `held=`. `flock "$(git rev-parse --git-common-dir)/smelt-cluster.lock" scripts/check.sh` still completes, with a notice to drop the outer flock. `CHECK_SCRATCH_DB=1 scripts/check-server start` comes up while a gate holds the cluster lock; a second `start` on the same `CHECK_PORT` from another check worktree says `waiting for port …` naming the first. Automated: `scripts/test-check-scripts` |
| SME-137 | Traces in Grafana | With `docker compose up -d tempo grafana` and the dev server restarted in a recreated `smelt` container, ask the model to read a file that doesn't exist in its sandbox. Within about ten seconds, [http://localhost:8182](<http://localhost:8182>) → Explore → Tempo → TraceQL `{ name = "turn" }` lists the turn under its `POST /api/conversations/{id}/messages`; open it: `chat {model}` spans with token counts, a `tool read_file` span marked as an error with the file's error, and `agent request` under it. `{ status = error }` finds it too. The trace holds no message text. Grafana's menu has no Alerting, and opening it as `http://127.0.0.1:8182` redirects to `localhost`. Stop Tempo (`docker compose stop tempo`) and send another message: the reply comes as usual, and the server log shows one `opentelemetry_sdk` export error per batch. Automated: `telemetry`, `turn`, `anthropic::stream`, `mcp` and `sandbox` span tests |
| SME-212 | Database and cluster tests refuse to run outside the cluster lock | Not web-checkable (developer tooling). From a worktree with the fix, with no lock: `cargo test --features server -- --exact db::tests::instance::test_an_empty_database_gets_an_instance_that_owns_nothing_unlabelled sandbox::claims::log_tests::test_a_conversations_teardown_logs_what_it_deletes` fails both at once (0.00 s), each panicking at `src/test_lock.rs` with "run it with scripts/cluster-test"; the same through `scripts/cluster-test` passes. Automated: `scripts/test-cluster-lock`, `repo_lints::tests::test_every_sqlx_test_takes_the_cluster_lock` |
| SME-175 | A check server counts only its own answer | Not web-checkable (developer tooling). From a worktree with the fix, on a free port that isn't 8080 or 8081 (say 18095): `python3 -m http.server 18095 --bind 127.0.0.1 &`, then `CHECK_PORT=18095 CHECK_SCRATCH_DB=1 scripts/check-server start` exits 1 at once with `port 18095 is taken: pid N (python3) in <dir> listens on it` (the program's name only, never its arguments), checks nothing out, and leaves that server running. Stop it by its pid, and the same start says `check server up`. Automated: cases 12–17 in `scripts/test-check-server` |
| SME-186 | The check-server lows: a port wait that ends and names its holder, `.env` read as dotenvy reads it, one check worktree per checkout, and a pid file that only claims its own server | Not web-checkable (developer tooling). With one check server up on a port, a second start on that port — `CHECK_PORT_WAIT=5 CHECK_WORKTREE=<another worktree> CHECK_PORT=<the same port> CHECK_SCRATCH_DB=1 scripts/check-server start` — exits 1 within about 5 s with `port <p>: still held after 5s by pid N (dx) in <the first worktree>`, followed by the `CHECK_WORKTREE=<that worktree> CHECK_PORT=<p> scripts/check-server stop` that would free it, having checked nothing out and created, written or signalled nothing; leave the first server running and stop it yourself. `CHECK_PORT_WAIT=abc` exits 2. With `CHECK_WORKTREE` unset, `scripts/check-server status` names a log under `smelt-check-<this checkout>`; point `.check-server.pid` at any other live group and `stop` says it isn't this worktree's check server and leaves that group running. A `.env` `DATABASE_URL` holding a `$` reaches the scratch database URL substituted, first line winning, as dotenvy does. Automated: `scripts/test-check-server-guards` (G1–G5) and `scripts/test-dotenv-value` |
