# Feature checklist: Sandboxes
Part of the [Feature checklist](index.md).

Sandbox pods, terminals, files, Docker, dev servers, previews and their isolation.

| Ticket | Feature | How to check in the browser |
| -- | -- | -- |
| SME-7 | Sandbox pod | Ask for a pod: it shows Running in the sandbox panel and on `/pods`; asking for a second is refused |
| SME-9 | Terminals | Run `cd /tmp && export FOO=bar`, then `pwd && echo $FOO` in the same terminal: `/tmp`, `bar`; interrupt a `sleep` |
| SME-10 | Sandbox panel | Output streams live with no reload. stdout and stderr show grouped by stream, not interleaved (SME-187), and all of a command's lines show before its exit: `echo out1; echo err1 >&2; echo out2; echo err2 >&2` shows all four lines every time (SME-122 B12) |
| SME-11 | File tools | write, read, edit (a diff appears in the transcript); change the file from a terminal and edit with the old hash: refused |
| SME-12 | Pod limits, crash detection | A pod with `memory_limit` 64Mi running `head -c 300M /dev/zero \| tail -n 1`: "OOMKilled" notice, command marked lost, pod gone |
| SME-13 | Command finished notices | A command's finish wakes the model without a new message |
| SME-17 | Sandbox environment, volumes | Commands run as `sandbox` with passwordless `sudo`; `/sandbox-volumes` (linked from the sidebar): create and delete; a file written to a volume survives into a new pod |
| SME-42 | Sandbox dev servers | Ask the model to build a small web app (e.g. Vite + React) and start its dev server. It loads the app in its own browser at `http://localhost:<port>/`, with no tunnel or outside service, then shares a preview. An "Open preview · port N" link appears in the sandbox panel live and is still there after a reload. The link opens the app in a new tab, and an edit the model makes shows up there without a reload. After deleting the conversation, the link's page says there's no running sandbox. Dev: previews need port 8181 published (recreate the `smelt` container after pulling) |
| SME-33 | Docker in the sandbox | Ask the model to run a small compose app from `/workspace` (e.g. a web page served by a container, with a relative bind mount of its files): it runs with no `sudo`, and the page shows the files. Ask it to open a container's unpublished port in its own browser at the container's address, then share a preview with that `host`: the panel link reads "Open preview · <address>:<port>" and opens the page. Terminate and recreate the pod: `docker image ls` still lists the image. Recreate with `docker_memory_limit` 512Mi and run a container holding more (`docker run --rm debian:stable-slim sh -c 'head -c 900M /dev/zero \| tail -n 1'`: it needs GNU `tail`, since busybox's in `alpine` doesn't buffer): a notice says Docker restarted (OOMKilled), and the terminal and `/workspace` still work. `/pods` shows the pod's limit as the sandbox's plus Docker's. Dev: run `scripts/build-sandbox-image.sh` after pulling |
| SME-46 | A preview with no sandbox explains itself | In a new conversation (no sandbox), open `http://3000-<conversation id>.preview.localhost:8181/` (a check server needs `-- SMELT_PREVIEW_ADDR=0.0.0.0:8182 SMELT_PREVIEW_URL=http://{port}-{conversation}.preview.localhost:8182 SMELT_BASE_URL=http://localhost:8081` and port 8182 instead): the page says "This preview's sandbox isn't running", names port 3000 and the conversation, doesn't mention `create_pod`, and "Open the conversation" goes back to it. Stopping a sandbox with a preview open, then reloading the preview, shows the same page |
| SME-53 | Sandbox agent protocol versions | Ask the model to start a sandbox and run a command in a terminal: `/pods` shows the pod's Status as "Running · agent 1.0". An older agent: start a check server with `-- SANDBOX_IMAGE=docker.io/library/smelt-sandbox:v0` (an image of the pre-SME-53 agent, imported under that tag), have the model create a pod, restart the check server without the override, and ask for a terminal command: the failed "Opened a terminal" row says the sandbox runs an incompatible sandbox agent and to call terminate_pod, then create_pod; the model does, and the command runs in the new pod. Dev: run `scripts/build-sandbox-image.sh` after pulling, or every existing pod is reported as outdated |
| SME-76 | Robust terminals, capped tool results, headers on OAuth MCP servers | Ask the model to run `printf abc` in a terminal: it finishes (exit 0, output `abc`) and the next command in that terminal runs. Ask it to run `cat` with no arguments: it finishes at once instead of hanging. Ask it to run `sleep 600`, then another command in the same terminal: the refusal names the `sleep` command, its age and `send_signal`. Ask it to `read_file` a file over \~25 KB: the result says `truncated` and gives a `next_offset` that continues. A single line over 2,000 characters comes back cut with a note naming the line, how long it is and the `character` to read on with; write a file of one 40,000-character line in a terminal and ask for its last 20 characters: `read_file` alone reaches them (SME-189). On an OAuth MCP server's page, the header editor shows ("Extra headers (sent with the OAuth token)"); add a header and Save: it's listed after a reload; an `Authorization` header is refused. With `X-MCP-Toolsets: context,repos,issues,pull_requests,users,actions` on the GitHub server, the model can read a failed CI job's log with `get_job_logs`. Dev: run `scripts/build-sandbox-image.sh` after pulling |
| SME-77 | Sandbox pods reserve nothing | Start a sandbox in two conversations at the default limits on a small node: both run (before, the second stayed Pending with "Insufficient memory"). `/pods` shows each pod's memory limit and no CPU limit. Not web-checkable: the pod spec has `requests.memory: 0` and no CPU request or limit. Dev: patch the cluster's LimitRange first (no `cpu` max; see the ticket) |
| SME-79 | A notice when a command goes untouched | Ask the model to run `sleep 400` in a terminal, then a `terminal_command_status` on it, then stop talking to it. Five minutes later (within a minute of it) the transcript shows a notice reading "`sleep 400` is still running, untouched for 5 minutes", and the model gets a message naming the command, how long it has run, how long since anything touched it, its line counts, that "Nothing stopped it and smelt won't stop it", and what it can do — and the `sleep` is still running: smelt stopped nothing. Ask for `set_idle_notice` with `idle_notice_seconds` 600: the reply reads "idle notice for `<id>` set to 10 minutes" and no notice comes for 10 minutes; with `0` it reads "idle notice for `<id>` turned off" and none comes at all. Check its status again and the clock restarts, so nothing arrives 5 minutes after that either. Left alone from the start it is noticed again every 5 minutes, twice, three times, until it ends — and when it does it still gets its finish notice (the SME-13 row). Dev: `SANDBOX_IDLE_NOTICE_MINUTES=1` on a check server waits a minute, and `=0` turns the notices off for commands started after. Automated: `db::tests::commands` (due over `GREATEST(created_at, touched_at, idle_notice_at)`, `0` = never, notices repeat until touched, the finish notice stays owed), `sandbox::tests::idle_notice` (a pass wakes only conversations with something due, and repeats), `turn::tests::wake::test_wake_drains_an_idle_notice_and_the_command_keeps_running`, and the tools' tests (status's two fields, read and signal touching, `set_idle_notice` refusing a command that isn't running) |
| SME-90 | Other sites can't reach a sandbox container | Ask the model to run a web server in a Docker container (the SME-33 row) and open it in a browsing session at the container's address: the page loads, with its own images and scripts. Not web-checkable: another site's `<img>` of the container is refused with a 403 (browser tier scenario: a script the container page fetches with `referrerpolicy=no-referrer` is refused) |
| SME-157 | Containers get the pod's uplink MTU | Not web-checkable (a cluster test): `sandbox::pod_lifecycle_tests::test_docker_containers_get_the_pods_uplink_mtu` starts a pod with a Docker sidecar on a real cluster and checks that containers come up with the MTU of the interface carrying the pod's default route, not Docker's default 1500 — on the default bridge, and on a user-defined bridge created after dockerd started, which is what `--default-network-opt` reaches — and that dockerd carries both MTU flags. A web-checkable shadow: create a sandbox with Docker and ask the model to `git clone https://github.com/cconstantine/smelt.git` inside a container: it completes with no recv failure |
| SME-180 | git never runs a command in another database's sandbox pod | A repo cloned into a conversation's pod still clones and lists its `AGENTS.md` files, the model can still load one, and a new SSH key still reaches the live pods (the SME-32 rows). Not web-checkable: git's kube exec reads the pod before every exec and refuses another database's with `NotOurs` (real-cluster test `sandbox::tests::guards::test_kube_exec_and_the_agent_dial_refuse_another_databases_pod`) |
| SME-121 | A server runs its own sources' sandbox image | After restarting the dev server onto the change (and running `scripts/build-sandbox-image.sh` once if the first sandbox says the image is missing), ask the model to start a sandbox and run a command: it works, and `/pods` shows "Running · agent 1.0". A missing image can't be served by a check server: `check-server start -- SANDBOX_IMAGE=docker.io/library/smelt-sandbox:src-nosuchimage` stops at `cluster-doctor`, which names the image and `scripts/build-sandbox-image.sh`. The failed call's `ErrImageNeverPull` advice is covered by `sandbox::tests::test_a_missing_image_is_a_startup_failure_that_says_how_to_build_it` and its neighbours. A stale image: with the SME-53 row's `smelt-sandbox:v0` image, start a check server with `-- SANDBOX_IMAGE=docker.io/library/smelt-sandbox:v0`, have the model create a pod and run a terminal command (no restart in between): the failed row says recreating the pod won't help until the image is rebuilt, then to replace the pod, and `/pods` says "old agent, rebuild the image, then restart" |
| SME-144 | A terminal's last command status | Ask the model to start a sandbox and run `for i in $(seq 1 300); do echo line $i; sleep 0.05; done; (exit 3)` in a terminal. The terminal's titlebar shows a blue "● running" pill next to "Connected". It stays in view while the output scrolls, and when you scroll the terminal up to the top. When the command ends it turns red, "✗ exit 3", and its tooltip names the command and "exited with status 3". Ask for `true`: green "✓ exit 0". Ask for `sleep 60` and reload: still "running". Check at a phone's width and in dark mode: the pill fits the titlebar and reads clearly. A terminal with no command yet shows no pill. While a command streams, scroll the terminal up a little and back to the bottom: it follows again (the titlebar doesn't change height as the pill changes). Automated: `chat` unit tests and the browser tier's `terminal_command_indicator` |
| SME-165 | Each request to a sandbox server is checked on its own connection | Not web-checkable on demand (it needs a server in the pod that ignores `Connection: close`). A web-checkable shadow: ask the model to start a dev server in its sandbox (the SME-42 row) and open it in a browsing session at `localhost`: the page and its scripts, styles and fetches all load. Automated: `egress_proxy` tests (a keep-alive reply marked `Connection: close`, 1xx and 101 heads) and the browser tier's `scenario_a_sandbox_connection_carries_one_request` (real Chrome against a keep-alive stand-in pod server: each connection carries one request) |
| SME-173 | Another conversation's preview can't reach this one's | In two conversations, ask each model to start a dev server and share a preview (the SME-42 row); in the second, ask for a page with `<img src="<the first conversation's preview URL>">` and open its preview: the image is refused with a 403 (DevTools' Network tab), since every `*.preview.localhost` preview is same-site with every other. The first conversation's preview link from the sandbox panel still opens, and its page's scripts and styles from another of its own ports still load. Automated: `fetch_guard` tests (Chromium's measured header sets) and `preview::server::tests::test_a_preview_only_answers_its_own_pages_and_direct_visits` |
