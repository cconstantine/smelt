# Feature checklist: Tools and browsing
Part of the [Feature checklist](index.md).

The model's tools: todos, search, fetch, the browser.

| Ticket | Feature | How to check in the browser |
| -- | -- | -- |
| SME-8 | Tool use | Ask "what's on the todo list?": the transcript shows one row, "Checked the todo list", with its result a click away, and the model answers from it. Work that runs on in the background is a terminal command (the SME-13 row); there's no tasks panel since SME-54 |
| SME-19 | glob, grep | Both find a file written earlier |
| SME-20 | Todo list | The todo panel updates live as the model calls `todowrite` |
| SME-21 | webfetch, http_request | Fetch a real page; GET a JSON API. Since SME-155 no address is refused: a private address (e.g. `http://10.0.0.1/`) fails to connect with a clear message, and `localhost` is reachable |
| SME-22 | Browsing sessions | Open a session: the panel streams; click a link and use the address bar in the panel; the model reads the same page; the chat stays usable at a laptop width (1400px) |
| SME-24 | Web search | The model searches and cites a source |
| SME-69 | Chrome found outside the build checkout | Start a check server from a worktree (`CHECK_SCRATCH_DB=1 scripts/check-server start`, which now passes `BROWSER_CHECK_CACHE` instead of symlinking): ask the model to `webfetch` `https://example.com`: it returns the page's text, not "chrome-headless-shell not found". Not web-checkable: a binary run with `BROWSER_CHECK_CACHE` unset and no `.browser-check-cache` in its build checkout says where it looked and to set the variable |
| SME-119 | One failed browse or fetch doesn't break the next | Not web-checkable: neither failure has a trigger in the UI (no browsing call can panic under the session lock today, and the shared browser's runtime fails only when the OS refuses threads). The SME-22 and SME-21 rows still pass. Automated: `browsing` and `webfetch` unit tests and the browser tier's `scenario_open_after_a_poisoned_session_lock` |
| SME-184 | The address bar picks http for a local address typed without a scheme | In a conversation with a sandbox, run `python3 -m http.server 5173 --bind 127.0.0.1 &` in a terminal and open a browsing session. In the Live Browser's address bar type `localhost:5173` and Enter: the bar reads `http://localhost:5173/`, no error shows, and the panel shows "Directory listing for /". Type `example.com`: the bar reads `https://example.com/`. Delete the conversation afterwards. Automated: `browsing::server::tests::test_normalize_address_gives_local_and_private_addresses_http` and `…_gives_public_names_https` |
| SME-237 | Every tool has a class | Not web-checkable on its own: the class shows on the call's trace span, and what filters by it is the SME-241 row below. In Grafana (SME-137's setup), ask the model to `http_request` `DELETE https://example.com/`: its `tool http_request` span has `smelt.tool.class = destructive`; a `todoread` span has `read-only`. A `POST` carrying an `X-HTTP-Method-Override: DELETE` header classes `destructive` too (SME-241). Automated: `anthropic::tools::class::tests`, `mcp::tests::classes` |
| SME-240 | Override an MCP tool's class on the server's page | Open `/mcp-servers/exa`: the Tool-classes section reads `web_search_exa` `read-only — from the server`; choose `destructive` and the row says `destructive — your override`; reload, still your override; choose "Server's answer" and it's `read-only — from the server` again. Automated: `db::tests::mcp` (the `mcp_tool_classes` section), `mcp::tests::classes` (the override tests), `api::mcp::tests` (the merge and the checks), `mcp_servers::tests` (the select value and the origin note) |
| SME-241 | A persona's `smelt.tools` rules decide which tools it's offered and which it may call, and a child inherits its parent's | In a test repo, write `.agents/personas/readonly.md` whose frontmatter has `smelt:` with `tools:` holding `class: read-only` and `allow: [github/create_pull_request_review]`, and start an agent with that persona. In its context view the offered-tool list has no `start_agent` and no `browser_click` (both writing) but still has `http_request` and `terminate_pod` (both read-only); ask the agent to `http_request` a POST: the tool result refuses it, naming the class ceiling; ask it to start an agent: refused the same way, by its own rules. Start a second agent from a persona with no `class`: `start_agent` is offered there. With `SMELT_AGENT_DEPTH=2` on the server, an agent at depth 2 is refused a third with the depth message. Open `/mcp-servers/new` and name a server `a/b`: the save is refused, naming the rule; a server named that way before shows the line under its name field saying its tools can only be ruled on by class. Ask a persona whose rules name a server that isn't configured (`gh/create_*`) and `list_personas` says which patterns rule nothing, as does `start_agent`'s notice to the parent. Automated: `personas::tests` (the grammar and the report's wording), `anthropic::tools::server::tests::rules` (the offer filter and the refusals), `agents::tests::rules` (chain of three, edit-after-start, depth, the parent's notice), `db::tests::agents` (depth, root and chain rows), `mcp::tests::classes` and `mcp::tests::spans` (offer filter, refusal before the send), `mcp::tests::names` and `api::mcp::tests` (the name rule and the edit-page report), `mcp_servers::tests` (the note), `git::server::persona_tests` (the listing's note) |
