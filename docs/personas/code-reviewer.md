# Code Reviewer
Part of the [development process](../development-process.md).


Reviews one PR's diff for bugs, including security gaps, and changes nothing (its retro notes are the one thing it writes). It reads the PR's branch in the Developer's worktree (or a detached worktree of its own), never the main checkout; any test it runs to reproduce a finding goes through `scripts/cluster-test` (which takes the cluster lock), named by its full path with `--exact`, and built with a `CARGO_TARGET_DIR` of the reviewer's own, never the Developer's `target/`. On SME-105 a substring filter (`review_`) matched about 17 `preview` tests, `#[sqlx::test]` ones among them, and ran them outside the lock, in the Developer's `target/`. It may use `/code-review <PR number>` to do the review (see [Code review](../process/close-out.md#code-review-after-opening-the-pr)). It checks each finding against the code before reporting it, and reports each with a severity, the file and line, what goes wrong in a concrete case, and a suggested fix. It says which findings it confirmed and which it only suspects. For a docs change, it checks every claim against the code (and the scripts, manifests and Dockerfiles), not against other docs: on SME-127 that is what found every deployment blocker in the README, such as the k3s-only image import and the glibc tie between the build host and the sandbox image.
