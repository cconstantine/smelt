# Integrator
Part of the [development process](../development-process.md).
smelt's machine persona file is `.agents/personas/integrator.md`; its `smelt.tools` encode what this page says the persona may do — the only persona rules that allow a merge.


Finishes one **Approved** ticket:

1. Reads the user's answers to the questions and acts on them on the branch.
2. Fetches `origin/main`. If it has not moved since the PR's head was last gated, CI on that head *is* the gate: there is no local re-run, and the report says so with both shas. If it has moved, merges it into the branch (not a rebase: the PR is open, and force-pushing it is ruled out) and pushes. Whether it gates again locally is keyed on overlap (the SME-364 retrospective). **When `main`'s new commits touch none of the branch's changed files and none of the gate's own files, CI on the pushed merge head is the gate.** The gate's own files are anything `scripts/check.sh` runs or reads besides the sources it checks: `scripts/`, `src/repo_lints.rs` and `src/repo_lints/`, `clippy.toml`, `build.rs`, `Cargo.toml`, `Cargo.lock`, `.cargo/config.toml`, `migrations/`, `.github/`, `Dockerfile`, `docker-compose*.yml` and `docker/sandbox/`, for example. The report says so with the two file lists. Otherwise it runs the gate again (`scripts/check.sh`, which takes the cluster lock itself). To check, before merging, take the old base, `base=$(git merge-base HEAD origin/main)`, and compare `git diff --name-only --no-renames $base..origin/main` (`main`'s move) against `git diff --name-only --no-renames $base HEAD` (the branch's files). `--no-renames` lists both paths of a move, as CI's own docs-only check does: without it, a file `main` moved away from one of the branch's paths hides the overlap. On SME-71 two re-gates after `main` moved into files the branch never touched cost about an hour of the lock each. When the PR adds a lint or a gate check, the gate on the merged tree, local or CI, covers it: code from `main` wasn't written against the new rule. Merge with a merge commit, not a squash: the per-finding "SME-N review R, finding M" commits are the audit trail (SME-254's Q2).
3. Merges the PR once CI passes on that head, and never over a red, a known flake's included (SME-329; [done.md](../process/done.md) has the one re-run allowed, for a red where no test ran). The merge never moves the ticket — status at merge is a seat/human decision, and the Linear↔GitHub integration is expected to be configured not to advance it (see [close-out.md](../process/close-out.md#keeping-linear-current)) — so after merging it re-reads the issue's status after a few seconds (the first read is not trustworthy) and moves the ticket to **In Review** for the user's close-out — a seat decision, never the merge's. Then it cleans up: on the user's machine, it removes the branch's worktrees; from a conversation sandbox it removes its own checkout and names the worktrees still on the user's machine in its report (SME-254, finding 1 — from a sandbox this step was silently un-doable).

**A retrospective ticket** has no branch until the Integrator makes one. It acts on every proposal the user didn't mark as disagreed: a process or doc change goes on a new branch (see [Rules every persona follows](rules.md)) and into one PR, which gets one round of [code review](../process/close-out.md#code-review-after-opening-the-pr) and merges once CI passes; a code change becomes a Backlog ticket in the project the notes behind it came from (or in Maintenance). It records the declined proposals in the ticket and moves it to **Done** — the exception to the seat's post-merge In Review move: this ticket's user close-out was the answers to the proposals, so the seat moves it straight to Done after the merge.
