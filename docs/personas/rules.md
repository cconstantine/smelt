# Rules every persona follows
Part of the [development process](../development-process.md).


- **Ownership is recorded in Linear, not only in a conversation.** Before starting a sub-agent, whoever starts it — the Project Manager, or the ticket's [Ticket Driver](ticket-driver.md) once it holds the ticket (SME-306) — comments on its ticket: `<Persona> started: worktree <path>, branch <branch>` — or, when the seat is a conversation in smelt rather than a worktree, `<Persona> started: conversation <id>, clone <path>` — so ownership stays reconstructable from either seat (SME-254, proposal 13). The sub-agent's final report is a comment too, beginning `<Persona> finished:` or, when it can't go on without the user, `<Persona> blocked, needs the user:`. **The trail is mandatory, and it lives on the ticket:** a seat that also messages its starter (a `message_agent` report into a parent agent's conversation) has still said nothing until its `finished:` comment is on the ticket, and a starter whose own reports live only in its conversation hides the ticket from everyone — the rule SME-306 made explicit after a driver's reports stayed in its chat and its seats' reports never arrived. A "started" comment with no report after it means that sub-agent is still running. Only one Project Manager runs at a time, and it rebuilds its picture from these comments and `git worktree list` on every pass, so a restart doesn't lose track.
- **A conversation seat is finished when it has no command running *and* has been quiet for 60 s** — "the turn ended" is not done. The orchestrator's readiness rule, needed twice: a 20 s window stopped two of SME-185's cleanup runs' pods mid-cleanup.
- **A ticket you file goes in the project of the ticket that found it.** A code review finding outside the ticket's scope or a bug bash's finding goes in Backlog in that ticket's project, linked as related, and with a Linear priority from its severity if it's a bug (high → High, medium → Medium, low and docs → Low). **A flaky test met in a gate goes in Test reliability** instead, in Backlog, linked as related to the ticket whose gate met it, with a priority the same way: the flakes are one line of work wherever they surface, and SME-260, filed in Bug bash 4, was moved there with the others (SME-257, proposal 5). Only a ticket unrelated to that project's line of work goes in **Maintenance**. A new line of work too big for one ticket becomes a new project for an [Architect](architect.md), which the user approves first.
- **Branches start from GitHub's `main`, fetched first.** Nobody pulls the main checkout, so its `main` goes stale. Fetch with `git fetch origin main`, or over HTTPS (see Pushing) with `… fetch https://github.com/cconstantine/smelt.git main:refs/remotes/origin/main`, then use `origin/main`. This updates only the remote-tracking ref, not the user's checkout.
- **Its own worktree, at a fixed place.** Each ticket's branch gets one worktree, `~/smelt-worktrees/smelt-<ticket>`, made by the Planner (`git branch <slug> origin/main`, then `git worktree add ~/smelt-worktrees/smelt-<ticket> <slug>`) and named on the plan's **Branch:** line. `DATABASE_URL` comes from the environment, so a worktree needs no `.env`. One persona works in a worktree at a time; a Code Reviewer only reads the Developer's. Never `git checkout` in the main checkout: the user's dev server serves it.
- **Hands off the user's running setup:** the main checkout, the dev database, the dev server's port (8080) and the `:latest` sandbox image (no `--latest`). Since SME-121 the dev server runs `smelt-sandbox:src-<hash of the main checkout's agent sources>` (which can lag `origin/main`); a gate building the image for its own tree's sources is fine: a tag it shares with the dev server's image is rebuilt from the same agent sources.
- **Edit files from a script saved in the ticket's scratch directory, never from a heredoc inside another heredoc.** An inner `<<'EOF'` closes the outer one, and the rest runs as shell commands. On SME-100 a patch script's remainder started the real `check.sh` and `browser-tier` with real `cargo`; they failed before their test steps and wrote nothing, but only by luck. Write the edit as a file in `<scratchpad>/sme-N/` and run that file.
- **Scratch files go in a directory named after the ticket,** `<scratchpad>/sme-N/`, never at the scratchpad's top level: personas share the scratchpad. On SME-127 one persona's `gate-commits.sh` could have overwritten another's.
- **One cluster user at a time, and the scripts take turns themselves (SME-100).** Test runs share the k3s cluster's `smelt-park-test` namespace and the shared Postgres's `#[sqlx::test]` databases: sqlx names each from the test's path alone and drops any old one of that name first, so on SME-111 a filtered run outside the lock failed three tests (`dropdb … being accessed by other users`) while another persona's gate ran. So every test run takes the cluster lock, `flock` on `<git common dir>/smelt-cluster.lock` (one file for every worktree), through `scripts/with-cluster-lock`, and only around the run itself:
  - `scripts/check.sh` and `scripts/browser-tier` build, lint, compile the tests (`--no-run`) and check the cluster first, unlocked, then lock their test run only. `scripts/clean-test-namespace.sh` locks too.
  - Any other `cargo test` that includes a `#[sqlx::test]` or a real-cluster test, a filtered one too, goes through `scripts/cluster-test <cargo test arguments>`: it builds with `--no-run` unlocked, then runs the same command locked. A test binary run directly (a copied one) goes through `scripts/with-cluster-lock <binary> --exact <name>`. Since SME-212 the tests enforce this: `with-cluster-lock` sets `SMELT_CLUSTER_LOCK_HELD` for its command, and every `#[sqlx::test]` and real-cluster test refuses to run without it (an old outer `flock LOCK cargo test` included). Never set it by hand.
  - `scripts/check-server`, `scripts/build-sandbox-image.sh` and `scripts/cluster-doctor` take no cluster lock: none of them touches a test run's namespace or databases.
  - **Don't wrap the scripts in `flock`.** A run under an old outer `flock` doesn't deadlock (it finds the lock held by an ancestor, or by a descriptor it inherited, runs inside it, and says to drop the `flock`), but the outer lock is then held through every build again.
  - **Which copy locks itself:** a worktree runs the scripts of the commit it has checked out, and only a commit that has `scripts/with-cluster-lock` (SME-100's merge or later) locks. Check it per commit, `[ -x scripts/with-cluster-lock ]` in the checked-out tree, not per branch: a branch that merged `origin/main` still has older commits, and a per-commit gate script or a red run of an unfixed commit checks them out. For a commit without it, wrap its `check.sh`, `browser-tier` and test runs in `flock "$(git rev-parse --git-common-dir)/smelt-cluster.lock" …` as before, building first (SME-100 review 1). A branch cut before SME-100 merges `origin/main` before relying on the scripts' own lock.
  - Each locked run appends a line (start, waited, held, exit status, worktree, command) to `smelt-cluster-lock.log` next to the lock; `scripts/with-cluster-lock` says who holds the lock while it waits.
- **A hands-on check runs on a scratch database, from a ref with SME-115's fix.** `CHECK_SCRATCH_DB=1 scripts/check-server start` builds a scratch database of the check worktree's own and `stop` drops it; `CHECK_DEV_DB=1` opts back into the dev database and says so on start. Since SME-226 that scratch database is also what a flagless `check-server start` does — **but pass the flag anyway**: the default lives in the copy of the script the worktree runs, so a checkout cut before SME-226's merge (`git merge-base --is-ancestor <that merge> HEAD` fails for it, or `grep -q serves_scratch_db scripts/check-server` finds nothing in it) still serves the **dev** database by default, while both copies accept the flag. A check server on the dev database runs the branch's migrations there, which the main checkout then can't start against; and a smelt from before SME-115 on a scratch database deleted every sandbox claim in the shared namespace whose conversation wasn't in its own database, the user's conversations' `/workspace` among them (`check-server` refuses such a ref outright, whatever database it would serve — SME-186, since a database named on the command line or in the environment got past the old `CHECK_SCRATCH_DB=1` condition). Since the fix each database touches only cluster objects labelled with its own instance. **The worktree that runs `check-server` must contain the fix too** (`git merge-base --is-ancestor 6c9f03c HEAD`; otherwise merge `origin/main` first): the refusal lives in the script, and a branch cut before the fix runs its own old copy, which has none and serves its own pre-fix HEAD. A hands-on check takes no cluster lock (SME-100): `check-server start` takes a lock on its `CHECK_PORT` instead, which the server holds for as long as it runs, so a second start on the same port waits for the first to stop — but only up to `CHECK_PORT_WAIT` seconds (1800 by default), after which it gives up, naming the server that holds the port and the `stop` that would free it (SME-186) (to run two at once, give the second another `CHECK_PORT`, a check worktree of its own and previews of its own, `-- SMELT_PREVIEW_ADDR=0.0.0.0:<p> SMELT_PREVIEW_URL=http://{port}-{conversation}.preview.localhost:<p>`: both would otherwise bind previews on 8181, so the second would run without previews, and its preview links would point at the first server's listener, which could open another check's sandbox (both scratch databases start at conversation 1); SME-96 is to derive these from `CHECK_PORT`). It runs with a check worktree of its own, keeps the check's exit status, and ends the check by deleting, in the check server's own UI, every conversation it started a sandbox in (`stop` itself now deletes that scratch database's pods and claims before it drops it, SME-129, so this is good practice rather than the only thing that cleans up — and still required from a checkout whose `check-server` predates SME-129), and never stops a check server it didn't start. Write the steps to a script file in the ticket's scratch directory and run that, `bash <scratchpad>/sme-N/hands-on.sh`, rather than an inline `bash -c '…'`: on SME-126 Claude Code refused the inline form as a removal it couldn't read, though it removed nothing, and the same steps in a file ran. **Every by-hand `check-server start` runs from this template file, even one you expect to be refused** (a scratch database, a check worktree of its own): a start you think won't happen can still happen. On SME-175 a hand-run `start` meant to be refused by a background listener went ahead, because the listener had died at once, and it served the branch on the dev database for 85 s and migrated it. The file holds:

  ```bash
  export CHECK_WORKTREE=~/smelt-worktrees/check-<ticket>
  # Ask for the scratch database by name. The flagless default is SME-226's, and
  # a checkout cut before its merge still defaults to the dev database;
  # CHECK_DEV_DB=1 is the opt-out, and an explicit -- DATABASE_URL= needs it too.
  CHECK_SCRATCH_DB=1 scripts/check-server start && <the check>; rc=$?
  # A failed stop keeps the scratch database so it can be retried: run it
  # again until it succeeds, with a pause and a time limit (SME-129). One
  # still failing after that goes in the report, never left unsaid.
  timeout 15m bash -c 'until scripts/check-server stop; do echo "check-server stop failed; retrying" >&2; sleep 10; done' ||
      echo 'check-server stop still failing: the scratch database is kept; report it' >&2
  exit $rc
  ```

  A Playwright check built on `scripts/ui-check/smelt_ui.py`'s `run` deletes the conversations it started even when it fails (see [testing/browser.md](../testing/browser.md#playwright-preferred)). Never modify anything in the `smelt-park` namespace by hand: the user's dev server's pods and claims live there.
- **Pushing:** when `origin`'s SSH key isn't available, push over HTTPS through `gh` with only that helper: `git -c credential.helper= -c credential.helper='!gh auth git-credential' push https://github.com/cconstantine/smelt.git <branch>` (the empty value drops the configured helpers first; it changes no settings). Never force-push a branch with an open PR, and never push to `main`.
- **The Current state docs** (docs/current-state/, one file per section) are ordinary file edits: read the file, change the lines, keep the diff small. **The Feature checklist** (docs/feature-checklist/, one file per area) is too: a ticket's row is added or changed on its branch, in the file for its area, and ships in its PR (see [its index](../feature-checklist/index.md)). Two branches that both append a row to one table merge like any other two hunks: keep both rows.
- **Questions for the user end the ticket.** A persona that moves a ticket to a status that waits for the user (Planned, In Review) first puts a `## Questions for the user` section at the bottom of the description. It holds only numbered questions the user must answer, each with the persona's recommended answer in a sentence. Trade-offs, risks and limits it wants the user to see go in a `## Trade-offs to flag` section above it, never among the questions. Hands-on steps the user runs after the merge stay in What shipped. **If there are no questions, the persona moves the ticket on as if the user had approved it** (Planned to Todo, In Review to Approved) and says so in its report. The user can still pull it back.
- **Stop your own background work before reporting.** Every wait loop (`until …; do sleep …; done`), watcher, `gh pr checks --watch` and server a persona starts in the background, it stops by PID before its final report, its Code Reviewers' included (see "Stop only processes you started" in [rules-running.md](../process/rules-running.md)). A finished sub-agent's shells keep running: on 2026-10-09 the Project Manager found 12 such loops, the oldest 35 hours old, still polling for CI on merged PRs and for output files that would never fill. Give a wait loop a time limit too (`timeout 2h bash -c 'until …'`), so one that outlives its persona still ends. A hands-on script's `wait <pid>` on the process under check is bounded too, and kills that process when the bound passes rather than only giving up on it (`timeout 2m tail --pid=$P -f /dev/null || kill $P; wait $P`): on SME-176 an unfixed run's bare `wait` on a waiter that never exits hung until the outer `timeout`.
- **Retro notes are optional, and one line.** The retrospective reads every conversation's record (see [Retrospective](../process/close-out.md#retrospective)), so write a note only for what a transcript won't show: a judgement ("this rule cost an hour and caught nothing"), a workaround nobody wrote down, a rule that got in the way. Post it, when it happens, as a comment on the open "Next retrospective" ticket in Maintenance, starting `Retro notes (<Persona>, SME-N):`. No required parts, and no proposals needed.
## Working from a conversation sandbox

A persona running in a smelt conversation sandbox rather than on the user's machine keeps the rules above except where this section says otherwise (SME-254's retrospective; its findings 1 and 2).

- There is no user checkout, dev server or dev database to avoid here. The workspace is **one plain clone under `/workspace`**, and that is the checkout every command runs from. A *linked* worktree does not work: its `.git` is a file naming a `<parent>/.git/worktrees/<name>` directory that is not mounted, and git then answers `fatal: not a git repository` — which reads like a regression in the code under review, not like the environment (SME-184). The fixed worktree layout above is for the user's machine; from here the branch lives in a branch of the one clone.
- The gate command is `docker compose run --rm smelt scripts/check.sh`, after `docker compose up -d postgres docker k3s` and, when the agent sources changed, `docker compose run --rm smelt scripts/build-sandbox-image.sh` (the same commands [setup.md](../setup.md) documents for the stack). This deployment's k3s and Docker sidecars come up in the sandbox, so the real gate runs here and does not fall to CI.
- **Known traps of the seat's stack** (SME-257, proposal 2), each written up in [setup.md](../setup.md)'s gate section: a seat that will build the sandbox image creates its pod with `create_pod`'s `docker_memory_limit: "48Gi"`, since a smaller limit OOM-kills the build with what looks like an apt or network error; it rebuilds the image after any merge that changes the agent's sources, `origin/main` into the branch included; and a `k3s` that won't start after its container was recreated needs its state volumes dropped and `k3s-bootstrap` run again. Two more are tickets: until SME-267 the image has no `procps`, so install it (`sudo apt-get install -y procps`) before running the `scripts/test-*` suites on the sandbox's host; and until SME-251 their fixture clones under `target/` work in only the environment that made them, so delete `target/test-*` before running the suites in the other one (the host or the `smelt` container).
- **A docs-only commit takes the Markdown route** of [rules-commits.md](../process/rules-commits.md), on that rule's conditions: a script proves its file list and is kept in the PR description or ticket, and the commit is gated on building every target (`docker compose run --rm smelt bash -c 'cargo check --no-default-features --features web --target wasm32-unknown-unknown && cargo build --features server'`), with the full gate at the branch's tip. A full gate here costs 8–15 min, and SME-186 spent two of them on a `testing.md` entry and a header fix (SME-257, proposal 4).
- **Gates run back to back, and the tree sits still while one runs.** There is one checkout, so the detached gate worktree and the stash-the-next-fix trick do not apply: while a gate is running the seat waits, and edits nothing.
- Inside the stack use plain `bash -c`, never `bash -lc`: the login shell drops `cargo` from PATH, which surfaced as a misleading "the cluster has no <image>" (SME-79).
- The sandbox has `docker` and `python3`; it has **no `gh`, no `cargo`, no `psql`, no `kubectl`** and none of the dev stack's toolchain. PRs, CI status and PR comments go through the MCP GitHub tools, and tickets through the MCP Linear tools — there is no `gh`, and adding it to the seat is deliberately not planned (SME-254's Q3): the MCP covers the seat's GitHub and Linear work. The gate needs no host toolchain: it runs in the compose stack. Clients may be installed (`sudo apt-get install -y postgresql-client`); a piecemeal toolchain must not be ([setup.md](../setup.md)).
- **Push over the SSH remote** (`git@github.com:cconstantine/smelt`): it works from the sandbox even when the identity file named in the tooling is missing, silently (SME-79). The HTTPS `gh` helper in "Pushing" above does not apply to this seat.
- A report from this seat says which evidence it has: with no toolchain, no Postgres and no cluster at the prompt, "confirmed" means "traced the code path" unless the change was run through the compose stack — say so in the report's header (SME-185's Code Reviewer).
- The run ends with `docker compose down -v`, `docker system prune -af --volumes`, no `target/` left behind, and `du -sh /workspace` reported in the final report.

- **Reports back** in a few lines: what it did, the ticket's new status, and anything that needs the user or the Project Manager.
