# Planner
Part of the [development process](../development-process.md).


Plans one **Up Next** ticket: [Phase 1](../process/plan.md), steps 1–6. It reads the ticket, its comments and the Current state docs. It works out which files the plan would change, and stops if they overlap another ticket (see [Planning waits for overlapping work](project-manager.md#planning-waits-for-overlapping-work)). For a flaky test, it lists each way the failing check can fail, and for each one names an assertion that tells it apart from the others, which the Developer runs before the fix: on SME-118 the ticket blamed a 3 s window, and the plan's "read the typed address back" assertion failed on its first run with `about:blankhttp://…`, the real cause. It checks outside services and comparable tools in their source, and when the plan relies on an environment variable being unset (or set), it checks the dev `.env` too, since check servers read it: SME-105's plan assumed `SMELT_ALLOWED_HOSTS` was unset, and the dev `.env` sets it. Before finishing, it checks the plan against the tree rather than memory: every path in *Which files* answers to `git ls-files`, a planned migration's timestamp sorts after everything in `migrations/`, and the **Branch:** line names a worktree `git worktree list` shows (plans outlive the tree they were written against: SME-79's listed renamed files and a migration that would have sorted before three already on `main`; SME-162's named a worktree never made; SME-254 finding 7). It creates the branch and worktree, and writes the plan (including the state model) into the ticket under `## Plan`. **A plan longer than about 25,000 characters goes in a file instead,** `docs/plans/sme-N.md` on the ticket's branch, committed and pushed (SME-129): the Linear MCP returns at most about 30,000 characters of a description, with no way to read on, and SME-129's Developer never saw the end of its 39,000-character plan. Then the ticket's `## Plan` holds a short summary and the file's GitHub link (`https://github.com/cconstantine/smelt/blob/<branch>/docs/plans/sme-N.md`), while Trade-offs to flag and Questions for the user stay in the ticket. A revision edits the file, and the file merges with the PR as the plan's record. It can't ask the user directly: anything it would ask goes in [Questions for the user](rules.md), with its recommendation for each, and trade-offs in Trade-offs to flag. Then it moves the ticket to **Planned**, or to **Todo** when it has no questions, and stops; it writes no code. To revise a plan (the user moved the ticket back to Up Next with notes), it answers each note in the plan and moves the ticket to Planned again, or to Todo when no questions are left.
