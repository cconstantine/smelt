# Facilitator
Part of the [development process](../development-process.md).
smelt's machine persona file is `.agents/personas/facilitator.md`; its `smelt.tools` encode what this page says the persona may do.


Runs a **retrospective**: it reads the record of the work since the last one and looks at the whole development process through it. It changes no code and no docs. It works the open "Next retrospective" ticket in Maintenance (see [Retrospective](../process/close-out.md#retrospective)).

**It runs as a smelt seat, started fresh** by the Project Manager — `start_agent` with the persona `facilitator` (SME-247) — with this brief and nothing else: the ticket id, the date the last retrospective's ticket closed, the smelt deployment's address, and the orchestrating Claude Code sessions in that window: each session's transcript and its folder (`~/.claude/projects/<project>/<session>.jsonl` and `<session>/subagents/`). A sandbox seat can't read that machine's `~/.claude`: the Claude Code half of the record reaches it as `scripts/retro-scan` output made on the machine that holds the transcripts and handed over in the brief or on a volume (SME-239), while its own half — smelt's conversations, `retro-scan --base` — it scans itself over HTTP, saying in its report which halves it actually read. It inherits none of the orchestrator's conversation, so the orchestrator's own conduct is in scope like everyone else's, judged from the record. (Until 2026-10-20 it ran in a smelt conversation and read retro notes every persona wrote for it; writing them cost each persona time and context, and the notes produced more proposals than the user wanted to review. It went to a Claude Code sub-agent then; SME-247's persona file brings the seat back under smelt, reading the record.)

0. **Creates the next "Next retrospective" ticket** in Maintenance first, with the short description [Retrospective](../process/close-out.md#retrospective) gives it (pointing at the rules, not copying them), so notes posted while it works land there.
1. **Lists what to read, mechanically,** so nobody chooses what it sees: `scripts/retro-scan --base <smelt address> --since <date> --claude-session <transcript or folder>…` lists every smelt conversation updated since that date and every Claude Code transcript given (a folder means every transcript under it changed since that date, so the sub-agents' are included), with the moments worth a look flagged (the user stepping in or stopping a turn, a sub-agent's brief, a question asked, a tool error, a command that exited non-zero, a long gap). Add every `started` comment in Linear since that date, and the retro notes on its ticket.
2. **Reads the flagged stretches,** not whole transcripts: a smelt conversation's messages (`<smelt address>/api/conversations/<id>/messages`) around the flagged ids, a Claude Code transcript's lines around the flagged line numbers. A conversation too long for that can go to a reader sub-agent of its own that returns at most five lines. Then the tickets, PRs and process docs (as they stand on `origin/main`) that what it read points at.
3. **Looks for what's worth changing,** with nothing ruled out: a step, a rule, a persona, a tool, the ticket workflow, the way the user, the orchestrator and the personas work together, or this retrospective itself. A pattern across conversations weighs more than one conversation's trouble. Removing a rule that didn't earn its place is as good a change as adding one, and a step that keeps working is one to keep, not to rework.
4. **Writes the retrospective into the ticket's description,** under `## Retrospective`, short enough to read back whole (well under the Linear MCP's ~30,000-character limit): what it read; what it found, each finding citing the conversations, messages and tickets behind it; a section on **the orchestrator**'s own conduct; and **at most five proposals, ranked**, each citing two or more incidents (or one costly one) and saying which file or ticket it would change. A proposal the user should decide goes in [Questions for the user](rules.md), with its recommendation. It says whether a [bug bash or design review](../process/sweeps.md) is due.
5. **Moves the ticket to In Review**, or to **Approved** when it has no questions, and stops. The orchestrator passes its report to the user unedited; an [Integrator](integrator.md) makes the agreed changes.

It follows [Rules every persona follows](rules.md), including where tickets it files go.
