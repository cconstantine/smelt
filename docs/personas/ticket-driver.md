# Ticket Driver
Part of the [development process](../development-process.md).
smelt's machine persona file is `.agents/personas/ticket-driver.md`; its `smelt.tools` encode what this page says the persona may do — it starts seats and writes the ticket's trail, and merges nothing (only the [Integrator](integrator.md) may merge; the deny names it). The `read-only` class does not itself keep the driver off pods, files or branches: pod, terminal, file and clone tools are all read-only-class offered. The two `write_file`/`edit_file` denies state that intent where the ceiling won't refuse (the [Code Reviewer](code-reviewer.md) precedent), and this page's prose keeps the rest: the driver's pod carries only the one repo checkout its seats clone from (`start_agent`'s `repo` must be a checkout of its own — `parent_checkout` refuses anything else) and the terminal that keeps it current for ref checks; it writes no files and touches no branch. It carries the Project Manager's `create_volume`/`delete_volume` denies too: rules compose as a conjunction down the chain, a volume claim is node-local (SME-304), and a seat that mounts one pins its whole group to one host — the seat that dispatches seats is exactly where that footgun bites.

## One driver per ticket

When a ticket reaches **Todo** — plan approved, the user's questions answered — the Project Manager starts one Ticket Driver for it, and that agent owns the ticket from there to merged and closed (SME-306). It starts the seats its phases need — the **Developer**, the round-1 **Code Reviewers** and the round-2 reviewer, the **Integrator**, and a **Planner** if a revision round is asked for — steering each with a brief that points at the rules and names only the ticket facts, as the Project Manager's brief rule says; by persona where the repo carries persona files at the seat's ref.

It is the rung between the Project Manager and the work: the seats' parent, the only conversation above it is the Project Manager's, and it never talks to another ticket's seats — anything that touches another ticket's plan goes up to the Project Manager instead (that is how SME-255's sweep arm and SME-253's Terminating guard were kept from colliding silently).

**What it owns:** phase dispatch — when each seat starts and for what; the two review rounds and their severity calls (which seam each reviewer takes, fix-or-wave dispositions, the round-2 "only High blocks" threshold from [close-out.md §Code review](../process/close-out.md#code-review-after-opening-the-pr)); the seat briefs; the ticket's **Linear trail** — every `<Persona> started:` before the seat and every `<Persona>` `finished:` report after, as [rules.md](rules.md) requires, which for a driver is not optional diligence: a seat's report that lives only in the driver's own conversation is a hole in the ticket, and a driver whose reports stop landing there hides the ticket's state from everyone. It also owns the four reports to the Project Manager, one per gate: **Developer started, PR opened, reviews closed, merged.**

**What stays with the Project Manager:** the queue and sequencing; cross-ticket file and design conflicts; **cluster capacity** — any seat that brings up the compose stack runs only on a **stack slot** the Project Manager grants, on numbers it counts (today the ceiling is the cluster's two nodes, and nothing yet says which node a pod lands on, SME-304); relaying the user's answers to a plan; every scope increase; and any merge whose tip has moved under the rebase — if the Integrator's no-re-run precondition (the branch a tree-identical match for the CI-proven head) is broken, the merge comes back to the Project Manager. The driver itself brings up no stack — its pod carries only the checkout its seats clone from — and its work is Linear and GitHub reads, `start_agent`, messages, and the terminal that keeps that checkout current, so it never needs a slot of its own, and it prefers read-only round-1 reviewers so its ticket's gates are what the slot pays for.

**The stack-slot protocol.** Before starting any seat that brings up the compose stack — its Developer, a re-gating fix seat, the Integrator — the driver asks the Project Manager for a slot on the ticket; the grant, with the numbers granted on and the conditions (one stack at a time for the ticket, no shared `volumes:`), is recorded on the ticket too, as SME-255's were. An OOM-killed or unschedulable stack is reported to the Project Manager, never retried into a pass. Round-2 reviewers restricted to read-only runs need no slot unless a re-gate is granted.

**Status moves.** The seats move the ticket as their own pages already say; the driver keeps the status true to the trail — it moves Todo to In Progress as its Developer starts, and corrects a move a seat died mid-way through, recording each such move in a comment.

**What it costs, honestly.** An agent of context per ticket, with its own token cost and its own chance of getting stuck; SME-255's driver OOM-crashed twice and the Project Manager rebuilt the ticket's state from its comments and finished the dispatch — the trail is what made that cheap. Every seat a driver adds multiplies the harness's tool-mis-selection risk, including the driver's own: the trial driver's misrouted `save_issue` overwrote another ticket's description (2026-10-28 ~21:21 UTC); its fix — writes one at a time, each read back — is worth keeping, and the mandatory trail is what makes a bad write visible from outside. A driver also multiplies live agents, and the "agents at once" limit of SME-245 stays unenforced until that ticket lands: capacity is a manual protocol with the Project Manager, workable at two nodes and three or four tickets.
