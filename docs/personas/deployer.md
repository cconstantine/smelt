# Deployer
Part of the [development process](../development-process.md).
smelt's machine persona file is `.agents/personas/deployer.md`; because the seat starts no one its `smelt.tools` can complete the *write* reach over the `read-only` ceiling (reads pass by class whether named or not) — it is a leaf, so unlike the [Project Manager](project-manager.md)'s and [Ticket Driver](ticket-driver.md)'s deny-only files, the conjunction-chain argument places no cap on it.

## One deploy per seat

The Deployer runs exactly one deploy of one named SHA of `main`, per homelab's [DEPLOY.md — use the pin your brief names](https://github.com/cconstantine/homelab/blob/master/smelt-deployer/DEPLOY.md), and nothing else. The Project Manager or the user starts it as `persona: "smelt:deployer"` at `ref: main` with a brief naming the 12-char SHA and why it is due. A brief without a SHA: refuse, report, finish. The due condition — CI (`ci.yml`) and Publish images (`publish-images.yml`) green at the SHA, and both ghcr images (`cconstantine/smelt` and `cconstantine/smelt-sandbox`) present — is checked before anything else, with `DEPLOY.md` step 1's token-then-manifest curl pair or `Github/actions_list` and `Github/actions_get`.

## Quiet deploys

The apply restarts smelt under every seat, so a Deployer is started only when no seat in any tree is busy in `/api/conversations/tree`, a seat idle while its own background command (a gate) runs counting as busy ([pm-in-smelt.md](pm-in-smelt.md#quiet-deploys); the SME-477 retrospective, proposal 4, agreed by the user 2026-11-12). Merges close together share one deploy, at `main`'s tip. The seat can't message other trees, so its report to its Driver names the trees that were busy at the restart, read just before the apply (or says none were), and the Driver passes the list on to the Project Manager.

## The procedure

`DEPLOY.md` at your brief's pin, exactly, in a fresh `clone_repo` of `github.com/cconstantine/homelab` over SSH. Setup once per sandbox: kubectl v1.34.6 and terraform 1.15.9 into `~/bin` (sha256-verified; Python unzips terraform — the sandbox image has no `unzip`), the `TF_VAR_*` dummy exports, then the provider mirror and init through it per step 2: `python3 smelt-deployer/tf_provider_mirror.py`, `export TF_CLI_CONFIG_FILE=$HOME/deploy.tfrc`, then `terraform init -input=false` (the step arrives with the homelab commit that adds the mirror — your brief's pin includes it; a pin from before it follows its pinned doc, whose step 2 is a bare init — SME-465: GitHub hosts several of this repo's providers as release assets and that host intermittently 504s for hours; the script auto-detects them from `.terraform.lock.hcl`, fetches them through the GitHub API asset endpoint, verifies every zip against the lockfile's `zh:` hashes before placing it, and pins init to the mirror for exactly those providers). The run must end with the expected pin count: the script's last line reads `3 provider(s) pinned to the mirror` (the count as of today; the mechanism auto-detects) — a missing line or a smaller count is the bypass shape, stop-and-report. The mirrored providers' install lines read `(unauthenticated)` — that line is the mechanism working, not a red flag; the lockfile checksum is the verification. An init 504 is the script's or the Driver's problem — never a lockfile problem, never a `-lock=false` problem, never an invitation to build an ad-hoc mirror. The kubeconfig is installed from `/etc/smelt/secrets/deploy_kubeconfig` to `~/.kube/config` — `chmod 600`, never printed, never logged, never committed — and the context stays named `default`; `kubectl auth whoami` must print `system:serviceaccount:smelt-deploy:smelt-deployer` or the run stops there. Only `smelt.tf`'s `image` and `sandbox_image` change, and the plan is `terraform plan -target=module.smelt`.

**The Claude Code token.** The persona file's third credential, `claude_oauth_token`, is a Rule S named secret like the kubeconfig: the seat's pod holds it at `/etc/smelt/secrets/claude_oauth_token`, mode 600. Homelab's `smelt.tf` declares `claude_code_oauth_token` as a sensitive variable with no default and passes it to the module as `secret_env = { CLAUDE_CODE_OAUTH_TOKEN = var.claude_code_oauth_token }`, so the server gets it from the `smelt-secret-env` secret through a `secretKeyRef`, never in the pod spec ([the module's README](../../terraform/smelt/README.md)). Before the plan, and in the same shell as the apply (`DEPLOY.md`'s export bullet in the setup step, from the homelab commit that adds the variable — your brief's pin includes it), the seat checks the file exists and isn't empty, then exports `TF_VAR_claude_code_oauth_token="$(cat /etc/smelt/secrets/claude_oauth_token)"` — never echoed, never `set -x`, never written anywhere else. The plan shows it as `(sensitive value)`. A missing or empty file is a stop-and-report — and it is not the missing variable that catches it: `$(cat <missing file>)` exports an empty string, which a variable with no default accepts. What stops it is the exists-and-not-empty check before the export, and behind that the module's validation refusing an empty `secret_env` value at plan: the user stores `claude_oauth_token` on `/secrets`, and the seat never makes up a value. A changed token rolls the server pod at apply, through the module's `smelt/secret-env-sha256` annotation; an unchanged one doesn't.

## Stop-and-report, never apply past them

Any touch outside `module.smelt.*`; any destroy or replace (`-/+`) — above all `kubernetes_stateful_set_v1.database`, `kubernetes_secret_v1.database`, `random_password.database` and `kubernetes_namespace_v1.park`: a namespace replace cascades — all four lose smelt's database; any `Forbidden`; any state lock (wait and retry — never `-lock=false`, never `force-unlock`); a whoami mismatch; a missing image. Reporting goes to the starter and as a `Deployer finished:` comment on the ticket the deploy belongs to (the brief names it; the standing case is SME-326), the trail [rules.md](rules.md) requires.

## The due-condition brief is the go; the first run is the exception

A brief naming the 12-char SHA and why it is due is the instruction to run the deploy through apply — "apply" is no standing password, and later deploys go on the due condition alone. The one exception is named by its brief: the first deploy after this merges is the stop-at-plan run — it stops after the checked `terraform plan -target=module.smelt` and reports, and applies only when the user says apply (the user's answer of 2026-10-30, comment `ef64ebc6`). Apply runs `terraform apply -input=false smelt.plan 2>&1 | tee ~/deploy-<SHA>.log` with the one-line "smelt will restart" notice first: the apply restarts the smelt server this seat runs under, by homelab's design — the seat's pod, terminals and the running apply survive it — and the seat re-reads the log's tail after. Never re-apply a stale plan file after an interrupted apply.

## Verify, push, report

`Apply complete!` in the log; `kubectl -n smelt-park get deploy smelt -o jsonpath=…image…` names the new SHA; `rollout status` clean. Then `git push origin HEAD:master` for the `smelt <SHA>` commit — `git-ssh`, this seat's one push. A refused push is reported with the commit sha, never dropped: repo behind cluster is the drift that re-applies an old image. A stop-and-report discards its local commit so nothing dangles. The `finished:` report goes per rules.md; the `started:` trail line is whoever dispatched the seat.

## Never

Print, log or commit the kubeconfig, its token or the Claude Code token; `terraform destroy`, any `terraform state` command, or any `-target` beyond `module.smelt`; recreate its own pod mid-deploy — `terminate_pod` is denied machine-side precisely for this; start another agent (denied); merge, move a ticket, or delete anything (denied); touch the `smelt-park` workload by hand outside Terraform. And never hand-edit, drop or re-record `.terraform.lock.hcl` hashes, never run `-lock=false`, and never wire up an ad-hoc provider mirror outside DEPLOY.md's step (SME-465): the lockfile's hashes are what verify the mirror — editing them makes a download "pass" by removing the verification.
