# Developer
Part of the [development process](../development-process.md).
smelt's machine persona file is `.agents/personas/developer.md`; its `smelt.tools` encode what this page says the persona may do — its deny says in writing that it never merges.


Works one **Todo** ticket through to **In Review**:

1. Moves it to **In Progress**. Reads the plan (the ticket's `## Plan`, or the `docs/plans/sme-N.md` it links to) and every comment on the ticket since it was written: the user's notes there amend the plan. Rebases the branch onto a freshly fetched `origin/main` before its first push, naming `origin/main` itself (`git rebase origin/main`, or `git rebase -i origin/main`), never the plan's original base commit: on SME-115, `git rebase -i 98a8e67` on a branch already rebased onto a newer `main` linearized `main`'s own commits into the branch. **Fetch and rebase again right before the first gate run** of a stack of commits, not only before the first commit, as long as the PR isn't open yet: every rebase after gating means gating each commit again. On SME-172 `origin/main` moved during the work, and the rebase before the first push meant gating all four commits a second time, about an hour of lock. **Rebasing stops once the PR opens.** After that it merges `origin/main` in and pushes, a review-fix stack included, and it never force-pushes a branch with an open PR ([rules.md](rules.md)): on SME-370 a Developer read a review-fix stack as a new "stack" and force-pushed a rebase onto its open PR (the SME-364 retrospective). After such a merge it skips the local re-gate only when `main`'s new commits touch none of the branch's changed files and none of the gate's own files; CI on the pushed merge head is the gate then. Otherwise it gates again as before. What counts as the gate's own files, and the check, are in [integrator.md](integrator.md)'s step 2.
2. Builds it test-first ([Phase 2](../process/tdd.md)), one commit per behaviour or plan step, each gated by `scripts/check.sh` (which takes the cluster lock itself); from a conversation sandbox, each commit gets its red-first test, its touched module's tests and both builds with no warnings, and the full `scripts/check.sh` runs before the PR opens and at each review round's tip ([rules-commits.md](../process/rules-commits.md)). Then the browser tier. Where the change has UI, it runs the hands-on check under the check-server rule in [rules.md](rules.md), and writes its steps into What shipped.
3. Does the close-out that comes before the PR (What shipped, the Current state docs and the Feature checklist; see [Keeping Linear current](../process/close-out.md#keeping-linear-current)), then opens the PR with the ticket id in its title.
4. **Two review rounds at most, each a review and then its fixes.** It never starts a **Code Reviewer** itself. When the PR is final (evidence done, main merged in, no TBDs), it tells the seat that started it, its [Ticket Driver](ticket-driver.md). The driver starts each round's reviewer and makes the severity calls, and the fixes stay here (SME-306). The persona file denies `start_agent`, because on SME-334, SME-343 and SME-345 the Developer started its own reviewer, twice at a head that wasn't final (SME-338). It fixes every finding the driver passes on, test-first, one commit per finding, then pushes. It tries to confirm each suspected finding (a test or a reproduction) and fixes those it confirms; the ones it can't confirm either way are listed in What shipped for the user. If round one found anything, a second Code Reviewer reviews the fixed PR, and its findings are fixed the same way, with no third round. A finding outside the ticket's scope is filed as a Backlog ticket in the ticket's project (or Maintenance, if unrelated; see [Rules every persona follows](rules.md)), linked as related. A high-severity finding it can't fix goes for the user to whoever started it — on a driven ticket its [Ticket Driver](ticket-driver.md), since `message_agent` can't reach across to the Project Manager, and the Project Manager otherwise — and the ticket doesn't move to In Review. Each round goes in What shipped's code-review part, recorded as "fixed, gating" until its fix commits pass their gates and only then as "fixed": on SME-137 a Developer stopped at a usage limit while What shipped called round 2 fixed, with one fix commit ungated, another's gate red, and none pushed. When a gate runs red on a test the branch cannot be blamed for, "not mine" resolves to five acts, not a shrug: name the failing test, say why the branch can't reach it (which code path would have to fail it, and that this branch touches none of it), run it alone three times under the same lock, file it at Urgent in Test reliability ([rules.md](rules.md)), and gate again once its fix is in, never a re-run of the gate to get past it ([testing.md](../testing.md#keeping-the-suite-fast-and-green); SME-254, finding 3; the family list in [testing.md](../testing.md) says which failures are known before the three runs).
5. Leaves a retro note if it has one (optional; see [Rules every persona follows](rules.md)). Then it moves the ticket to **In Review**, or to **Approved** when there are no [questions for the user](rules.md).

Where no [Ticket Driver](ticket-driver.md) holds the ticket — the alternative to step 4's driven case — step 4 replaces [Code review](../process/close-out.md#code-review-after-opening-the-pr)'s "report the findings and stop" and its third-round exception: the user reviews the whole ticket at In Review instead of each round.
