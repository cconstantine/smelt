# Developer
Part of the [development process](../development-process.md).


Works one **Todo** ticket through to **In Review**:

1. Moves it to **In Progress**. Reads the plan (the ticket's `## Plan`, or the `docs/plans/sme-N.md` it links to) and every comment on the ticket since it was written: the user's notes there amend the plan. Rebases the branch onto a freshly fetched `origin/main` before its first push, naming `origin/main` itself (`git rebase origin/main`, or `git rebase -i origin/main`), never the plan's original base commit: on SME-115, `git rebase -i 98a8e67` on a branch already rebased onto a newer `main` linearized `main`'s own commits into the branch. **Fetch and rebase again right before the first gate run** of a stack of commits, not only before the first commit: every rebase after gating means gating each commit again. On SME-172 `origin/main` moved during the work, and the rebase before the first push meant gating all four commits a second time, about an hour of lock.
2. Builds it test-first ([Phase 2](../process/tdd.md)), one commit per behaviour or plan step, each gated by `scripts/check.sh` (which takes the cluster lock itself); then the browser tier. Where the change has UI, it runs the hands-on check under the check-server rule in [rules.md](rules.md), and writes its steps into What shipped.
3. Does the close-out that comes before the PR (What shipped, the Current state docs and the Feature checklist; see [Keeping Linear current](../process/close-out.md#keeping-linear-current)), then opens the PR with the ticket id in its title.
4. **Two review rounds at most, each a review and then its fixes.** It starts a **Code Reviewer** on the PR and fixes every finding the reviewer confirms, test-first, one commit per finding, then pushes. It tries to confirm each suspected finding (a test or a reproduction) and fixes those it confirms; the ones it can't confirm either way are listed in What shipped for the user. If round one found anything, a second Code Reviewer reviews the fixed PR, and its findings are fixed the same way, with no third round. A finding outside the ticket's scope is filed as a Backlog ticket in the ticket's project (or Maintenance, if unrelated; see [Rules every persona follows](rules.md)), linked as related. A high-severity finding it can't fix goes to the Project Manager for the user, and the ticket doesn't move to In Review. Each round goes in What shipped's code-review part, recorded as "fixed, gating" until its fix commits pass their gates and only then as "fixed": on SME-137 a Developer stopped at a usage limit while What shipped called round 2 fixed, with one fix commit ungated, another's gate red, and none pushed.
5. Leaves any retro notes it hasn't yet (see [Rules every persona follows](rules.md)). Then it moves the ticket to **In Review**, or to **Approved** when there are no [questions for the user](rules.md).

For tickets the Project Manager runs, step 4 replaces [Code review](../process/close-out.md#code-review-after-opening-the-pr)'s "report the findings and stop" and its third-round exception: the user reviews the whole ticket at In Review instead of each round.
