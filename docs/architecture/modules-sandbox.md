# Modules: the sandbox, browsing and the binaries

Part of [architecture.md](../architecture.md)'s module map. The sandbox and its pods, language servers, git, fetching and browsing, previews, and the extra binaries.

| Module | Feature-gated? | Purpose |
|---|---|---|
| `src/api/sandbox.rs` | no (wire types ungated; the server function is isomorphic) | The sandbox panel's snapshot: `get_sandbox_state` and its DTOs (`SandboxSnapshot`, pods, terminals, commands). |
| `src/api/pods.rs` | no (server functions are isomorphic) | The "Sandboxes" page (route `/pods`, `PodsRoute`): `get_pods`/`stop_pod`/`get_live_pod_conversations`, the app-wide `subscribe_app_events` stream, and the pure pieces behind them (idle calculation, Kubernetes quantity and metrics parsing). Each sandbox pod is listed with the language-server pods running next to it. See [api/events.md](../api/events.md#app-wide-events-and-pods). |
| `src/api/sandbox_volumes.rs` | no (server functions are isomorphic) | The `/sandbox-volumes` page's server functions: `list_sandbox_volumes`, `create_sandbox_volume`, `delete_sandbox_volume`, over `sandbox`'s volume functions. |
| `src/sandbox/` | `server` only | The coding-session sandbox lifecycle against a k8s namespace (a hermetic `docker-compose.yml`-provided `k3s` cluster for tests, the real `homelab` cluster for production), in modules (SME-56): `spec` (pod and claim specs, pure), `adopt` (adopting objects from before SME-115), `manager` (the `SandboxManager` and each pod's lifecycle), `claims` (a conversation's claims and Docker restarts), `agent` (the sandbox agent connection and registry), `ports` (connections into a pod), `files` (terminals and file tools), `watch` (the pod watcher), `exec` (kube exec); `mod.rs` re-exports them all, so callers say `sandbox::X`. git's commands in a pod's sandbox container (a clone, reading `AGENTS.md` files, installing keys) go through `PodShell` (kube exec, which sees exit codes and takes stdin); the model's own commands go through the agent's terminals. Before `init()` builds the manager, every call that needs it returns `SandboxError::NotInitialized` rather than panicking. `NAMESPACE` resolves to `smelt-park` for a real running instance, `smelt-park-test` under `#[cfg(test)]`, so `cargo test`'s real-cluster tests can never collide with a real dev instance's pods/PVCs in the same cluster, or vice versa (see [k8s/smelt-park-rbac.yaml](../../k8s/smelt-park-rbac.yaml)) — see [SME-7](https://linear.app/smelt-agent/issue/SME-7). Every real server shares `smelt-park` (the dev server, a check server on a scratch database), and names its objects after its own database's ids, so each object smelt creates (sandbox pods, both conversation claims, volume claims, language server pods) is labelled `smelt/instance=<id>` with its database's `smelt_instance` id, and a server deletes, reuses, mounts, watches and reads only objects with its own (SME-115; `spec::ownership`: Ours, Unlabelled or Foreign). Every selector it lists or watches by includes its instance; a sandbox pod or claim deleted by name is read first, checked to be ours, and deleted with a `uid` precondition (language server pods are found by a selector that includes the instance, and smelt's own just-created or returned pods are deleted by name); a bind point (`ensure_conversation_pvcs`, a pod of the same name, a volume claim, a language server pod) refuses one that isn't ours with `SandboxError::NotOurs`; and readers treat another database's pod of the same name as absent (`read_our_pod`). Objects from before the fix carry no label: only the database that owns them (`owns_unlabelled`, fixed at migrate time) adopts them at startup (`sandbox::adopt` labels the unlabelled claims and pods of conversations and volumes it still has; it never deletes), and a bind point adopts one startup missed. A fresh database's id sequences start above 2,000,000,000 (`db::start_ids_clear_if_fresh`), so a scratch server's names don't meet the dev server's. Built on top of that: pod/terminal/command as three separately-guarded lifecycles (`create_pod`/`create_terminal`/`run_terminal_command`/...), at most one live pod per conversation (`create_pod` refuses a second; a unique index backs it, migration `20260928090000_one_live_pod_per_conversation.sql`), each with N terminals, a small `axum` agent binary (`src/bin/sandbox_agent.rs`, see below) that's the pod's own `ENTRYPOINT` (genuine PID 1, running as a pre-created non-root user with passwordless `sudo` — a custom image, `docker/sandbox/Dockerfile`, built and delivered with no registry involved by `scripts/build-sandbox-image.sh`) multiplexing every terminal that pod hosts over one WebSocket connection — see [SME-9](https://linear.app/smelt-agent/issue/SME-9) and [SME-17](https://linear.app/smelt-agent/issue/SME-17). `reconnect_if_needed`/`try_reconnect` transparently re-establish a lost connection to a still-`Running` pod (e.g. after a smelt restart) rather than leaving it stuck "disconnected." Every connect goes through `connect_with_retry`, behind a per-pod lock, so a pod has one connection; it checks the agent's hello, and a pod whose agent speaks another major is reported as outdated (`TerminalError::AgentOutdated`) and never treated as a crash. The error's advice depends on the refused pod's image (`PodImage`, SME-121): another image than a new pod would get means replacing the pod helps; the same image means it can't, so the model is told not to retry and to ask the user to rebuild the image and then replace the pod (`/pods` says "rebuild the image, then restart"); an image that couldn't be read gets both. A pod whose image isn't on the node fails `create_pod` at once (`ErrImageNeverPull` is a fatal waiting reason, its sidecar's too) with the command that builds it. A request (`TerminalConnection::request`) fails with the agent's own refusal, a timeout, or `Disconnected` at once when the socket drops (SME-53). Also owns generic, purpose-agnostic pod volumes (`create_volume`/`delete_volume`, PVC-backed, `src/api/sandbox_volumes.rs` exposes them via the `/sandbox-volumes` UI) — every configured volume is mounted into every pod unconditionally, so `SandboxManager::create` first recreates any volume claim missing from the namespace (`ensure_volume_claims`; one missing claim otherwise stops every pod from starting), and a mount path must be absolute (`validate_mount_path`). `open_pod_target` opens a TCP connection to any port in a conversation's own live pod through a port-forward (looked up from the conversation, so nothing reaches another conversation's pod), and `pod_port_is_listening` probes one; the sandbox routes and previews use both (SME-42). The host is the pod's own `localhost` or, since SME-33, a Docker container's address, reached through the agent's relay on `127.0.0.1:8089`, which names the target on one line, answers `ok` once connected and refuses anything outside `docker_net`'s range. It refuses the sandbox agent's own ports (`check_reachable_port`, 8088 and 8089): the agent's WebSocket runs commands with no login and the relay reaches every container, so any website or fetched page could otherwise drive them through a preview or the model's browser; the agent also listens on loopback only, out of the pod's containers' reach. Every pod has a Docker sidecar (SME-33, `build_pod_spec`): a privileged native sidecar started with `docker/sandbox/start-dockerd.sh` so it and its containers stay in its own cgroup, sharing `/workspace` and a socket directory with the unprivileged sandbox container, with `/var/lib/docker` on the conversation's own claim and `/workspace` on another (SME-32) (`ensure_conversation_pvcs`, deleted by `teardown_conversation`, swept at startup by `sweep_orphaned_conversation_claims`, which deletes only this database's claims of conversations it no longer has). `create_pod` waits out the conversation's previous pod first (`wait_for_conversation_pods_gone`), and `watch_pods` reports a sidecar restart to the model (`note_docker_restarts`, `report_docker_restart`). See [setup/sandbox.md](../setup/sandbox.md#docker-in-the-sandbox). |
| `src/lsp/` | `server` only | Language servers next to the sandbox (SME-35). `client.rs`: a JSON-RPC client over any byte stream (`Content-Length` framing, `$/cancelRequest` on timeout, server requests answered by a handler, every request failed when the stream ends). `session.rs`: one initialized server, its roots, versioned document sync and published or pulled diagnostics. `pods.rs`: the server pods (`lsp-<pod id>-<name>`, same node as the sandbox, owned by it), their install, listing and state, stdio over `pods/exec`, and `note_server_stop` for `watch_pods`. `ops.rs`: the `lsp` tool's operations as readable text, UTF-16 positions, and applying a rename's edits. `manager.rs`: what the tools call, joining the configs, the sandbox pod, server pods and sessions (one per server pod, reopened at most 3 times in 5 minutes). `config.rs`: saving a config and which pods a change stops. `catalog.rs`: the page's lookup. |
| `src/api/language_servers.rs` | no (server functions are isomorphic) | The `/language-servers` page's server functions. |
| `src/git.rs` | wire types ungated (`SshKeySummary`, `GitIdentity`, `RepoSummary`, `RepoStatus`, `TrustRequest`, `ProjectInstructions`, `RepoTrustSummary`); the rest `server` only | Git support (SME-32). One SSH key (`ssh-key` crate: generate ed25519, import OpenSSH) and the commit identity, written into every pod's `/etc/smelt` by `pod_git_files` + `sandbox::install_git_files` (at `create_pod`, and into every live pod on a change, serialised). A conversation's repos: `remote_key` normalises every URL form of a remote to one identity and refuses URLs git could read as options or transport helpers; `clone_repo`/`attach_repo` (plan, record, start the pod if there's none, run) clone over kube exec straight into `/workspace/<dir>` (git refuses an existing directory; the error explains a cut-off clone's leftovers), with a guard marking a clone cut off midway as interrupted, and list the checkout's `AGENTS.md` files. `load_instructions` (the model's tool) resolves an `AGENTS.md` path to a repo, reads it, and loads it (`loaded_instructions`) or, for a remote the user hasn't decided about, records an `instruction_requests` row with the exact file for the trust card; `decide_trust` loads exactly that file on Trust. `render_project_instructions` is the system prompt's section. |
| `src/api/git.rs` | no (server functions are isomorphic) | The `/git` page's and the repo panel's server functions, thin wrappers over `src/git.rs`. |
| `src/agent_protocol.rs` | `server` only (also compiled into `sandbox_agent` with `#[path]`) | The sandbox agent's wire protocol, the one definition both ends use (SME-53): `ClientMessage` (smelt to the agent, requests carry a `request_id`), `AgentMessage` (`hello`, `output`, `exit`, a `reply` per request, `protocol_error`) and the file results. Versioned major.minor (`PROTOCOL_VERSION`): the agent says hello with its version first, smelt refuses another major, and any minor of its own major works. `src/fixtures/agent_protocol_v1.jsonl` holds one example of every message, which must parse and serialize to the same bytes, so a breaking change can't slip in without a major bump. |
| `src/docker_net.rs` | `server` only (also compiled into `sandbox_agent` with `#[path]`) | The address range a sandbox pod's Docker networks come from (`172.20.0.0/14`, dockerd's `--bip` and `--default-address-pool`) and `container_address`, which of those a host names. The server's browser routes and previews and the agent's relay judge an address with the same code (SME-33). |
| `src/fetch_guard.rs` | `server` only | Shared helpers for everything that fetches on the model's behalf (`src/webfetch.rs`, `src/http_request.rs`, `src/browsing.rs`): the URL parse every one of them does (`parse_fetch_target` — `http`/`https` only), resolution that must succeed and hands back the addresses to connect to (`resolve_target`, SME-51 B4), response-text truncation (`truncate`), and the sandbox-route helpers: `sandbox_host`/`is_sandbox_host` (which hosts mean the conversation's pod, SME-42), `browser_sends_sec_fetch`, and `allows_request_from` (who may send a request to a server in the pod, SME-90). One source of truth rather than several copies that could drift apart. It used to also hold the SSRF guard that refused every non-public address; **SME-155 removed it** — addresses are no longer filtered, only the scheme is checked. |
| `src/egress_proxy.rs` | `server` only | A small HTTP proxy (`CONNECT` tunnels plus absolute-form forwarding) that reaches ports inside a sandbox pod. It resolves every target itself and connects to exactly the address it resolved. SME-155 removed the address filtering it used to do, so it is now purely the routing mechanism: `start_with_sandbox` starts one for a single browser context (a browsing session or a `webfetch` call, set as that context's own `proxyServer` over CDP): a sandbox host there (`fetch_guard::sandbox_host`: a `localhost` name, or since SME-33 a Docker container's address in the pod) goes to that port in the conversation's pod through `sandbox_dial` (`sandbox::open_pod_target`, bounded by `with_timeout`), with a readable 502 when there's no pod or nothing listening; every other host is simply fetched (SME-42, SME-155). Only requests from the sandbox's own pages, the model's own navigations and plain page loads reach the sandbox (`fetch_guard::allows_request_from`, from `Origin` and `Sec-Fetch-*`, read inside a `CONNECT` tunnel for WebSockets); another site's page is refused with a 403. Browsers send no `Sec-Fetch-*` to a container's plain-http address, so there a request without `Origin` gets through only as a page load (`Upgrade-Insecure-Requests`) or with a `Referer` from the sandbox (SME-90). |
| `src/headless_chrome.rs` | `server` only | Launches `chrome-headless-shell` with `PR_SET_PDEATHSIG`, so Linux kills it the moment the launching process dies (SIGKILL included), then connects chromiumoxide to it. It exists because chromiumoxide only stops Chrome when its `Browser` is dropped, and the shared browser lives in a static that never is: every server restart and test run used to leave a whole Chrome running. Chrome is spawned from a dedicated thread that lives as long as Chrome does, because the death signal follows the spawning *thread*, not just the process. Each launch gets its own profile directory, and directories left by dead processes are removed on the next launch. Used by both the shared browser and `src/browser_tests.rs`'s harness. |
| `src/preview.rs` | `server` only | Sandbox previews for the user's browser (SME-42): a reverse proxy on a listener of its own (`SMELT_PREVIEW_ADDR`) where each request's `Host`, matched against `SMELT_PREVIEW_URL` (`PreviewTemplate`), names a conversation and a port. The request reaches that port in that conversation's pod over `sandbox::open_pod_target`, with `Host` set to `localhost:<port>`. Since SME-33 the `{port}` slot can also carry a Docker container's address (`172-21-0-2-3000`), and the request then goes to that container with `Host` set to its own address. HTTP/1 via hyper, one upstream port-forward per browser connection, upgrades (live reload) passed through, redirects to `localhost:<port>` pointed back at the preview. Its own listener because `dx serve`'s dev proxy replaces `Host`. The same `allows_request_from` rule keeps other sites open in the user's browser from sending requests to a preview; only the conversation's own previews and opening the link directly get through (at a plain-http preview address that isn't `localhost`, which gets no `Sec-Fetch-*`, `Upgrade-Insecure-Requests` and `Referer` decide, as for containers). The model shares a port with the `sandbox_preview_url` tool; ports are kept in `sandbox_pod_previews` and shown as links in the sandbox panel. |
| `src/webfetch.rs` | `server` only (its own real-browser tests additionally need `browser-test`) | The `webfetch` tool: navigates a real headless browser (`chromiumoxide`/`chrome-headless-shell` over CDP — the same dependency `src/browser_tests.rs` uses, now also a genuine runtime dependency of the app itself, not just its tests) to a URL and returns its rendered, readable text (`document.body.innerText`). A process-global, lazily-launched shared browser (`tokio::sync::OnceCell`) — launched on first `webfetch` call, not at server startup. Nothing that uses it shares browser data: `new_isolated_page` gives each `webfetch` call, and each `browsing` session, a browser context of its own (cookies, storage, cache, service workers), and `dispose_isolated` deletes it afterwards. Each call's page loads the URL the model asked for after `fetch_guard::parse_fetch_target` has checked its scheme; no address is filtered (SME-155). Popups are refused outright with `--block-new-web-contents`. See [SME-21](https://linear.app/smelt-agent/issue/SME-21). |
| `src/http_request.rs` | `server` only | The `http_request` tool: a plain HTTP client (`reqwest`, no browser, no JS execution) for hitting an API directly — much cheaper than `webfetch` for a JSON endpoint or anything that doesn't need real page rendering. `reqwest`'s own automatic redirect-following is disabled; redirects are followed manually, one hop at a time, so each hop's target is resolved once and connected to that address (SME-51 B4). A non-2xx status is returned as normal data, not a tool error. See [SME-21](https://linear.app/smelt-agent/issue/SME-21). |
| `src/browsing.rs` | wire types (`BrowserFrame`/`BrowserInputEvent`) ungated; the `chromiumoxide`-driven session logic itself is `server` only (its own real-browser scenarios additionally need `browser-test`, run inline inside `webfetch::browser_tests::test_fetch_scenarios` — see that test's own doc comment) | A persistent, per-conversation browsing *session* (`open_browser_session`/`close_browser_session`/`browser_navigate`/`browser_click`/`browser_fill`/`browser_back`/`browser_read`) — unlike `webfetch`'s fresh-page-per-call shape, the same real page stays open across many tool calls, on `webfetch`'s own shared browser (`crate::webfetch::shared_browser`). At most one session per conversation, mirroring the sandbox pod's own precedent. Also drives the live panel: a reference-counted CDP screencast (`Page.startScreencast`, started on the first live-panel viewer and stopped on the last) streams frames over a dedicated per-conversation channel (not `ConversationEvent` — see that enum's own doc comment), and real mouse/keyboard input from the panel is forwarded back via `Input.dispatchMouseEvent`/`dispatchKeyEvent`/`insertText` — the user can watch and interact with the same real page the model is browsing, with no locking between the two (CDP just serializes whichever commands arrive). The session's viewport is pinned to a fixed size matching the screencast bounds exactly, so the frontend's click-coordinate math needs no scale-factor lookup. See [SME-22](https://linear.app/smelt-agent/issue/SME-22). |
| `src/api/browsing.rs` | no (wire types ungated, matching `src/browsing.rs`; server functions are isomorphic) | Browser-facing server functions for the live panel: `get_browsing_state`, `subscribe_browser_frames`, `send_browser_input`, `navigate_browser` — separate from `anthropic::tools`' model-facing dispatch, same split `api::chat`'s `get_sandbox_state`/`subscribe_conversation_events` already has relative to the sandbox terminal tools. |
| `src/bin/sandbox_agent.rs` | `server` (`[[bin]]`) | The sandbox pod's own `ENTRYPOINT` (SME-9): one WebSocket server multiplexing the pod's terminals, each a persistent `bash` in its own process group, plus the Docker relay on `127.0.0.1:8089`. It says hello with its protocol version first, answers a message it can't parse with a `protocol_error` (logging the error, never the message), and holds one connection at a time: a newer one replaces the older, and events that arrive with no connection wait for the next (SME-53). Compiles `src/docker_net.rs` and `src/agent_protocol.rs` in with `#[path]`; it's a separate crate root, so it can't reach `main.rs`'s modules. |
| `src/bin/sandbox_image_import.rs` | `server` (`[[bin]]`) | CLI run by `scripts/build-sandbox-image.sh`, never by the server: streams a `docker save` tarball into the cluster's node through a short-lived pod and `ctr images import`s it, so the sandbox image needs no registry (SME-17). With `--check <references>` (`scripts/cluster-doctor`) it only lists the node's images (`ctr images ls -q`) and fails naming the ones missing (SME-102). |
| `src/bin/sandbox_instance_cleanup/main.rs` | `server` (`[[bin]]`) | CLI run by `scripts/check-server stop` — and by `start`, over a leftover — before the scratch database is dropped (SME-129): it reads the database's own `smelt_instance` row (`SELECT instance_id::text, owns_unlabelled FROM smelt_instance`, the query `db::smelt_instance` runs) and deletes exactly that instance's objects, pods (sandbox and language server, grace 0) first and their claims (`sandbox-workspace-N`, `sandbox-docker-N`, `sandbox-volume-N`) after, each by name under a `uid` precondition, so an object made again under the same name is left alone; it waits for the pods, then the claims, to go, and exits 0 only when none is left. It refuses (exit 2, deleting nothing) a `--database-url` whose database isn't `smelt_scratch_*`, is `--dev-database-url`'s, owns the objects made before SME-115, has a non-UUID instance, or still has another connection; a database that is gone or was never migrated is a success. `--dry-run` lists what it would delete, and `--list` opens no database to print the namespace's pods and claims grouped by their `smelt/instance` label, which is how a stranded instance is found. Nothing without that exact label is ever deleted. |
| `src/browser_tests.rs` | `test`, `browser-test` | One `#[ignore]`d end-to-end test (real Postgres, real k3s, real headless Chrome over CDP via `chromiumoxide`, a mock Anthropic upstream) running about two dozen scenarios in sequence: the sandbox panel (cold load, live streaming, reload), context usage and compaction, todos, streaming across tabs, stopping a turn, the Sandboxes page, the settings pages, phone width, the 404 page, dark mode, previews of a dev server and a Docker container, and repo trust. `src/webfetch.rs` has its own separate `#[ignore]`d real-browser test (real navigation, the sandbox route) rather than a scenario folded into this one — a different concern (a feature's own browser-driving logic, not DOM/panel rendering) with its own module. See [testing.md](../testing.md). |
